#### Теоретический фундамент и архитектура

В современной веб-разработке 2026 года оптимизация времени ответа сервера (**Latency**) является критическим фактором. Фоновая обработка позволяет приложению отправить HTTP-ответ клиенту немедленно, делегируя выполнение вторичных операций (таких как отправка уведомлений, очистка временных файлов или запись логов аудита) на этап после завершения транзакции.

Механика работы `fastapi.BackgroundTasks` глубоко интегрирована с движком **Starlette**. Когда объект `BackgroundTasks` передается в _path operation function_, задачи добавляются во внутреннюю очередь. ASGI-сервер (Uvicorn или Granian) сначала полностью завершает передачу тела ответа клиенту и только после этого приступает к выполнению запланированного списка функций.

**Выполнение функций:**

- **Асинхронные (`async def`)**: Выполняются непосредственно в основном цикле событий (**Event Loop**). Это эффективно для операций ввода-вывода (I/O), но требует осторожности: если корутина будет слишком тяжелой, она может замедлить обработку новых входящих запросов.
- **Синхронные (`def`)**: FastAPI автоматически запускает их в отдельном тред-пуле Starlette (используя `anyio.to_thread.run_sync`), что предотвращает блокировку **Event Loop** блокирующими вызовами (например, классическими библиотеками для отправки Email).

**Границы применимости:** `BackgroundTasks` относятся к типу **Transient Tasks** (временных задач в памяти). Они идеально подходят для легких I/O-операций, но имеют критические ограничения:

1. **Отсутствие Persistence**: Задачи хранятся в оперативной памяти текущего процесса. Если сервер упадет или будет перезагружен до завершения задач, они будут безвозвратно утеряны.
2. **Отсутствие воркеров**: Выполнение происходит в том же процессе, что и обработка API, что не позволяет масштабировать задачи отдельно от веб-сервера.
3. **Управление контекстом**: Ресурсы, инжектированные через `Depends` (например, сессия БД), закрываются сразу после отправки ответа. Попытка использовать закрытую сессию в фоновой задаче приведет к ошибке `InterfaceError` или `ClosedResourceError`.

#### Практическая реализация и синтаксис

Для безопасной работы с базой данных в фоновых задачах необходимо использовать фабрики сессий (`async_sessionmaker`) для создания независимого контекста внутри самой задачи.

**Эндпоинт регистрации с фоновым уведомлением и управлением сессией:**

```
from fastapi import FastAPI, BackgroundTasks, Depends, status
from sqlalchemy.ext.asyncio import AsyncSession
from .database import async_session_maker, get_db
from .schemas import UserCreate
from .services import send_welcome_email

app = FastAPI()

async def notify_user_task(email: str):
    # Создаем НОВУЮ сессию, так как сессия из запроса будет закрыта
    async with async_session_maker() as session:
        try:
            # Выполнение асинхронной задачи (например, логирование в БД)
            # ...
            await send_welcome_email(email)
        except Exception as e:
            # Обязательный перехват ошибок внутри задачи
            print(f"Background task failed: {e}")

@app.post("/register", status_code=status.HTTP_202_ACCEPTED)
async def register_user(
    user_data: UserCreate,
    background_tasks: BackgroundTasks,
    db: AsyncSession = Depends(get_db) # Сессия только для основного запроса
):
    # Логика сохранения пользователя в БД
    # ...
    # Добавление задачи в очередь выполнения ПОСЛЕ ответа
    background_tasks.add_task(notify_user_task, user_data.email)

    return {"message": "Registration in progress. Check your email shortly."}
```

#### Глоссарий терминов

- **[`fastapi.BackgroundTasks`](https://fastapi.tiangolo.com/reference/background/)** — встроенный класс для планирования функций, выполняемых после завершения передачи HTTP-ответа.
- **In-process Background Execution** — выполнение фоновой логики в рамках одного процесса с основным приложением без использования внешних брокеров сообщений.
- **Starlette Thread Pool Execution** — механизм изоляции синхронных функций в отдельных потоках для сохранения неблокирующего поведения ASGI-приложения.
- **Transient Tasks** — задачи, жизненный цикл которых ограничен временем жизни процесса приложения (отсутствие гарантии выполнения при сбоях).
- **Context Leakage / Session Lifetime** — архитектурная ошибка, возникающая при попытке доступа к ресурсам (БД, файлы), чей контекст был уничтожен по завершении HTTP-запроса.

#### Практический кейс: Асинхронная регистрация метрик и отправка системных уведомлений

**Сценарий:** Реализация API для критической системы мониторинга. При получении сигнала об аномалии эндпоинт должен мгновенно ответить `202 Accepted`, чтобы разблокировать вызывающее устройство, а затем выполнить тяжелую рассылку уведомлений (SMS, Email) и записать детальную аналитику в PostgreSQL.

**Анализ поведения:** При использовании `BackgroundTasks`, если во время отправки Email процесс сервера будет убит (например, по OOM или при деплое), аналитика не будет записана, а уведомление не уйдет. Для системно-критичных задач в 2026 году рекомендуется переход на Celery или Taskiq с брокером Redis/RabbitMQ, однако для легких сценариев `BackgroundTasks` обеспечивают минимальный оверхед и простоту поддержки кода.

#### Вопросы и задания для самопроверки

1. **Вопрос:** Как изменится поведение ASGI-сервера, если вы добавите в `BackgroundTasks` функцию, определенную через `def`, внутри которой вызывается `time.sleep(10)`?
    - _Ответ: Сервер запустит её в отдельном потоке (thread), поэтому основной Event Loop продолжит обрабатывать запросы других пользователей без задержек._
2. **Задача:** Код падает с ошибкой `ClosedResourceError` при попытке фонового обращения к БД. Что нужно изменить в сигнатуре фоновой функции?
    - _Решение: Необходимо прекратить передачу сессии через `Depends` в фоновую функцию. Вместо этого следует передавать фабрику сессий (`async_sessionmaker`) и открывать новый контекст `async with` внутри тела фоновой функции._
3. **Практическое задание:** Напишите декоратор `track_background_task`, который будет оборачивать фоновую функцию, замерять время её выполнения с помощью `time.perf_counter()` и записывать результат в логи, даже если задача завершилась с исключением.
