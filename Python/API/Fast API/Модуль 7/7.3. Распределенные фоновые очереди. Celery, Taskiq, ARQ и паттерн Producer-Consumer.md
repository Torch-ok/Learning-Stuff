#### Теоретический фундамент и архитектура

В то время как `BackgroundTasks` выполняются внутри того же процесса, что и основное приложение, распределенные очереди задач реализуют паттерн **Producer-Consumer** (Издатель — Потребитель) [59, 8.2 draft]. Эта архитектура разделяет ответственность между тремя компонентами:

1. **Producer (FastAPI)**: Принимает HTTP-запрос, формирует задачу и отправляет её в брокер, моментально возвращая клиенту `task_id` или статус `202 Accepted` [45, 593, 8.4 draft].
2. **Message Broker (Redis / RabbitMQ)**: Промежуточное хранилище (очередь), которое гарантирует сохранность задачи до момента её вычитки воркером [46, 731, 8.2 draft].
3. **Worker (Consumer)**: Изолированный процесс (или группа процессов), который считывает задачи из брокера и выполняет тяжелые I/O или CPU-bound операции (обработка видео, генерация PDF, массовые рассылки) [8.2 draft, 8.4 draft].

**Обзор экосистемы 2026:**

- **Celery**: Промышленный стандарт с мощной экосистемой (Flower для мониторинга), но требующий осторожности при интеграции с асинхронным кодом из-за своей исторически синхронной природы [8.2 draft, 8.4 draft].
- **Taskiq**: Современная асинхронно-нативная альтернатива. Её преимущество — полная поддержка **Dependency Injection** (`Depends`) и моделей Pydantic v2, что позволяет использовать те же зависимости (например, `AsyncSession`), что и в эндпоинтах FastAPI [4.1 draft, 629, 8.2 draft].
- **ARQ**: Минималистичная библиотека, использующая `redis.asyncio` для эффективного управления очередями в неблокирующем режиме [7.2 draft, 8.2 draft].

Гарантии доставки в очередях позволяют настроить **Retry Policy** с использованием **Exponential Backoff** (экспоненциальная задержка между попытками), что предотвращает «шторм запросов» к внешним API при их временной недоступности [8.2 draft].

**Проверка статуса задачи и получение результата:**

```
@app.get("/tasks/{task_id}")
async def get_task_status(task_id: str):
    # Доступ к Result Backend через брокер
    result = await redis_broker.result_backend.get_result(task_id)
    if not result:
        return {"status": "PENDING"}
    return {"status": "SUCCESS", "data": result.return_value}
```

#### Глоссарий терминов

- **Producer-Consumer Pattern** — архитектурная модель, разделяющая создание и выполнение задач через посредника (брокера) [60, 8.2 draft].
- **[Message Broker (Redis / RabbitMQ)](https://fastapi.tiangolo.com/tutorial/sql-databases/)** — сервис для хранения и передачи сообщений между FastAPI и воркерами .
- **Result Backend** — хранилище (обычно Redis), где воркеры оставляют результаты выполнения и статусы задач для их последующей проверки сервером [8.2 draft].
- **Taskiq / ARQ / Celery Workers** — независимые процессы ОС, выполняющие код фоновых задач отдельно от процесса веб-сервера [8.2 draft].
- **Exponential Backoff & Retry Policy** — стратегия повторных попыток выполнения задачи, при которой время ожидания увеличивается после каждой ошибки [8.2 draft].
- **Dead Letter Queue (DLQ)** — очередь для «отравленных» сообщений, которые не удалось обработать после всех настроенных попыток [8.2 draft].

#### Практический кейс: Построение асинхронного воркера для ресурсоемкой обработки данных

**Сценарий**: Обработка больших CSV-файлов с транзакциями.

1. **FastAPI (Producer)**: Принимает файл через `UploadFile`, сохраняет его в S3 и отправляет сообщение в Taskiq [658, 8.4 draft].
2. **Брокер (Redis)**: Удерживает задачу в очереди.
3. **Worker (Taskiq)**: Запускается в отдельном Docker-контейнере. Он считывает файл чанками через `StreamingResponse` логику, парсит данные и через `Depends(get_async_session)` сохраняет каждую транзакцию в PostgreSQL [5.1 draft, 607, 708]. **Преимущество**: Если парсинг файла займет 10 минут и потребует 2 ГБ RAM, это никак не отразится на работоспособности FastAPI-сервера, так как ресурсы потребляются изолированным процессом-воркером.

    - _Ответ: `BackgroundTasks` ограничены памятью одного пода (инстанса). Если под умрет, задачи исчезнут. Распределенные очереди позволяют запускать сотни отдельных воркеров на разных узлах, гарантируя выполнение задач даже при перезагрузке API-сервера [8.1 draft, 8.2 draft]._
