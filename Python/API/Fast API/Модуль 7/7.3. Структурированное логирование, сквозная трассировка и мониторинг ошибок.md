#### Теоретический фундамент и архитектура

В современных распределенных системах и микросервисных архитектурах 2026 года стандартное текстовое логирование через модуль `logging` признано недостаточно эффективным из-за сложности автоматизированного парсинга и поиска данных. Переход к структурированному логированию (Structured Logging), в частности в формате JSON, позволяет инструментам мониторинга (ELK Stack, DataDog, Sentry) мгновенно индексировать атрибуты запросов, такие как идентификаторы пользователей, уровни важности и временные метки.

Ключевые элементы системы Observability:

- **JSON-логирование**: Замена обычных строк на структурированные объекты. Это позволяет сохранять не только сообщение об ошибке, но и полный стек вызовов, контекст выполнения и метаданные окружения (например, имя пода в Kubernetes или версию API).
- **Correlation ID (Request ID)**: Генерация уникального идентификатора для каждого входящего HTTP-запроса через Middleware. Этот ID пробрасывается через все уровни приложения и внешние вызовы, позволяя связать разрозненные логи в единую цепочку событий.
- **Distributed Tracing (OpenTelemetry)**: Использование концепций **Spans** и **Traces** для мониторинга латентности и прохождения запроса через цепочку микросервисов.
- **Мониторинг ошибок с Sentry**: Инструмент действует как «камера видеонаблюдения» для приложения, перехватывая исключения в реальном времени, собирая данные о поведении пользователей и технических метриках (CPU, задержки).
- **Глобальный обработчик исключений**: Использование `@app.exception_handler(Exception)` необходимо для создания централизованной точки перехвата нештатных ситуаций. Это предотвращает утечку внутренней технической информации (stack trace) в HTTP-ответах, заменяя их на безопасные JSON-объекты со статусом **500 Internal Server Error**.

#### Практическая реализация и синтаксис

Современная настройка логирования и обработки ошибок требует интеграции на уровне всего приложения `FastAPI`.

**Настройка структурированного логирования (JSON) и Middleware для Request ID:**

```
import time
import uuid
from fastapi import Request, FastAPI
# В Python 2026 используются принципы создания логгеров с транспортами
from structlog import get_logger

logger = get_logger()

@app.middleware("http")
async def add_correlation_id(request: Request, call_next):
    # Генерация или извлечение ID для сквозного отслеживания
    request_id = request.headers.get("X-Request-ID", str(uuid.uuid4()))
    start_time = time.perf_counter() #

    # Сохранение ID в контекст запроса для всех последующих логов
    response = await call_next(request)

    process_time = time.perf_counter() - start_time #
    logger.info(
        "request_processed",
        path=request.url.path,
        method=request.method,
        request_id=request_id,
        duration=process_time
    )
    response.headers["X-Request-ID"] = request_id
    return response
```

[Middleware](https://fastapi.tiangolo.com/tutorial/middleware/), [Concurrency and async / await](https://fastapi.tiangolo.com/async/)

**Глобальный перехватчик неперехваченных ошибок:**

```
from fastapi.responses import JSONResponse
from fastapi import status

@app.exception_handler(Exception)
async def global_exception_handler(request: Request, exc: Exception):
    # Логирование критического сбоя для Sentry и внутренних логов
    logger.error("unhandled_exception_occurred", error=str(exc))

    # Маскировка технической ошибки для клиента
    return JSONResponse(
        status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
        content={"detail": "An internal server error occurred. Please contact support."}
    )
```

[Handling Errors](https://fastapi.tiangolo.com/tutorial/handling-errors/), [Response Status Code](https://fastapi.tiangolo.com/tutorial/response-status-code/)

#### Глоссарий терминов

- **[Structured Logging (`structlog`)](https://fastapi.tiangolo.com/tutorial/bigger-applications/#apirouter)** — подход к записи логов в виде машиночитаемых данных (JSON), упрощающий дебаг и мониторинг трафика.
- **Correlation ID / Request ID** — уникальная метка запроса, позволяющая отслеживать его выполнение между Middleware, роутерами и сервисами.
- **[Distributed Tracing (OpenTelemetry)](https://fastapi.tiangolo.com/deployment/concepts/)** — технология наблюдения за жизненным циклом запроса в распределенных системах для поиска узких мест производительности.
- **[Sentry Exception Tracking](https://fastapi.tiangolo.com/tutorial/handling-errors/)** — сервис мониторинга, агрегирующий ошибки, стек-трейсы и контекст окружения для быстрого реагирования на инциденты.
- **Context Variables (`contextvars`)** — механизм Python для хранения данных, специфичных для текущего асинхронного контекста (например, текущего пользователя или ID запроса).
- **[Global Exception Handler](https://fastapi.tiangolo.com/tutorial/handling-errors/#install-custom-exception-handlers)** — централизованная функция для перехвата и форматирования любых типов ошибок в приложении.

#### Практический кейс: Построение системы Observability для распределенного API

**Сценарий**: Высоконагруженный API сервис электронных платежей требует прозрачности при обработке транзакций. Необходимо быстро находить причины отказов, когда запрос проходит через 20+ микросервисов.

**Реализация**:

1. **Сквозной ID**: Каждый запрос в Middleware получает `X-Request-ID`. Если клиент (фронтенд) уже прислал его в заголовках, сервис использует его, сохраняя непрерывность трассировки.
2. **Структурированные логи**: При возникновении ошибки в лог в формате JSON записывается не только текст, но и `user_id`, `order_amount` и `request_id`. Это позволяет в ElasticSearch мгновенно найти все логи, относящиеся к одной неудачной покупке.
3. **Sentry Integration**: Критические исключения (например, `DB Connection Timeout`) автоматически отправляются в Sentry со статусом `Error`. Бизнес-ошибки (например, `Insufficient funds`) логируются как `Warning` и не вызывают алертов дежурных инженеров.
4. **Результат**: Время поиска (MTTR) причин сбоя сокращается с часов до минут благодаря фильтрации всех событий системы по одному Correlation ID.

#### Вопросы и задания для самопроверки

1. **Вопрос**: Почему стандартная библиотека `logging` может негативно влиять на производительность асинхронного приложения при записи на диск под высокой нагрузкой?
    - _Ответ: Стандартные вызовы записи в файл являются блокирующими (I/O bound). В асинхронной среде это может привести к блокировке Event Loop, поэтому рекомендуется использовать асинхронные обработчики или выносить логирование в отдельный поток._
2. **Задача**: Напишите Middleware, которое после завершения обработки запроса добавляет заголовок `X-Process-Time` в ответ клиенту, используя данные из `time.perf_counter()`.
3. **Практическое задание**: Реализуйте кастомный обработчик для `HTTPException`, который при получении ошибки 404 будет логировать URL путь, к которому пытался обратиться пользователь, но возвращать при этом пустой ответ для скрытия структуры API от ботов.
