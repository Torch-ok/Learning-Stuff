#### Теоретический фундамент и архитектура

В высоконагруженных системах 2026 года кэширование является критическим инструментом для превращения медленных эндпоинтов в «супербыстрые». Использование In-Memory хранилища Redis в сочетании с официальным асинхронным клиентом `redis.asyncio` позволяет обрабатывать тысячи запросов в секунду (RPS) без блокировки основного `Event Loop`.

**Архитектурные аспекты:**

- **Управление соединениями**: Для эффективной работы используется `Connection Pool`. Жизненный цикл пула подключений к Redis настраивается через современный механизм `lifespan` в FastAPI, который управляет событиями запуска и завершения приложения в асинхронном контексте.
- **Стратегия Cache-Aside (Lazy Loading)**: Это наиболее распространенный паттерн, при котором приложение сначала проверяет наличие данных в кэше. Если данных нет (Cache Miss), они извлекаются из основной базы данных (PostgreSQL), сериализуются и записываются в кэш для последующего использования.
- **TTL (Time To Live) и Eviction**: Установка времени жизни ключей (например, 60 секунд или 5 минут) гарантирует актуальность данных и предотвращает переполнение памяти. При дефиците памяти Redis применяет политики вытеснения, такие как `LRU` (Least Recently Used).
- **Инвалидация**: При выполнении `mutation`-запросов (создание, обновление или удаление ресурса) кэш должен быть явно сброшен или обновлен, чтобы избежать отдачи устаревших данных клиенту.
- **Проблема Cache Stampede**: Ситуация, когда при истечении TTL популярного ключа сотни одновременных запросов «пробивают» кэш и создают пиковую нагрузку на БД. Решается использованием распределенных блокировок (`Distributed Locks`), предотвращающих конкурентное обновление одной и той же записи в кэше.

#### Практическая реализация и синтаксис

Современная интеграция требует использования `async context manager` для управления ресурсами и `Pydantic v2` для молниеносной сериализации на стороне Rust-ядра.

**Инициализация Redis через Lifespan и внедрение зависимости:**

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI, Depends
from redis.asyncio import Redis, ConnectionPool

# Глобальный пул соединений
pool = ConnectionPool.from_url("redis://localhost:6379", decode_responses=True)

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Startup: Инициализация клиента Redis
    app.state.redis = Redis(connection_pool=pool)
    yield
    # Shutdown: Закрытие соединений
    await app.state.redis.close()

app = FastAPI(lifespan=lifespan)

async def get_redis(request: Request) -> Redis:
    # Инъекция через Depends
    return request.app.state.redis
```

**Реализация паттерна Cache-Aside с Pydantic v2:**

```python
from typing import Annotated
from pydantic import BaseModel

class Product(BaseModel):
    id: int
    name: str
    price: float

@app.get("/products/{product_id}")
async def get_product(
    product_id: int,
    redis: Annotated[Redis, Depends(get_redis)]
):
    cache_key = f"product:{product_id}"

    # 1. Проверка кэша
    cached_data = await redis.get(cache_key)
    if cached_data:
        # Десериализация объекта
        return Product.model_validate_json(cached_data)

    # 2. Имитация получения из БД при Cache Miss
    product = await fetch_product_from_db(product_id)

    # 3. Запись в кэш с TTL 300 секунд
    await redis.set(
        cache_key,
        product.model_dump_json(),
        ex=300
    )
    return product
```

#### Глоссарий терминов

- **[`redis.asyncio`](https://fastapi.tiangolo.com/deployment/server-workers/)** — высокопроизводительный асинхронный клиент для взаимодействия с Redis без блокировки `Event Loop`.
- **Connection Pooling** — механизм переиспользования открытых сетевых соединений для снижения накладных расходов на хэндшейки.
- **[Cache-Aside Pattern](https://fastapi.tiangolo.com/tutorial/encoder/)** — стратегия кэширования, где приложение берет на себя ответственность за чтение и запись в кэш.
- **Time To Live (TTL) & Cache Eviction** — параметры ограничения времени хранения данных и автоматического удаления старых записей.
- **[Cache Invalidating / Cache Flushing](https://fastapi.tiangolo.com/tutorial/body-updates/)** — процесс принудительного удаления данных из кэша при обновлении информации в основной БД.
- **Cache Stampede / Dog-piling** — эффект лавинообразного роста нагрузки на БД при одновременном запросе одного и того же отсутствующего в кэше ресурса.

#### Практический кейс: Высоконагруженное кэширование каталога товаров

**Сценарий**: Популярный интернет-магазин с нагрузкой 3 000 RPS. Эндпоинт получения деталей товара обращается к PostgreSQL, что занимает в среднем 4.7 секунды под нагрузкой.

**Реализация**:

1. **Слой кэширования**: Внедряется Redis с TTL 5 минут (300 сек).
2. **Инвалидация**: В эндпоинт `PUT /products/{id}` добавляется вызов `await redis.delete(f"product:{id}")`. Теперь при изменении цены пользователь увидит актуальные данные мгновенно.
3. **Защита от Stampede**: Перед запросом в БД воркер пытается установить `NX` (Not Exists) ключ-блокировку в Redis. Остальные воркеры ждут разблокировки или повторно проверяют кэш.

**Результат**: Время ответа сокращается с 4.7с до 0.0001с (в 47 000 раз). Пропускная способность сервера ограничивается только мощностью сетевого стека, а не производительностью дисковой подсистемы БД.

#### Вопросы и задания для самопроверки

1. **Вопрос**: Почему выполнение метода `.keys("product:*")` в Redis считается опасным на production-окружениях и чем его заменить?
    - _Ответ: Метод `.keys()` является блокирующим (O(N)) и может «подвесить» весь сервер Redis. На продакшне следует использовать асинхронную итерацию через `SCAN`, которая возвращает ключи частями, не блокируя доступ другим клиентам._
2. **Задача**: Измените код эндпоинта обновления товара так, чтобы он не просто удалял старый кэш, а обновлял его новыми данными (стратегия `Write-Through`), используя `model_dump_json()`.
3. **Практическое задание**: Напишите сервис-обертку, который при записи в Redis автоматически добавляет к данным мета-поле `cached_at` с текущим временем `UTC`, используя `Pydantic settings` для конфигурации.
