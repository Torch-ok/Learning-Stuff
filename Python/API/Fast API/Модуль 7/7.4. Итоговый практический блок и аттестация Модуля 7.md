#### Сквозной практический кейс: Сервис генерации PDF-отчетов с кэшированием в Redis и фоновой обработкой

**Постановка задачи:** Реализовать высокопроизводительный сервис формирования аналитики. Система должна мгновенно отдавать кэшированный результат из Redis, а в случае отсутствия — ставить задачу на генерацию PDF в очередь воркеров, подтверждая запрос статусом **202 Accepted**.

**Пошаговый алгоритм выполнения:**

1. **Проверка кэша и REST-интерфейс:** Эндпоинт `GET /reports/{report_id}` проверяет наличие ключа в Redis через `redis.asyncio` [7.2 draft]. При хите (Cache Hit) возвращается прямая ссылка на файл или его содержимое. Используется `Annotated` для инъекции клиента Redis.
    
2. **Постановка задачи (Cache Miss):** Если данных нет, FastAPI выступает в роли **Producer**. Задача отправляется в очередь **Taskiq** или **Celery**. Клиенту возвращается JSON с `task_id` и HTTP-статусом **202**, что является стандартом для долгоиграющих процессов [45, 620, 7.3 draft].
    
3. **Выполнение в Consumer (Worker):** Изолированный воркер считывает задачу из брокера [8.4 draft]. Используя асинхронный генератор для эффективной записи, он рендерит PDF, загружает его в хранилище и записывает в Redis статус готовности с TTL на 24 часа [7.2 draft, 712].
    
4. **Опрос статуса:** Клиент обращается к `GET /tasks/{task_id}`, где FastAPI проверяет **Result Backend** (Redis). Если задача завершена, возвращается URL готового отчета [7.3 draft, 8.2 draft].
    
5. **Graceful Degradation:** При временной недоступности Redis система должна переходить на прямое обращение к PostgreSQL или возвращать ошибку с предложением повторить запрос позже, не блокируя основной `Event Loop` [315, 638, 7.1 draft].
    

#### Комплексный контрольный тест для самопроверки

1. **Вопрос:** В каком сценарии `fastapi.BackgroundTasks` категорически проигрывают Celery/Taskiq?
    
    - _Ответ: В задачах, требующих строгой гарантии выполнения (Persistence) при перезагрузке сервера или при необходимости масштабирования вычислительных ресурсов (CPU-bound) отдельно от API [7.1 draft, 7.3 draft]._
2. **Задача на Redis:** Лимит оперативной памяти на инстансе Redis исчерпан. Какую политику `maxmemory-policy` следует выбрать для кэширования API-ответов, чтобы в памяти оставались только часто запрашиваемые отчеты?
    
    - _Решение: `allkeys-lru` (Least Recently Used), которая удаляет ключи, не использовавшиеся долгое время [7.2 draft]._
3. **Практическое задание:** Напишите логику инвалидации кэша: при вызове `PATCH /orders/{id}` необходимо удалить кэшированный PDF-отчет по этому заказу из Redis, используя метод `delete()` [34, 182, 7.2 draft].
    
4. **Задача на отказоустойчивость:** Настройте воркер так, чтобы он не удалял задачу из очереди до тех пор, пока не получит подтверждение успешной записи PDF в хранилище. Какой параметр конфигурации Celery за это отвечает?
    
    - _Ответ: `task_acks_late = True`. Это гарантирует повторную обработку задачи другим воркером при падении текущего контейнера [8.2 draft]._
5. **Вопрос на архитектуру:** Какое преимущество дает разделение Redis на два логических инстанса: один как Брокер (Broker), а другой как хранилище результатов (Result Backend)?
    
    - _Ответ: Это позволяет изолировать высоконагруженную очередь сообщений от хранилища данных, оптимизировать настройки TTL и памяти для разных типов нагрузки [8.2 draft, 7.2 draft]._
