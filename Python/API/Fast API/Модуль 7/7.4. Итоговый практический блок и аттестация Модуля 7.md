#### Сквозной практический кейс: Полноценное тестирование и система Observability для платежного роутера

**Постановка задачи:** Спроектировать и реализовать систему тестирования и мониторинга для критически важного модуля — платежного роутера, отвечающего за связь между FastAPI и внешним банковским шлюзом [7.4 prompt]. Необходимо гарантировать 100% надежность проведения транзакций и прозрачность отладки при возникновении сбоев.

**Пошаговый алгоритм выполнения:**

1. **Инфраструктура тестирования (PostgreSQL в Docker):** Используйте библиотеку 'testcontainers' для автоматического поднятия изолированного контейнера PostgreSQL перед началом прогона тестов [345, 7.2 draft]. Это обеспечит поддержку всех нативных типов данных 'asyncpg' и SQLAlchemy 2.0 Async, исключая расхождения с продакшн-средой.
    
2. **Асинхронные тесты и мокирование внешнего API:** Для тестирования эндпоинта '/payments/process' используйте 'httpx.AsyncClient'. Чтобы не выполнять реальные финансовые операции, подмените банковский сервис на 'AsyncMock' через 'app.dependency_overrides'.
    
    ```
    # Пример мокирования в conftest.py
    @pytest.fixture
    def mock_bank_api():
        mock = AsyncMock()
        mock.charge.return_value = {"status": "success", "tx_id": "999"}
        app.dependency_overrides[get_bank_service] = lambda: mock
        yield mock
        app.dependency_overrides.clear()
    ```
    
3. **Внедрение сквозного Correlation ID:** Реализуйте 'Middleware', которое извлекает 'X-Request-ID' из входящих заголовков или генерирует новый UUID [158, 161, 7.3 draft]. Этот идентификатор должен автоматически добавляться в каждый контекст логирования 'structlog', позволяя связать лог "Начало транзакции" с логом "Ошибка в БД".
    
4. **Мониторинг аномалий через Sentry:** Настройте интеграцию с 'Sentry SDK', чтобы автоматически перехватывать все необработанные исключения и ошибки валидации 422. Добавьте 'correlation_id' и 'user_id' в теги Sentry для быстрого воспроизведения сценария падения.
    
5. **Контроль качества кода (Code Coverage):** Запустите тесты с использованием флага '--cov=app', чтобы рассчитать процент покрытия бизнес-логики тестами. В пайплайне CI/CD (GitHub Actions) установите порог (threshold) в 90%, ниже которого деплой в продакшн будет заблокирован.
    

#### Комплексный контрольный тест для самопроверки

1. **Вопрос:** Какой атрибут 'AsyncMock' необходимо использовать, чтобы асинхронный метод 'process_payment' возвращал статус "COMPLETED"?
    
    - _Ответ: 'mock_service.process_payment.return_value = "COMPLETED"'. В асинхронных тестах важно, чтобы возвращаемое значение было доступно для 'await' [7.2 draft]._
2. **Задача на безопасность:** При настройке 'structlog' обнаружилось, что в логи попадает заголовок 'Authorization' с JWT-токеном. Как это исправить?
    
    - _Решение: Необходимо добавить процессор в конфигурацию логгера, который будет фильтровать (mask) чувствительные поля 'password', 'token' и 'Authorization' перед выводом в JSON [7.3 draft]._
3. **Практическое задание:** Напишите 'pytest'-фикстуру 'auth_client', которая возвращает 'httpx.AsyncClient' с уже предустановленным заголовком 'Authorization: Bearer <test_token>' для тестирования защищенных платежных эндпоинтов.
    
4. **Задача на конфигурацию:** Реализуйте глобальную подмену зависимости 'get_settings' на 'TestSettings' для всего экземпляра 'app' во время выполнения тестов.
    
    - _Решение: 'app.dependency_overrides[get_settings] = lambda: TestSettings()'. Не забудьте вызвать '.clear()' после завершения теста._
5. **Вопрос на архитектурное сравнение:** Почему использование реального PostgreSQL в Docker через 'testcontainers' предпочтительнее SQLite 'in-memory' для интеграционных тестов платежной системы?
    
    - _Ответ: SQLite не поддерживает многие функции PostgreSQL (например, сложные 'JOIN', специфические индексы или типы JSONB), что может привести к ситуации, когда тесты проходят на SQLite, но код падает в продакшне на реальной базе [7.2 draft]._
