#### Теоретический фундамент и архитектура

Для обеспечения надежности асинхронных приложений в 2026 году критически важен принцип изоляции и детерминированности тестов: результаты выполнения не должны зависеть от состояния внешних систем, таких как реальные базы данных, очереди сообщений или сторонние API. Тесты, взаимодействующие с внешними ресурсами, подвержены "флакированию" (нестабильности) из-за сетевых задержек или недоступности сервисов. Изоляция позволяет превратить сложные интеграционные сценарии в предсказуемые проверки бизнес-логики.

Основным инструментом реализации этого принципа в FastAPI является механизм `app.dependency_overrides`. Это словарь, позволяющий на лету подменять любую зависимость, объявленную через `Depends`, на её имитацию (mock) или альтернативную версию для тестирования. После завершения тестовой сессии или конкретного теста крайне важно очищать этот словарь, чтобы избежать эффекта "протекания состояния" (state leakage) между тестами.

При тестировании асинхронного I/O кода используется `unittest.mock.AsyncMock`, который позволяет эмулировать возвращаемые значения корутин и проверять факты их вызова с определенными аргументами. Для работы с базами данных применяются две основные стратегии:

- **Асинхронная SQLite в памяти:** использование драйвера `sqlite+aiosqlite` позволяет мгновенно создавать чистую БД для каждого теста.
- **Изолированная PostgreSQL в Docker:** использование паттерна **Testcontainers** обеспечивает запуск идентичной продакшну среды в изолированном контейнере, что гарантирует поддержку специфичных для Postgres типов и функций.

Для обеспечения транзакционной чистоты вместо полной пересборки схем перед каждым тестом часто применяется паттерн отката транзакции: тест выполняется внутри транзакции, которая принудительно откатывается в блоке `finally` фикстуры.

#### Практическая реализация и синтаксис

Пример настройки `conftest.py` с подменой БД и внешнего почтового сервиса:

```
import pytest
from unittest.mock import AsyncMock
from app.main import app
from app.database import get_db

# Мок сервиса отправки почты
mock_email_service = AsyncMock()

@pytest.fixture(autouse=True)
def override_dependencies():
    # Подмена реальных компонентов на тестовые
    app.dependency_overrides[get_db] = override_get_db
    app.dependency_overrides[send_email_task] = mock_email_service
    yield
    # Обязательная очистка после теста
    app.dependency_overrides.clear()
```

Имитация ответа внешней платежной системы через `AsyncMock`:

```
async def test_payment_process(client: AsyncClient):
    # Настройка ожидаемого поведения мока
    mock_stripe_api.charge.return_value = {"status": "succeeded", "id": "ch_123"}

    response = await client.post("/payments/charge", json={"amount": 1000})

    assert response.status_code == 200
    assert response.json()["transaction_id"] == "ch_123"
    # Проверка, что метод был вызван с корректной суммой
    mock_stripe_api.charge.assert_called_once_with(amount=1000)
```

> [!warning] Актуализация синтаксиса 
> Использование стандартного `MagicMock` для асинхронных функций приведет к ошибке, так как он не является `awaitable`. В 2026 году для всех асинхронных зависимостей и вызовов внешних библиотек необходимо использовать исключительно `AsyncMock`.

#### Глоссарий терминов

- **[`app.dependency_overrides`](https://fastapi.tiangolo.com/advanced/testing-dependencies/)** — встроенный механизм FastAPI для глобальной замены зависимостей в тестовом окружении.
- **`AsyncMock`** — объект из библиотеки `unittest.mock`, предназначенный для имитации асинхронных функций и объектов.
- **Testcontainers Pattern** — подход к интеграционному тестированию, использующий автоматический запуск реальных сервисов (БД, Redis) в Docker-контейнерах.
- **Transaction Rollback Pattern** — стратегия очистки тестовых данных путем отката транзакции сессии базы данных после каждого теста.
- **Mocking External Services** — замена реальных сетевых вызовов к сторонним API на предопределенные ответы для ускорения и стабилизации тестов.
- **Deterministic Testing** — свойство тестов всегда возвращать одинаковый результат при неизменном коде, исключая влияние внешних факторов.

#### Практический кейс: Настройка отказоустойчивого CI-пайплайна

**Сценарий:** Сервис обработки заказов зависит от PostgreSQL, Redis (кэш) и Stripe API (платежи).

**Реализация:**

1. **База данных:** В CI-пайплайне GitHub Actions запускается `service container` с PostgreSQL. Схема создается автоматически через `alembic upgrade head`.
2. **Redis:** Для тестов уровня роутера Redis подменяется на мок-объект через `app.dependency_overrides`, чтобы исключить задержки сетевого I/O.
3. **Внешнее API:** Вызовы к Stripe API оборачиваются в `AsyncMock`, возвращающий успешные или ошибочные JSON-ответы в зависимости от сценария теста.
4. **Результат:** Тесты проходят полностью в изолированной среде. Использование `autouse` фикстур для отката транзакций гарантирует, что данные первого теста не повлияют на второй, предотвращая накопление ошибок в базе.

#### Вопросы и задания для самопроверки

1. **Вопрос:** Почему отсутствие вызова `app.dependency_overrides.clear()` в `tearDown` или после `yield` фикстуры может привести к скрытым ошибкам в CI/CD?
    - _Ответ: Если один тест подменил зависимость (например, убрал проверку JWT), а другой тест полагается на реальную проверку, то без очистки второй тест пройдет несанкционированно, маскируя дыру в безопасности._
2. **Задача:** Код `await my_mock()` вызывает `TypeError: 'MagicMock' object is not awaitable`. Как это исправить?
    - _Решение: Заменить `MagicMock` на `AsyncMock`._
3. **Практическое задание:** Реализуйте фикстуру `db_session`, которая создает асинхронную сессию SQLAlchemy, начинает транзакцию через `session.begin()`, передает сессию в тест через `yield`, а затем вызывает `session.rollback()` и `session.close()`.
