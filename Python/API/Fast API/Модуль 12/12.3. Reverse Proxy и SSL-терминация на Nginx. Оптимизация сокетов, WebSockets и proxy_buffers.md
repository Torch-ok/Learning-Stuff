#### Теоретический фундамент и архитектура

В архитектуре промышленного уровня 2026 года Nginx выступает в роли критически важного входного шлюза (**Gateway**) перед FastAPI-сервером (Uvicorn или Granian). Его основная задача — освободить приложение от задач сетевого уровня, таких как **SSL-терминация**, и обеспечить безопасность от атак типа Slowloris, эффективно буферизируя запросы.

**Варианты межпроцессного взаимодействия (IPC):**

1. **TCP-сокеты (`127.0.0.1:8000`)**: Стандартный способ взаимодействия через сетевой стек ОС. Прост в настройке, особенно в Docker-сетях, где Nginx и FastAPI находятся в разных контейнерах.
2. **Unix Domain Sockets (`unix:/tmp/uvicorn.sock`)**: Более производительный метод для случаев, когда Nginx и ASGI-сервер запущены на одной физической или виртуальной машине. Он исключает накладные расходы на инкапсуляцию TCP-пакетов и проверку контрольных сумм.

**Поддержка дуплексных соединений и стриминга:** Для работы **WebSockets** и **Server-Sent Events (SSE)** Nginx требует специфической настройки проброса заголовков `Upgrade` и `Connection`. Без этого прокси-сервер будет обрывать соединения, воспринимая их как некорректные HTTP-запросы. При использовании асинхронного стриминга данных FastAPI автоматически отправляет заголовок `X-Accel-Buffering: no`, чтобы предотвратить задержки в Nginx, вызванные буферизацией.

**Оптимизация буферизации:** Параметры `proxy_buffers` позволяют Nginx удерживать ответы приложения в памяти, не блокируя воркеры Uvicorn/Granian при передаче больших JSON-пакетов медленным клиентам. Это критично для масштабируемости системы при высоких нагрузках.

#### Практическая реализация и синтаксис

**Пример конфигурации `nginx.conf` с SSL и оптимизацией:**

```nginx
upstream fastapi_app {
    # Использование TCP-сокета (стандарт для Docker)
    server 127.0.0.1:8000;
    # Или Unix-сокет: server unix:/tmp/uvicorn.sock;
}

server {
    listen 80;
    server_name api.example.com;
    # Редирект HTTP на HTTPS
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name api.example.com;

    # Настройки SSL (Certbot / Let's Encrypt)
    ssl_certificate /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    location / {
        proxy_pass http://fastapi_app;

        # Проброс заголовков для определения реального IP клиента
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Поддержка WebSockets и SSE
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 86400s; # Сутки для долгоживущих соединений

        # Тюнинг буферов для больших JSON ответов
        proxy_buffering on;
        proxy_buffer_size 8k;
        proxy_buffers 8 64k;
        proxy_busy_buffers_size 128k;
    }
}
```

[Nginx Proxy](https://fastapi.tiangolo.com/deployment/concepts/#proxies), [HTTPS setup](https://fastapi.tiangolo.com/deployment/https/)

**Подключение `ProxyHeadersMiddleware` в FastAPI:**

Для того чтобы FastAPI корректно считывал проброшенные заголовки (например, видел `https`, а не `http`), необходимо использовать встроенное Middleware.

```python
from fastapi import FastAPI
from fastapi.middleware.proxy_headers import ProxyHeadersMiddleware

app = FastAPI()

# Добавление поддержки прокси-заголовков
app.add_middleware(ProxyHeadersMiddleware, trusted_hosts=["127.0.0.1"])
```

[Middleware docs](https://fastapi.tiangolo.com/tutorial/middleware/), [Trusted Hosts](https://fastapi.tiangolo.com/reference/middleware/)

#### Глоссарий терминов

- **[Reverse Proxy & SSL Termination](https://fastapi.tiangolo.com/deployment/concepts/)** — использование Nginx для расшифровки HTTPS-трафика и его распределения между инстансами приложения.
- **Unix Domain Sockets vs TCP Sockets** — методы IPC; Unix-сокеты оптимизированы для связи процессов внутри одного ядра ОС.
- **[WebSocket Proxying](https://fastapi.tiangolo.com/advanced/websockets/)** — механизм переключения протокола с HTTP на WebSocket через заголовки `Upgrade`.
- **`proxy_buffers` & `proxy_buffer_size`** — директивы Nginx для управления памятью, выделяемой под хранение ответов бэкенда.
- **Reverse Proxy Headers** — служебные заголовки (`X-Forwarded-For`), передающие информацию о клиенте через слои прокси.
- **FastAPI `ProxyHeadersMiddleware`** — компонент, позволяющий приложению «доверять» заголовкам, установленным прокси-сервером.

#### Практический кейс: Проектирование production-конфигурации Nginx

**Сценарий**: Необходимо запустить чат-микросервис, который отдает историю сообщений (большие JSON) и поддерживает активные WebSocket-сессии.

**Реализация**:

1. **Отказ от задержек**: Применение `X-Accel-Buffering: no` со стороны FastAPI для моментальной доставки SSE-событий в браузер.
2. **SSL-оптимизация**: Использование TLS 1.3 и HTTP/2 для ускорения загрузки фронтенд-ресурсов (статики).
3. **Безопасность IPC**: Использование Unix-сокетов с ограниченными правами доступа (`chown www-data:www-data`), что предотвращает ошибку **502 Bad Gateway**, возникающую при попытке Nginx прочитать сокет без прав.

#### Вопросы и задания для самопроверки

1. **Вопрос**: Почему без использования `ProxyHeadersMiddleware` вызовы `request.client.host` в FastAPI всегда будут возвращать IP-адрес Nginx (например, 127.0.0.1)?
    - _Ответ: Так как соединение физически устанавливается между Nginx и приложением, ОС видит адрес прокси. Реальный IP клиента зашит в заголовке `X-Forwarded-For`, который Middleware должен распарсить._
2. **Задача**: Пользователи SSE-стриминга жалуются, что сообщения приходят «пачками» раз в 10 секунд. Какую настройку Nginx нужно проверить?
    - _Решение: Проверьте `proxy_buffering`. Если оно включено, Nginx будет копить данные стрима. FastAPI должен посылать заголовок `X-Accel-Buffering: no` для отключения этого поведения._
3. **Практическое задание**: Рассчитайте общее количество памяти, которое Nginx может выделить под буферизацию одного запроса, если установлено `proxy_buffers 16 32k`.
    - _Ответ: $16 \times 32,\text{КБ} = 512,\text{КБ}$ на одно соединение._
