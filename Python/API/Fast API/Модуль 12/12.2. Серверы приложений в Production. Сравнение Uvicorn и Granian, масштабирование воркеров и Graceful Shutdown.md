
#### Теоретический фундамент и архитектура

Переход к промышленной эксплуатации FastAPI в 2026 году требует отказа от упрощенных методов запуска в пользу высокопроизводительных ASGI-серверов, способных эффективно утилизировать системные ресурсы и обеспечивать надежную остановку процессов.

**Выбор ASGI/Rust HTTP-сервера:**

- **Uvicorn** — проверенный временем индустриальный стандарт на базе `uvloop` и `httptools`. Он идеально подходит для большинства задач, обеспечивая высокую скорость обработки асинхронных соединений.
- **Granian** — современная альтернатива на базе Rust, предлагающая экстремальную производительность (поддержка интерфейсов ASGI/RSGI) и минимальный оверхед при обработке сетевого трафика.

**Модель процессинга и воркеры:** Для параллельной обработки запросов на многоядерных системах используется многопроцессорная модель. Поскольку один процесс Python ограничен одним ядром процессора, запуск нескольких воркеров (`workers`) позволяет масштабировать приложение горизонтально. Рекомендуемое количество воркеров обычно рассчитывается по формуле $(2 \times \text{CPU cores}) + 1$, что позволяет эффективно переключаться между задачами во время ожидания I/O-операций.

**Управление процессами и сигналы ОС:** В контейнеризированных средах (Docker) использование встроенных менеджеров воркеров Uvicorn или Granian (иногда в связке с Gunicorn как менеджером процессов) является стандартом, заменяющим внешние супервизоры. Критически важным аспектом является обработка сигналов `SIGTERM` и `SIGINT`. Если приложение запущено в Docker как **PID 1** без специального инициализатора (например, `tini`), оно может игнорировать сигналы остановки от оркестратора, что приводит к принудительному «убийству» процесса по таймауту вместо планового завершения.

**Graceful Shutdown:** Современный механизм `lifespan` в FastAPI позволяет приложению перехватывать событие завершения и выполнять **Graceful Shutdown**: закрывать пулы соединений с PostgreSQL и Redis, завершать асинхронные задачи и очищать временные ресурсы до того, как сервер окончательно прекратит работу.

#### Практическая реализация и синтаксис

Для запуска приложения в режиме `production` необходимо использовать команды, оптимизированные для высокой нагрузки и стабильности.

**Пример запуска через Uvicorn (стандартный подход):**

```
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4 --no-access-log
```

**Пример запуска через Granian (высокопроизводительный Rust-core):**

```
granian --interface asgi app.main:app --host 0.0.0.0 --port 8000 --workers 4
```

**Настройка Dockerfile с использованием `tini` для корректной обработки сигналов:**

```
FROM python:3.12-slim
# Установка системного инициализатора
RUN apt-get update && apt-get install -y tini && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY . .
# Сборка зависимостей через uv
RUN uv sync --frozen
# Использование tini как точки входа
ENTRYPOINT ["/usr/bin/tini", "--"]
CMD ["fastapi", "run", "app/main.py", "--host", "0.0.0.0", "--port", "8000"]
```

#### Глоссарий терминов

- **ASGI Application Server (Uvicorn / Granian)** — интерфейс между веб-сервером и асинхронным Python-приложением для обработки HTTP-трафика.
- **Rust-based HTTP Server (Granian)** — высокопроизводительный сервер приложений, написанный на языке Rust для снижения задержек и потребления памяти.
- **Multi-process Worker Model** — метод запуска нескольких экземпляров приложения для параллельной утилизации мощностей CPU.
- **`SIGTERM` / `SIGINT` Handling** — процесс перехвата системных сигналов завершения для выполнения очистки ресурсов [8.3 draft].
- **PID 1 Problem & `tini` / `dumb-init`** — архитектурная особенность контейнеров, требующая посредника для корректной передачи сигналов управления процессам.
- **Graceful Shutdown Timeout** — временной период, в течение которого сервер дожидается завершения обработки активных запросов перед выключением.

#### Практический кейс: Настройка высоконагруженного узелка Uvicorn/Granian под 8-ядерный сервер

**Сценарий:** Настройка API, способного обрабатывать до 10 000 RPS на 8-ядерном сервере.

1. **Конфигурация воркеров:** Установка параметра `--workers 17` (на базе формулы $8 \times 2 + 1$) для компенсации задержек I/O при работе с БД.
2. **Оптимизация производительности:** Отключение `access-log` для исключения блокирующих операций записи в стандартный поток вывода при каждом запросе.
3. **Отказоустойчивость:** Интеграция `tini` в Docker-образ гарантирует, что при получении `SIGTERM` (например, при обновлении пода в Kubernetes) FastAPI успеет завершить транзакции в PostgreSQL и закрыть соединения в Redis через блок `lifespan`.
4. **Бенчмарк:** Использование Granian позволяет снизить p99 задержку на 15–20% по сравнению с классическим Uvicorn за счет более эффективной реализации сетевого стека на Rust.

#### Вопросы и задания для самопроверки

1. **Вопрос:** Почему использование флага `--reload` категорически запрещено в production-окружении?
    - _Ответ: Механизм `reload` потребляет значительные ресурсы CPU для мониторинга файловой системы и может вызвать неконтролируемые перезапуски воркеров при изменении временных файлов, что приводит к обрыву соединений и нестабильности._
2. **Задача:** Как предотвратить внезапный разрыв активных WebSocket-соединений при плановом перезапуске контейнера?
    - _Решение: Необходимо настроить параметр Graceful Shutdown в оркестраторе (например, `terminationGracePeriodSeconds` в K8s) и убедиться, что ASGI-сервер транслирует сигналы в `lifespan` функцию FastAPI, которая плавно закроет сокеты._
3. **Практическое задание:** Составьте CLI-команду запуска Granian, которая будет использовать 2 воркера, каждый из которых запускает 4 внутренних Rust-треда (threads) для обработки входящих асинхронных задач.
