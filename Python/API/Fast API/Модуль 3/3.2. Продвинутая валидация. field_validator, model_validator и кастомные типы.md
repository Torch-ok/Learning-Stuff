#### Теоретический фундамент и архитектура

Продвинутая валидация в Pydantic v2 позволяет реализовывать сложную логику, выходящую за рамки простых ограничений типов. Основным инструментом для проверки отдельных атрибутов является декоратор `@field_validator`, который может работать в двух режимах: `mode='before'` для обработки «сырых» входных данных до их приведения к типам Pydantic и `mode='after'` для работы с уже типизированными значениями. Если валидация требует одновременного доступа к нескольким полям, используется `@model_validator`, где режим `before` предоставляет доступ к исходному словарю данных, а `after` — к уже инициализированному экземпляру класса через `self`.

Для получения контекста выполнения, например, доступа к значениям других полей в процессе валидации текущего, в современные валидаторы передается аргумент `info` (тип `ValidationInfo`), что критически важно для кросс-полярных проверок. Механизмы Pydantic v2 также поддерживают интеграцию с `pydantic_core` для создания максимально быстрых кастомных типов, использующих низкоуровневые схемы Rust для валидации на этапе парсинга. Это позволяет инкапсулировать логику проверки (например, формата международного номера телефона или IBAN) непосредственно в определение типа данных.

#### Практическая реализация и синтаксис

Современный синтаксис требует использования `Annotated` для связывания типов и валидаторов.

**Пример схемы с валидацией сложности пароля и нормализацией данных:**

```python
from typing import Annotated
from pydantic import BaseModel, Field, field_validator, model_validator, EmailStr

class UserRegisterSchema(BaseModel):
    email: EmailStr
    password: Annotated[str, Field(min_length=8, max_length=128)]
    confirm_password: str

    @field_validator("email", mode="after")
    @classmethod
    def normalize_email(cls, v: str) -> str:
        # Приведение email к нижнему регистру для консистентности в БД
        return v.lower()

    @model_validator(mode="after")
    def verify_password_match(self) -> "UserRegisterSchema":
        # Кросс-полевая валидация: проверка совпадения паролей
        if self.password != self.confirm_password:
            raise ValueError("passwords do not match")
        return self
```

> [!warning] Актуализация синтаксиса 
> В Pydantic v2 устаревшие декораторы `@validator` и `@root_validator` из первой версии заменены на более производительные и строго типизированные `@field_validator` и `@model_validator`.

#### Глоссарий терминов

- **[`@field_validator`](https://fastapi.tiangolo.com/tutorial/body-fields/#body-fields)** — декоратор для создания функций, проверяющих или преобразующих значение конкретного поля модели.
- **[`@model_validator`](https://fastapi.tiangolo.com/tutorial/body-nested-models/#nested-models)** — инструмент для валидации всей структуры данных, позволяющий проверять зависимости между полями.
- **[Mode `before` vs Mode `after`](https://fastapi.tiangolo.com/tutorial/query-params-str-validations/#custom-validation)** — параметры, определяющие, будет ли валидатор запущен до или после стандартного процесса парсинга типов Pydantic.
- **[`ValidationInfo`](https://fastapi.tiangolo.com/tutorial/response-model/#response-model-return-type)** — объект контекста, предоставляющий валидатору доступ к метаданным и значениям уже обработанных полей.
- **[Cross-field Validation (Кросс-полярная валидация)](https://fastapi.tiangolo.com/tutorial/security/simple-oauth2/#check-the-password)** — процесс проверки бизнес-логики, зависящей от нескольких атрибутов модели одновременно.
- **[Custom Pydantic Types](https://fastapi.tiangolo.com/tutorial/extra-data-types/#other-data-types)** — пользовательские классы, расширяющие стандартные типы Python дополнительной логикой валидации и сериализации.

#### Практический кейс: Реализация комплексной валидации финансовой транзакции

**Сценарий:** Необходимо создать модель `TransferSchema` для перевода средств. Модель должна проверять корректность валют, лимиты суммы и гарантировать, что отправитель и получатель — разные счета.

**Реализация:**

1. **Валидация полей:** Используется `Field(gt=0)` для суммы, чтобы исключить отрицательные переводы.
2. **Регулярные выражения:** Для проверки формата счета (IBAN) в `Field` передается параметр `pattern`, соответствующий международному стандарту.
3. **Бизнес-логика в модели:** Через `@model_validator(mode='after')` проверяется, что `from_account_id != to_account_id`. При нарушении выбрасывается `ValueError`, который FastAPI автоматически конвертирует в ответ **422 Unprocessable Entity**.
4. **Нормализация:** Валидатор `mode='before'` может автоматически преобразовывать типы валют в верхний регистр (например, "usd" -> "USD") до основной проверки.

В случае ошибки клиент получит JSON с полем `loc`, указывающим на конкретные поля или на корень модели (`__root__`), если ошибка возникла в `model_validator`.

2. **Задача:** Исправьте ошибку в коде кросс-полярного валидатора, который пытается сравнить даты бронирования, но падает с `AttributeError` из-за того, что одно из полей не прошло базовую валидацию типов.
3. **Практическое задание:** Напишите схему `PhoneNumber`, которая использует кастомный тип или `field_validator` с регулярным выражением для проверки, что строка начинается с `+` и содержит от 10 до 15 цифр.
