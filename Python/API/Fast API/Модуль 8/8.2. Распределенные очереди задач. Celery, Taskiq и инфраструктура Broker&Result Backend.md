### 8.2. Механизм Middleware: Конвейер обработки запросов, безопасность и логирование Latency

#### Теоретический фундамент и архитектура

В архитектуре FastAPI 2026 года **Middleware** (промежуточное ПО) представляет собой функцию или класс, который работает как «перехватчик» для каждого входящего HTTP-запроса и каждого исходящего ответа. Middleware образует конвейер: запрос проходит через все слои промежуточного ПО сверху вниз до попадания в _path operation function_, а ответ возвращается в обратном порядке — снизу вверх.

**Создание кастомного промежуточного ПО:** Для реализации кастомной логики в FastAPI чаще всего используется декоратор `@app.middleware("http")` или наследование от `starlette.middleware.base.BaseHTTPMiddleware`. Это позволяет внедрять сквозную функциональность, такую как проверка прав доступа или аутентификация, до того как запрос будет обработан контроллером. Однако стоит учитывать, что использование `BaseHTTPMiddleware` может вносить дополнительные накладные расходы в высоконагруженных системах по сравнению с низкоуровневыми **Pure ASGI Middleware**.

**Безопасность инфраструктурного слоя:**

- **`CORSMiddleware`**: Критически важный компонент для взаимодействия фронтенда и бэкенда, работающих на разных доменах или портах. Он управляет заголовками **Cross-Origin Resource Sharing**, разрешая или блокируя запросы на основе белого списка источников (`allow_origins`), методов (`allow_methods`) и учетных данных (`allow_credentials`).
- **`TrustedHostMiddleware`**: Защищает приложение от атак через заголовок `Host`, гарантируя, что сервер обрабатывает запросы только с разрешенных доменных имен.

**Логирование и трассировка:** Middleware идеально подходит для мониторинга производительности (Latency). Путем фиксации времени начала запроса и вычисления разницы после вызова `call_next(request)` можно точно определить время обработки каждого эндпоинта. Для отладки в распределенных системах часто внедряется **Correlation-ID** (`X-Request-ID`), который пробрасывается через все слои и микросервисы для сквозного поиска в логах.

> [!warning] Актуализация синтаксиса При использовании стриминговых ответов (`StreamingResponse`) или `EventSourceResponse` внутри `BaseHTTPMiddleware` могут возникать сложности с изменением заголовков ответа, так как тело ответа может начать передаваться до завершения работы Middleware.

#### Практическая реализация и синтаксис

**Кастомный Middleware для замера времени (Latency):**

```
import time
from fastapi import Request
from starlette.middleware.base import BaseHTTPMiddleware

class ProcessTimeMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        start_time = time.perf_counter()

        # Передача управления следующему слою
        response = await call_next(request)

        process_time = time.perf_counter() - start_time
        # Добавление кастомного заголовка в ответ
        response.headers["X-Process-Time"] = str(process_time)
        return response

app.add_middleware(ProcessTimeMiddleware)
```

**Настройка CORS и Trusted Hosts через `pydantic-settings`:**

```
from fastapi.middleware.cors import CORSMiddleware
from starlette.middleware.trustedhost import TrustedHostMiddleware
from .config import settings # Загрузка через pydantic-settings

app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.allowed_origins, # Список из ENV
    allow_credentials=True,
    allow_methods=["*"], # Разрешить все методы
    allow_headers=["*"],
)

app.add_middleware(
    TrustedHostMiddleware,
    allowed_hosts=["api.example.com", "*.example.com"]
)
```

#### Глоссарий терминов

- **[ASGI Middleware Architecture](https://fastapi.tiangolo.com/tutorial/middleware/)** — иерархическая структура слоев обработки, оборачивающая ASGI-приложение для модификации запросов и ответов.
- **[`BaseHTTPMiddleware`](https://fastapi.tiangolo.com/reference/middleware/)** — высокоуровневый класс FastAPI/Starlette для упрощенного создания HTTP-промежуточного ПО.
- **[`CORSMiddleware` & Cross-Origin Security](https://fastapi.tiangolo.com/tutorial/cors/)** — механизм безопасности, предотвращающий несанкционированный доступ к API с других доменов.
- **`TrustedHostMiddleware` & Host Header Attacks** — слой защиты, верифицирующий соответствие заголовка `Host` заданному списку разрешенных значений.
- **[Latency Tracking / Process Time Header](https://www.youtube.com/watch?v=PythonFastAPICorey)** — практика измерения времени обработки запроса на стороне сервера и передачи этого значения в метаданных ответа.
- **Correlation-ID (`X-Request-ID`)** — уникальный идентификатор запроса, используемый для связывания логов различных компонентов системы.

#### Практический кейс: Построение сквозного конвейера аудита и безопасности

**Сценарий**: Необходимо обеспечить безопасность и наблюдаемость банковского API.

**Реализация**:

1. **Фильтрация хостов**: `TrustedHostMiddleware` отсекает запросы с поддельными заголовками, предотвращая атаку "Host Header Injection".
2. **Строгий CORS**: `CORSMiddleware` настраивается на конкретный домен React-приложения (например, `https://bank.example.com`), запрещая запросы от вредоносных сайтов.
3. **Идентификация**: Middleware генерирует `X-Request-ID`. Если в запросе уже есть такой заголовок (от Nginx), он сохраняется; если нет — создается новый UUID.
4. **Аудит Latency**: Система фиксирует, что запрос к эндпоинту `/transactions` занял 450 мс, и выводит это в структурированный лог вместе с `Request-ID`.

**Риски производительности**: При наслоении более 10-15 слоев `BaseHTTPMiddleware` в высоконагруженном приложении (3000+ RPS) может наблюдаться деградация пропускной способности из-за особенностей асинхронного переключения контекста в Python.

#### Вопросы и задания для самопроверки

1. **Вопрос**: Почему `app.add_middleware(CORSMiddleware, ...)` должен добавляться раньше, чем Middleware для проверки авторизации?
    - _Ответ: Так как Middleware выполняются в порядке, обратном добавлению (LIFO для ответов), CORS должен быть одним из внешних слоев, чтобы корректно обрабатывать Preflight-запросы (OPTIONS) до того, как сработает логика авторизации, которая может выкинуть 401 ошибку._
2. **Задача**: Вы добавили `X-Request-ID` в Middleware, но при использовании `StreamingResponse` заголовок не всегда доходит до клиента. В чем причина?
    - _Решение: В `BaseHTTPMiddleware` после вызова `await call_next(request)` ответ может начать отправляться «кусками». Заголовки должны быть установлены в объекте `Response` до того, как начнется стриминг данных._
3. **Практическое задание**: Реализуйте простейшее Middleware через декоратор `@app.middleware("http")`, которое проверяет наличие заголовка `User-Agent` и возвращает `400 Bad Request`, если он отсутствует.
