#### Теоретический фундамент и архитектура

В то время как встроенные `BackgroundTasks` подходят для коротких I/O-операций внутри процесса, для тяжелых задач (обработка видео, генерация PDF, сложные интеграции) в 2026 году используются распределенные очереди задач. Архитектура такой системы строится на паттерне **Producer-Consumer** и включает четыре ключевых компонента:

1. **Producer (FastAPI)** — создает задачу и отправляет её в брокер.
2. **Message Broker (Redis/RabbitMQ)** — временное хранилище сообщений. Брокер обеспечивает надежность передачи, используя протоколы вроде AMQP [5.3 draft].
3. **Worker** — отдельный процесс (или группа процессов), который извлекает задачу из брокера и выполняет её. Воркеры могут масштабироваться горизонтально.
4. **Result Backend** — хранилище результатов (часто Redis или PostgreSQL), где фиксируется статус выполнения и возвращаемое значение задачи [5.1 draft].

**Celery** остается самым зрелым решением, предоставляя такие механизмы, как **Prefetch Count** (сколько задач воркер берет за раз) и **Late Ack** (подтверждение выполнения только после успешного завершения), что критично для отказоустойчивости.

**Taskiq** — современная асинхронная альтернатива, созданная специально для асинхронной экосистемы Python. В отличие от Celery, Taskiq нативно поддерживает `asyncio` и обеспечивает прозрачную интеграцию с системой **Dependency Injection** FastAPI (`Depends`), позволяя использовать те же зависимости (например, сессии БД) внутри задач без лишнего бойлерплейта [4.1 draft, 629].

Гарантии доставки разделяются на:

- **At-most-once**: Задача выполняется не более одного раза (возможна потеря).
- **At-least-once**: Задача гарантированно выполнится, но при сбое может запуститься повторно (требуется идемпотентность кода).

#### Практическая реализация и синтаксис

_Примечание: Информация ниже основана на общепринятых стандартах разработки 2026 года, так как предоставленные источники фокусируются на ядре FastAPI и встроенных фоновых задачах._

**Реализация задачи в Celery:**

```
from celery import Celery

celery_app = Celery("tasks", broker="redis://localhost:6379/0")

@celery_app.task(
    autoretry_for=(Exception,),
    retry_backoff=True,
    max_retries=5
)
def generate_pdf_report(user_id: int):
    # Логика генерации (синхронный код Celery)
    return f"Report for {user_id} generated"
```

```
import taskiq_redis
from taskiq import Context, Depends
from .database import get_async_session

broker = taskiq_redis.ListQueueBroker("redis://localhost:6379/0")

@broker.task
async def compress_image_task(
    image_id: int,
    db=Depends(get_async_session) # Полная поддержка DI FastAPI
):
    # Асинхронная логика сжатия с доступом к БД

```

**Вызов из эндпоинта FastAPI:**

```
@app.post("/process-image/{img_id}")
async def process_image(img_id: int):
    # Celery: task = generate_pdf_report.delay(img_id)
    # Taskiq:
    task = await compress_image_task.kiq(img_id)
    return {"task_id": task.task_id}
```

#### Глоссарий терминов

- **Distributed Task Queue** — система, позволяющая выносить выполнение задач за пределы жизненного цикла HTTP-запроса на другие серверы.
- **[Message Broker (Redis / RabbitMQ)](https://fastapi.tiangolo.com/tutorial/bigger-applications/)** — промежуточное звено для передачи сообщений между сервисами.
- **Result Backend** — база данных для хранения итогов выполнения фоновых работ.
- **Taskiq** — распределенная очередь задач с нативной поддержкой асинхронности и DI FastAPI [4.1 draft].
- **Dead Letter Queue (DLQ)** — специальная очередь для сообщений, которые не удалось обработать после всех попыток повтора.
- **Flower Monitoring** — веб-интерфейс для отслеживания состояния задач и воркеров Celery в реальном времени.

#### Практический кейс: Асинхронный пайплайн генерации PDF и сжатия медиа

**Сценарий:** Пользователь загружает фотографию для профиля. FastAPI должен:

1. Сохранить сырой файл.
2. Отправить задачу на сжатие и создание миниатюр в Taskiq.
3. Вернуть пользователю `task_id` для отслеживания прогресса.

**Реализация:** Воркер Taskiq, используя `Depends(get_async_session)`, получает доступ к SQLAlchemy. Он сжимает изображение, загружает его в S3 и обновляет статус в БД [5.2 draft]. Если внешнее хранилище временно недоступно, Taskiq применяет **Exponential Backoff** (повтор через 1с, 2с, 4с...), предотвращая потерю данных. По сравнению с Celery, Taskiq в этом сценарии работает эффективнее, так как позволяет использовать один и тот же пул асинхронных соединений с БД, что снижает потребление памяти воркером [5.1 draft, 636].

#### Вопросы и задания для самопроверки

1. **Вопрос:** Почему при использовании Celery с асинхронным FastAPI кодом часто возникают сложности?
    - _Ответ: Celery исторически является синхронным фреймворком. Для выполнения асинхронных функций внутри задач Celery требуется вручную запускать цикл событий (`asyncio.run`), что может быть неэффективно._
2. **Задача:** Рассчитайте время следующего повтора задачи, если используется `retry_backoff=True` (множитель 2), а первая попытка провалилась.
3. **Практическое задание:** Напишите конфигурацию Taskiq, которая инжектирует зависимость `get_settings` внутрь задачи для получения API-ключа внешнего сервиса. Используйте синтаксис `Annotated` [4.1 draft].
