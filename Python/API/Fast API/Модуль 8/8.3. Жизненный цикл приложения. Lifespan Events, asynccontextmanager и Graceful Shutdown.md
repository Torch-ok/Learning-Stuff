#### Теоретический фундамент и архитектура

В современной разработке на FastAPI версии 2026 управление жизненным циклом приложения перешло на декларативный подход с использованием параметра `lifespan`. Ранее применявшиеся декораторы `@app.on_event("startup")` и `@app.on_event("shutdown")` официально признаны устаревшими и не рекомендуются для новых проектов. Новый механизм базируется на использовании асинхронного контекстного менеджера `@asynccontextmanager`, который позволяет в рамках одной функции описать как логику подготовки ресурсов, так и их очистку.

**Механика выполнения Lifespan-событий:** При запуске ASGI-сервера (Uvicorn или Granian) управление сначала передается в функцию `lifespan` до выполнения инструкции `yield`. В этот момент инициализируются критически важные компоненты: создаются таблицы в базе данных через асинхронный движок SQLAlchemy 2.0, устанавливаются соединения с Redis и настраиваются пулы HTTP-клиентов `httpx.AsyncClient`. Если на этом этапе возникает исключение (например, база данных недоступна), сервер завершит работу с ошибкой, не начав прием входящего трафика, что предотвращает работу приложения в "битом" состоянии.

**Управление состоянием и Graceful Shutdown:** Все созданные ресурсы могут быть безопасно сохранены в объекте `app.state`, что делает их доступными для всех роутеров через объект `Request` [7.2 draft]. После выполнения кода до `yield` приложение начинает обрабатывать запросы. Когда процесс получает сигнал завершения (`SIGTERM` или `SIGINT`), выполнение функции `lifespan` возобновляется сразу после инструкции `yield`. Этот этап называется **Graceful Shutdown**: здесь происходит закрытие пулов соединений и корректная остановка фоновых задач, что гарантирует отсутствие утечек памяти и целостность данных в транзакциях.

> [!warning] Актуализация синтаксиса 
> Использование `@app.on_event` более не гарантирует правильный порядок очистки ресурсов при возникновении ошибок инициализации и считается устаревшим подходом.

#### Практическая реализация и синтаксис

Современный шаблон `lifespan` объединяет настройку базы данных и внешних клиентов в единый защищенный контекст.

**Реализация Lifespan с SQLAlchemy и Redis:**

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI, Request
from sqlalchemy.ext.asyncio import create_async_engine
from redis.asyncio import Redis, ConnectionPool
import httpx

# Определение асинхронного контекстного менеджера
@asynccontextmanager
async def lifespan(app: FastAPI):
    # --- Startup: Инициализация ресурсов ---
    # Создание пула соединений для Redis [7.2 draft]
    redis_pool = ConnectionPool.from_url("redis://localhost:6379", decode_responses=True)
    app.state.redis = Redis(connection_pool=redis_pool)

    # Создание общего HTTP-клиента для внешних запросов
    app.state.http_client = httpx.AsyncClient()

    # Пример выполнения миграций или создания таблиц
    # await create_db_and_tables()

    yield # Здесь приложение начинает принимать запросы

    # --- Shutdown: Плавная остановка (Graceful Shutdown) ---
    await app.state.redis.close() # [7.2 draft]
    await app.state.http_client.aclose() #
    print("All connections closed safely") #

# Передача lifespan в экземпляр приложения
app = FastAPI(lifespan=lifespan)

@app.get("/status")
async def get_status(request: Request):
    # Доступ к ресурсам через состояние приложения [7.2 draft]
    redis = request.app.state.redis
    return {"redis_active": await redis.ping()}
```

#### Глоссарий терминов

- **[FastAPI Lifespan Context Manager](https://fastapi.tiangolo.com/advanced/events/)** — современный механизм управления жизненным циклом приложения через единый асинхронный контекст.
- **[`@asynccontextmanager` (PEP 533)](https://docs.python.org/3/library/contextlib.html#contextlib.asynccontextmanager)** — декоратор Python для создания функций, поддерживающих протокол `async with`, используемый для управления ресурсами.
- **`app.state` Storage** — объект внутри инстанса `FastAPI`, предназначенный для хранения и передачи произвольных данных и объектов между этапами жизненного цикла [7.2 draft].
- **Graceful Shutdown Pattern** — процесс завершения работы приложения, при котором оно перестает принимать новые запросы, дорабатывает текущие и корректно закрывает соединения.
- **`SIGTERM` / `SIGINT` Handling** — обработка системных сигналов операционной системы для инициации процесса плавного выключения сервера.
- **Resource Connection Leakage** — критическая ошибка, при которой соединения с БД или Redis не закрываются явно, что приводит к исчерпанию лимитов дескрипторов ОС.

#### Практический кейс: Безопасный цикл инициализации ресурсов

**Сценарий:** Микросервис должен при старте проверить доступность PostgreSQL и Redis. Если PostgreSQL не отвечает в течение 5 секунд, сервис должен упасть, не входя в состояние "Ready" в Kubernetes.

**Реализация:**

1. **Health Check при старте:** В блоке `lifespan` до `yield` выполняется `await session.execute(text("SELECT 1"))`. Если база данных не готова, выбрасывается исключение, и процесс Uvicorn завершается с ненулевым кодом.
2. **Изоляция клиентов:** Экземпляр `httpx.AsyncClient` создается один раз в `lifespan` и закрывается через `aclose()`. Это в разы эффективнее создания клиента на каждый запрос, так как сохраняет открытыми TCP-соединения (Connection Pooling).
3. **Предотвращение "зависаний":** Типовая ошибка 2026 года — забытый `await` при закрытии ресурсов в блоке shutdown. Использование `lifespan` гарантирует, что даже если один из этапов очистки упадет, остальные части блока (в рамках `finally`) могут быть выполнены для предотвращения блокировки процесса в памяти.

#### Вопросы и задания для самопроверки

1. **Вопрос:** В чем заключается фундаментальное преимущество `lifespan` перед старым методом `@app.on_event("startup")` при работе с исключениями?
    - _Ответ: В `lifespan` вы можете использовать стандартные конструкции `try...finally` вокруг `yield`. Это гарантирует, что код очистки сработает даже если инициализация части ресурсов завершилась ошибкой, в то время как `on_event` не имеет связи между этапами старта и остановки._
2. **Задача:** Организуйте корректную последовательность закрытия: сначала отключение приема новых HTTP-запросов, затем закрытие фонового клиента API, и в последнюю очередь — закрытие пула БД.
    - _Решение: Это реализуется естественным порядком кода после `yield`. ASGI-сервер сам перестает подавать запросы в приложение до возобновления контекста `lifespan`._
3. **Практическое задание:** Добавьте в блок `lifespan` до `yield` логику "Readiness Probe": выполните проверочный запрос к Redis через `ping()`. Если ответа нет более 2 секунд — вызовите `sys.exit(1)`, чтобы предотвратить запуск неисправного пода в кластере.
