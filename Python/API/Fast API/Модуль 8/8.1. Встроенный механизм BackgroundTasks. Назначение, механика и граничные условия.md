#### Теоретический фундамент и архитектура

В высоконагруженных асинхронных приложениях 2026 года одной из ключевых метрик является латентность (Latency) — время, за которое сервер формирует HTTP-ответ. Для оптимизации этого показателя операции, не требующие немедленного возврата результата клиенту (отправка email, генерация отчетов, запись аналитических логов), выносятся в фоновую обработку.

Класс `fastapi.BackgroundTasks` предоставляет встроенный инструмент для выполнения задач **после** отправки ответа клиенту. Механика работы основана на интеграции с движком Starlette: как только основной `Response` сформирован и передан ASGI-серверу, управление переходит к списку запланированных фоновых задач.

**Типы выполняемых функций:**

- **Асинхронные (`async def`)**: Выполняются непосредственно в основном Event Loop. Это эффективно для I/O-задач (запросы к сторонним API, работа с Redis), но требует осторожности, чтобы не перегрузить цикл событий.
- **Синхронные (`def`)**: FastAPI автоматически запускает их в отдельном тред-пуле (через `anyio.to_thread.run_sync`), что предотвращает блокировку Event Loop.

**Границы применимости:** `BackgroundTasks` являются процессом "внутри приложения" (In-process). Они идеально подходят для легковесных задач, но имеют критические ограничения:

1. **Отсутствие Persistence**: Если процесс приложения упадет или будет перезапущен, все запланированные, но не завершенные задачи будут безвозвратно утеряны.
2. **CPU-bound задачи**: Тяжелые вычисления (обработка видео, ML-модели) могут замедлить работу сервера даже в тред-пуле; для таких задач рекомендуются внешние воркеры (Celery/Taskiq).
3. **Управление ресурсами**: Главная проблема — жизненный цикл зависимостей. Если сессия БД инжектирована через `Depends` с `yield`, она будет закрыта (выполнится блок `finally`) сразу после формирования ответа, но **до** того, как фоновая задача начнет к ней обращаться.

#### Практическая реализация и синтаксис

Для работы с ресурсами в фоновых задачах необходимо самостоятельно управлять их жизненным циклом, используя фабрики сессий.

**Пример отправки отчета с собственным управлением сессией БД:**

```
from fastapi import FastAPI, BackgroundTasks, Depends, status
from typing import Annotated
from .database import async_session_maker  # Фабрика сессий (см. 5.1)
from .email import send_email_service

app = FastAPI()

async def send_report_task(user_email: str):
    # В фоновой задаче создаем НОВУЮ сессию, так как сессия из запроса уже закрыта
    async with async_session_maker() as session:
        # Логика сбора данных для отчета
        # ...
        await send_email_service(user_email, "Ваш отчет готов")

@app.post("/reports/generate", status_code=status.HTTP_202_ACCEPTED)
async def generate_report(
    email: str,
    background_tasks: BackgroundTasks # Инъекция класса задач
):
    # Добавляем задачу в очередь выполнения после ответа
    background_tasks.add_task(send_report_task, email)
    return {"message": "Report generation started"}
```

#### Глоссарий терминов

- **[`fastapi.BackgroundTasks`](https://fastapi.tiangolo.com/tutorial/background-tasks/)** — класс FastAPI для планирования функций, которые должны выполниться после возврата HTTP-ответа.
- **In-process Background Execution** — выполнение задач в рамках того же процесса ОС, в котором запущено веб-приложение.
- **Starlette Thread Pool Execution** — механизм запуска синхронных функций (`def`) в отдельных потоках для сохранения неблокирующего поведения Event Loop.
- **Transient Tasks vs Persistent Queues** — различие между временными задачами (в памяти) и устойчивыми очередями (в БД/Redis), гарантирующими доставку.
- **Context Leakage / Session Lifetime** — архитектурная проблема, при которой фоновая задача пытается использовать ресурсы (БД, сокеты), уже освобожденные основным запросом.

#### Практический кейс: Асинхронная выгрузка и анонимизация файлов

**Сценарий:** Реализация эндпоинта для выгрузки логов безопасности. Система должна мгновенно подтвердить получение запроса, а затем в фоне прочитать файл, удалить из него персональные данные (анонимизация) и сохранить результат на S3-хранилище.

**Алгоритм реализации:**

1. **Мгновенный ответ:** Эндпоинт возвращает статус **202 Accepted**. Это сообщает клиенту, что запрос принят, но обработка еще продолжается.
2. **Изоляция фоновой логики:** Функция анонимизации создается как `async def`, чтобы эффективно использовать `httpx.AsyncClient` для загрузки результата в облако.
3. **Обработка ошибок:** Так как `BackgroundTasks` не имеют доступа к HTTP-контексту, исключения внутри них не перехватываются глобальными `exception_handler`. Внутри фоновой задачи обязательно используется блок `try...except` с логированием в `structlog` или отправкой алерта в Sentry [139, 401, 7.3 draft].

#### Вопросы и задания для самопроверки

1. **Вопрос:** Что произойдет, если в `BackgroundTasks` добавить обычную функцию `def`, внутри которой вызывается `time.sleep(10)`?
    - _Ответ: FastAPI запустит ее в отдельном потоке (Thread Pool), поэтому основной Event Loop не заблокируется и сможет обрабатывать другие запросы._
2. **Задача:** Исправьте ошибку: фоновая задача падает с `ClosedResourceError` при попытке использовать `db: Session = Depends(get_db)`.
    - _Решение: Убрать `Depends` из аргументов фоновой функции; вместо этого передавать в нее фабрику сессий или создавать новую сессию через асинхронный контекстный менеджер внутри тела функции._
3. **Практическое задание:** Напишите декоратор-обертку `background_worker`, который оборачивает любую фоновую задачу в блок `try...except`, записывает время начала/конца выполнения и в случае ошибки отправляет stack trace в логгер.
