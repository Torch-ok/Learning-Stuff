#### Теоретический фундамент и архитектура

В высоконагруженных асинхронных приложениях 2026 года качественная обработка ошибок — это не просто вызов `HTTPException`, а выстраивание многоуровневой системы трансляции внутренних состояний системы во внешние понятные ответы.

**Иерархия исключений: FastAPI vs Starlette** FastAPI предоставляет собственный класс `HTTPException`, который является расширенной версией `starlette.exceptions.HTTPException`. Главное различие заключается в параметре `detail`: версия FastAPI позволяет передавать любой объект, который может быть сериализован в JSON (словари, списки), тогда как Starlette ограничивает разработчика только строками. Однако при регистрации глобальных обработчиков через `@app.exception_handler` настоятельно рекомендуется перехватывать именно `StarletteHTTPException`, чтобы охватить ошибки, возникающие во внутренних компонентах или сторонних плагинах.

**Архитектурная изоляция (Separation of Concerns)** Одной из распространенных проблем является «размазывание» HTTP-статусов по слоям бизнес-логики и репозиториев. Если функция в `service` слое выбрасывает `HTTPException(status_code=404)`, она нарушает принцип изоляции: бизнес-логика начинает «знать» о протоколе передачи данных. Правильный подход заключается в проектировании **Domain-Specific Exceptions** (например, `InsufficientFundsError`), которые не содержат HTTP-кодов, а лишь описывают суть сбоя внутри предметной области.

**Централизованная обработка и переопределение** С помощью декоратора `@app.exception_handler()` приложение может перехватывать как кастомные ошибки, так и стандартные исключения FastAPI. Это позволяет:

1. **Транслировать доменные ошибки**: превращать `EntityNotFoundError` в структурированный 404 ответ.
2. **Кастомизировать `RequestValidationError`**: изменять формат ошибок Pydantic v2 (статус 422) на более дружелюбный или скрывать технические детали во избежание утечек информации о системе.
3. **Маскировать системные сбои**: перехватывать любые необработанные `Exception`, логировать их и возвращать клиенту стандартизированный ответ 500 Internal Server Error без стек-трейса.

#### Практическая реализация и синтаксис

Для реализации чистого кода мы сначала определяем базовый класс исключения предметной области, а затем создаем обработчик, который формирует ответ в формате JSON.

**Создание кастомных исключений:**

```python
# app/exceptions.py
class DomainException(Exception):
    """Базовый класс для всех ошибок бизнес-логики."""
    def __init__(self, message: str, code: str = "domain_error"):
        self.message = message
        self.code = code

class InsufficientFundsError(DomainException):
    """Исключение при нехватке средств на кошельке."""
    pass
```

[Handling Errors](https://fastapi.tiangolo.com/tutorial/handling-errors/), [Python API Tutorial](https://www.youtube.com/watch?v=PythonFastAPICorey)

**Реализация глобального Exception Handler:**

```python
from fastapi import FastAPI, Request, status
from fastapi.responses import JSONResponse
from fastapi.exceptions import RequestValidationError
from starlette.exceptions import HTTPException as StarletteHTTPException

app = FastAPI()

@app.exception_handler(InsufficientFundsError)
async def insufficient_funds_handler(request: Request, exc: InsufficientFundsError):
    # Трансляция бизнес-ошибки в 400 Bad Request
    return JSONResponse(
        status_code=status.HTTP_400_BAD_REQUEST,
        content={
            "error_code": exc.code,
            "message": exc.message,
            "path": request.url.path
        }
    )

@app.exception_handler(RequestValidationError)
async def validation_exception_handler(request: Request, exc: RequestValidationError):
    # Переопределение формата 422 ошибки
    return JSONResponse(
        status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
        content={"detail": "Invalid input data", "errors": exc.errors()}
    )
```

#### Глоссарий терминов

- **[`fastapi.HTTPException` vs `starlette.HTTPException`](https://fastapi.tiangolo.com/tutorial/handling-errors/#fastapis-httpexception-vs-starlettes-httpexception)** — FastAPI расширяет класс Starlette, позволяя передавать в `detail` любые данные для JSON-ответа.
- **[Custom Domain Exceptions](https://www.youtube.com/watch?v=PythonFastAPICorey)** — классы исключений, специфичные для бизнес-логики приложения, не привязанные к HTTP.
- **[Centralized `@app.exception_handler`](https://fastapi.tiangolo.com/tutorial/handling-errors/#install-custom-exception-handlers)** — механизм FastAPI для перехвата определенных типов исключений и возврата кастомных `Response`.
- **[`RequestValidationError` Customization](https://fastapi.tiangolo.com/tutorial/handling-errors/#override-request-validation-exceptions)** — процесс изменения стандартного ответа 422, который выбрасывает Pydantic при несоответствии входящих данных схеме.
- **RFC 7807 (Problem Details)** — стандарт формирования структурированных ответов об ошибках в HTTP API (реализуется через `JSONResponse`).
- **Error Handling Hierarchy** — порядок обработки исключений, где более специфичные обработчики имеют приоритет над общими базовыми классами.

#### Практический кейс: Стандартизация ответов ошибок для банковского API

**Сценарий**: В сервисе банковских транзакций при попытке списания сумма превышает текущий баланс кошелька.

1. **Вызов в сервисе**: Слой сервиса обнаруживает нехватку средств и вызывает `raise InsufficientFundsError("Insufficient funds on card", code="balance_too_low")`.
2. **Трансляция**: Глобальный обработчик перехватывает это исключение. Вместо того чтобы выдать 500 ошибку или стандартный `HTTPException`, он формирует ответ с кодом 400 и бизнес-метаданными.
3. **Безопасность**: Для всех остальных непредвиденных исключений (например, разрыв соединения с БД) настроен обработчик `Exception`, который пишет полный лог ошибки во внутреннюю систему логирования (например, Winston/Morgan аналоги), но клиенту возвращает только `{"error": "Internal server error"}` без деталей реализации.

#### Вопросы и задания для самопроверки

1. **Вопрос**: Почему использование `fastapi.HTTPException` внутри функций репозитория или сервиса считается нарушением архитектурной чистоты?
    - _Ответ: Репозитории и сервисы отвечают за данные и логику, они должны быть переиспользуемыми. Привязка к HTTP-статусам делает их зависимыми от веб-фреймворка, что усложняет тестирование и миграцию на другие интерфейсы (например, gRPC или CLI)._
2. **Задача**: Напишите обработчик для `RequestValidationError`, который вместо списка всех ошибок Pydantic возвращает только сообщение о первом найденном нарушении.
3. **Практическое задание**: Создайте базовый класс `AppException` и два наследника. Настройте один `@app.exception_handler(AppException)`, который будет автоматически логировать `stack trace` ошибки перед отправкой ответа клиенту.
