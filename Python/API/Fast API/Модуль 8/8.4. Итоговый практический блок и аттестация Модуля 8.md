#### Сквозной практический кейс: Распределенная обработка медиа и WebSocket-оповещение

**Постановка задачи:** Спроектировать сервис обработки видео (кодирование), который минимизирует время ожидания пользователя. Система должна принимать файл, возвращать `task_id`, выполнять тяжелую работу в фоне на отдельном воркере и транслировать прогресс (0-100%) в реальном времени через WebSocket [8.4 prompt].

**Пошаговый алгоритм выполнения:**

1. **Приемка и инициализация (FastAPI REST):** Создайте эндпоинт `POST /video/process`, принимающий `UploadFile`. Вместо обработки файла в теле запроса, FastAPI сохраняет его во временное хранилище и отправляет задачу в **Taskiq** или **Celery** [8.1 draft, 8.2 draft]. Клиент немедленно получает `202 Accepted` и уникальный `task_id`.
    
2. **Фоновое выполнение (Worker):** Воркер извлекает задачу и начинает кодирование видео. На каждом этапе (например, каждые 10%) воркер вызывает метод `publish` в **Redis Pub/Sub**, отправляя JSON со статусом в канал, имя которого соответствует `task_id` [8.3 draft].
    
3. **Real-time трансляция (FastAPI WebSocket):** Клиент открывает соединение `WS /ws/video/{task_id}`. Эндпоинт использует `ConnectionManager` для регистрации клиента [8.3 draft]. Внутри обработчика запускается асинхронный цикл, который подписывается на соответствующий канал в Redis. Как только в канале появляется обновление от воркера, сервер вызывает `websocket.send_json(update)`.
    
4. **Graceful Degradation:** В случае падения воркера статус задачи проверяется в **Result Backend** (Redis) [8.2 draft]. Если WebSocket-соединение обрывается, эндпоинт ловит `WebSocketDisconnect` и отписывается от канала Redis, предотвращая утечки памяти [8.3 draft].
    
5. **Автоматизированное тестирование:** Используйте `httpx.AsyncClient` для проверки REST-части и библиотеку `websockets` для эмуляции поведения фронтенда в асинхронных тестах [602, 603, 7.4 draft].
    

#### Комплексный контрольный тест для самопроверки

1. **Вопрос:** В каком из перечисленных сценариев использование встроенных `BackgroundTasks` вместо Celery является критической ошибкой проектирования?
    
    - _Ответ: В сценариях, требующих Persistence (сохранения задачи при перезагрузке сервера) или при выполнении CPU-bound задач, которые могут заблокировать воркеры основного приложения [8.1 draft, 8.2 draft]._
2. **Задача на Event Loop:** Исправьте код, вызывающий "заикание" (latency) WebSocket-сервера:
    
    ```
    @app.websocket("/ws")
    async def ws_handler(websocket: WebSocket):
        await websocket.accept()
        while True:
            data = await websocket.receive_text()
            # ОШИБКА: блокирующий вызов
            with open(f"{data}.log", "r") as f:
                content = f.read()
            await websocket.send_text(content)
    ```
    
    _Решение: Использовать `anyio.to_thread.run_sync` для чтения файла или асинхронные библиотеки (например, `aiofiles`), чтобы не блокировать цикл событий для других подключенных пользователей [8.1 draft, 8.3 draft]._
    
3. **Практическое задание:** Реализуйте в `ConnectionManager` метод `ping_all()`, который раз в 30 секунд отправляет пустое сообщение всем клиентам. Если `send` завершается ошибкой — удаляйте сокет из списка активных [8.3 draft].
    
4. **Задача на отказоустойчивость:** Настройте декоратор задачи в Celery так, чтобы при возникновении `DatabaseError` задача отправлялась в **Dead Letter Queue (DLQ)** после 3 безуспешных попыток перезапуска с экспоненциальной задержкой [8.2 draft].
    
5. **Вопрос на архитектурное сравнение:** В чем заключается фундаментальное различие распределения нагрузки между Celery и Taskiq?
    
    - _Ответ: Celery использует протокол AMQP (или Redis как имитацию), где брокер активно управляет очередями и подтверждениями (Ack). Taskiq ориентирован на нативную асинхронность и упрощенную интеграцию с DI FastAPI, часто используя Redis списки как транспорт [8.2 draft]._
