#### Сквозной практический кейс: Комплексный модуль устойчивости (Resilience), безопасности и логирования

**Постановка задачи:** Спроектировать архитектурный контур приложения, который гарантирует корректную инициализацию ресурсов, безопасность передачи данных между доменами и стандартизированную обработку всех типов исключений [285, 310, 651, 8.4 prompt].

**Пошаговый алгоритм выполнения:**

1. **Настройка Lifespan и `app.state`:** Используйте `@asynccontextmanager` для инициализации асинхронного движка SQLAlchemy и клиента Redis. Сохраните инстансы в `app.state.db` и `app.state.redis`, чтобы они были доступны через объект `Request` в Middleware и роутерах [323, 8.3 draft].
    
2. **Реализация логирующего Middleware:** Создайте класс на базе `BaseHTTPMiddleware`. В методе `dispatch` генерируйте UUID для `X-Request-ID`, замеряйте время начала запроса через `time.perf_counter()` и добавляйте идентификатор в заголовки ответа `response.headers` [63, 570, 8.2 draft].
    
3. **Стандартизация ошибок (RFC 7807):** Опишите базовое исключение `AppBusinessError`. Реализуйте `@app.exception_handler(AppBusinessError)`, который возвращает `JSONResponse` со статусом 400 и полями `type`, `title`, `status`, `detail` и `instance` (путь запроса) согласно RFC 7807.
    
4. **Безопасный роут и Graceful Shutdown:** Напишите эндпоинт, имитирующий бизнес-операцию (например, перевод средств). Если баланс недостаточен, выбрасывайте `InsufficientFundsError`. Убедитесь, что при получении `SIGTERM` Lifespan-контекст корректно закрывает все соединения с БД и Redis в блоке `finally` [651, 8.3 draft].
    
5. **Логирование и Маскирование:** В Middleware логируйте метод, путь и статус-код. В глобальном обработчике `Exception` (для ошибок 500) записывайте полный стек ошибки в `error.log`, но клиенту отдавайте только общее сообщение "Internal Server Error" без технических деталей [63, 73, 8.1 draft].
    

#### Комплексный контрольный тест для самопроверки

1. **Вопрос:** Почему `CORSMiddleware` должен регистрироваться первым (или быть самым внешним) в стеке?
    
    - _Ответ: Браузеры отправляют Preflight-запросы (OPTIONS) до основного запроса. Если Middleware авторизации сработает раньше CORS и вернет 401, браузер заблокирует запрос из-за отсутствия CORS-заголовков в ответе об ошибке [571, 8.2 draft]._
2. **Задача на маскирование:** При падении базы данных PostgreSQL клиент получает JSON со строкой подключения `postgresql+asyncpg://user:pass@host/db`. Как это исправить через `exception_handler`?
    
    - _Решение: Нужно перехватить базовый `Exception` или специфичный для БД класс, залогировать `exc` внутри сервера, а в `JSONResponse` передать только безопасный текст `detail="Database connection error"` [73, 447, 8.1 draft]._
3. **Практическое задание:** Реализуйте "Circuit Breaker" Middleware. Оно должно проверять `request.app.state.db_health`. Если флаг не готов — мгновенно возвращать `503 Service Unavailable`, не допуская запрос к роутеру [531, 8.3 draft].
    
4. **Задача на отладку:** Исключение, возникшее внутри Middleware _после_ вызова `await call_next(request)`, не перехватывается вашим обработчиком `@app.exception_handler(Exception)`. Почему?
    
    - _Решение: Обработчики исключений FastAPI работают на уровне маршрутизации. Ошибки внутри Middleware должны обрабатываться блоком `try...except` непосредственно в теле Middleware [77, 8.2 draft]._
5. **Вопрос на архитектуру:** В чем преимущество регистрации HTTP-клиента `httpx.AsyncClient` в `app.state` через Lifespan по сравнению с созданием нового клиента внутри каждой функции `Depends`?
    
    - _Ответ: Это позволяет использовать Connection Pooling (переиспользование TCP-соединений), что значительно снижает задержки и нагрузку на CPU при частых внешних вызовах [407, 8.3 draft]._
