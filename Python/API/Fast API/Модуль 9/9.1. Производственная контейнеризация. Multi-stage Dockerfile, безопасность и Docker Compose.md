#### Теоретический фундамент и архитектура

Контейнеризация Python-приложений в 2026 году является стандартом для обеспечения изоляции и воспроизводимости среды выполнения. Основная цель — упаковать код и все его зависимости (библиотеки, системные рантаймы) в единый «магический ланчбокс», который будет работать идентично на локальной машине разработчика, в CI/CD и на продакшн-серверах.

**Оптимизация сборки через Multi-stage Build:** Для минимизации размера образа и сокращения вектора атак (Attack Surface) применяется техника многоэтапной сборки. Процесс разделяется на стадии:

1. **Builder**: установка компиляторов и инструментов сборки (например, `uv` или `gcc`), необходимых для сборки зависимостей.
2. **Runner**: финальный образ (обычно на базе `slim` или `alpine`), куда копируются только готовые артефакты и скомпилированные пакеты. Это позволяет исключить из продакшн-образа исходный код инструментов сборки и временные файлы.

**Эффективное использование кэша слоев:** Docker рассматривает каждую инструкцию в `Dockerfile` как отдельный слой. Для ускорения повторных сборок критически важно соблюдать порядок: сначала копировать файлы зависимостей (`requirements.txt`, `pyproject.toml`, `uv.lock`) и выполнять их установку, а только затем копировать исходный код приложения. В этом случае при изменении кода Docker не будет переустанавливать все библиотеки заново, используя закэшированный результат предыдущего шага.

**Стандарты безопасности:** Запуск приложения от имени `root` пользователя запрещен, так как любая уязвимость в коде может дать злоумышленнику полный доступ к хост-системе. Рекомендуется создавать системного пользователя с ограниченными правами доступа только к директории `/app`. Также необходимо использовать системные механизмы очистки временных пакетов и игнорировать ненужные файлы через `.dockerignore`.

**Оркестрация через Docker Compose:** `Docker Compose` позволяет описывать многоконтейнерные приложения в одном YAML-файле, управляя сервисами (API, БД, Redis), сетями для их взаимодействия и томами (Volumes) для сохранения данных при перезагрузке контейнеров.

#### Практическая реализация и синтаксис

**Оптимизированный production-ready `Dockerfile` (с использованием `uv`):**

```
# Stage 1: Builder
FROM python:3.12-slim as builder

# Установка uv для молниеносной сборки зависимостей
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/

WORKDIR /app
# Сначала копируем только файлы зависимостей для кэширования слоев
COPY pyproject.toml uv.lock ./
# Сборка зависимостей в отдельную директорию
RUN uv sync --frozen --no-dev --no-install-project

# Stage 2: Runner
FROM python:3.12-slim as runner

# Создание непривилегированного пользователя для безопасности
RUN groupadd -r app && useradd -r -g app app

WORKDIR /app

# Копируем установленные зависимости из Builder
COPY --from=builder /app/.venv /app/.venv
# Копируем код приложения
COPY ./app /app/app

# Настройка окружения
ENV PATH="/app/.venv/bin:$PATH"
# Смена владельца файлов
RUN chown -r app:app /app
# Переключение на non-root пользователя
USER app

EXPOSE 8000

# Запуск через Granian/Uvicorn с обработкой сигналов завершения
CMD ["granian", "--interface", "asgi", "--host", "0.0.0.0", "app.main:app"]
```

**Комплексный `docker-compose.yml` (Nginx + FastAPI + Postgres + Redis):**

```
version: '3.8'

services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: fast_api_prod
    healthcheck: # Проверка готовности БД
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER} -d fast_api_prod"]
      interval: 5s
      timeout: 5s
      retries: 5
    volumes:
      - postgres_data:/var/lib/postgresql/data
    networks:
      - backend

  redis:
    image: redis:7-alpine
    networks:
      - backend

  api:
    build: .
    env_file: .env
    depends_on:
      db:
        condition: service_healthy # Ждем полной готовности Postgres
    networks:
      - backend

  nginx:
    image: nginx:stable-alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on:
      - api
    networks:
      - backend

volumes:
  postgres_data:

networks:
  backend:
```

#### Глоссарий терминов

- **Multi-stage Build** — технология Docker, позволяющая использовать несколько инструкций `FROM` в одном Dockerfile для разделения процесса сборки и финального рантайма.
- **Docker Layer Caching** — механизм повторного использования слоев образа, если инструкции и копируемые файлы не изменились, что критически ускоряет сборку.
- **Non-root Container Security** — практика запуска процессов в контейнере от имени пользователя без прав администратора для минимизации рисков взлома хоста.
- **`docker-compose` Specification** — стандарт описания многоконтейнерных приложений, определяющий зависимости, конфигурации и ресурсы сервисов.
- **Container Healthcheck** — встроенная в Docker команда для мониторинга «здоровья» и готовности сервиса к обработке трафика.

#### Практический кейс: Сборка и минимизация production-образа

**Сценарий:** Изначальный образ FastAPI сервиса, собранный «в лоб» на базе `python:3.12-full`, весил 1.2 ГБ и запускался от `root`.

**Решение:**

1. **Смена базы:** Переход на `python:3.12-slim` сократил размер на 600 МБ.
2. **Multi-stage**: Вынос установки `psycopg2` и компиляции зависимостей в стадию `builder` позволил удалить системные пакеты `gcc` и `musl-dev` из финального образа.
3. **Слои:** Инструкции `COPY requirements.txt` и `RUN pip install` были вынесены перед копированием кода, что сократило время пересборки при изменении бизнес-логики с 3 минут до 5 секунд.
4. **Безопасность:** Добавление `USER app` и удаление кэша `pip` (`--no-cache-dir`) позволило пройти аудит безопасности без замечаний. **Результат:** Итоговый образ весит 142 МБ, собирается мгновенно и защищен от атак повышения привилегий.

#### Вопросы и задания для самопроверки

1. **Вопрос:** Почему команда `COPY . .` должна находиться как можно ниже в `Dockerfile`?
    - _Ответ: Так как код приложения меняется чаще всего, помещение этой команды в начало приведет к инвалидации кэша для всех последующих слоев (включая установку библиотек) при каждом коммите._
2. **Задача:** Найдите ошибку безопасности в инструкции: `RUN apt-get install -y vim git curl`.
    - _Ответ: В продакшн-образе не должно быть инструментов отладки и Git, так как они упрощают действия злоумышленника при захвате контейнера. Также отсутствуют команды очистки кэша пакетов._
3. **Практическое задание:** Напишите `healthcheck` для Docker Compose, который проверяет работоспособность FastAPI приложения, обращаясь к эндпоинту `/healthz` внутри контейнера.
    - _Подсказка: Используйте `curl -f http://localhost:8000/healthz || exit 1`._
