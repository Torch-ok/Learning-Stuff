#### Теоретический фундамент и архитектура

История веб-разработки на Python неразрывно связана с развитием протоколов взаимодействия между веб-сервером и приложением. Классический стандарт WSGI (PEP 3333) долгие годы был основой индустрии, реализуя синхронную модель «один запрос — один поток». В этой архитектуре поток сервера блокируется до тех пор, пока приложение не завершит обработку запроса, что создает серьезные ограничения при высокой нагрузке (проблема C10K). WSGI не имеет встроенной поддержки современных протоколов реального времени, таких как `WebSockets` или Server-Sent Events (SSE), так как они требуют длительного неблокирующего удержания соединения.

Переход к асинхронности ознаменовался появлением спецификации ASGI (PEP 3090), которая является духовным наследником WSGI, но спроектирована для работы в асинхронной среде `asyncio`. Протокол ASGI позволяет обрабатывать тысячи конкурентных запросов в рамках одного процесса (Event Loop), эффективно переключаясь между задачами в моменты ожидания I/O-операций. Структура взаимодействия в ASGI строится на трех ключевых компонентах: `scope` (словарь с метаданными соединения), `receive` (асинхронный метод для получения данных от клиента) и `send` (асинхронный метод для отправки данных клиенту).

**Сравнительный анализ веб-фреймворков:**

- **Синхронное поколение (Django, Flask):** Эти фреймворки по своей природе являются синхронными и часто используют блокирующий ввод-вывод. Для масштабирования им требуется запуск большого количества тяжелых рабочих процессов (workers) через Gunicorn, что увеличивает потребление оперативной памяти и накладные расходы на переключение контекста между потоками ОС. Несмотря на добавление элементов асинхронности в последних версиях, их ядро остается верным старым стандартам.
- **Асинхронное поколение (FastAPI, Litestar):** FastAPI построен на базе `Starlette` и использует всю мощь ASGI для достижения производительности, сравнимой с решениями на Node.js или Go. Основное отличие заключается в нативной поддержке `async`/`await`, интеграции с Pydantic v2 (написанном на Rust) для мгновенной валидации данных и автоматической генерации документации `OpenAPI`. Это обеспечивает не только скорость исполнения, но и исключительный Developer Experience (DX) за счет типизации и подсказок в IDE.

#### Практическая реализация и синтаксис

Для понимания разницы рассмотрим минимальные реализации приложений на низком уровне.

**Пример низкоуровневого ASGI-приложения:** Это база, на которой работают современные серверы вроде `Uvicorn` или `Granian`.

```
async def app(scope, receive, send):
    # Проверка типа события в scope
    if scope['type'] == 'http':
        # Отправка заголовков ответа
        await send({
            'type': 'http.response.start',
            'status': 200,
            'headers': [
                [b'content-type', b'application/json'],
            ],
        })
        # Отправка тела ответа
        await send({
            'type': 'http.response.body',
            'body': b'{"message": "Hello from pure ASGI"}',
        })
```

**Пример низкоуровневого WSGI-приложения:** Обратите внимание на отсутствие `async` и использование итерируемого объекта для возврата данных.

```
def app(environ, start_response):
    status = '200 OK'
    headers = [('Content-type', 'application/json')]
    start_response(status, headers)
    return [b'{"message": "Hello from WSGI"}']
```

#### Глоссарий терминов

- **WSGI (PEP 3333)** — Web Server Gateway Interface, синхронный стандарт взаимодействия между Python-приложением и веб-сервером.
- **ASGI (PEP 3090)** — Asynchronous Server Gateway Interface, асинхронный стандарт, поддерживающий HTTP, WebSockets и другие протоколы.
- **Scope** — словарь в ASGI, содержащий информацию о текущем соединении: метод, путь, заголовки, параметры.
- **Receive / Send callables** — асинхронные вызываемые объекты для получения сообщений от сервера и отправки ответов клиенту.
- **Event Loop Overheads** — накладные расходы на работу событийного цикла, которые могут проявляться при выполнении тяжелых вычислительных задач внутри асинхронных функций.

#### Практический кейс: Анализ пропускной способности WSGI vs ASGI

**Сценарий:** Сравнение Gunicorn + Flask против Uvicorn + FastAPI при задержке I/O в 1 секунду (имитация долгого запроса к БД или внешнему API).

**Бенчмаркинг (команды CLI):** Для тестирования используем `autocannon` для генерации нагрузки (100 конкурентных соединений в течение 10 секунд).

```
# Запуск FastAPI приложения (ASGI)
uv run fastapi run main.py --port 8000

# Тестирование пропускной способности
autocannon -c 100 -d 10 http://127.0.0.1:8000/io-heavy
```

[Learn Fast API With This ONE Project / YouTube](https://www.youtube.com/watch?v=LearnFastAPI)

**Анализ результатов:**

1. **WSGI (Gunicorn + Flask):** Если запущено 4 воркера, сервер сможет обработать только 4 запроса одновременно. Остальные 96 запросов будут стоять в очереди, так как потоки заблокированы ожиданием в 1 секунду.
2. **ASGI (Uvicorn + FastAPI):** Благодаря `Event Loop` и ключевому слову `await`, сервер отпускает выполнение запроса во время ожидания I/O и берет в работу следующий. В итоге за 10 секунд ASGI-сервер обработает тысячи запросов, в то время как WSGI — всего несколько десятков.

    
    _Подсказка: ищите ответ в разнице между `time.sleep()` и `asyncio.sleep()`._
