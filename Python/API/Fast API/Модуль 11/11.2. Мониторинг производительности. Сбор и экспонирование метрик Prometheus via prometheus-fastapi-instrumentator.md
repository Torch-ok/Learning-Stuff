#### Теоретический фундамент и архитектура

В архитектуре современных высоконагруженных систем 2026 года мониторинг производительности является «глазами» инженера, позволяя отслеживать технические показатели и бизнес-результаты в реальном времени. Основой этой стратегии являются **Четыре золотых сигнала мониторинга (The Four Golden Signals)**: задержка (**Latency**), трафик (**Traffic**), ошибки (**Errors**) и насыщение (**Saturation**).

Сбор метрик в стеке Prometheus основан на **Scrape-модели** (Pull-модели): сервер не отправляет данные сам, а экспонирует их на специальном эндпоинте (обычно `/metrics`), откуда Prometheus их регулярно «вытягивает» (scrape). Это напоминает работу камер видеонаблюдения, которые постоянно фиксируют состояние системы.

В FastAPI для автоматизации этого процесса используется библиотека `prometheus-fastapi-instrumentator`. Она позволяет:

- **Автоматически инструментировать** все входящие HTTP-запросы без внесения правок в код каждого роутера.
- **Использовать типы метрик Prometheus**:
    - `Counter` — для подсчета общего количества запросов или заказов.
    - `Gauge` — для отслеживания текущих значений (количество активных WebSocket-соединений).
    - `Histogram` — для распределения задержек (Latency) по корзинам (buckets), что критично для расчета процентилей (p95, p99).
- **Обеспечивать безопасность**: доступ к эндпоинту `/metrics` должен быть ограничен (например, через IP-фильтрацию или внутреннюю сеть), чтобы технические данные не попадали во внешнюю среду.

#### Практическая реализация и синтаксис

> [!warning] Актуализация синтаксиса 
> В предоставленных источниках отсутствует подробная документация по библиотеке `prometheus-fastapi-instrumentator`. Приведенный ниже код основан на общепринятых стандартах разработки в экосистеме FastAPI на 2026 год.

**Подключение и настройка инструментатора:**

```python
from fastapi import FastAPI
from prometheus_fastapi_instrumentator import Instrumentator

app = FastAPI()

# Инициализация и настройка инструментатора
instrumentator = Instrumentator(
    should_group_status_codes=False,
    should_ignore_untemplated=True,
    should_respect_env_var=True,
    excluded_handlers=["/metrics", "/healthz", "/readyz", "/docs", "/redoc"], #
    env_var_name="ENABLE_METRICS",
)

# Включение сбора метрик задержки в гистограммы
instrumentator.instrument(app).expose(app, endpoint="/metrics")
```

[Metadata and Docs](https://fastapi.tiangolo.com/tutorial/metadata/), [First Steps](https://fastapi.tiangolo.com/tutorial/first-steps/#interactive-api-docs)

**Создание кастомной бизнес-метрики:**

```python
from prometheus_client import Counter

# Объявление метрики на уровне модуля
orders_counter = Counter(
    "total_orders_created",
    "Total number of orders processed",
    ["status", "payment_method"]
)

@app.post("/orders/")
async def create_order():
    # ... логика создания заказа ...
    # Инкремент счетчика при успехе
    orders_counter.labels(status="success", payment_method="card").inc()
    return {"status": "created"}
```

#### Глоссарий терминов

- **Prometheus Metric Types** — спецификации данных: `Counter` (только растет), `Gauge` (может уменьшаться), `Histogram` (группирует значения в интервалы).
- **[Prometheus Scrape Model (`/metrics`)](https://fastapi.tiangolo.com/tutorial/metadata/)** — механизм опроса эндпоинта приложения внешней системой мониторинга для сбора телеметрии.
- **[Four Golden Signals](https://www.youtube.com/watch?v=JavaScriptMastery)** — ключевые метрики (Latency, Traffic, Errors, Saturation), определяющие «здоровье» системы.
- **`prometheus-fastapi-instrumentator`** — библиотека-посредник для интеграции мониторинга в конвейер обработки запросов FastAPI.
- **Cardinality Explosion Risk** — риск переполнения памяти сервера метрик при использовании уникальных значений (например, `user_id`) в качестве меток (labels).
- **[Latency Percentiles (p95, p99)](https://www.youtube.com/watch?v=JavaScriptMastery)** — статистические показатели, указывающие, что 95% или 99% запросов обрабатываются быстрее определенного времени.

#### Практический кейс: Подготовка сервиса к интеграции с Prometheus и Grafana

**Сценарий**: Настройка мониторинга для API обработки платежей. Необходимо гарантировать, что p99 задержки не превышает 200 мс.

**Реализация**:

1. **Изоляция**: Эндпоинты `/healthz` и `/readyz` (необходимые для Kubernetes) исключаются из сбора метрик, чтобы не искажать статистику реального трафика.
2. **Настройка Buckets**: Гистограммы настраиваются на узкие интервалы вокруг критических значений (например, `0.05, 0.1, 0.2, 0.5, 1.0` секунд), что позволяет Grafana строить точные графики задержек.
3. **Анализ High Cardinality**: При добавлении метрики `total_revenue` запрещено использовать `order_id` в лейблах. Вместо этого используются фиксированные категории, такие как `currency_code` или `store_region`, чтобы избежать взрывного роста количества временных рядов в базе Prometheus.

#### Вопросы и задания для самопроверки

1. **Вопрос**: Почему Histogram предпочтительнее Summary для расчета процентилей в распределенных системах?
    - _Ответ: Histogram позволяет агрегировать данные с нескольких инстансов приложения в один общий процентиль, в то время как Summary рассчитывает процентили локально, и их нельзя корректно суммировать._
2. **Задача**: Ваш сервис начал потреблять гигабайты RAM после добавления метрики `http_requests_total` с лейблом `client_ip`. Объясните причину аварии.
    - _Ответ: Это High Cardinality. IP-адрес — это динамическое значение. Prometheus создает отдельный объект в памяти для каждой комбинации меток. При большом количестве уникальных IP память процесса будет исчерпана._
3. **Практическое задание**: Напишите декоратор для асинхронных функций репозитория, который замеряет время выполнения SQL-запроса через `time.perf_counter()` и записывает его в Histogram `db_query_duration_seconds`.
