#### Теоретический фундамент и архитектура

В высоконагруженных микросервисных системах 2026 года концепция **Observability** (наблюдаемости) заменяет классическое "чтение логов". Структурированное логирование превращает текстовые сообщения в машиночитаемые потоки событий, что критически важно для анализа поведения пользователей и отладки ошибок в реальном времени.

**Принципы 12-Factor App (Logs):** Согласно методологии **12-Factor App**, приложение не должно заботиться об управлении файлами логов. Вместо записи на диск (что нарушает принципы контейнеризации), логи выводятся как поток событий в `stdout` и `stderr`. Это позволяет внешним агентам (Vector, Fluentbit) агрегировать их в централизованные системы, такие как **ELK Stack**, **Loki** или **Data Dog**.

**Сравнение инструментов:**

- **`structlog`** — промышленный стандарт для асинхронного Python. Он предоставляет конвейер процессоров (**Processors Pipeline**), позволяя гибко изменять структуру лога (добавлять таймстампы, уровни и метаданные) до его финального рендеринга в JSON.
- **`loguru`** — популярная альтернатива, ориентированная на удобство (DX), обеспечивающая быструю настройку вывода без сложной конфигурации.

**Механика Correlation-ID и трассировки:** Для связывания логов в рамках одного HTTP-запроса используется **Correlation-ID** (обычно заголовок `X-Request-ID`) [63, 8.2 draft]. С помощью контекстных переменных (**`contextvars`**) этот идентификатор автоматически пробрасывается во все вызовы логгера внутри корутин, не требуя ручной передачи параметров в каждую функцию [8.4 draft].

**Очистка логов (PII Redaction):** Безопасность требует исключения персональных данных (PII) из логов. В 2026 году для этого используются типы `SecretStr` из Pydantic v2, которые автоматически маскируют значения (пароли, токены) при попытке их вывода или сериализации.

#### Практическая реализация и синтаксис

**Настройка `structlog` с JSON-рендерером:**

```python
import structlog
from pydantic import SecretStr

# Конфигурация процессоров (Pipeline)
structlog.configure(
    processors=[
        structlog.processors.TimeStamper(fmt="iso"), # ISO 8601 формат
        structlog.processors.add_log_level,
        structlog.processors.JSONRenderer() # Вывод в JSON
    ],
    logger_factory=structlog.PrintLoggerFactory(),
)

logger = structlog.get_logger()
```

**Middleware для проброса Correlation-ID:**

```python
import uuid
from fastapi import Request
from starlette.middleware.base import BaseHTTPMiddleware
from contextvars import ContextVar

# Переменная контекста для ID запроса
request_id_ctx: ContextVar[str] = ContextVar("request_id", default=None)

class StructuredLoggingMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        # Перехват или генерация ID
        request_id = request.headers.get("X-Request-ID", str(uuid.uuid4()))
        token = request_id_ctx.set(request_id)

        # Обогащение контекста логгера
        structlog.contextvars.clear_contextvars()
        structlog.contextvars.bind_contextvars(request_id=request_id)

        response = await call_next(request)
        response.headers["X-Request-ID"] = request_id
        request_id_ctx.reset(token)
        return response
```

[Middleware Tutorial](https://fastapi.tiangolo.com/tutorial/middleware/), [8.2 draft]

#### Глоссарий терминов

- **[Structured Logging & JSON Format](https://fastapi.tiangolo.com/tutorial/encoder/)** — подход к записи логов в виде структурированных данных (ключ-значение), обеспечивающий легкий парсинг поисковыми движками.
- **[12-Factor App: Logs Principle](https://fastapi.tiangolo.com/deployment/concepts/)** — методология, предписывающая рассматривать логи как непрерывный поток событий в стандартный вывод.
- **`structlog` Processors Pipeline** — цепочка функций-обработчиков, которые последовательно модифицируют объект лога перед его записью.
- **Correlation-ID / Request-ID** — уникальный UUID запроса для сквозной идентификации всех связанных событий в распределенной системе [63, 8.4 draft].
- **Context Variables (`contextvars`)** — механизм Python для хранения состояния, изолированного в рамках текущей асинхронной корутины.
- **[Log Enrichment & PII Redaction](https://fastapi.tiangolo.com/tutorial/handling-errors/)** — процесс дополнения логов контекстными данными и очистки от чувствительной информации во избежание утечек.

#### Практический кейс: Построение единого асинхронного конвейера JSON-логирования

**Сценарий**: Необходимо объединить логи FastAPI (бизнес-логика), Starlette (ошибки роутинга) и Uvicorn (сетевой уровень) в единый JSON-поток для ELK.

**Реализация**:

1. **Перехват логов**: Стандартная библиотека `logging` настраивается на использование обработчика, который перенаправляет записи в процессоры `structlog`.
2. **Обогащение**: Middleware замеряет `process_time` и добавляет его в финальный JSON лога вместе с `X-Request-ID`.
3. **Результат**: Каждая строка в `stdout` представляет собой валидный JSON, содержащий время, уровень (INFO/ERROR), путь эндпоинта, IP клиента и идентификатор сессии.

#### Вопросы и задания для самопроверки

1. **Вопрос**: Почему запись логов в файлы `error.log` внутри Docker-контейнера считается анти-паттерном?
    - _Ответ: При перезапуске контейнера локальные файлы стираются. Файлы на диске усложняют масштабирование и требуют ручной настройки ротации, в то время как 12-Factor App требует передачи ответственности за хранение логов инфраструктуре._
2. **Задача**: Вы запустили фоновую задачу через `asyncio.create_task()`. Почему в её логах пропал `request_id` и как это исправить?
    - _Решение: `contextvars` не всегда наследуются автоматически в новые задачи без явного копирования контекста. Необходимо использовать `structlog.contextvars.bind_contextvars` внутри самой задачи._
3. **Практическое задание**: Напишите процессор для `structlog`, который ищет ключи `password` или `token` в словаре события и заменяет их значения на строку `***`.
