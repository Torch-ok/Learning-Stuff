#### Сквозной практический кейс: Развертывание полнофункционального Observability-стека (JSON-логи + Prometheus + OpenTelemetry)

**Постановка задачи:** Спроектировать и собрать комплексную систему наблюдаемости для высоконагруженного FastAPI-сервиса. Система должна обеспечивать поиск задержек в БД, визуализацию ошибок в логах через `Trace ID` и отображение технических/бизнес-метрик в Grafana [60, 273, 11.4 prompt].

**Пошаговый алгоритм выполнения:**

1. **Централизованная инициализация (Lifespan):** Настройте запуск OpenTelemetry `TracerProvider` и экспорт метрик Prometheus внутри асинхронного контекстного менеджера `lifespan`. Это гарантирует, что все подсистемы мониторинга будут готовы до начала обработки веб-запросов [323, 651, 8.3 draft].
    
2. **Middleware и Correlation-ID:** Реализуйте кастомный слой `BaseHTTPMiddleware`, который извлекает заголовок `X-Request-ID` (или генерирует новый) и сохраняет его в `contextvars`. Обогатите контекст `structlog`, чтобы каждый последующий лог в рамках корутины содержал этот идентификатор [63, 570, 11.1 draft].
    
3. **Инструментация I/O ресурсов:** Используйте автоматические инспекторы для SQLAlchemy 2.0 (`asyncpg`) и Redis. Каждый SQL-запрос к PostgreSQL или команда в Redis должны автоматически оборачиваться в дочерние спаны (Child Spans) относительно основного HTTP-запроса [5.1 draft, 7.2 draft, 11.3 draft].
    
4. **Связывание логов и трасс:** В конфигурацию процессоров `structlog` добавьте функцию, которая извлекает текущий `trace_id` из контекста OpenTelemetry и добавляет его в поле лога. Это позволит инженерам в интерфейсе Grafana переходить от сообщения об ошибке прямо к визуальному дереву трассировки [70, 11.3 draft].
    
5. **Бизнес-мониторинг и отладка:** Добавьте в эндпоинт оформления заказов кастомную метрику `Counter(total_orders)`. Проведите сквозной тест: вызовите ошибку, найдите её в логах по `X-Request-ID`, перейдите в Jaeger по `Trace ID` для выявления узкого места в БД и убедитесь, что метрика ошибок на эндпоинте `/metrics` увеличилась [62, 11.2 draft].
    

#### Комплексный контрольный тест для самопроверки

1. **Вопрос:** Какова основная цель разделения мониторинга на три столпа (Logs, Metrics, Traces)?
    
    - _Ответ: Метрики (Metrics) служат для алертинга и понимания "что" происходит (RPS, CPU); Трассировка (Traces) показывает "где" именно задержка; Логи (Logs) объясняют "почему" произошла ошибка, предоставляя детальный контекст [60, 62, 11.3 draft]._
2. **Задача на OTel Spans:** Ошибки, обработанные в `@app.exception_handler`, отображаются в Jaeger как успешные (зеленые) спаны. Как это исправить?
    
    - _Решение: Внутри обработчика исключений необходимо получить текущий спан через `trace.get_current_span()` и явно установить статус `span.set_status(StatusCode.ERROR)` [514, 11.3 draft]._
3. **Практическое задание:** Напишите код для настройки `BatchSpanProcessor` в OpenTelemetry, который использует `TraceIdRatioBased` сэмплер для записи только 10% всех входящих трасс [11.3 draft].
    
4. **Задача на безопасность:** Эндпоинт `/metrics` по умолчанию публичен. Как ограничить к нему доступ, используя только средства FastAPI (Dependencies)?
    
    - _Решение: Добавить в метод `expose()` инструментатора параметр `dependencies=[Depends(verify_internal_network)]`, где зависимость проверяет заголовок `X-Forwarded-For` или наличие внутреннего токена [11.2 draft]._
5. **Вопрос на производительность:** Какой из столпов Observability вносит наибольший overhead на CPU и RAM при 5000+ RPS в FastAPI?
    
    - _Ответ: Трассировка (Tracing) и структурированное логирование (Logging) вносят существенную нагрузку на CPU из-за интенсивной сериализации JSON и сетевого экспорта данных. Метрики (Metrics) обычно имеют наименьший overhead, так как хранят только агрегированные счетчики в памяти [11.1 draft, 11.2 draft, 11.3 draft]._
