#### Теоретический фундамент и архитектура

Система внедрения зависимостей FastAPI поддерживает использование функций-генераторов, что является основным механизмом для управления жизненным циклом ресурсов в рамках одного HTTP-запроса. Использование ключевого слова `yield` вместо `return` превращает обычную зависимость в мощный инструмент контекстного управления, аналогичный асинхронным контекстным менеджерам Python (`async contextmanager`).

**Жизненный цикл зависимости с `yield` строго детерминирован:**

1. **Подготовка (Code before yield):** Весь код, написанный до оператора `yield`, выполняется непосредственно перед вызовом эндпоинта или другой зависимости, которая запрашивает данный ресурс. Здесь происходит открытие соединений, создание сессий базы данных или инициализация транзакций.
2. **Передача управления (The yield point):** В этой точке FastAPI приостанавливает выполнение генератора и передает управление (вместе с объектом, указанным после `yield`) в эндпоинт.
3. **Очистка (Code after yield):** После того как эндпоинт завершил свою работу и сформировал HTTP-ответ (даже если в процессе возникло исключение), выполнение генератора возобновляется с кода, следующего за `yield`. В этой фазе закрываются сетевые дескрипторы, освобождаются пулы соединений и завершаются транзакции.

Безопасность выполнения гарантируется блоками `try...finally`. Если внутри эндпоинта произойдет ошибка (например, `HTTPException`), FastAPI пробросит ее обратно в генератор в точку `yield`, что позволяет корректно выполнить блок `finally` и избежать утечек памяти или "висящих" соединений с БД.

#### Практическая реализация и синтаксис

Современный стандарт 2026 года для работы с асинхронными сессиями SQLAlchemy 2.0 предполагает использование `async sessionmaker` и строгую очистку в блоке `finally`.

**Пример асинхронного генератора сессии БД:**

```python
from typing import Annotated, AsyncGenerator
from fastapi import Depends
from sqlalchemy.ext.asyncio import AsyncSession
# Предполагается, что сессия создается через async_sessionmaker
from .database import async_session_local

async def get_db() -> AsyncGenerator[AsyncSession, None]:
    # 1. Открытие ресурса
    async with async_session_local() as session:
        try:
            # 2. Передача сессии в эндпоинт
            yield session
        finally:
            # 3. Гарантированное закрытие (Cleanup)
            await session.close()

# Создание alias для удобства использования
SessionDep = Annotated[AsyncSession, Depends(get_db)]
```

**Управление границами транзакции (Transactional Boundaries):**

```python
async def get_transactional_db(db: SessionDep):
    try:
        yield db
        # Если эндпоинт отработал без ошибок, фиксируем изменения
        await db.commit()
    except Exception:
        # В случае любого сбоя в эндпоинте откатываем транзакцию
        await db.rollback()
        raise
```

> [!warning] Актуализация синтаксиса 
> В старых версиях SQLAlchemy часто использовался метод `db.close()` без `await`. В SQLAlchemy 2.0 Async (FastAPI 2026) необходимо использовать только асинхронные вызовы `await session.close()` и `await session.commit()` внутри генераторов.

#### Глоссарий терминов

- **[Async Generator Dependency](https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/)** — зависимость, использующая `async def` и `yield` для управления состоянием ресурса.
- **[Yield in Depends](https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/)** — точка разграничения между фазой инициализации и фазой очистки ресурса в FastAPI.
- **[Resource Cleanup (Очистка ресурсов)](https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/)** — процесс освобождения системных ресурсов (БД, файлы, сокеты) после завершения запроса.
- **Context Management в DI** — использование системы внедрения зависимостей для управления контекстом выполнения, альтернатива ручному использованию `with`.
- **Transactional Boundaries** — определение четких рамок начала и завершения (commit/rollback) базы данных в рамках одного запроса.

#### Практический кейс: Безопасное управление подключениями к БД и внешним сокетам

**Сценарий:** Необходимо реализовать зависимость для работы с внешним сервисом очередей или базой данных, которая должна логировать время удержания соединения и гарантированно закрывать сокет, даже если клиент оборвал соединение или возникла ошибка `HTTP 404/422`.

**Реализация:**

1. **Логирование старта:** В коде до `yield` фиксируется `start_time` через `time.perf_counter()`.
2. **Устойчивость к ошибкам:** Весь процесс оборачивается в `try...finally`. Даже если эндпоинт выбросит `HTTPException(status_code=404)`, код после `yield` всё равно выполнится.
3. **Результат:** В блоке `finally` вычисляется разница во времени, которая отправляется в логгер, а затем вызывается асинхронное закрытие сокета `await connection.disconnect()`. Это предотвращает утечки файловых дескрипторов и позволяет мониторить "зависшие" соединения в продакшне.

#### Вопросы и задания для самопроверки

1. **Вопрос:** Будет ли выполнен код после `yield`, если в функции эндпоинта возникло исключение `ValueError`?
    - _Ответ: Да, если код после `yield` обернут в блок `finally` или если FastAPI корректно обрабатывает завершение генератора после выхода из области видимости запроса._
2. **Задача:** Найдите утечку ресурсов:
    
    ```
    async def get_socket():
        s = await open_connection()
        yield s
        await s.close()
    ```
    
    _Подсказка: если `yield s` бросит исключение из эндпоинта, `s.close()` никогда не будет вызван. Используйте `try...finally`._
3. **Практическое задание:** Напишите асинхронную зависимость `get_lock`, которая использует `asyncio.Lock()`. Она должна захватывать блокировку (`await lock.acquire()`) перед `yield` и гарантированно освобождать ее после `yield`.
