#### Теоретический фундамент и архитектура

В SQLAlchemy 2.0 декларативное описание моделей претерпело значительные изменения, перейдя к современному синтаксису Python на основе аннотаций типов. Основным строительным блоком является класс `DeclarativeBase`, от которого наследуются все сущности приложения. Для определения атрибутов таблиц используются типизированные аннотации `Mapped[...]`, которые обеспечивают отличную поддержку IDE, и функция `mapped_column()`, отвечающая за детальную конфигурацию SQL-колонки, такую как `primary_key`, `unique` или `nullable`.

Связи между таблицами (`relationship`) описывают логическую иерархию данных: от простых One-to-Many до сложных Many-to-Many структур. Однако в асинхронной среде программист сталкивается с критическим ограничением: ленивая загрузка (Lazy Loading), привычная по синхронному коду, здесь не поддерживается. При попытке обратиться к связанному объекту (например, `post.author`), который не был загружен заранее, SQLAlchemy выбросит исключение `MissingGreenlet` или `AwaitRequired`, так как неявный запуск SQL-запроса в асинхронном контексте невозможен.

Для решения этой проблемы и предотвращения **проблемы N+1 запросов** (когда для списка из N объектов выполняется N дополнительных запросов к БД) используются стратегии жадной загрузки (**Eager Loading**):

- **`selectinload`** — выполняет дополнительный запрос с использованием оператора `IN`, что является наиболее эффективным способом загрузки коллекций (One-to-Many) в асинхронном режиме.
- **`joinedload`** — использует SQL-оператор `JOIN` для получения связанных данных в одном запросе, что идеально подходит для одиночных связей Many-to-One или One-to-One.

CRUD-операции в стиле 2.0 строятся на использовании объекта `select()`, который передается в метод сессии `execute()`. Это заменяет устаревший интерфейс `session.query()` и позволяет более гибко управлять процессом выполнения запроса, используя методы `.scalars()` для получения объектов Python вместо сырых строк базы данных.

#### Практическая реализация и синтаксис

Современное описание моделей и связей требует четкого указания типов для корректной работы асинхронных драйверов.

**Пример моделей данных E-commerce:**

```python
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship
from sqlalchemy import ForeignKey, String, Text, select
from sqlalchemy.ext.asyncio import AsyncSession
from sqlalchemy.orm import selectinload

class Base(DeclarativeBase):
    pass

class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    username: Mapped[str] = mapped_column(String(50), unique=True)
    # One-to-Many связь
    orders: Mapped[list["Order"]] = relationship(back_populates="user")

class Order(Base):
    __tablename__ = "orders"
    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    user: Mapped["User"] = relationship(back_populates="orders")
```

[SQL (Relational) Databases](https://fastapi.tiangolo.com/tutorial/sql-databases/), [SQLAlchemy 2.0 Models](https://fastapi.tiangolo.com/tutorial/sql-databases/#create-models)

**Асинхронные CRUD-функции с оптимизацией связей:**

```python
# Получение заказа с загрузкой списка товаров через selectinload
async def get_order_details(db: AsyncSession, order_id: int):
    query = (
        select(Order)
        .options(selectinload(Order.user)) # Жадная загрузка пользователя
        .where(Order.id == order_id)
    )
    result = await db.execute(query)
    return result.scalars().one_or_none()

# Массовое обновление статусов (Update)
from sqlalchemy import update

async def mark_orders_as_shipped(db: AsyncSession, user_id: int):
    stmt = (
        update(Order)
        .where(Order.user_id == user_id)
        .values(status="shipped")
    )
    await db.execute(stmt)
    await db.commit()
```

[SQLAlchemy 2.0 select syntax](https://fastapi.tiangolo.com/tutorial/sql-databases/#read-heroes), [Async updates](https://fastapi.tiangolo.com/tutorial/body-updates/#update-replacing-with-put)

> [!warning] Актуализация синтаксиса 
> В SQLAlchemy 2.0 стандартный метод `session.query(User).get(1)` заменен на более явный `db.execute(select(User).where(User.id == 1)).scalars().first()`. Прямые вызовы `query` считаются устаревшими и не рекомендуются для асинхронного использования.

#### Глоссарий терминов

- **[`DeclarativeBase`](https://fastapi.tiangolo.com/tutorial/sql-databases/)** — новый базовый класс в SQLAlchemy 2.0 для декларативного описания моделей, заменяющий функцию `declarative_base()`.
- **[`Mapped` & `mapped_column`](https://fastapi.tiangolo.com/tutorial/sql-databases/)** — инструменты типизации, позволяющие описать структуру таблицы и объектов Python в едином стиле.
- **[N+1 Query Problem](https://fastapi.tiangolo.com/tutorial/sql-databases/)** — антипаттерн производительности, при котором приложение делает лишние запросы к БД для каждого элемента в списке.
- **[Eager Loading (`selectinload` / `joinedload`)](https://fastapi.tiangolo.com/tutorial/sql-databases/)** — стратегии предварительной загрузки связанных данных для исключения дополнительных запросов.
- **[`MissingGreenlet` Exception](https://fastapi.tiangolo.com/tutorial/sql-databases/)** — специфическая ошибка асинхронной SQLAlchemy, возникающая при попытке доступа к не загруженным заранее атрибутам связи.
- **[SQLAlchemy 2.0 `select()` Syntax](https://fastapi.tiangolo.com/tutorial/sql-databases/)** — новый объектно-ориентированный способ построения SQL-запросов, ориентированный на явное выполнение через `session.execute()`.

#### Практический кейс: Оптимизация тяжелых выборок и предотвращение N+1

**Сценарий:** Эндпоинт `/api/v1/orders/{id}` возвращал полную информацию о заказе, но падал с ошибкой `MissingGreenlet` при попытке сериализации списка товаров во фронтенд-ответ.

**Проблема:** В коде эндпоинта использовался простой `select(Order)`, а связанные сущности `Order.items` загружались "лениво". В асинхронном режиме Pydantic не мог прочитать эти поля, так как они требовали блокирующего обращения к БД.

**Решение:**

1. **Рефакторинг запроса:** В запрос был добавлен `.options(selectinload(Order.items))`, что заставило SQLAlchemy выполнить один дополнительный эффективный запрос с `IN (...)`.
2. **Результат:** Количество запросов сократилось с 1 + N (где N — количество позиций в заказе) до ровно 2.
3. **Производительность:** Latency эндпоинта снизился на 40% за счет исключения сетевых задержек на лишние запросы, а ошибка `MissingGreenlet` полностью исчезла.

#### Вопросы и задания для самопроверки

1. **Вопрос:** Почему в асинхронной SQLAlchemy обращение к `user.posts` выдаст ошибку, если в запросе не был указан `selectinload`?
    - _Ответ: Потому что асинхронный событийный цикл не может приостановить выполнение для синхронного (блокирующего) дозапроса данных из базы._
2. **Задача:** У вас есть связь One-to-One (Профиль пользователя). Какую стратегию загрузки лучше выбрать — `joinedload` или `selectinload`?
    - _Ответ: `joinedload`, так как она объединит данные в один SQL-запрос через JOIN, что быстрее для одиночных связей._
3. **Практическое задание:** Напишите эндпоинт, который получает список всех пользователей (`User`) и их последних 5 заказов (`Order`), используя пагинацию (`limit`, `offset`) и жадную загрузку `selectinload`.
