#### Теоретический фундамент и архитектура

Эволюция SQLAlchemy до версии 2.0 принесла фундаментальные изменения в работе с данными, включая полноценную поддержку асинхронности и отказ от неявных механизмов в пользу явного синтаксиса. В современном стеке 2026 года стандартом для высоконагруженных систем является использование асинхронного драйвера `asyncpg`, который обеспечивает нативную работу с бинарным протоколом PostgreSQL и превосходит по производительности классические решения. Переход на `SQLAlchemy 2.0 Async` требует использования расширения `sqlalchemy.ext.asyncio`, предоставляющего специализированные классы для неблокирующего взаимодействия с СУБД.

Ключевыми компонентами асинхронного подключения являются:

- **`AsyncEngine`**: Создается через `create_async_engine` и управляет пулом соединений с базой данных. Настройка параметров пула, таких как `pool_size` (количество постоянных соединений) и `max_overflow` (допустимое временное превышение), критична для предотвращения простоев приложения.
- **`async_sessionmaker`**: Фабрика, генерирующая экземпляры `AsyncSession`. Она настраивается с параметром `expire_on_commit=False`, что предотвращает ошибки при обращении к атрибутам объектов после завершения транзакции в асинхронной среде.

В основе работы с объектами лежит паттерн **Unit of Work** (Единица работы), реализованный через `AsyncSession`. Сессия отслеживает изменения состояний объектов и гарантирует выполнение транзакций по принципам ACID: либо все изменения применяются атомарно через `commit()`, либо полностью откатываются через `rollback()` при возникновении ошибки. Для безопасного внедрения в FastAPI сессия оформляется как зависимость через `Depends` с использованием асинхронного генератора `yield`, что обеспечивает автоматическое закрытие соединения и очистку ресурсов после завершения каждого HTTP-запроса.

#### Практическая реализация и синтаксис

Современный модуль `database.py` для работы с PostgreSQL (asyncpg) строится на использовании `create_async_engine` и `async_sessionmaker`.

**Пример конфигурации подключения (`app/database.py`):**

```
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker, AsyncSession
from typing import AsyncGenerator

# URL для PostgreSQL с использованием драйвера asyncpg
DATABASE_URL = "postgresql+asyncpg://user:password@localhost/dbname"

# Создание асинхронного движка с настройками пула
engine = create_async_engine(
    DATABASE_URL,
    pool_size=20,
    max_overflow=10,
    pool_pre_ping=True
)

# Фабрика сессий
async_session_maker = async_sessionmaker(
    bind=engine,
    class_=AsyncSession,
    expire_on_commit=False,
    autoflush=False
)

# Зависимость для эндпоинтов
async def get_async_session() -> AsyncGenerator[AsyncSession, None]:
    async with async_session_maker() as session:
        try:
            yield session
        finally:
            await session.close()
```

[SQL (Relational) Databases](https://fastapi.tiangolo.com/tutorial/sql-databases/), [Python FastAPI Tutorial (Part 7): Sync vs Async](https://www.youtube.com/watch?v=PythonFastAPITutorial7)

Управление транзакциями в асинхронном режиме требует явного вызова `await` для методов `commit()`, `rollback()` и `refresh()`. Использование конструкции `async with session.begin()` позволяет автоматически зафиксировать транзакцию при успешном завершении блока кода или откатить её при исключении.

> [!warning] Актуализация синтаксиса В SQLAlchemy 2.0 методы `db.add()`, `db.commit()` и `db.refresh()` должны вызываться исключительно в асинхронном контексте с использованием `await`, если используется `AsyncSession`. Устаревший синхронный вызов `session.commit()` заблокирует Event Loop.

#### Глоссарий терминов

- **[SQLAlchemy 2.0 Async](https://fastapi.tiangolo.com/tutorial/sql-databases/)** — современная версия ORM с полной поддержкой асинхронного программирования и типизации.
- **[`AsyncEngine`](https://fastapi.tiangolo.com/deployment/server-workers/)** — объект, управляющий пулом асинхронных соединений и обеспечивающий связь с драйвером БД.
- **[`asyncpg`](https://fastapi.tiangolo.com/tutorial/sql-databases/)** — высокопроизводительный асинхронный драйвер для работы Python с PostgreSQL.
- **[`AsyncSession` & `async_sessionmaker`](https://fastapi.tiangolo.com/tutorial/sql-databases/)** — инструменты для управления транзакциями и жизненным циклом объектов в рамках Unit of Work.
- **[Unit of Work Pattern](https://fastapi.tiangolo.com/tutorial/sql-databases/)** — паттерн, группирующий операции с базой данных в одну транзакцию для обеспечения целостности данных.
- **[Connection Pooling (`QueuePool`)](https://fastapi.tiangolo.com/tutorial/sql-databases/)** — механизм переиспользования открытых соединений для снижения нагрузки на БД и ускорения запросов.

#### Практический кейс: Настройка отказоустойчивого асинхронного пула соединений

**Сценарий:** Проектирование API для обработки 10 000 конкурентных соединений (C10K) с использованием PostgreSQL.

**Расчет ресурсов:** Для обеспечения стабильности при запуске нескольких воркеров (например, 4 процесса через `uvicorn --workers 4`) необходимо учитывать суммарный лимит соединений СУБД. Если каждый воркер настроен с `pool_size=20` и `max_overflow=10`, то максимально приложение может открыть `4 * (20 + 10) = 120` соединений.

**Оптимизация:**

1. **Защита от обрывов**: Параметр `pool_pre_ping=True` заставляет SQLAlchemy проверять "живучесть" соединения перед выдачей его из пула, что критично для облачных баз данных с агрессивными таймаутами TCP.
2. **Обработка ошибок**: При превышении лимита пула возникает ошибка `QueuePool limit exceeded`. Решением является увеличение `pool_size` или оптимизация времени удержания сессии через своевременный `yield` и закрытие в блоке `finally`.

#### Вопросы и задания для самопроверки

1. **Вопрос**: Почему прямой вызов `session.commit()` без обработки исключений в блоке `try...except` может быть опасен в асинхронном приложении?
    - _Ответ: Если транзакция не будет корректно закрыта или откачена при ошибке, соединение может остаться в "зависшем" состоянии, блокируя ресурсы пула._
2. **Задача**: Рассчитайте максимальное количество соединений к базе, если запущено 8 воркеров Granian, в конфигурации которых `pool_size` установлен в 15, а `max_overflow` равен 5.
3. **Практическое задание**: Напишите асинхронную функцию-обертку, которая принимает `AsyncSession` и выполняет атомарный перевод средств между двумя счетами (Update баланса отправителя, Update баланса получателя, Commit), используя паттерн Unit of Work.
