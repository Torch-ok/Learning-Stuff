#### Теоретический фундамент и архитектура

Alembic является стандартом для управления миграциями в экосистеме Python и SQLAlchemy. Его основное назначение — инкрементальное отслеживание изменений в схеме базы данных и возможность отката к любой точке во времени, аналогично системе Git для программного кода. В современных асинхронных проектах 2026 года Alembic адаптируется для работы с драйверами вроде `asyncpg` через специализированный шаблон конфигурации, позволяющий запускать миграции внутри цикла событий `asyncio`.

Архитектура Alembic строится на трех столпах:

- **`alembic.ini`** — файл глобальной конфигурации, определяющий настройки подключения и логирования.
- **`env.py`** — скрипт, выполняющийся при каждом запуске команд Alembic; он настраивает контекст выполнения миграций и содержит ссылку на метаданные моделей.
- **`versions/`** — директория, хранящая файлы ревизий (скрипты миграций), каждый из которых содержит функции `upgrade()` и `downgrade()`.

Механизм автогенерации (`--autogenerate`) — одна из самых мощных функций Alembic. Он сравнивает текущее состояние базы данных с метаданными моделей, унаследованных от `DeclarativeBase`, и автоматически создает файл ревизии с необходимыми изменениями. Однако автогенерация имеет ограничения: Alembic может не заметить добавление индексов, специфических ограничений или изменений в кастомных типах данных без дополнительной настройки. В продакшн-средах запуск миграций (`alembic upgrade head`) должен выполняться централизованно перед стартом приложения, чтобы гарантировать консистентность схемы во всех репликах ASGI-сервера.

#### Практическая реализация и синтаксис

Для инициализации асинхронного проекта Alembic используется команда с флагом шаблона:

```bash
# Инициализация Alembic с асинхронным шаблоном
uv run alembic init -t async alembic
```

**Настройка `env.py` для асинхронного драйвера:** Критически важно импортировать `Base` из файла моделей (где определены все сущности), а не из файла подключения, чтобы Alembic «увидел» все таблицы. Для безопасности URL подключения переопределяется динамически из Pydantic `settings`.

```python
from app.models import Base  # Импортируем из моделей
from app.config import settings
from alembic import context

# Передаем метаданные для автогенерации
target_metadata = Base.metadata  #

def run_migrations_online():
    # Переопределяем URL подключения из настроек приложения
    config = context.config
    config.set_main_option("sqlalchemy.url", settings.DATABASE_URL) #

    # В асинхронном шаблоне здесь настраивается асинхронный движок
    # и вызов асинхронного контекста миграций
    ...
```

**Основные CLI-команды:**

```bash
# Создание миграции на основе изменений в моделях
uv run alembic revision --autogenerate -m "Add user phone number"

# Применение всех миграций до актуальной версии (head)
uv run alembic upgrade head

# Откат на одну ревизию назад
uv run alembic downgrade -1
```

**Entrypoint для Docker-контейнера (`entrypoint.sh`):** Скрипт обеспечивает выполнение миграций до запуска сервера.

```bash
#!/bin/bash
set -e

# Ожидание готовности БД и применение миграций
uv run alembic upgrade head #

# Запуск ASGI-сервера (Granian или Uvicorn)
exec uv run granian app.main:app --interface asgi --workers 4
```

#### Глоссарий терминов

- **[Alembic](https://fastapi.tiangolo.com/tutorial/sql-databases/#create-database-tables-on-startup)** — инструмент для миграций баз данных в SQLAlchemy, позволяющий управлять версиями схемы.
- **Async Migration (`env.py`)** — конфигурация скрипта `env.py`, адаптированная для запуска миграций в неблокирующем режиме.
- **[Auto-generate Revisions](https://fastapi.tiangolo.com/tutorial/sql-databases/)** — процесс автоматического создания кода миграции путем сравнения моделей Python с реальными таблицами в БД.
- **[Target Metadata](https://fastapi.tiangolo.com/tutorial/sql-databases/)** — объект `MetaData` из SQLAlchemy, который сообщает Alembic структуру ожидаемых таблиц.
- **Migration Rollback (`downgrade`)** — команда возврата схемы базы данных к состоянию одной из предыдущих ревизий.
- **Container Entrypoint Migrations** — паттерн автоматического запуска `upgrade head` при старте Docker-контейнера перед инициализацией основного процесса приложения.

#### Практический кейс: Безопасное проведение миграций в CI/CD

**Сценарий:** Приложение развертывается через Docker Compose с несколькими репликами API-сервера. Если каждая реплика попытается выполнить миграции одновременно, может возникнуть состояние гонки (race condition).

**Решение:**

1. **Вынос в отдельный шаг:** В CI/CD пайплайне или Docker Compose файле миграции выносятся в отдельный временный контейнер, который завершается до старта основных сервисов.
2. **Кастомные скрипты:** Для операций, которые Alembic не генерирует автоматически (например, создание составного индекса или предзаполнение таблиц справочников), в функции `upgrade()` вручную прописывается SQL через `op.execute()` или `op.create_index()`.
3. **Результат:** Гарантированное обновление схемы без конфликтов и возможность безопасного отката (`downgrade`) при неудачных тестах.

#### Вопросы и задания для самопроверки

1. **Вопрос:** Почему не рекомендуется использовать `base.metadata.create_all(engine)` в продакшн-окружении для создания таблиц?
    - _Ответ: Этот метод не поддерживает миграции (изменение существующих колонок, удаление данных) и только создает отсутствующие таблицы._
2. **Задача:** Вы добавили новое поле в класс модели, запустили `revision --autogenerate`, но файл миграции пустой. Проверьте, правильно ли настроен импорт `Base` и `target_metadata` в вашем `env.py`.
3. **Практическое задание:** Напишите bash-команду для CI/CD процесса, которая проверяет текущую ревизию базы данных (`alembic current`) и в случае расхождения с `head` блокирует деплой.
