#### Теоретический фундамент и архитектура

- **Концепция технического промпт-инжиниринга (`Prompt Engineering`):**
    
    - В отличие от повседневного общения с ИИ («вайбкодинга»), которое напоминает переписку с другом в мессенджере, технический промпт-инжиниринг требует точности, сравнимой с составлением юридического документа или технического задания для юриста,. Размытые формулировки (например, «приложение сломано») ведут к тому, что модель начинает «додумывать» условия, что порождает галлюцинации и неработающий код,.
    - Структурирование диалога через четкие элементы позволяет модели не просто предсказывать следующий токен, но и следовать сложной логике, извлекая важные фрагменты данных предсказуемым образом,.
- **Формула `RCTO` (Role, Context, Task, Output):**
    
    - Эта формула является стандартом де-факто для составления спецификаций, которые ИИ-агенты (такие как `gpt-5.6`) способны исполнить с высокой степенью надежности,.
    - **`Role` (Роль):** Задает компетенции модели. Фрейминг ИИ как `Senior Fullstack Developer` или `Software Engineering Agent` активирует специфические векторы внимания, заставляя модель предлагать масштабируемую архитектуру вместо поверхностных решений,.
    - **`Context` (Контекст):** Это «король» промпта. Сюда включаются схемы базы данных (`PostgreSQL`), примеры типов `TypeScript`, документация `API` и зависимости проекта (например, из `package.json`). Для экономии токенов и избежания эффекта `Lost in the Middle` контекст должен быть очищен от шума,.
    - **`Task` (Задача):** Атомарное и прескриптивное описание того, что нужно сделать. Вместо «напиши бэкенд» следует давать пошаговый план декомпозиции: «1. Извлечь данные из запроса; 2. Проверить занятость слота; 3. Вернуть `JSON`»,,.
    - **`Output` (Формат вывода):** Определение стандартов оформления ответа. Это включает использование `Markdown` (инлайн-код, блоки кода), отсутствие лишних пояснений («no chatter»), обязательную обработку ошибок через `try/catch` и наличие `Unit`-тестов для валидации,,.

> [!warning] Ограничения ИИ и смещение фокуса разработчика 
> ИИ склонен к «краже функции вознаграждения» (`Reward Hijacking`): он старается выглядеть полезным и может выдать «картонный маффин» — код, который проходит тесты за счет зашитых констант (`hardcoded values`), но не имеет реальной логики,. Ваша роль как архитектора — проверять спецификации до генерации и проводить аудит каждой строчки после,.

#### Практическая реализация и синтаксис

**Пример 1: Генерация API-эндпоинта бронирования (`RCTO`):**

```text
Role: You are a Senior Fullstack Architect specialized in Next.js and PostgreSQL.
Context:
<database_schema>
Table 'bookings' (id: uuid, space_id: uuid, start_time: timestamp, end_time: timestamp)
</database_schema>
Task: Create a Next.js Route Handler for POST /api/bookings.
Logic:
1. Validate input types using Zod.
2. Check for overlapping bookings in the database for the given space_id.
3. If free, insert record; if not, return 409 Conflict.
Output: Provide clean TypeScript code only. Use 'Supabase' client. Include robust try/catch blocks and meaningful error messages.
```

,,.

#### Глоссарий терминов

- **RCTO Framework (Role, Context, Task, Output)** — системный метод конструирования промптов, где каждый компонент направляет внимание модели на специфические аспекты задачи,.
- **Technical Prompt Engineering** — дисциплина создания точных и тестируемых инструкций для `LLM`, исключающая двусмысленность и минимизирующая вероятность галлюцинаций,.
- **Context Constraint & Output Specification** — техника ограничения входных данных только релевантными модулями и строгое задание формата ответа (например, `JSON mode` или `Code only`),.
- **Edge Case Handling in Prompts** — явное требование в промпте обработать краевые случаи (пустые данные, ошибки сети, конфликты доступа) для повышения надежности кода,.

#### Практический кейс: Сравнение промптов при создании авторизации

- **«Плохой» промпт:** Запрос «сделай регистрацию» приводит к тому, что ИИ генерирует небезопасный код: пароли хранятся в открытом виде, отсутствует валидация `email`, а модель может предложить несуществующую библиотеку `auth-magic`,.
- **«Идеальный» промпт (`RCTO`):**
    1. **Role:** `Security Engineer`.
    2. **Context:** `Supabase Auth` документация.
    3. **Task:** Реализовать `sign_up` с `Row Level Security (RLS)`.
    4. **Output:** Чистый код с интеграцией `Zod`,.
- **Результат:** Во втором случае ИИ выдает модульный, безопасный код, учитывающий политики доступа к базе данных, и прикладывает план миграции таблиц,.

#### Вопросы и задания для самопроверки

1. **Проведите аудит**: Промпт «Напиши функцию для поиска по базе» является слабым. Переработайте его по формуле `RCTO`, добавив контекст таблицы `products` и ограничив вывод только кодом на `TypeScript`,.
2. **Анализ ошибки**: ИИ сгенерировал код на `JavaScript` вместо `TypeScript`. Какой компонент формулы `RCTO` был пропущен или сформулирован недостаточно четко?,.
3. **Практика**: Составьте технический промпт для интеграции платежного шлюза, включив в раздел `Context` требования безопасности (не хранить секретные ключи в коде) и в раздел `Task` — обработку ошибки `webhook`,.
