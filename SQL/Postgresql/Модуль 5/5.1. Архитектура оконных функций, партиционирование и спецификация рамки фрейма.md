#### Теоретический фундамент и архитектура

**Концепция оконной обработки данных в PostgreSQL:** Оконные функции («Window Functions») представляют собой особый режим вычислений, при котором функция обрабатывает не только текущую строку, но и её окружение («vicinity») — набор строк, связанных с ней логически или физически [Advanced SQL — Video #29](https://notebook.google.com/notebook/1). В отличие от обычной агрегации с применением `GROUP BY`, которая сворачивает группу строк в одну результирующую строку, оконные функции сохраняют детальность исходного набора данных: каждая строка таблицы остается на месте, дополняясь результатом вычисления [Advanced SQL — Video #29](https://notebook.google.com/notebook/1), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/432).

**Порядок выполнения оконных функций в Pipeline запроса:** Внутренний механизм PostgreSQL обрабатывает оконные функции на финальных этапах выполнения запроса. Типовой конвейер выглядит следующим образом: `FROM` -> `WHERE` -> `GROUP BY` -> `HAVING` -> вычисление **`WINDOW`** функций -> `SELECT` (проекция) -> `ORDER BY` [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/434), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/436). Поскольку оконные функции вычисляются после фильтрации данных, в SQL наложен строгий запрет на их использование внутри секций `WHERE` и `HAVING`. Если требуется отфильтровать данные по результату работы окна, запрос необходимо обернуть в подзапрос или обобщенное табличное выражение (**CTE**) [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/62), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/447).

**Структура спецификации окна `OVER()`:** Инструкция `OVER()` определяет контекст, в котором будет работать функция [Advanced SQL — Video #29](https://notebook.google.com/notebook/5).

- **Партиционирование (`PARTITION BY`):** Логически разделяет результирующий набор на непересекающиеся группы (партиции). Вычисления внутри окна производятся отдельно для каждой группы, и границы партиции являются непреодолимым барьером для окна [Advanced SQL — Video #30](https://notebook.google.com/notebook/20), [Advanced SQL — Video #30](https://notebook.google.com/notebook/21).
- **Сортировка внутри окна (`ORDER BY`):** Задает последовательность обработки строк. Это критически важно не только для функций ранжирования, но и для агрегатов, так как наличие сортировки активирует динамический фрейм (рамку) [Advanced SQL — Video #29](https://notebook.google.com/notebook/5), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/446).
- **Именованные окна:** Для предотвращения дублирования длинных спецификаций в PostgreSQL используется секция `WINDOW`, располагающаяся перед финальным `ORDER BY`. Это позволяет один раз описать параметры окна и ссылаться на них по имени [Advanced SQL — Video #29](https://notebook.google.com/notebook/10), [Advanced SQL — Video #29](https://notebook.google.com/notebook/11).

**Границы и типы рамок оконных фреймов (Window Frame):** Фрейм — это подмножество строк внутри текущей партиции, по которому непосредственно производится расчет [Advanced SQL — Video #29](https://notebook.google.com/notebook/4).

- **`ROWS` (физический тип):** Определяет границы на основе физического смещения строк (например, «3 строки назад») [Advanced SQL — Video #29](https://notebook.google.com/notebook/7).
- **`RANGE` (логический тип):** Учитывает значения в колонке сортировки. Строки с одинаковыми значениями формируют «группу сверстников» (`peer group`) и обрабатываются вместе [Advanced SQL — Video #29](https://notebook.google.com/notebook/7), [Advanced SQL — Video #29](https://notebook.google.com/notebook/9).
- **Границы фрейма:**
    - `UNBOUNDED PRECEDING` — от начала партиции.
    - `CURRENT ROW` — текущая строка (или группа строк при `RANGE`).
    - `n PRECEDING` / `n FOLLOWING` — смещение на `n` строк.
    - `UNBOUNDED FOLLOWING` — до конца партиции [Advanced SQL — Video #29](https://notebook.google.com/notebook/6), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/449).

**Поведение по умолчанию:** Если в `OVER()` указан `ORDER BY`, но не задан фрейм, PostgreSQL использует `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. Это означает расчет «накопительным итогом» от начала раздела до текущей позиции [Advanced SQL — Video #29](https://notebook.google.com/notebook/9), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/450).

#### Практическая реализация и синтаксис

Пример вывода детальной информации о сотрудниках с расчетом средней зарплаты по их отделу:

```
SELECT ename,
       deptno,
       sal,
       -- Агрегация без потери детальных строк
       AVG(sal) OVER(PARTITION BY deptno) as avg_dept_sal
FROM emp
ORDER BY deptno;
```

[Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/437), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/438).

Использование именованного окна и физического фрейма для расчета скользящего среднего:

```
SELECT ename,
       sal,
       hiredate,
       -- Использование именованного окна 'w'
       AVG(sal) OVER w as moving_avg
FROM emp
WINDOW w AS (
    ORDER BY hiredate
    ROWS BETWEEN 3 PRECEDING AND CURRENT ROW
)
ORDER BY hiredate;
```

[Advanced SQL — Video #29](https://notebook.google.com/notebook/11), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/453).

**Разница между ROWS и RANGE при наличии дубликатов:** Если в поле `hiredate` есть одинаковые даты, `RANGE` (по умолчанию) включит все строки с этой датой в текущий расчет, что может привести к скачкообразному изменению суммы. `ROWS` будет обрабатывать каждую строку строго индивидуально [Advanced SQL — Video #29](https://notebook.google.com/notebook/17), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/449).

#### Глоссарий терминов

- **Window Function Context** — область видимости (окно), внутри которой функция имеет доступ к соседним строкам текущей партиции [Advanced SQL — Video #29](https://notebook.google.com/notebook/1).
- **OVER Clause** — синтаксическая конструкция, инициирующая оконный режим обработки запроса [Advanced SQL — Video #29](https://notebook.google.com/notebook/5).
- **Partitioning (PARTITION BY)** — процесс разделения набора данных на логические группы, в рамках которых состояние оконной функции сбрасывается [Advanced SQL — Video #30](https://notebook.google.com/notebook/20).
- **Window Frame Specification** — определение точных границ (начала и конца) набора строк внутри партиции, участвующих в вычислении для текущей строки [Advanced SQL — Video #29](https://notebook.google.com/notebook/4).
- **Physical Frame (ROWS) vs Logical Frame (RANGE)** — различие между позиционным смещением в строках и логическим смещением на основе значений ключа сортировки [Advanced SQL — Video #29](https://notebook.google.com/notebook/7).
- **Default Frame Boundary** — стандартная рамка `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, применяемая при наличии сортировки [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/450).
- **Named Window Clause (WINDOW)** — инструмент для выноса и повторного использования спецификаций окон в теле запроса [Advanced SQL — Video #29](https://notebook.google.com/notebook/10).

#### Практический кейс: Динамическое распределение доли продаж внутри категорий

В аналитических отчетах e-commerce часто требуется рассчитать вклад каждого товара в выручку категории. Классический подход требует сложного самосоединения или подзапроса с `GROUP BY`. С помощью оконных функций это решается за один проход по данным [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/202), [SQL. Сборник рецептов, 2-е издание.pdf](https://notebook.google.com/notebook/128).

**Решение:**

```
SELECT product_name,
       category_id,
       price,
       -- Сумма цен всех товаров в ТЕКУЩЕЙ партиции (категории)
       SUM(price) OVER(PARTITION BY category_id) as category_total,
       -- Расчет доли (Price / Total * 100)
       ROUND((price / SUM(price) OVER(PARTITION BY category_id)) * 100, 2) as pct_contribution
FROM products;
```

Этот подход исключает накладные расходы на создание промежуточных таблиц и позволяет PostgreSQL оптимизировать чтение данных [SQL. Сборник рецептов, 2-е издание.pdf](https://notebook.google.com/notebook/129), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/418).
