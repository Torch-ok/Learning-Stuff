#### Сводный академический глоссарий Модуля 5

| Термин          | Категория    | Академическое определение                                                                                                            |
| :-------------- | :----------- | :----------------------------------------------------------------------------------------------------------------------------------- |
| Window Function | Вычисления   | Функция, выполняющая расчеты над набором строк (окном), логически связанных с текущей записью, без объединения их в одну строку.     |
| OVER Clause     | Синтаксис    | Инструкция, определяющая границы и характеристики окна, в рамках которого будет выполнена оконная функция.                           |
| PARTITION BY    | Группировка  | Элемент спецификации окна, разделяющий результирующий набор на логические подмножества для независимого выполнения расчетов.         |
| Window Frame    | Кадрирование | Подмножество строк внутри партиции (физическое `ROWS` или логическое `RANGE`), определяющее точный диапазон данных для агрегации.    |
| ROW_NUMBER()    | Ранжирование | Функция, присваивающая каждой строке уникальный порядковый номер в зависимости от заданного порядка сортировки.                      |
| RANK()          | Ранжирование | Алгоритм присвоения рангов, при котором строки с одинаковыми значениями получают один ранг, создавая разрыв в последующей нумерации. |
| DENSE_RANK()    | Ранжирование | Плотное ранжирование, исключающее пропуски в последовательности номеров при наличии дубликатов значений.                             |
| NTILE()         | Статистика   | Функция для распределения строк по заданному количеству равных групп (корзин) на основе их ранга.                                    |
| LAG / LEAD      | Смещение     | Функции доступа к значениям атрибутов в предшествующих (`LAG`) или последующих (`LEAD`) строках относительно текущей.                |
| Running Total   | Агрегация    | Накопительный итог, вычисляемый как сумма значений от начала партиции до текущей строки включительно.                                |
| Moving Average  | Агрегация    | Скользящее среднее, рассчитываемое по динамическому фрейму фиксированного размера для сглаживания данных.                            |
| LAST_VALUE Trap | Ошибки       | Логическая ошибка, возникающая при использовании `LAST_VALUE` с дефолтным фреймом `RANGE`, ограничивающим расчет текущей строкой.    |

#### Сквозной практический кейс: Комплексный аналитический дашборд клиентов (RFM, Скользящее среднее, LTV Growth)

**Постановка задачи:** Спроектировать SQL-запрос для формирования финансового дашборда, который объединяет показатели жизненного цикла клиента (LTV), динамику выручки сервиса и сегментацию пользователей по лояльности.

**Пошаговый алгоритм выполнения:**

1. **Вычисление накопительного LTV:** Для каждой транзакции пользователя рассчитываем общую сумму всех его покупок на текущий момент. Используем `SUM(amount) OVER (PARTITION BY user_id ORDER BY created_at)`. Это позволяет видеть прогресс накопления ценности клиента без использования коррелированных подзапросов.
2. **Расчет 30-дневного скользящего среднего выручки:** Для сглаживания ежедневных колебаний продаж применяем `AVG(daily_revenue) OVER (ORDER BY date ROWS BETWEEN 29 PRECEDING AND CURRENT ROW)`. Явная спецификация `ROWS` гарантирует учет фиксированного количества дней (строк), что критично при наличии пропусков в данных.
3. **Ранжирование и сегментация клиентов:** В рамках каждого региона присваиваем клиентам ранги по суммарным тратам через `DENSE_RANK()`, чтобы корректно обработать пользователей с одинаковыми чеками. Для маркетингового отсечения используем `NTILE(10)`, разделяя базу на 10 децилей и выделяя верхние 10% (дециль 1) как VIP-сегмент.
4. **Расчет динамики чека (Growth):** Используем `LAG(amount) OVER (PARTITION BY user_id ORDER BY created_at)` для получения суммы предыдущей покупки. Разница между текущим и прошлым значением позволяет анализировать рост или деградацию покупательской способности клиента.

#### Комплексный контрольный тест для самопроверки

1. **Вопрос на кадрирование:** В чем заключается фундаментальное различие между результатами `SUM(val) OVER (ORDER BY id ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` и `SUM(val) OVER (ORDER BY id RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`, если в столбце `id` есть дубликаты?.
2. **Задача на рефакторинг:** Перепишите запрос, выполняющий самосоединение (`Self-Join`) таблицы `sales` для поиска суммы продаж за вчерашний день, на использование оконной функции `LAG()`. Объясните, почему этот подход производительнее.
3. **Поиск логических ошибок:** Почему при расчете накопительного итога запрос `SELECT SUM(val) OVER (PARTITION BY user_id)` вернет общую сумму за все время для каждой строки, а не увеличивающуюся сумму? Какого ключевого слова не хватает в `OVER()`?.
4. **Практика дедупликации:** Напишите SQL-скрипт с использованием `WITH` и `ROW_NUMBER()`, который идентифицирует полные дубликаты в таблице заказов (поля `user_id`, `order_date`, `amount`) и оставляет только одну запись с минимальным `ctid` (или PK).
5. **Оптимизация производительности:** Опишите стадию `Incremental Sort` в плане выполнения оконной функции. Как создание индекса по колонкам `(branch_id, sale_date)` может помочь ускорить запрос `SUM(amount) OVER (PARTITION BY branch_id ORDER BY sale_date)`?. _(Подсказка: оконные функции крайне чувствительны к порядку данных, который может гарантировать индекс)_.
