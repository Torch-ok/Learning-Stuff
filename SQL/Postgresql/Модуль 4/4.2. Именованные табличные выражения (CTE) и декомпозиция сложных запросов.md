#### Теоретический фундамент и архитектура

Концепция **Common Table Expressions (CTE)**, реализуемая через предложение `WITH`, представляет собой механизм определения временных именованных результирующих наборов, которые существуют только в рамках выполнения одного SQL-запроса [Advanced SQL — Video #11](https://notebook.google.com/notebook/4), [SQL. Сборник рецептов](https://notebook.google.com/notebook/518). В отличие от обычных подзапросов, CTE позволяют архитектору БД описывать логику вычислений поэтапно, разделяя сложный процесс на небольшие, логически завершенные блоки [Advanced SQL — Video #11](https://notebook.google.com/notebook/4).

**Основные преимущества и характеристики CTE:**

- **Повышение читаемости (Readability):** Использование `WITH` превращает «лапшу» из вложенных подзапросов в вертикально организованную структуру, где каждый именованный блок (`t1`, `t2` ... `tn`) можно воспринимать как локальную переменную или временную таблицу [Advanced SQL — Video #11](https://notebook.google.com/notebook/4), [SQL. Сборник рецептов](https://notebook.google.com/notebook/520).
- **Область видимости (Scope):** CTE являются «локальными привязками» (`local bindings`). Они не видны и не могут быть вызваны за пределами того оператора (`SELECT`, `INSERT`, `UPDATE` или `DELETE`), в котором они определены [Advanced SQL — Video #11](https://notebook.google.com/notebook/4).
- **Декомпозиция и отладка:** CTE идеально подходят для поэтапного тестирования запросов. Разработчик может изолировать сложный узел логики в отдельном выражении и проверить его результат на верхнем уровне, не затрагивая остальную часть запроса [Advanced SQL — Video #11](https://notebook.google.com/notebook/4).

**Поведение материализации и оптимизация:** В архитектуре PostgreSQL именованные выражения долгое время служили «оптимизационным барьером» (`Optimization Barrier`). Это означало, что СУБД сначала полностью вычисляла CTE, сохраняла результат в памяти или на диске (материализовала), и только потом использовала его в основном запросе [SQL. Сборник рецептов](https://notebook.google.com/notebook/241). Начиная с PostgreSQL 12, поведение по умолчанию изменилось в сторону **инлайн-развертывания (Inlining)**. Теперь оптимизатор может встраивать код CTE в основной запрос для применения фильтров из внешнего `WHERE` непосредственно к источнику данных [SQL. Сборник рецептов](https://notebook.google.com/notebook/159), [SQL. Сборник рецептов](https://notebook.google.com/notebook/241). Однако для тяжелых вычислений, которые используются в запросе многократно, инженер может явно потребовать кэширования через синтаксис `AS MATERIALIZED` [SQL. Сборник рецептов](https://notebook.google.com/notebook/241).

**Модифицирующие CTE (Data-Modifying CTEs):** PostgreSQL позволяет выполнять операции `INSERT`, `UPDATE` и `DELETE` внутри блока `WITH`. В сочетании с предложением `RETURNING` это создает мощные конвейеры обработки данных. Например, можно удалить строки из активной таблицы и в рамках того же атомарного запроса вставить их в архив [SQL. Сборник рецептов](https://notebook.google.com/notebook/541).

> [!warning] Актуализация синтаксиса 
> Использование глубоко вложенных подзапросов в блоке `FROM` без применения CTE считается устаревшей практикой, затрудняющей поддержку кода и его оптимизацию. Стандарт SQL:2016 и выше предполагает использование `WITH` для всех сложных трансформаций [SQL. Сборник рецептов](https://notebook.google.com/notebook/241), [SQL. Сборник рецептов](https://notebook.google.com/notebook/519).

#### Практическая реализация и синтаксис

Пример последовательного расчета ежемесячной прибыли с последующей фильтрацией через цепочку CTE:

```
WITH MonthlySales AS (
    -- Шаг 1: Агрегация сырых данных по месяцам
    SELECT
        EXTRACT(MONTH FROM InvoiceDate) AS SaleMonth,
        SUM(Total) AS MonthlyTotal
    FROM invoices
    GROUP BY 1
),
SalesComparison AS (
    -- Шаг 2: Расчет разницы с предыдущим месяцем
    SELECT
        SaleMonth,
        MonthlyTotal,
        LAG(MonthlyTotal) OVER (ORDER BY SaleMonth) AS PrevMonthTotal
    FROM MonthlySales
)
-- Шаг 3: Финальная выборка и фильтрация
SELECT *
FROM SalesComparison
WHERE MonthlyTotal > PrevMonthTotal;
```

[Advanced SQL — Video #11](https://notebook.google.com/notebook/4), [SQL. Сборник рецептов](https://notebook.google.com/notebook/518).

Реализация атомарного процесса архивации данных:

```
WITH MovedRows AS (
    -- Удаление старых записей и их возврат "на лету"
    DELETE FROM active_logs
    WHERE log_date < NOW() - INTERVAL '1 year'
    RETURNING *
)
-- Вставка удаленных строк в архивную таблицу
INSERT INTO archived_logs
SELECT * FROM MovedRows;
```

[SQL. Сборник рецептов](https://notebook.google.com/notebook/541), [Advanced SQL — Video #11](https://notebook.google.com/notebook/4).

Использование `MATERIALIZED` для предотвращения повторных вычислений:

```
WITH HeavyCalc AS MATERIALIZED (
    -- Принудительное кэширование результата тяжелой агрегации
    SELECT complex_function(data) as result, category_id
    FROM big_table
    GROUP BY category_id
)
SELECT * FROM HeavyCalc h1
JOIN HeavyCalc h2 ON h1.category_id <> h2.category_id;
```

[SQL. Сборник рецептов](https://notebook.google.com/notebook/241).

#### Глоссарий терминов

- **Common Table Expression (CTE)** — временный именованный результирующий набор данных, определяемый внутри запроса [SQL. Сборник рецептов](https://notebook.google.com/notebook/518).
- **WITH Clause** — ключевое слово SQL для инициализации блока именованных табличных выражений [Advanced SQL — Video #11](https://notebook.google.com/notebook/4).
- **CTE Materialization Barrier** — особенность планировщика, при которой CTE вычисляется изолированно от основного запроса [SQL. Сборник рецептов](https://notebook.google.com/notebook/241).
- **Inlining CTEs** — процесс встраивания логики CTE в основной план выполнения для оптимизации [SQL. Сборник рецептов](https://notebook.google.com/notebook/241).
- **Data-Modifying CTE** — именованное выражение, выполняющее изменение данных (`INSERT/UPDATE/DELETE`) [SQL. Сборник рецептов](https://notebook.google.com/notebook/541).
- **Pipeline DML with RETURNING** — паттерн передачи результатов изменения данных из одного CTE в другой для цепочечной обработки [Advanced SQL — Video #11](https://notebook.google.com/notebook/4).

#### Практический кейс: Разделение сложного аналитического конвейера обработки данных

**Сценарий:** Необходимо рассчитать чистую прибыль интернет-магазина, учитывая налоги, стоимость доставки и примененные скидки, которые хранятся в разных таблицах. **Решение:** Вместо одного гигантского запроса с множеством `JOIN`, строится конвейер из 4-х CTE:

1. `BaseOrders`: собирает базовые данные из `orders` [SQL. Сборник рецептов](https://notebook.google.com/notebook/518).
2. `DiscountApplied`: вычисляет размер скидок для каждого заказа [Advanced SQL — Video #11](https://notebook.google.com/notebook/4).
3. `ShippingCosts`: агрегирует затраты на логистику из таблицы `shipping_manifests`.
4. `FinalMetrics`: объединяет результаты предыдущих шагов для вычисления маржинальности. Такой подход исключает дублирование кода (например, расчет скидок не нужно повторять в разных частях запроса) и позволяет оптимизатору PostgreSQL эффективно распределить нагрузку на I/O [SQL. Сборник рецептов](https://notebook.google.com/notebook/520).
