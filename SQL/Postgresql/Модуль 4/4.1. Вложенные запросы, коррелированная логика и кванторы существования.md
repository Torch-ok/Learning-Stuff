#### Теоретический фундамент и архитектура

Подзапрос (`Subquery`) — это запрос, содержащийся внутри другого SQL-выражения, называемого содержащим выражением (`Containing statement`) [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/81). В PostgreSQL подзапросы всегда заключаются в круглые скобки и обычно выполняются до начала обработки основного запроса, выступая в роли временных таблиц с областью видимости, ограниченной рамками одного выражения [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/81).

**Классификация подзапросов по типу возвращаемого результата:**

- **Скалярные подзапросы (`Scalar Subqueries`):** Возвращают ровно одну строку и одну колонку (таблица 1x1) [Advanced SQL — Video #05](https://notebook.google.com/notebook/2). Такие подзапросы могут использоваться в любом месте, где допустимо выражение: в блоках `SELECT`, `WHERE`, `ORDER BY` и `HAVING` [Advanced SQL — Video #05](https://notebook.google.com/notebook/2), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/127). Если скалярный подзапрос не находит данных, он возвращает `NULL` [Advanced SQL — Video #05](https://notebook.google.com/notebook/2).
- **Векторные / Многоколоночные подзапросы:** Возвращают одну строку с несколькими столбцами. Это позволяет выполнять сравнение кортежей: `(col1, col2) = (SELECT ...)`, что значительно сокращает код при проверке сложных условий целостности [Advanced SQL — Video #05](https://notebook.google.com/notebook/3), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/102).
- **Табличные подзапросы (`Derived Tables`):** Возвращают несколько строк и столбцов. При использовании в блоке `FROM` такие подзапросы формируют виртуальную таблицу. Согласно стандарту ANSI SQL, им **обязательно** должен быть присвоен псевдоним (`Alias`), иначе возникнет синтаксическая ошибка [SQL. Сборник рецептов](https://notebook.google.com/notebook/270).

**Зависимость подзапросов от внешнего контекста:**

- **Некоррелированные подзапросы (`Uncorrelated Subqueries`):** Полностью самодостаточны и не зависят от внешнего запроса [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/85). Они вычисляются однократно перед выполнением внешнего запроса [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/105).
- **Коррелированные подзапросы (`Correlated Subqueries`):** Ссылаются на столбцы из внешнего запроса (правила области видимости или `Scoping rules`) [Advanced SQL — Video #05](https://notebook.google.com/notebook/4), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/85). Такой подзапрос логически выполняется по одному разу для каждой строки-кандидата внешнего запроса, что может привести к сложности $O(N^2)$ при отсутствии оптимизаций [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/105).

**Операторы проверки условий и кванторы:**

- **`IN` vs `EXISTS`:** Оператор `IN` проверяет наличие значения в наборе, возвращенном подзапросом [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/90). `EXISTS` — это квантор существования, который возвращает `TRUE`, если подзапрос вернул хотя бы одну строку; фактический список столбцов в `SELECT` подзапроса (обычно пишут `SELECT 1`) значения не имеет [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/111).
- **Подводные камни `NOT IN`:** Если подзапрос в `NOT IN` возвращает хотя бы один `NULL`, весь основной запрос вернет пустой набор строк. Это происходит из-за трехзначной логики: сравнение любого значения с `NULL` дает `UNKNOWN`, что делает все условие `WHERE` неопределенным [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/99), [SQL. Сборник рецептов](https://notebook.google.com/notebook/292). Оператор `NOT EXISTS` лишен этого недостатка, так как он проверяет факт наличия строк, а не равенство значений [SQL. Сборник рецептов](https://notebook.google.com/notebook/298).
- **Кванторы `ANY` и `ALL`:** Позволяют сравнивать скалярное значение с каждым элементом набора [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/96). `= ANY` эквивалентен `IN`, тогда как `<> ALL` эквивалентен `NOT IN` [Alan_Beaulieu-Learning_SQL-RU.pdf](98, 101).

#### Практическая реализация и синтаксис

Расчет отклонения цены товара от средней через скалярный подзапрос:

```
SELECT product_name, price,
       price - (SELECT AVG(price) FROM products) AS price_diff
FROM products
ORDER BY price_diff DESC;
```

[Advanced SQL — Video #05](https://notebook.google.com/notebook/2), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/127).

Поиск клиентов с крупными покупками через коррелированный подзапрос и `EXISTS`:

```
-- Выбор клиентов, у которых есть хотя бы один заказ выше 50 000
SELECT c.customer_id, c.last_name
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.customer_id
      AND o.total_amount > 50000
);
```

[Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/111).

> [!warning] Актуализация синтаксиса 
> Использование `NOT IN` с подзапросами, которые могут содержать `NULL`, является критической ошибкой логики. Всегда заменяйте такие конструкции на `NOT EXISTS` для обеспечения корректной обработки неопределенных значений [SQL. Сборник рецептов](https://notebook.google.com/notebook/292), [SQL. Сборник рецептов](https://notebook.google.com/notebook/298).

Безопасный аналог `NOT IN` через `NOT EXISTS`:

```
-- Безопасный поиск сотрудников без привязки к отделу
DELETE FROM employees e
WHERE NOT EXISTS (
    SELECT 1 FROM departments d
    WHERE d.dept_id = e.dept_id
);
```

[SQL. Сборник рецептов](https://notebook.google.com/notebook/298), [SQL. Сборник рецептов](https://notebook.google.com/notebook/116).

#### Глоссарий терминов

- **Scalar Subquery** — вложенный запрос, возвращающий единственное значение (одну ячейку данных) [Advanced SQL — Video #05](https://notebook.google.com/notebook/2).
- **Correlated Subquery** — подзапрос, выполнение которого зависит от значений текущей строки внешнего запроса [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/85).
- **Derived Table** — подзапрос в блоке `FROM`, результат которого трактуется как временная таблица [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/20).
- **Subquery Unnesting** — оптимизация СУБД, при которой вложенный запрос преобразуется в операцию `JOIN` для повышения производительности [Advanced SQL — Video #05](https://notebook.google.com/notebook/6).
- **Existential Quantifier (`EXISTS`)** — логический оператор, проверяющий наличие хотя бы одного кортежа в результирующем наборе подзапроса [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/110).
- **Anti-Join / Semi-Join Transformation** — способы внутренней реализации операторов `EXISTS` и `NOT EXISTS` в плане выполнения запроса [SQL. Сборник рецептов](https://notebook.google.com/notebook/300).
- **Null Sensitivity in NOT IN** — особенность SQL, при которой наличие `NULL` в списке `NOT IN` делает условие невыполнимым для всех строк [SQL. Сборник рецептов](https://notebook.google.com/notebook/292).

#### Практический кейс: Поиск аномальных транзакций без использования JOIN

**Сценарий:** Необходимо выявить клиентов, чей объем транзакций за день существенно превышает типичное поведение в их регионе. **Решение:** Используется коррелированный подзапрос в блоке `WHERE`. Для каждой строки транзакции подзапрос вычисляет среднюю сумму операций по всем клиентам того же региона за последний месяц. Основной запрос сравнивает текущую транзакцию с этим «региональным эталоном». Такой подход позволяет избежать накладных расходов на создание огромных промежуточных `JOIN`-таблиц в памяти, выполняя фильтрацию «на лету» [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/105), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/187).
