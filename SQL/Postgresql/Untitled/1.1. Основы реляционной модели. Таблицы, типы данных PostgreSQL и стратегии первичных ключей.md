
#### Теоретический фундамент и архитектура

Реляционная модель данных, предложенная Эдгаром Ф. Коддом в 1970 году, основывается на представлении информации в виде наборов таблиц [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebooklm.google.com/notebook/45), [Шилдс Уолтер SQL.pdf](https://notebooklm.google.com/notebook/49). В этой модели сущности (`Entities`) реального мира описываются отношениями (`Relations`), которые в SQL реализуются как таблицы [Advanced SQL — Chapter 01 — Video #02](https://notebooklm.google.com/notebook/34). Каждая таблица состоит из строк (кортежей или `Tuples`) и столбцов (атрибутов или `Attributes`), причем порядок строк в таблице не определен — она представляет собой «мешок строк» (`Bag of rows`) [Advanced SQL — Chapter 01 — Video #02](https://notebooklm.google.com/notebook/34).

**Выбор и специфика типов данных PostgreSQL:**

- **Числовые:** Для целых чисел используются `INTEGER` (4 байта) и `BIGINT` (8 байт) [Advanced SQL — Chapter #03 — Video #14](https://notebooklm.google.com/notebook/2). Для финансовых расчетов строго предписано использование `NUMERIC` (`DECIMAL`), так как этот тип реализует арифметику с произвольной точностью на уровне программного обеспечения, что исключает ошибки округления [Advanced SQL — Chapter #03 — Video #14](https://notebooklm.google.com/notebook/2). Использование типов `FLOAT` или `DOUBLE PRECISION` в финансовых транзакциях запрещено: они основаны на стандарте IEEE 754 (числа с плавающей точкой), что неизбежно ведет к накоплению погрешностей при математических операциях [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebooklm.google.com/notebook/45), [Advanced SQL — Chapter #03 — Video #14](https://notebooklm.google.com/notebook/2).
- **Текстовые:** PostgreSQL поддерживает `CHAR(n)`, `VARCHAR(n)` и `TEXT`. Вопреки распространенному мифу, `TEXT` в PostgreSQL не уступает в производительности `VARCHAR`, так как внутренне они используют одинаковую структуру хранения [Advanced SQL — Chapter #03 — Video #14](https://notebooklm.google.com/notebook/2). Данные размером более 2 КБ обрабатываются механизмом `TOAST`, который выносит их в отдельные области хранения, чтобы не замедлять сканирование основной таблицы [Advanced SQL — Chapter #03 — Video #14](https://notebooklm.google.com/notebook/2).
- **Временные:** Рекомендуемым типом является `TIMESTAMP WITH TIME ZONE` (`TIMESTAMPTZ`). Он внутренне хранит время в UTC и автоматически преобразует его в часовой пояс клиента при выводе, что критически важно для корректной работы распределенных приложений [Advanced SQL — Chapter #03 — Video #15](https://notebooklm.google.com/notebook/3).
- **Идентификаторы:** Тип `UUID` обеспечивает глобальную уникальность, позволяя генерировать идентификаторы без обращения к центральной базе данных, что необходимо для микросервисной архитектуры [Advanced SQL — Chapter #03 — Video #13](https://notebooklm.google.com/notebook/1).

**Первичные ключи (Primary Key):** Первичный ключ (`PK`) — это ограничение, объединяющее свойства `UNIQUE` и `NOT NULL`, служащее для уникальной идентификации каждой строки [Шилдс Уолтер SQL.pdf](https://notebooklm.google.com/notebook/49).

- **Natural vs Surrogate:** Естественные ключи используют реально существующие атрибуты (например, VIN-код автомобиля), однако архитекторы чаще выбирают суррогатные ключи (искусственные ID), так как они гарантируют неизменность связей при изменении бизнес-данных [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebooklm.google.com/notebook/45).
- **IDENTITY:** В современном PostgreSQL для генерации ключей следует использовать синтаксис `GENERATED ALWAYS AS IDENTITY`, соответствующий стандарту SQL:2003, который обеспечивает более строгий контроль над последовательностями, чем устаревший тип `SERIAL` [Advanced SQL — Chapter #03 — Video #21](https://notebooklm.google.com/notebook/9).
- **UUID как PK:** Использование `UUID` удобно для распределенных систем, однако случайная природа `UUIDv4` может приводить к значительной фрагментации `B-Tree` индексов и снижению производительности вставок по сравнению с инкрементальными ключами [Advanced SQL — Chapter #03 — Video #13](https://notebooklm.google.com/notebook/1).

> [!warning] Актуализация синтаксиса 
> Использование типа `BIGSERIAL` считается устаревшим подходом. В новых проектах следует использовать `BIGINT GENERATED ALWAYS AS IDENTITY` для обеспечения соответствия стандарту ANSI SQL и лучшей управляемости [Advanced SQL — Chapter #03 — Video #21](https://notebooklm.google.com/notebook/9).

#### Практическая реализация и синтаксис

При проектировании схем следует учитывать выравнивание данных в памяти (`Alignment Padding`), располагая столбцы фиксированного размера (например, 8-байтовые `BIGINT` и `TIMESTAMPTZ`) в начале таблицы или группами, чтобы минимизировать расход дискового пространства [Advanced SQL — Chapter #03 — Video #14](https://notebooklm.google.com/notebook/2).

```
-- Создание таблицы пользователей с современным синтаксисом IDENTITY
CREATE TABLE users (
    -- PK с использованием IDENTITY
    user_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,

    -- Группировка 8-байтовых типов для оптимизации хранения (Alignment)
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    last_login TIMESTAMP WITH TIME ZONE,

    -- Использование TEXT вместо VARCHAR(255)
    email TEXT NOT NULL UNIQUE,
    username TEXT NOT NULL,

    -- Логический тип
    is_active BOOLEAN NOT NULL DEFAULT TRUE
);

-- Создание таблицы заказов с использованием UUID
CREATE TABLE orders (
    -- Генерация UUID на уровне БД
    order_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id BIGINT NOT NULL,

    -- Финансовый тип с защитой от отрицательных значений
    total_amount NUMERIC(15, 2) NOT NULL
        CHECK (total_amount >= 0),

    order_date DATE NOT NULL DEFAULT CURRENT_DATE,

    -- Внешний ключ (FK)
    CONSTRAINT fk_user
        FOREIGN KEY (user_id)
        REFERENCES users(user_id)
);
```

#### Глоссарий терминов

- **Relational Data Model** — модель организации данных в виде двумерных таблиц, основанная на математической теории отношений [Advanced SQL — Chapter 01 — Video #02](https://notebooklm.google.com/notebook/34).
- **Primary Key Constraint** — ограничение целостности, гарантирующее, что каждое значение в колонке уникально и не является `NULL` [Шилдс Уолтер SQL.pdf](https://notebooklm.google.com/notebook/49).
- **Surrogate Key vs Natural Key** — выбор между использованием искусственно сгенерированного идентификатора и уникального атрибута из предметной области [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebooklm.google.com/notebook/45).
- **TIMESTAMP WITH TIME ZONE (TIMESTAMPTZ)** — предпочтительный тип PostgreSQL для хранения меток времени с автоматическим учетом сдвига часовых поясов [Advanced SQL — Chapter #03 — Video #15](https://notebooklm.google.com/notebook/3).
- **PostgreSQL IDENTITY Column** — механизм автоматического приращения значений первичного ключа, соответствующий современным стандартам SQL [Advanced SQL — Chapter #03 — Video #21](https://notebooklm.google.com/notebook/9).
- **UUID (Universally Unique Identifier)** — 128-битный тип данных для создания уникальных идентификаторов в распределенных средах [Advanced SQL — Chapter #03 — Video #13](https://notebooklm.google.com/notebook/1).

#### Практический кейс: Проектирование таблицы учетных записей для highload-сервиса

Сценарий: Проектирование таблицы `accounts` для системы с сотнями миллионов записей. Для обеспечения максимальной производительности `B-Tree` индекса и экономии места в качестве первичного ключа выбирается `BIGINT IDENTITY` (8 байт), так как он компактнее `UUID` (16 байт) и обеспечивает последовательную вставку [Advanced SQL — Chapter #03 — Video #14](https://notebooklm.google.com/notebook/2). Для хранения баланса используется `NUMERIC(19, 4)`, что позволяет избежать накопления ошибок округления, характерных для `FLOAT`, и поддерживать точность до четырех знаков после запятой [Advanced SQL — Chapter #03 — Video #14](https://notebooklm.google.com/notebook/2). Все даты регистрируются в `TIMESTAMPTZ` для обеспечения единой временной шкалы в UTC для глобальных операций [Advanced SQL — Chapter #03 — Video #15](https://notebooklm.google.com/notebook/3).
