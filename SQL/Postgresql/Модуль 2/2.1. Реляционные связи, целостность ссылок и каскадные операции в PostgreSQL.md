
#### Теоретический фундамент и архитектура

В реляционной модели данные организуются через отношения между таблицами, основанные на совпадении значений ключевых полей [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/348), [Шилдс Уолтер SQL.pdf](https://notebook.google.com/notebook/827).

**Классификация типов связей:**

- **Связь «Один к одному» (`1:1`):** Редкий случай, когда одной записи в первой таблице соответствует ровно одна запись во второй. Проектируется либо путем объединения в единую широкую таблицу, либо через создание второй таблицы, где первичный ключ одновременно является внешним ключом (`FOREIGN KEY`) к первой таблице с наложенным ограничением уникальности (`UNIQUE`) [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/362), [Шилдс Уолтер SQL.pdf](https://notebook.google.com/notebook/827).
- **Связь «Один ко многим» (`1:N`):** Классический паттерн «родитель — потомок» (`parent-child`). Внешний ключ размещается на «многой» стороне (в дочерней таблице) и ссылается на первичный ключ родительской таблицы [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/372), [Вся база SQL за 1 час](https://notebook.google.com/notebook/810), [Шилдс Уолтер SQL.pdf](https://notebook.google.com/notebook/833).
- **Связь «Многие ко многим» (`N:M`):** Реализуется через промежуточную таблицу (Junction / Pivot Table). Она содержит внешние ключи на обе связываемые таблицы, которые вместе обычно формируют составной первичный ключ (`Composite Primary Key`) [Шилдс Уолтер SQL.pdf](https://notebook.google.com/notebook/835), [Шилдс Уолтер SQL.pdf](https://notebook.google.com/notebook/839).

**Обеспечение ссылочной целостности (Referential Integrity):** Внешний ключ (`FOREIGN KEY`) — это ограничение, гарантирующее, что значение в столбце соответствует существующему первичному ключу в связанной таблице [Вся база SQL за 1 час](https://notebook.google.com/notebook/809), [Шилдс Уолтер SQL.pdf](https://notebook.google.com/notebook/829). Это предотвращает появление «осиротевших» строк (`orphaned rows`) и «висячих указателей» [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/491). Проверка целостности на стороне СУБД надежнее уровня приложения, так как база данных гарантирует атомарность и защиту от некорректных данных на системном уровне [Вся база SQL за 1 час](https://notebook.google.com/notebook/812).

**Индексация внешних ключей:** PostgreSQL не создает индексы на колонки `FOREIGN KEY` автоматически [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/495). Отсутствие индексов на FK приводит к деградации производительности при удалении записей из родительской таблицы, так как СУБД вынуждена сканировать всю дочернюю таблицу (`Sequential Scan`), а также может вызывать избыточные блокировки строк, провоцируя Deadlocks в высоконагруженных системах [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/705).

**Каскадные действия (`ON DELETE` и `ON UPDATE`):**

- `NO ACTION` (по умолчанию): СУБД выдает ошибку при попытке удаления родительской строки, если есть зависимые потомки. Разница с `RESTRICT` заключается в том, что `NO ACTION` позволяет отложить проверку ограничения до конца транзакции [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/491), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/500).
- `CASCADE`: При удалении или обновлении родителя изменения автоматически распространяются на все дочерние записи. Это удобно для автоматической очистки, но несет риски случайного удаления больших объемов данных [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/502).
- `SET NULL` / `SET DEFAULT`: При удалении родителя колонки внешнего ключа в дочерних строках принимают значение `NULL` или значение по умолчанию, что позволяет сохранить исторические записи [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/490).

**Откладываемые ограничения (`DEFERRABLE`):** Механизм `DEFERRABLE INITIALLY DEFERRED` позволяет временно игнорировать проверку ограничений внутри транзакции. Это необходимо для решения проблемы циклических ссылок, когда две таблицы ссылаются друг на друга, и вставка данных в «первую» невозможна без существования «второй» [SQL. Сборник рецептов](https://notebook.google.com/notebook/794).

#### Практическая реализация и синтаксис

Создание нормализованной схемы данных с учетом выравнивания (`Alignment Padding`) и ссылочной целостности:

```
-- Таблица пользователей (Родитель)
CREATE TABLE users (
    user_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    email TEXT NOT NULL UNIQUE,
    username TEXT NOT NULL
);

-- Таблица профилей (Связь 1:1)
CREATE TABLE profiles (
    user_id BIGINT PRIMARY KEY, -- PK совпадает с FK
    bio TEXT,
    avatar_url TEXT,
    CONSTRAINT fk_profile_user FOREIGN KEY (user_id)
        REFERENCES users(user_id) ON DELETE CASCADE
);

-- Таблица заказов (Связь 1:N)
CREATE TABLE orders (
    order_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    user_id BIGINT NOT NULL,
    total_amount NUMERIC(15, 2) NOT NULL DEFAULT 0 CHECK (total_amount >= 0),
    CONSTRAINT fk_order_user FOREIGN KEY (user_id)
        REFERENCES users(user_id) ON DELETE RESTRICT
);

-- Промежуточная таблица (Связь N:M) с доп. атрибутами
CREATE TABLE order_items (
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    price_at_purchase NUMERIC(15, 2) NOT NULL,
    PRIMARY KEY (order_id, product_id), -- Составной PK
    CONSTRAINT fk_item_order FOREIGN KEY (order_id)
        REFERENCES orders(order_id) ON DELETE CASCADE,
    CONSTRAINT fk_item_product FOREIGN KEY (product_id)
        REFERENCES products(product_id) ON DELETE RESTRICT
);
```

**Пример циклической связи с отложенной проверкой:**

```
-- Использование DEFERRABLE для вставки взаимозависимых данных
ALTER TABLE users ADD COLUMN last_order_id BIGINT;

ALTER TABLE users
ADD CONSTRAINT fk_last_order FOREIGN KEY (last_order_id)
REFERENCES orders(order_id)
DEFERRABLE INITIALLY DEFERRED;
```

#### Глоссарий терминов

- **Foreign Key (FK) Constraint** — ограничение, связывающее колонку одной таблицы с первичным ключом другой для обеспечения логической связи [Шилдс Уолтер SQL.pdf](https://notebook.google.com/notebook/829), [Вся база SQL за 1 час](https://notebook.google.com/notebook/811).
- **Referential Integrity** — состояние базы данных, при котором все внешние ключи указывают на реально существующие записи [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/491), [Вся база SQL за 1 час](https://notebook.google.com/notebook/812).
- **Junction Table (Pivot Table)** — связующая таблица, используемая для реализации отношений «многие ко многим» [Шилдс Уолтер SQL.pdf](https://notebook.google.com/notebook/835).
- **Cascade Actions (ON DELETE CASCADE)** — правила автоматического изменения или удаления дочерних строк при модификации родительской записи [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/502).
- **Deferred Constraints (DEFERRABLE)** — механизм переноса проверки ограничений целостности на момент фиксации транзакции (`COMMIT`) [SQL. Сборник рецептов](https://notebook.google.com/notebook/794).
- **Unindexed Foreign Key Locking Problem** — проблема снижения производительности и возникновения дедлоков из-за отсутствия индексов на колонках внешних ключей [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/705).

#### Практический кейс: Проектирование безопасной схемы заказов и корзины товаров

При проектировании e-Commerce системы критически важно защитить историю финансовых операций. Если использовать `ON DELETE CASCADE` для связи `order_items` -> `products`, то удаление товара из каталога приведет к исчезновению информации о нем из всех старых чеков, что нарушит бухгалтерскую отчетность [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/503).

Правильное архитектурное решение:

1. Для связи `orders` -> `order_items` используем `ON DELETE CASCADE`, так как при удалении заказа позиции внутри него теряют смысл [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/502).
2. Для связи `order_items` -> `products` используем `ON DELETE RESTRICT` или `ON DELETE NO ACTION`. Это физически запретит удаление товара из базы, пока на него ссылается хотя бы один оформленный заказ [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/491).
3. Дополнительно в `order_items` денормализуются поля `price_at_purchase` и `title`, чтобы зафиксировать состояние товара на момент продажи [Шилдс Уолтер SQL.pdf](https://notebook.google.com/notebook/839).
