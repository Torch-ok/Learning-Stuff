#### Теоретический фундамент и архитектура

Работа с данными в реляционных СУБД часто требует применения теоретико-множественного подхода, где результаты нескольких запросов комбинируются в единый результирующий набор.

**Правила работы операторов множеств:** Для корректного выполнения операций объединения (`UNION`), пересечения (`INTERSECT`) и разности (`EXCEPT`) должны соблюдаться строгие правила совместимости: количество столбцов во всех объединяемых подзапросах должно быть одинаковым, а их типы данных — совместимыми (СУБД должна иметь возможность привести их к общему типу). Порядок следования колонок определяет структуру финального набора, при этом имена столбцов в результате берутся из первого запроса в цепочке.

**Разбор операторов объединения и вычитания:**

- **`UNION` vs `UNION ALL`**: Оператор `UNION ALL` является наиболее простым и быстрым, так как он просто суммирует строки всех запросов, сохраняя все дубликаты. В отличие от него, чистый `UNION` выполняет неявную операцию `DISTINCT`, что требует значительных ресурсов на сортировку или хэширование данных для выявления и удаления повторяющихся записей.
- **`INTERSECT` vs `INTERSECT ALL`**: Оператор `INTERSECT` возвращает только те строки, которые присутствуют в обоих наборах данных (пересечение множеств). Версия `INTERSECT ALL` сохраняет дубликаты в количестве, соответствующем минимальному числу вхождений строки в обоих запросах.
- **`EXCEPT` vs `EXCEPT ALL`**: Операция разности `EXCEPT` (в Oracle — `MINUS`) возвращает строки из первого запроса, которых нет во втором. `EXCEPT ALL` учитывает количество дубликатов: если строка встречается в первом наборе 3 раза, а во втором — 1 раз, в результате останется 2 вхождения.

**Тонкости фильтрации при соединении таблиц (`JOIN`):** При использовании `LEFT JOIN` существует критическая разница в размещении условий фильтрации. Условие в секции `ON` определяет, какие строки правой таблицы будут присоединены к левой; если совпадений нет, левая строка сохраняется с `NULL` значениями. Если же бизнес-условие на правую таблицу поместить в секцию `WHERE`, это фактически превратит `LEFT JOIN` в `INNER JOIN`, так как фильтр отсечет строки, где правая часть равна `NULL` из-за отсутствия связи. Для упрощения синтаксиса при соединении таблиц по колонкам с идентичными именами рекомендуется использовать псевдоним `USING (column_name)`.

#### Практическая реализация и синтаксис

Объединение активных и архивных клиентов с сохранением всех записей:

```
-- Использование UNION ALL для максимальной производительности без удаления дублей
SELECT customer_id, last_name, 'ACTIVE' as status
FROM active_customers
UNION ALL
SELECT customer_id, last_name, 'ARCHIVE' as status
FROM archive_customers;
```

.

Поиск покупателей, активных в 2025 году, но прекративших заказы в 2026 году:

```
-- Оператор EXCEPT вычитает идентификаторы клиентов 2026 года из списка 2025 года
SELECT customer_id FROM orders WHERE order_date BETWEEN '2025-01-01' AND '2025-12-31'
EXCEPT
SELECT customer_id FROM orders WHERE order_date BETWEEN '2026-01-01' AND '2026-12-31';
```

.

Сравнение логики фильтрации в `LEFT JOIN`:

```
-- Вариант 1: Условие в ON. Сохранит ВСЕХ пользователей, покажет заказы только со статусом 'NEW'
SELECT u.username, o.order_id
FROM users u
LEFT JOIN orders o ON u.user_id = o.user_id AND o.status = 'NEW';

-- Вариант 2: Условие в WHERE. Удалит пользователей без заказов или с заказами в других статусах (INNER JOIN)
SELECT u.username, o.order_id
FROM users u
LEFT JOIN orders o ON u.user_id = o.user_id
WHERE o.status = 'NEW';
```

.

#### Глоссарий терминов

- **Set Operations (`UNION`, `INTERSECT`, `EXCEPT`)** — операции обработки наборов строк как математических множеств.
- **Deduplication Overhead (`UNION` vs `UNION ALL`)** — дополнительные затраты ресурсов СУБД на поиск и удаление дубликатов при использовании `UNION`.
- **Set Difference (`EXCEPT`)** — логическая операция «вычитания», возвращающая элементы первого множества, отсутствующие во втором.
- **Set Intersection (`INTERSECT`)** — операция поиска общих элементов, присутствующих во всех объединяемых наборах.
- **Predicate Pushdown / ON vs WHERE Filtering Logic** — архитектурное различие между фильтрацией данных в момент соединения и фильтрацией уже сформированного результата.

#### Практический кейс: Консолидация данных из разрозненных филиальных таблиц

**Сценарий**: Построение единого справочника контактов из трех региональных баз данных. Для создания консолидированного отчета используется оператор `UNION`, который автоматически устраняет дубликаты клиентов, зарегистрированных в нескольких филиалах одновременно. Для оптимизации производительности в каждый подзапрос встраивается фильтрация архивных клиентов (`WHERE is_archived = FALSE`) до этапа объединения, что снижает объем данных, подвергаемых дорогостоящей операции дедупликации. Использование `ORDER BY` применяется только один раз в самом конце составного запроса для финальной сортировки справочника.

2. **Задача**: Таблица A содержит записи {1, 1, 2}, таблица B — {1}. Предскажите результат выполнения `EXCEPT` и `EXCEPT ALL` между таблицами A и B.
3. **Практика**: Исправьте запрос, который должен вывести всех сотрудников и их отделы, но из-за условия `WHERE d.name = 'IT'` скрывает сотрудников, не приписанных ни к одному отделу.
