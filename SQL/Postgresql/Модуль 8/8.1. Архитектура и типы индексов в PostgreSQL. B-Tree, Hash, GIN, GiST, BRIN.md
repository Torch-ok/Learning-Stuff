#### Теоретический фундамент и архитектура

В архитектуре PostgreSQL индексы — это вспомогательные структуры, предназначенные для повышения скорости извлечения подмножества строк без необходимости полного сканирования таблицы (`Sequential Scan`),. Вместо перебора всех данных сервер использует индекс для быстрого обнаружения физического местоположения записей, идентифицируемых через **TID (Tuple ID)** — указатель, состоящий из номера блока и порядкового номера записи внутри него,.

**Внутреннее устройство и механизмы работы основных типов индексов:**

- **`B-Tree` (Balanced Tree):** Самый распространенный тип индекса, используемый по умолчанию,. Это сбалансированное дерево, состоящее из уровней узлов: корневого (`root`), промежуточных (`internal/branch`) и листовых (`leaf`). Листья содержат значения индексируемых столбцов и соответствующие `TID`. Сервер поддерживает дерево сбалансированным при вставке и удалении данных, обеспечивая стабильную логарифмическую скорость поиска.
    - **Применение:** Поддерживает операторы сравнения ` = `, `<`, `>`, `<=`, `>=`, а также `BETWEEN`, `IN`, `IS NULL` и эффективно используется для сортировки `ORDER BY`.
- **`Hash`-индексы:** Основаны на хэш-таблице. PostgreSQL сопоставляет значение столбца с 32-битным хэш-кодом.
    - **Применение:** Поддерживают только оператор точного совпадения (` = `). В современных версиях PostgreSQL (начиная с v10) они стали отказоустойчивыми (логируются в WAL) и могут конкурировать с `B-Tree` по скорости в специфических сценариях точечного поиска.
- **`GIN` (Generalized Inverted Index):** Инвертированный индекс, идеально подходящий для составных типов данных, таких как массивы (`ANY`) и `JSONB`,. Он хранит список «терминов» (ключей или элементов), и для каждого термина — список или дерево ссылок (`Posting List` / `Posting Tree`) на строки, где этот термин встречается.
- **`GiST` (Generalized Search Tree):** Обобщенное сбалансированное дерево поиска. Оно позволяет индексировать сложные структуры (геометрию, диапазоны, полнотекстовый поиск).
    - **Применение:** Поддерживает операторы перекрытия и вхождения (`&&`, `@>`, `<@`). Позволяет реализовывать специфические правила поиска для пользовательских типов данных.
- **`BRIN` (Block Range Index):** Индекс по блочным диапазонам. Вместо хранения ссылок на каждую строку, он хранит только минимальное и максимальное значения для группы страниц (блоков) таблицы.
    - **Применение:** Идеален для очень больших таблиц (`Time-Series`), где данные физически упорядочены по индексируемому столбцу (например, дата создания лога).

**Сравнительный анализ и нагрузка:** Индексы требуют дополнительного места на диске и в оперативной памяти. Каждая операция `INSERT`, `UPDATE` или `DELETE` вызывает накладные расходы, так как СУБД должна обновлять не только таблицу, но и все связанные с ней индексы. `B-Tree` обычно требует больше места, чем компактный `BRIN`, но обеспечивает более точный поиск в неупорядоченных данных,.

#### Практическая реализация и синтаксис

Создание различных типов индексов через ключевое слово `USING`:

```
-- Стандартный B-Tree индекс
CREATE INDEX idx_orders_customer ON orders USING BTREE (customer_id);

-- Hash индекс для быстрого поиска по точному совпадению
CREATE INDEX idx_users_email_hash ON users USING HASH (email);

-- GIN индекс для поиска внутри JSONB документов
CREATE INDEX idx_products_attrs_gin ON products USING GIN (attributes);

-- GiST индекс для диапазонов дат
CREATE INDEX idx_booking_period_gist ON bookings USING GIST (stay_period);

-- BRIN индекс для огромной таблицы логов (экономия места)
CREATE INDEX idx_logs_created_at_brin ON system_logs USING BRIN (created_at);
```

,,.

Примеры сценариев, когда планировщик выбирает индекс:

1. **`B-Tree`:** `SELECT * FROM orders WHERE order_id BETWEEN 100 AND 200;`.
2. **`GIN`:** `SELECT * FROM products WHERE attributes @> '{"color": "red"}';`.
3. **`BRIN`:** `SELECT COUNT(*) FROM archives WHERE event_date > '2025-01-01';` (на таблице в 100ГБ+).

Мониторинг использования и размера индексов:

```
-- Проверка размера индекса и количества сканирований
SELECT
    indexrelname AS index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    idx_scan AS number_of_scans
FROM pg_stat_user_indexes
WHERE schemaname = 'public';
```

#### Глоссарий терминов

- **B-Tree Index Architecture** — структура в виде сбалансированного дерева, обеспечивающая поиск за время $O(\log n)$,.
- **Hash Index** — тип индекса, использующий хэш-функции для сопоставления значений ключей, эффективный только для поиска по равенству.
- **Generalized Inverted Index (GIN)** — индекс, оптимизированный для поиска элементов внутри составных значений (массивы, документы),.
- **Generalized Search Tree (GiST)** — расширяемая структура для реализации индексации произвольных типов данных.
- **Block Range Index (BRIN)** — сверхлегкий индекс, хранящий метаданные о диапазонах страниц таблицы.
- **Tuple ID (TID)** — системный идентификатор физического адреса строки в PostgreSQL (номер страницы и индекс внутри страницы).
- **Posting List / Posting Tree** — структуры внутри GIN индекса, хранящие наборы TID для каждого уникального терма.

#### Практический кейс: Выбор правильной стратегии для Time-Series

**Сценарий:** Таблица `event_logs` содержит 500 миллионов строк. Поле `created_at` всегда увеличивается (данные вставляются последовательно). **Проблема:** Обычный `B-Tree` индекс по `created_at` занимает 15 ГБ, что замедляет бэкапы и переполняет `Shared Buffers`. **Решение:** Замена на `BRIN`. Поскольку данные физически упорядочены по времени, `BRIN` хранит только Min/Max для каждых 128 страниц. **Результат:** Размер индекса сократился до 45 МБ (в ~300 раз), при этом запросы по диапазонам дат работают с сопоставимой скоростью, так как планировщик быстро отсекает ненужные блоки страниц,.

#### Вопросы и задания для самопроверки

1. **Вопрос:** Почему `BRIN` становится бесполезным, если в таблицу с логами начать вставлять старые записи «задним числом»?
    - _Ответ: Это нарушит корреляцию между физическим порядком блоков и значениями дат, расширяя Min/Max диапазоны в индексе до полной потери избирательности._
2. **Задача:** Выберите тип индекса для столбца `tags TEXT[]`, если основной запрос — `WHERE tags && ARRAY['sql', 'postgres']`.
    - _Ответ: GIN, так как он поддерживает поиск пересечений в массивах._
3. **Практика:** Используя системное представление `pg_stat_user_indexes`, найдите в вашей базе данных все индексы, где `idx_scan = 0` (неиспользуемые индексы). Объясните, почему их стоит удалить.
