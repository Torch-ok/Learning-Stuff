#### Сквозной практический кейс: Оптимизация тяжелого аналитического SQL-запроса

**Постановка задачи:** Система поиска заказов в Highload e-Commerce при фильтрации по `order_date`, `status` и `region_id` показывает деградацию производительности до 12.5 секунд при 50 млн записей.

**Пошаговый алгоритм решения:**

1. **Сбор метрик:** Запуск `EXPLAIN (ANALYZE, BUFFERS)` выявил `Seq Scan` по основной таблице и `Hash Join`, который не поместился в `work_mem` и сбросил временные данные на диск (`spill to disk`), что увеличило I/O-нагрузку.
2. **Актуализация статистики:** Выполнена команда `ANALYZE orders`, чтобы планировщик получил свежие данные о распределении значений `status` (статистика была устаревшей, что приводило к выбору неверного типа соединения).
3. **Проектирование индекса:** Создан частичный составной индекс для активных заказов с покрывающими полями для агрегации:
    
    ```
    CREATE INDEX idx_orders_active_perf ON orders (region_id, order_date)
    INCLUDE (amount, category_id)
    WHERE status = 'completed';
    ```
    
    Использование `INCLUDE` позволяет перевести запрос в режим `Index Only Scan`.
4. **Рефакторинг условий:** Исправлено условие `WHERE DATE(order_date) = '2026-01-01'`. Прямое использование функций на столбце делает индекс бесполезным. Условие переписано в SARGable-вид: `WHERE order_date >= '2026-01-01' AND order_date < '2026-01-02'`.
5. **Финальный замер:** Повторный `EXPLAIN ANALYZE` показал переход от `shared read` (диск) к `shared hit` (кэш). Время выполнения сократилось до 40 мс.

#### Комплексный контрольный тест для самопроверки

1. **Тестовый вопрос:** Какой тип индекса необходимо создать для колонки `metadata JSONB`, чтобы ускорить работу оператора вхождения `metadata @> '{"tags": ["sql"]}'`?
    - _Ответ: GIN (Generalized Inverted Index)._
2. **Анализ плана:** В выводе `EXPLAIN (BUFFERS)` вы видите `shared read=10000, shared hit=50`. О чем это говорит инженеру по производительности?
    - _Ответ: Почти все данные читаются с диска, так как они отсутствуют в Shared Buffers (кэш-промах)._
3. **Задача на проектирование:** Опишите структуру индекса для запроса `SELECT region_id, SUM(total) FROM orders WHERE status = 'shipped' GROUP BY region_id`. Как избежать посещения основной таблицы (`Heap Fetches`)?.
    - _Ответ: Частичный индекс `(region_id) INCLUDE (total) WHERE status = 'shipped'`._
4. **Практика создания:** Вам нужно создать индекс на таблице объемом 1 ТБ, которая находится под постоянной `DML` нагрузкой. Какую модификацию команды `CREATE INDEX` вы примените, чтобы не заблокировать запись в таблицу?
    - _Ответ: Модификатор `CONCURRENTLY` [Architect Standard]._
5. **Вопрос по памяти:** Какой параметр в `postgresql.conf` отвечает за объем памяти, доступный для одного узла `Hash Join` или `Sort`, и к каким последствиям в плане выполнения ведет его недостаточное значение?
    - _Ответ: Параметр `work_mem`. Недостаток ведет к `External Merge` или `Hash Batch` (сброс на диск), что видно в EXPLAIN ANALYZE [Architect Standard]._
