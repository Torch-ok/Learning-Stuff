#### Теоретический фундамент и архитектура

В архитектуре PostgreSQL выбор наиболее эффективного пути к данным возложен на **Оптимизатор** (`Optimizer`). На основе накопленной статистики о распределении данных в таблицах он строит **План выполнения** (`Execution Plan`) — иерархическую структуру узлов, каждый из которых представляет конкретную операцию над данными.

**Инструменты анализа планов:**

- **Команда `EXPLAIN`**: Позволяет увидеть расчетный план выполнения без фактического запуска запроса. Она отображает стоимостные оценки (`cost`), ожидаемое количество строк (`rows`) и среднюю ширину строки в байтах (`width`).
- **Модификатор `ANALYZE`**: Заставляет сервер выполнить запрос, что позволяет сравнить планируемые показатели с фактическим временем выполнения (`actual time`) и реальным количеством строк.
- **Модификатор `BUFFERS`**: Предоставляет критически важную метрику для оптимизации I/O — количество страниц, прочитанных из кэша (`shared hit`) и с диска (`shared read`).
- **Стоимостная оценка (`Cost`)**: Математическая абстракция, где `startup_cost` — затраты до получения первой строки, а `total_cost` — полная стоимость узла.

**Методы доступа к данным (Access Methods):**

1. **`Seq Scan` (Последовательное сканирование)**: Сервер проверяет каждую строку таблицы одну за другой. Этот метод неизбежен, если условие фильтрации не проиндексировано или если таблица настолько мала, что чтение индекса будет дороже.
2. **`Index Scan`**: Использование индекса для поиска `TID` (идентификаторов строк) с последующим обращением к основной таблице (`Heap`) за остальными данными.
3. **`Index Only Scan`**: Самый быстрый метод, при котором все данные извлекаются напрямую из листовых страниц индекса без обращения к таблице.
4. **`Bitmap Index Scan` + `Bitmap Heap Scan`**: Промежуточный метод. Сначала индекс сканируется для создания битовой карты страниц, содержащих нужные данные, затем эти страницы читаются из таблицы в физическом порядке, что оптимизирует дисковое чтение.

**Алгоритмы соединения таблиц (Join Operators):**

- **`Nested Loop`**: Для каждой строки из внешней таблицы ищется соответствие во внутренней. Идеален при наличии индексов и небольших наборов данных.
- **`Hash Join`**: Создает хэш-таблицу в памяти (`work_mem`) для одной из таблиц и один раз сканирует вторую.
- **`Merge Join`**: Эффективен для предварительно отсортированных наборов или при использовании `B-Tree` индексов.

#### Практическая реализация и синтаксис

Команда полного профилирования запроса в PostgreSQL:

```
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, FORMAT TEXT)
SELECT c.fed_id, a.account_id
FROM account a
INNER JOIN customer c ON a.cust_id = c.cust_id
WHERE c.cust_type_cd = 'I';
```


Разбор плана с пакетным сканированием (`Bitmap Scan`):

```
Bitmap Heap Scan on invoices  (cost=12.33..45.10 rows=100 width=32) (actual time=0.045..0.120 rows=111 loops=1)
  Recheck Cond: (total = 1.98)
  Rows Removed by Filter: 0
  Buffers: shared hit=42 read=5
  ->  Bitmap Index Scan on idx_total  (cost=0.00..4.10 rows=100 width=0) (actual time=0.020..0.020 rows=111 loops=1)
        Index Cond: (total = 1.98)
```


- `Rows Removed by Filter`: Количество строк, которые были прочитаны с диска, но отсеяны после проверки условий (сигнал о неэффективном индексе).
- `shared hit=42`: Данные найдены в оперативной памяти (Shared Buffers).
- `shared read=5`: Выполнено 5 операций чтения страниц с диска.

Устранение `Seq Scan` через индексацию: Если план показывает `type: ALL` (или `Seq Scan` в PG):

```
-- Выявление медленного сканирования
EXPLAIN ANALYZE SELECT * FROM department WHERE name LIKE 'A%'; -- Показывает Seq Scan

-- Оптимизация
CREATE INDEX dept_name_idx ON department (name); --

-- Повторная проверка
EXPLAIN ANALYZE SELECT * FROM department WHERE name LIKE 'A%'; -- Теперь Index Scan
```

#### Глоссарий терминов

- **Execution Plan Cost** — оценочная стоимость выполнения узла запроса, рассчитанная планировщиком на основе статистики.
- **EXPLAIN (ANALYZE, BUFFERS)** — расширенная команда профилирования, предоставляющая данные о реальном времени и использовании памяти.
- **Sequential Scan (Seq Scan)** — полный перебор всех строк таблицы в физическом порядке их расположения в файле.
- **Index Scan vs Index Only Scan** — различие между поиском через индекс с походом в таблицу и полным получением данных из самого индекса.
- **Bitmap Index / Heap Scan** — двухэтапный метод доступа, минимизирующий хаотичное чтение диска за счет сортировки TID.
- **Join Algorithms** — методы физического сопоставления строк двух таблиц (циклы, хэширование или слияние).
- **Buffer Usage Metrics** — показатели эффективности использования системного кэша PostgreSQL (`Shared Buffers`).

#### Практический кейс: Диагностика Shared Buffers

В финансовом отчете по транзакциям за месяц наблюдалось замедление. Анализ `EXPLAIN (ANALYZE, BUFFERS)` выявил высокий показатель `shared read` (тысячи страниц). Это означало, что сервер каждый раз вытеснял данные из памяти и читал их с диска. **Решение**: Был создан составной индекс `(customer_id, transaction_date) INCLUDE (amount)`, что позволило переключить запрос в режим `Index Only Scan`. После оптимизации план показал `shared hit` для всех запрашиваемых страниц, а время выполнения сократилось с 2 секунд до 15 мс, так как индекс полностью поместился в `Shared Buffers`.

#### Вопросы и задания для самопроверки

1. **Вопрос**: Почему планировщик может выбрать `Seq Scan` для таблицы из 50 строк, даже если есть подходящий индекс?.
    - _Ответ: Накладные расходы на чтение страниц индекса и последующие переходы к Heap превышают стоимость простого последовательного чтения всех страниц маленькой таблицы._
2. **Задача**: В плане запроса узел `Hash Join` имеет `actual time=1.2..45.5`, а его дочерний узел `Seq Scan` — `actual time=0.1..1.1`. Какой узел является узким местом? Подсчитайте объем данных в КБ, если `shared hit=100`, а размер страницы — 8 КБ.
3. **Практика**: Найдите в логах `Slow Queries` запрос с большим значением `Rows Removed by Filter`. Предложите структуру индекса, которая позволит перенести этот фильтр в `Index Cond`.
