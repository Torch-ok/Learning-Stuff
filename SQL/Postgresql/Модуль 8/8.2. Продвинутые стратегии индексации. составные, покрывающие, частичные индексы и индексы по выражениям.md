#### Теоретический фундамент и архитектура

В высоконагруженных системах стандартных одноколоночных индексов часто недостаточно для достижения целевой производительности. Архитектор БД должен использовать комбинированные структуры, минимизирующие количество чтений с диска (`I/O`) и обращений к основной таблице (`Heap`).

**Составные (Composite) индексы:** Составной индекс — это `B-Tree` структура, построенная по нескольким столбцам одновременно.

- **Правило левого префикса (Left-Prefix Rule):** Порядок колонок имеет решающее значение. Индекс по `(A, B, C)` может быть эффективно использован для поиска по `(A)`, `(A, B)` или `(A, B, C)`, но практически бесполезен для поиска только по `(B)` или `(C)`. Это сравнимо с телефонной книгой: если данные отсортированы по фамилии, а затем по имени, вы не сможете быстро найти человека, зная только имя.
- **Селективность:** Первыми в индексе следует располагать колонки с наиболее высокой селективностью (уникальностью), чтобы планировщик мог максимально быстро отсечь ненужные ветви дерева.

**Покрывающие (Covering) индексы и предложение `INCLUDE`:** Концепция покрывающего индекса заключается в том, что индекс содержит **все** данные, необходимые для выполнения запроса.

- **Index Only Scan:** Если все запрашиваемые поля (`SELECT`) и поля фильтрации (`WHERE`) присутствуют в индексе, PostgreSQL выполняет `Index Only Scan`, не обращаясь к страницам таблицы (`Heap`), что кратно ускоряет выполнение.
- **Предложение `INCLUDE`:** Позволяет добавлять «полезную нагрузку» (payload) в листовые страницы индекса. В отличие от ключевых колонок, данные в `INCLUDE` не участвуют в сортировке и поиске, но доступны для чтения, что уменьшает размер индекса по сравнению с обычным составным индексом.
- **Карта Видимости (Visibility Map):** PostgreSQL проверяет `Visibility Map`, чтобы убедиться, что данные в индексе актуальны и не требуют проверки `MVCC` в `Heap`. Если таблица сильно засорена (`Bloat`), эффективность `Index Only Scan` падает из-за необходимости «прыжков» в таблицу.

**Частичные (Partial) индексы:** Индексы, созданные с предикатом `WHERE`. Они индексируют только подмножество строк таблицы.

- Это позволяет значительно экономить дисковое пространство и ускорять `INSERT`, если нас интересуют только специфические записи (например, только `status = 'active'`).

**Индексы по выражениям (Expression Indexes):** PostgreSQL позволяет индексировать результат вычисления функции над столбцом. Это незаменимо для регистронезависимого поиска или сложных расчетов.

#### Практическая реализация и синтаксис

Создание составного индекса и логика его использования:

```
-- Создание индекса по фамилии и имени
CREATE INDEX idx_emp_full_name ON employee (lname, fname);

-- Эффективное использование (левый префикс)
SELECT * FROM employee WHERE lname = 'Smith';
SELECT * FROM employee WHERE lname = 'Smith' AND fname = 'John';

-- Индекс НЕ будет использован эффективно (пропуск префикса)
SELECT * FROM employee WHERE fname = 'John';
```

Реализация покрывающего индекса для ускорения авторизации:
```sql
-- Добавляем username и email в INCLUDE для Index Only Scan
CREATE INDEX idx_users_auth ON users (user_id)
INCLUDE (username, email);

-- План запроса покажет Index Only Scan, так как данные возьмутся из индекса
EXPLAIN ANALYZE
SELECT username, email FROM users WHERE user_id = 42;
```

Создание частичного индекса и индекса по выражению:
```sql
-- Индексируем только необработанные заказы (Partial Index)
CREATE INDEX idx_orders_pending ON orders (created_at)
WHERE status = 'new';

-- Индекс для регистронезависимого поиска (Expression Index)
CREATE INDEX idx_user_email_lwr ON users (LOWER(email));
```

Безопасное создание индекса в `Production` среде:
```sql
-- Создание без блокировки таблицы на запись (Exclusive Lock)
CREATE INDEX CONCURRENTLY idx_huge_table_val ON huge_table (value);
```

#### Глоссарий терминов
* **Composite Index (Left-Prefix Rule)** — структура, требующая соблюдения порядка столбцов в запросе для эффективного поиска.
* **Covering Index & INCLUDE Clause** — индекс, содержащий дополнительные неключевые поля для предотвращения обращений к основной таблице.
* **Index Only Scan Mechanism** — режим выполнения запроса, при котором все данные извлекаются напрямую из индексных страниц.
* **Partial Indexing** — создание индекса по условию для оптимизации работы с подмножествами данных.
* **Expression / Functional Index** — индексация вычисляемых значений, например, приведенных к нижнему регистру строк.
* **Concurrent Index Creation (CONCURRENTLY)** — метод построения индекса в PostgreSQL, не блокирующий параллельные `DML` операции.
* **Visibility Map Interplay** — зависимость производительности индексного сканирования от актуальности карты видимости страниц.

#### Практический кейс: Оптимизация поиска пользователей

**Задача:** Обеспечить уникальность `email` без учета регистра и мгновенную авторизацию по `user_id`.
**Решение:**
1. Создаем уникальный индекс по выражению: `CREATE UNIQUE INDEX idx_user_email_unique ON users (LOWER(email))`. Это гарантирует, что `User@example.com` и `user@example.com` будут считаться дубликатами.
2. Для ускорения сессий создаем покрывающий индекс по `user_id` с включением профильных данных: `CREATE INDEX idx_user_session ON users (user_id) INCLUDE (username, role_id)`. В итоге при проверке сессии PostgreSQL выполнит `Index Only Scan`, что в 3-5 раз быстрее обычного поиска в нагруженной системе.

#### Вопросы и задания для самопроверки
1. **Вопрос:** Почему при наличии индекса `(a, b)` запрос `WHERE b = 1` выполнит `Seq Scan`, а запрос `WHERE a = 1 AND b = 1` — `Index Scan`?.
    * *Ответ: Нарушается правило левого префикса; без колонки 'a' дерево индекса не может быть эффективно пройдено.*
2. **Задача:** Спроектируйте частичный индекс для таблицы `tasks`, если поиск всегда идет по `is_completed = false`, а таких строк всего 1% от общего объема.
3. **Практика:** Выполните `EXPLAIN` запроса до и после добавления колонки в `INCLUDE`. Опишите изменение в графе `Extra` (или типе сканирования).
