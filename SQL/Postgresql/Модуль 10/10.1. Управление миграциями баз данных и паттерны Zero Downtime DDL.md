#### Теоретический фундамент и архитектура

В жизненном цикле высоконагруженного приложения база данных постоянно эволюционирует. Управление этими изменениями осуществляется через **миграции** — версионированные SQL-скрипты или программный код, переводящие схему БД из одного согласованного состояния в другое [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/12).

**Концепция эволюции схемы БД:**

- **Императивный подход:** Инженер описывает конкретные шаги изменения (например, `ALTER TABLE ... ADD COLUMN`). Большинство современных инструментов используют этот подход.
- **Декларативный подход:** Описывается желаемое финальное состояние (State), а инструмент (например, `Alembic` или `Alembic` в связке с `SQLAlchemy 2.0`) автоматически генерирует инструкции для достижения этого состояния (информация об инструментах Alembic/Goose и их специфике является внешней по отношению к предоставленным источникам).
- **Версионирование:** Каждая миграция имеет две функции: `up` (применение изменений) и `down` (откат в случае ошибки) [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/12).

**Проблема блокировок при DDL:** Операции изменения схемы (`DDL`) в PostgreSQL, такие как `ALTER TABLE`, требуют захвата блокировки самого высокого уровня — `ACCESS EXCLUSIVE LOCK` [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/232).

- Эта блокировка полностью запрещает любой доступ к таблице, включая `SELECT`, `INSERT`, `UPDATE` и `DELETE` [Alan_Beaulieu-Learning_SQL-RU.pdf](231, 232).
- В высоконагруженных системах длительное удержание такой блокировки приводит к накоплению очереди ожидающих транзакций, что может вызвать каскадный отказ приложения или `Deadlock` [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/235).

**Паттерны Zero Downtime DDL (Внешняя информация):** Для работы в `Production` 2026 года используются методы, исключающие долгие блокировки:

- **Безопасное добавление полей:** В актуальных версиях PostgreSQL добавление колонки с `DEFAULT NULL` происходит мгновенно (изменяются только метаданные в системном каталоге).
- **`NOT VALID` констрейнты:** Добавление ограничений `CHECK` или `NOT NULL` выполняется в два этапа. Сначала ограничение добавляется как `NOT VALID` (проверяется только для новых данных), затем выполняется `VALIDATE CONSTRAINT` (проверка существующих данных в фоновом режиме без блокировки на запись).
- **Индексация:** Использование `CREATE INDEX CONCURRENTLY` позволяет строить индекс, не блокируя `DML`-операции [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/240).

#### Практическая реализация и синтаксис

**Пример скрипта миграции (на базе логики Goose/Alembic, внешняя реализация):**

```
-- +goose Up
ALTER TABLE orders ADD COLUMN discount_code VARCHAR(20);

-- +goose Down
ALTER TABLE orders DROP COLUMN discount_code;
```

**Безопасное добавление NOT NULL (3 шага):**
*(Внимание: синтаксис NOT VALID требует проверки версии PostgreSQL; информация базируется на архитектурных стандартах 2026 года, выходящих за рамки базовых источников).*
1. Добавление колонки (без `NOT NULL`).
2. Установка констрейнта как `NOT VALID` (не блокирует таблицу надолго).
3. Валидация констрейнта фоновым процессом.

```sql
-- Шаг 1: Добавляем колонку
ALTER TABLE accounts ADD COLUMN status_code VARCHAR(10);

-- Шаг 2: Добавляем ограничение без проверки старых данных (мгновенно)
ALTER TABLE accounts ADD CONSTRAINT status_check
CHECK (status_code IS NOT NULL) NOT VALID;

-- Шаг 3: Проверяем данные без эксклюзивной блокировки
ALTER TABLE accounts VALIDATE CONSTRAINT status_check;
```

**Переименование колонки (Expand-Contract Pattern):**
Применяется, когда нельзя остановить API, которое всё ещё обращается к старому имени поля [Alan_Beaulieu-Learning_SQL-RU.pdf](230).
1.  **Expand:** Добавляем новую колонку `new_name`.
2.  **Parallel Writes:** Настраиваем триггер [Alan_Beaulieu-Learning_SQL-RU.pdf](141) или логику приложения для записи данных в оба поля.
3.  **Backfill:** Копируем старые данные в новые `UPDATE accounts SET new_name = old_name`.
4.  **Contract:** API переходит на `new_name`, старая колонка удаляется `ALTER TABLE ... DROP COLUMN` [Alan_Beaulieu-Learning_SQL-RU.pdf](110, 111).

#### Глоссарий терминов
* **Database Migrations** — процесс управления версиями схемы БД с возможностью прямого (`up`) и обратного (`down`) применения изменений.
* **Zero Downtime DDL** — набор техник изменения структуры БД, не приводящих к остановке обслуживания пользователей.
* **Expand-Contract Pattern** — стратегия обновления схемы, включающая временное сосуществование старой и новой структур для обеспечения обратной совместимости.
* **ACCESS EXCLUSIVE LOCK** — режим блокировки PostgreSQL, полностью закрывающий таблицу для любых операций на время выполнения DDL [Alan_Beaulieu-Learning_SQL-RU.pdf](232).
* **Concurrent Index Creation** — создание индекса в фоновом режиме без блокировки записи в таблицу [Alan_Beaulieu-Learning_SQL-RU.pdf](240).
* **Unvalidated Constraints** — ограничения, добавленные с флагом `NOT VALID`, позволяющие избежать сканирования всей таблицы под эксклюзивной блокировкой.
* **`pg_repack` Utility** — (внешний инструмент) расширение PostgreSQL для переупаковки таблиц и индексов без длительных блокировок, альтернатива `VACUUM FULL`.

#### Практический кейс: Миграция таблицы на 100M+ строк

**Сценарий:** Необходимо изменить тип данных ключевой колонки `order_id` с `INT` на `BIGINT` в таблице заказов под нагрузкой 5000 RPS. Прямой `ALTER TABLE ... TYPE` заблокирует таблицу на несколько часов для полной перезаписи данных [Alan_Beaulieu-Learning_SQL-RU.pdf](232).
**Решение:**
1.  Создается новая колонка `order_id_bigint` [Alan_Beaulieu-Learning_SQL-RU.pdf](110).
2.  Создается `BEFORE INSERT OR UPDATE` триггер [Alan_Beaulieu-Learning_SQL-RU.pdf](141), который копирует значения из `order_id` в `order_id_bigint` для всех новых и изменяемых строк.
3.  Запускается фоновый процесс ("Backfill"), который пачками по 5000 строк переносит старые данные `UPDATE orders SET order_id_bigint = order_id WHERE ...`, используя `COMMIT` после каждой пачки для снятия блокировок [Alan_Beaulieu-Learning_SQL-RU.pdf](233).
4.  Строится индекс по новой колонке через `CREATE INDEX CONCURRENTLY` [Alan_Beaulieu-Learning_SQL-RU.pdf](240).
5.  В момент минимальной нагрузки (Maintenance window) происходит финальное переименование колонок внутри короткой транзакции [Alan_Beaulieu-Learning_SQL-RU.pdf](232).

#### Вопросы и задания для самопроверки
1. **Вопрос:** Почему в PostgreSQL до версии 11 выполнение `ADD COLUMN DEFAULT 0` приводило к долгому простою на больших таблицах?.
    *   *Ответ: СУБД была вынуждена физически перезаписывать каждую строку таблицы, проставляя значение по умолчанию. В новых версиях значение по умолчанию хранится в системном каталоге и подставляется только при чтении.*
