#### Теоретический фундамент и архитектура

В архитектуре PostgreSQL эффективная эксплуатация требует понимания механизмов хранения и механизмов обеспечения отказоустойчивости. В отличие от СУБД, обновляющих данные «поверх» существующих, PostgreSQL использует модель **MVCC** (Multi-Version Concurrency Control) [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/231).

**Мультиверсионность (MVCC) и Bloat:**

- **Dead Tuples:** При выполнении `UPDATE` PostgreSQL не меняет строку на месте, а создает новую версию, помечая старую как удаленную. При `DELETE` строка также физически остается на диске, но помечается как «мертвая» [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/78).
- **Bloat (Разрастание):** Если старые версии строк не вычищаются вовремя, файлы таблиц и индексов начинают неконтролируемо расти, что приводит к деградации `I/O` и неэффективному использованию `Shared Buffers`.

**Механизм очистки (VACUUM):**

- **`VACUUM` (Standard):** Проходит по таблице, находит `Dead Tuples` и помечает место, которое они занимали, как свободное для повторного использования будущими `INSERT` или `UPDATE`. Этот процесс не блокирует чтение или запись и обновляет **Visibility Map**, что критично для эффективности `Index Only Scan`.
- **`VACUUM FULL`:** Полностью пересобирает таблицу, сжимая данные на диске и возвращая место операционной системе. Требует захвата `ACCESS EXCLUSIVE LOCK`, полностью блокируя любой доступ к таблице на время операции [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/232).

**Autovacuum и сбор статистики:**

- **Autovacuum Daemon:** Фоновый процесс, который автоматически запускает `VACUUM` и `ANALYZE`. Настройка параметров `autovacuum_vacuum_scale_factor` (процент измененных строк) и `autovacuum_vacuum_threshold` (фиксированное количество изменений) определяет частоту очистки.
- **ANALYZE:** Собирает статистику о распределении данных в столбцах. Это критически важно для **Optimizer**, чтобы он мог строить эффективные планы выполнения [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/17), [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/123).

**Репликация в PostgreSQL:**

1. **Physical Streaming Replication:** Передача байтовых изменений `WAL` (Write-Ahead Log) от `Primary` к `Standby`. Это обеспечивает идентичность узлов на физическом уровне и используется для высокой доступности (High Availability).
2. **Logical Replication:** Пересылка изменений конкретных строк на основе концепции **Publication** (издатель) и **Subscription** (подписчик). Позволяет реплицировать только выбранные таблицы и выполнять миграции между разными мажорными версиями PostgreSQL.

#### Практическая реализация и синтаксис

Диагностика состояния очистки через системные представления:

```
-- Поиск таблиц с наибольшим количеством "мертвых" строк
SELECT
    relname AS table_name,
    n_dead_tup,
    n_live_tup,
    last_autovacuum,
    last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

Команды резервного копирования (CLI):
```bash
# Логический бэкап в сжатом кастомном формате
pg_dump -Fc -h localhost -U user dbname > db_backup.dump

# Параллельное восстановление (в 4 потока)
pg_restore -j 4 -d dbname_new db_backup.dump

# Снятие физической копии (Base Backup)
pg_basebackup -h primary_host -D /var/lib/postgresql/data -P -R -X stream
```.

Настройка логической репликации:
```sql
-- На стороне Primary (Издатель)
CREATE PUBLICATION sales_pub FOR TABLE orders, order_items;

-- На стороне Standby (Подписчик)
CREATE SUBSCRIPTION sales_sub
CONNECTION 'host=primary_ip dbname=prod_db user=rep_user password=pass'
PUBLICATION sales_pub;
```

#### Глоссарий терминов
* **MVCC & Dead Tuples** — механизм контроля версий, при котором старые данные физически остаются в таблице до очистки [Alan_Beaulieu-Learning_SQL-RU.pdf](231).
* **Table / Index Bloat** — неэффективное использование дискового пространства из-за накопления мертвых строк и пустых страниц.
* **Autovacuum Daemon Tuning** — процесс конфигурации автоматической очистки для предотвращения деградации производительности.
* **Physical Streaming Replication** — потоковая передача WAL-логов для поддержки горячего резерва БД.
* **Logical Replication** — технология передачи данных на уровне транзакций строк, поддерживающая кросс-версионность.
* **Logical Backup (pg_dump)** — создание резервной копии в виде набора SQL-команд или бинарного архива [Alan_Beaulieu-Learning_SQL-RU.pdf](15).
* **Point-in-Time Recovery (PITR)** — технология восстановления БД на конкретный момент времени с использованием архивированных WAL.

#### Практический кейс: Disaster Recovery (PITR)
**Сценарий:** База данных e-Commerce объемом 1 ТБ подверглась атаке («вымогатель» удалил данные в 14:05:10). Необходимо восстановиться с минимальной потерей данных.
**Решение:**
1.  Используется последний еженедельный физический бэкап, снятый через `pg_basebackup`.
2.  Настраивается непрерывное архивирование `WAL` в удаленное хранилище (например, S3 через `pgBackRest`).
3.  Запускается процедура восстановления с параметром `recovery_target_time = '2026-08-03 14:05:00'`.
**Результат:** База восстанавливается за 10 секунд до инцидента. **RPO** (Recovery Point Objective) составляет менее 16 МБ (один сегмент WAL),.

#### Вопросы и задания для самопроверки
1. **Вопрос:** В чем ключевое преимущество логической репликации перед физической при обновлении PostgreSQL с версии 15 на версию 17?
    *   *Ответ: Логическая репликация не зависит от бинарного формата файлов, что позволяет передавать данные между разными версиями СУБД без простоя.*
2. **Задача:** Рассчитайте, при каком количестве изменений сработает `autovacuum` для таблицы в 10 млн строк, если `autovacuum_vacuum_scale_factor = 0.05`, а `threshold = 50`.
    *   *Ответ: (10,000,000 * 0.05) + 50 = 500,050 строк.*
3. **Практика:** Напишите bash-скрипт, который выполняет `pg_dump`, архивирует его через `gzip` и удаляет бэкапы старше 7 дней с помощью команды `find`.
