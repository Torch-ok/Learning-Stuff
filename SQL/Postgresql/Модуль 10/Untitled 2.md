#### Теоретический фундамент и архитектура

В архитектуре PostgreSQL каждое новое подключение инициирует создание отдельного серверного процесса (`backend process`) через системный вызов `fork()` процессом-менеджером `postmaster`,. Это фундаментально отличает PostgreSQL от СУБД, использующих потоки (`threads`), и накладывает существенные накладные расходы на ресурсы сервера.

**Архитектура процессов и накладные расходы:**

- **Fork Costs:** При создании соединения сервер выделяет память под стек процесса и локальные буферы (например, `work_mem`),. В высоконагруженных системах постоянное открытие/закрытие соединений («дребезг») создает критическую нагрузку на CPU и задержки (latency).
- **max_connections:** Этот параметр в `postgresql.conf` определяет жесткий лимит соединений. Однако его нельзя увеличивать бесконечно: большое количество активных процессов приводит к деградации производительности из-за переключений контекста CPU и конкуренции за `Shared Buffers` и блокировки,.
- **Connection Pooling (Пул соединений):** Стратегия, при которой открытые соединения не закрываются, а сохраняются в «бассейне» (pool) для повторного использования последующими запросами.

**Режимы работы прокси-слоя (PgBouncer):** _(Примечание: Подробная классификация режимов PgBouncer является архитектурным стандартом 2026 года и дополняет базовые сведения источников о жизненном цикле соединений,)_:

1. **Session Pooling:** Соединение закрепляется за клиентом на все время его сессии (от `login` до `logout`). Аналогично прямому подключению к БД.
2. **Transaction Pooling:** (Рекомендуемый для OLTP). Соединение возвращается в пул сразу после завершения транзакции (`COMMIT`/`ROLLBACK`). Это позволяет обслуживать тысячи клиентов через десятки реальных соединений с БД.
3. **Statement Pooling:** Соединение освобождается после каждого SQL-оператора. Несовместимо с многошаговыми транзакциями.

> [!warning] Актуализация синтаксиса В режиме `Transaction Pooling` нельзя использовать `PREPARED STATEMENTS` (без специальной настройки драйвера), временные таблицы и `LISTEN/NOTIFY`, так как эти объекты привязаны к конкретному серверному процессу, который может быть отдан другому клиенту между транзакциями.

#### Практическая реализация и синтаксис

Ниже приведены примеры конфигурации и кода, соответствующие индустриальным стандартам 2026 года (информация дополняет общие принципы программирования БД из источников,).

**Настройка PgBouncer (`pgbouncer.ini`):**

```
[databases]
; Настройка связи с реальной БД
ecommerce_db = host=127.0.0.1 port=5432 dbname=orders_prod

[pgbouncer]
listen_port = 6432
listen_addr = *
auth_type = md5
auth_file = /etc/pgbouncer/userlist.txt
; Ключевой параметр оптимизации
pool_mode = transaction
max_client_conn = 10000
default_pool_size = 100
```

**Использование асинхронного пула в Python (`asyncpg`):**

```
import asyncpg
import asyncio

async def run():
    # Создание пула на уровне драйвера приложения
    pool = await asyncpg.create_pool(
        dsn='postgres://user:pass@localhost:6432/ecommerce_db',
        min_size=10,
        max_size=20
    )

    async with pool.acquire() as connection:
        # Выполнение запроса внутри транзакции
        async with connection.transaction():
            result = await connection.fetch("SELECT * FROM products LIMIT 5")
            print(result)

    await pool.close()

asyncio.run(run())
```

**Конфигурация пула в SQLAlchemy 2.0:**

```
from sqlalchemy import create_engine

engine = create_engine(
    "postgresql+psycopg3://user:pass@localhost:6432/ecommerce_db",
    pool_size=10,             # Базовое количество соединений
    max_overflow=20,          # Допустимый всплеск сверх лимита
    pool_recycle=3600,        # Сброс соединений каждый час
    pool_pre_ping=True        # Проверка "живости" перед использованием
)
```

#### Глоссарий терминов

- **Backend Process Overhead** — затраты системных ресурсов (RAM/CPU) на порождение и обслуживание одного рабочего процесса PostgreSQL,.
- **Connection Pooling Architecture** — прослойка между приложением и БД для переиспользования установленных соединений.
- **PgBouncer Proxy** — легковесный менеджер пула соединений, минимизирующий нагрузку на ядро PostgreSQL.
- **Session vs Transaction Pooling** — выбор между длительным удержанием соединения за клиентом и агрессивным переиспользованием после каждого `COMMIT`.
- **Client-side Pool** — механизм управления соединениями внутри кода приложения (например, через `SQLAlchemy`),.
- **Prepared Statements Incompatibility** — ограничение режима `transaction pooling`, требующее особого внимания к стейтменту на уровне сессии.
- **Connection Pool Exhaustion** — критическое состояние, при котором все слоты пула заняты, и новые запросы встают в очередь (Queue).

#### Практический кейс: Защита СУБД от всплеска трафика

**Сценарий:** API-сервис маркетплейса столкнулся с наплывом 10 000 параллельных клиентов во время распродажи. Прямое увеличение `max_connections` до 10 000 привело к 100% утилизации CPU из-за context switching. **Решение:**

1. Внедрен `PgBouncer` перед PostgreSQL.
2. Установлен режим `pool_mode = transaction`.
3. Лимит реальных `backend` процессов в БД ограничен 100. **Результат:** Количество активных процессов в `pg_stat_activity` снизилось с 5000 до 100. Утилизация CPU упала с 100% до 25% за счет устранения накладных расходов на `fork()` и конкуренции процессов, при этом все 10 000 клиентов обслуживались с минимальной задержкой.

#### Вопросы и задания для самопроверки

1. **Вопрос:** Почему большое значение `max_connections` (например, 5000) вредно для производительности даже при наличии свободного объема RAM?,.
    - _Ответ: Основная проблема в CPU — ядро тратит больше времени на переключение между 5000 процессами, чем на полезные вычисления, плюс растет вероятность блокировок управляющих структур (LWLocks)._
2. **Задача:** Вы строите микросервис на `Go` с драйвером `Pgx`. Какой режим пулинга в `PgBouncer` вы выберете, если сервис использует `TEMPORARY TABLE` для промежуточных расчетов?.
    - _Ответ: Session Pooling, так как временные таблицы существуют только в рамках конкретного серверного процесса/сессии._
3. **Практика:** Настройте в `SQLAlchemy` параметр `pool_pre_ping`. Объясните, как он помогает избежать ошибок типа `Connection lost` при перезапуске PgBouncer.
