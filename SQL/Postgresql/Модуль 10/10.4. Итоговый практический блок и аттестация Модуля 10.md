#### Сквозной практический кейс: Проектирование и развертывание отказоустойчивого production-стенда

**Постановка задачи:** Развернуть инфраструктуру для высоконагруженного финансового API на базе PostgreSQL 16/17 с пулером соединений и системой миграций.

**Пошаговый алгоритм решения:**

1. **Создание манифеста `docker-compose.yml`:** Декларируем сервисы с разделением данных на `volumes` для персистентности:
    
    ````
    services:
      db:
        image: postgres:16-alpine
        volumes:
          - pg_data:/var/lib/postgresql/data
        environment:
          POSTGRES_PASSWORD: secret_pass
      pgbouncer:
        image: edoburu/pgbouncer
        ports:
          - "6432:6432"
        environment:
          DATABASE_URL: "postgres://user:pass@db:5432/finance_db"
          POOL_MODE: transaction
    ```.
    ````
    
2. **Конфигурация PgBouncer:** Файл `pgbouncer.ini` настраивает лимиты: `default_pool_size = 50`, `max_client_conn = 10000`. Режим `pool_mode = transaction` критичен для экономии CPU при 5000+ RPS,.
3. **Инициализация схемы:** Создаем базовые таблицы в 3NF с индексами: `CREATE TABLE transactions (...)` и `CREATE INDEX CONCURRENTLY` для предотвращения блокировок `DML` [Alan_Beaulieu-Learning_SQL-RU.pdf](9, 240).
4. **Реализация миграции (Alembic-style):** Для добавления колонки `balance_snapshot` используем паттерн безопасного наката:
    
    ```
    -- Up
    ALTER TABLE accounts ADD COLUMN balance_snapshot NUMERIC;
    -- Down
    ALTER TABLE accounts DROP COLUMN balance_snapshot;
    ```
    
    [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/110).
5. **Нагрузочное тестирование:** Запуск `pgbench -c 100 -j 10 -t 10000 -p 6432` для проверки стабильности пула при сотнях параллельных клиентов.
