#### Теоретический фундамент и архитектура

В архитектуре PostgreSQL серверный код позволяет перенести бизнес-логику максимально близко к данным, минимизируя сетевые задержки и обеспечивая атомарность сложных операций,. Основным языком для этого является `PL/pgSQL`, который расширяет стандартный SQL управляющими конструкциями, переменными и обработкой ошибок.

**Структура блока PL/pgSQL:** Программный блок состоит из необязательной секции объявления переменных `DECLARE` и обязательного исполнительного блока `BEGIN...END`. В отличие от чистых `SQL` функций, тело которых представляет собой набор команд, обернутых в строки, блоки `PL/pgSQL` позволяют использовать полноценное процедурное программирование,.

**Различия между хранимыми функциями и процедурами:**

- **Хранимые функции (`CREATE FUNCTION`):** Всегда возвращают значение (скалярное, `TABLE` или `SETOF`) и могут вызываться внутри `SELECT`, `UPDATE` или `INSERT` так же, как встроенные функции,. Внутри функций **запрещено** управление транзакциями (`COMMIT` / `ROLLBACK`), так как функция всегда выполняется в контексте внешней транзакции.
- **Хранимые процедуры (`CREATE PROCEDURE`):** Предназначены для выполнения действий, а не возврата данных (хотя могут использовать `INOUT` параметры). Главное отличие — поддержка управления транзакциями внутри тела: процедура может открывать и фиксировать транзакции через `COMMIT` и `ROLLBACK`, что критично для пакетной обработки данных в highload-системах,.

**Категории изменчивости (Volatility Categories):** Оптимизатор PostgreSQL использует эти метки для принятия решения о кэшировании результатов,.

- **`VOLATILE`** (по умолчанию): Функция может возвращать разные значения даже при одинаковых аргументах (например, генерация случайных чисел или выдача новых ID) и может иметь побочные эффекты.
- **`STABLE`**: Гарантирует одинаковый результат в рамках одного оператора сканирования таблицы.
- **`IMMUTABLE`**: Гарантирует абсолютную детерминированность: результат зависит только от входных аргументов и никогда не меняется (идеально для сложных математических расчетов и построения индексов по выражениям).

**Управляющие конструкции:**

- **Ветвление**: Реализуется через `IF...THEN...ELSIF...ELSE` или `CASE`,. Логика `CASE` в `PL/pgSQL` аналогична выражению `CASE` в `SELECT`, но позволяет выполнять блоки команд, а не просто возвращать значения,.
- **Циклы**: Поддерживаются `LOOP`, `WHILE` и `FOR`. Особое значение имеет цикл `FOR row IN query LOOP`, который позволяет итеративно обрабатывать результат `SELECT` без явного объявления курсоров.

**Обработка исключений и логирование:** Блок `BEGIN...EXCEPTION` позволяет перехватывать ошибки (например, `unique_violation`) и выполнять компенсационные действия или откатываться к `SAVEPOINT`,. Для отладки используются команды `RAISE NOTICE` (вывод информационных сообщений) и `RAISE EXCEPTION` (принудительная остановка транзакции с кодом ошибки),.

#### Практическая реализация и синтаксис

**Детерминированная (IMMUTABLE) функция для расчетов:**

```
CREATE OR REPLACE FUNCTION calculate_risk_index(base_val NUMERIC, multiplier NUMERIC)
RETURNS NUMERIC AS $$
BEGIN
    -- Детерминированный расчет
    RETURN ROUND(base_val * multiplier, 2);
END;
$$ LANGUAGE plpgsql IMMUTABLE;

-- Использование в индексе для ускорения поиска
CREATE INDEX idx_product_risk ON products (calculate_risk_index(price, tax_rate));
```

**Функция с возвратом таблицы и циклом:**
```sql
CREATE OR REPLACE FUNCTION get_active_sellers_stats()
RETURNS TABLE(seller_id INT, total_orders BIGINT) AS $$
DECLARE
    r RECORD;
BEGIN
    -- Цикл по результатам запроса
    FOR r IN SELECT s.id FROM sellers s WHERE s.status = 'active' LOOP
        seller_id := r.id;
        SELECT COUNT(*) INTO total_orders FROM orders WHERE s_id = r.id;
        RETURN NEXT; -- Добавление строки в результат
    END LOOP;
END;
$$ LANGUAGE plpgsql;
```

**Хранимая процедура с пакетным COMMIT:**
```sql
CREATE OR REPLACE PROCEDURE process_loyalty_batch()
AS $$
DECLARE
    r RECORD;
    counter INT := 0;
BEGIN
    FOR r IN SELECT user_id, balance FROM pending_bonuses LOOP
        UPDATE user_balances SET points = points + 100 WHERE id = r.user_id;
        counter := counter + 1;

        -- Фиксация транзакции каждые 1000 записей для снижения нагрузки на WAL
        IF counter % 1000 = 0 THEN
            COMMIT;
        END IF;
    END LOOP;
END;
$$ LANGUAGE plpgsql;
```,.

**Обработка ошибок в PL/pgSQL:**
```sql
BEGIN
    INSERT INTO users (email) VALUES ('duplicate@test.com');
EXCEPTION WHEN unique_violation THEN
    -- Логирование и кастомное исключение
    RAISE NOTICE 'User already exists, skipping...';
    RAISE EXCEPTION 'CRITICAL_ERROR: Attempted duplicate registration';
END;
```

#### Глоссарий терминов
* **PL/pgSQL Architecture** — блочная структура серверного языка, включающая секции `DECLARE`, `BEGIN`, `EXCEPTION` и `END`.
* **Stored Function vs Stored Procedure** — функциональное различие между объектами, возвращающими данные, и объектами, способными управлять транзакциями через `COMMIT`,.
* **Volatility Attributes** — параметры `IMMUTABLE`, `STABLE`, `VOLATILE`, определяющие степень детерминированности функции для оптимизатора,.
* **Cursor Loops in PL/pgSQL** — механизм `FOR record IN SELECT`, автоматически управляющий открытием и закрытием неявных курсоров.
* **Transaction Control inside Procedures** — уникальная возможность процедур фиксировать (`COMMIT`) изменения в БД до завершения всего блока кода.
* **PL/pgSQL Exception Handling** — перехват кодов ошибок времени выполнения с помощью блока `EXCEPTION` для обеспечения отказоустойчивости,.

#### Практический кейс: Разработка пакета начисления бонусов

**Сценарий**: Финтех-платформе необходимо раз в сутки начислять кэшбэк 100000+ пользователям. Прямой `UPDATE` может заблокировать таблицу надолго.
**Решение**:
1.  Создается процедура `process_daily_cashback`.
2.  Внутри используется цикл `FOR` по таблице предрассчитанных начислений.
3.  Для предотвращения раздувания `WAL` и блокировок, каждые 500 итераций вызывается `COMMIT`,.
4.  Весь блок обернут в `EXCEPTION`, где при любой непредвиденной ошибке выполняется `ROLLBACK` и запись в таблицу `error_log` через `RAISE NOTICE`,.

    *   *Ответ: Значение времени «застынет» в индексе в момент его создания и не будет обновляться, что приведет к логической неверности данных при поиске.*

3. **Практика**: Создайте функцию, которая при попытке `INSERT` проверяет существование записи и в случае `unique_violation` делает `UPDATE` существующей строки (паттерн UPSERT на уровне PL/pgSQL).
