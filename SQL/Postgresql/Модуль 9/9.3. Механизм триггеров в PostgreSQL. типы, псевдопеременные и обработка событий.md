#### Теоретический фундамент и архитектура

В архитектуре PostgreSQL триггеры представляют собой именованные модули, которые автоматически запускаются сервером базы данных при возникновении определенных событий, таких как вставка, изменение или удаление данных. В отличие от некоторых других СУБД, PostgreSQL использует двухуровневую модель: сначала инженер создает триггерную функцию с помощью `CREATE FUNCTION ... RETURNS TRIGGER`, а затем привязывает её к таблице через оператор `CREATE TRIGGER`.

**Время срабатывания триггеров (Trigger Timing):**

- **`BEFORE`**: Выполняется до того, как операция будет физически применена к строке. Это идеальное место для валидации бизнес-логики или модификации входящих данных в переменной `NEW` до их записи на диск.
- **`AFTER`**: Срабатывает после успешного завершения операции и проверки всех ограничений целостности. Используется для каскадных действий в других таблицах или формирования журналов аудита.
- **`INSTEAD OF`**: Специальный тип триггера, предназначенный исключительно для представлений (`Views`). Поскольку представления являются «виртуальными таблицами» и не всегда поддерживают автоматическое обновление, этот триггер перехватывает попытки `DML` и позволяет архитектору вручную распределить данные по базовым таблицам.

**Уровень детализации (Granularity):**

- **`FOR EACH ROW`**: Триггер вызывается один раз для каждой измененной строки. Это необходимо, когда логика зависит от значений конкретных полей (`NEW`/`OLD`).
- **`FOR EACH STATEMENT`**: Вызывается один раз на весь SQL-запрос, независимо от количества затронутых строк. Это значительно эффективнее для массовых операций, где не требуется анализ каждой отдельной записи.

**Специальные псевдопеременные:** Внутри триггерной функции на `PL/pgSQL` доступны контекстные переменные:

- **`NEW`**: Содержит состояние строки, которая будет вставлена или уже обновлена.
- **`OLD`**: Хранит состояние строки до момента обновления или удаления.
- **`TG_OP`**: Текстовая переменная, указывающая тип операции (`INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`), что позволяет использовать одну функцию для обработки разных событий.

#### Практическая реализация и синтаксис

**Автоматическое обновление временной метки (`updated_at`):**

```
CREATE OR REPLACE FUNCTION fn_stamp_updated_at()
RETURNS TRIGGER AS $$
BEGIN
    -- Модифицируем поле NEW перед записью
    NEW.updated_at := CURRENT_TIMESTAMP;
    RETURN NEW; -- Обязательно возвращаем NEW для продолжения операции
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER tr_products_timestamp
BEFORE UPDATE ON products
FOR EACH ROW
WHEN (OLD.* IS DISTINCT FROM NEW.*) -- Оптимизация: срабатывает только при реальных изменениях
EXECUTE FUNCTION fn_stamp_updated_at();
```

**Логирование изменений для аудита (`AFTER` триггер):**

```
CREATE OR REPLACE FUNCTION fn_audit_changes()
RETURNS TRIGGER AS $$
BEGIN
    IF (TG_OP = 'DELETE') THEN
        INSERT INTO audit_log(table_name, operation, old_data)
        VALUES (TG_TABLE_NAME, TG_OP, to_jsonb(OLD));
    ELSE
        INSERT INTO audit_log(table_name, operation, new_data)
        VALUES (TG_TABLE_NAME, TG_OP, to_jsonb(NEW));
    END IF;
    RETURN NULL; -- В AFTER-триггерах возвращаемое значение игнорируется
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER tr_audit_orders
AFTER INSERT OR UPDATE OR DELETE ON orders
FOR EACH ROW EXECUTE FUNCTION fn_audit_changes();
```

#### Глоссарий терминов
* **Trigger Function (`RETURNS TRIGGER`)** — специализированная хранимая функция, предназначенная для вызова механизмом триггеров.
* **BEFORE vs AFTER Triggers** — разделение логики на ту, что выполняется до фиксации данных (валидация), и ту, что после (логирование).
* **INSTEAD OF View Triggers** — механизм обеспечения модифицируемости виртуальных таблиц (представлений).
* **Row-Level vs Statement-Level Triggers** — выбор между точностью обработки каждой строки и производительностью на уровне всего запроса.
* **Context Pseudo-variables (`NEW`, `OLD`, `TG_OP`)** — встроенные переменные для доступа к данным и метаданным события внутри триггера.
* **Trigger Conditional Execution (`WHEN`)** — декларативное условие, позволяющее избежать лишних вызовов функции при невыполнении критериев.

#### Практический кейс: Обеспечение неизменяемости архива операций
**Сценарий**: В FinTech-системе таблица `processed_transactions` должна быть иммутабельной. Любая попытка изменить или удалить уже проведенную транзакцию должна блокироваться.
**Решение**:
Создается `BEFORE UPDATE OR DELETE` триггер на уровне строк. Внутри функции проверяется статус транзакции. Если статус равен 'PROCESSED', функция генерирует исключение через `RAISE EXCEPTION`. Это гарантирует согласованность данных и предотвращает финансовое мошенничество на уровне ядра СУБД, даже если у пользователя есть права `DML`.

#### Вопросы и задания для самопроверки
1. **Вопрос**: Почему в `BEFORE` триггере возвращение `NULL` приводит к отмене операции для текущей строки?
    *   *Ответ: Сервер интерпретирует NULL как сигнал о том, что строку не нужно вставлять или изменять в целевой таблице.*
2. **Задача**: Рассчитайте, сколько раз сработает функция триггера при выполнении `UPDATE users SET status = 'active'`, если в таблице 100 000 строк и триггер объявлен как `FOR EACH STATEMENT`.
    *   *Ответ: Ровно 1 раз.*
3. **Практика**: Напишите триггер `BEFORE INSERT`, который проверяет текущее количество записей в таблице `temporary_tokens` и выдает ошибку, если их количество превысило 1000.
