#### Теоретический фундамент и архитектура

Транзакция (`Transaction`) представляет собой механизм логической группировки нескольких SQL-выражений, который гарантирует, что либо все они будут выполнены успешно, либо не будет выполнено ни одно из них. В архитектуре PostgreSQL транзакционность опирается на фундаментальную модель **ACID**, обеспечивающую надежность данных в многопользовательской среде.

**Фундаментальные гарантии модели ACID:**

- **Атомарность (Atomicity):** Принцип «все или ничего». Если внутри транзакции происходит сбой (например, истечение времени ожидания или падение сервера), программа выдает команду `ROLLBACK`, и база данных возвращается в состояние, предшествовавшее началу транзакции.
- **Согласованность (Consistency):** Транзакция переводит базу данных из одного согласованного состояния в другое. Это обеспечивается строгим соблюдением ограничений целостности: `PRIMARY KEY`, `FOREIGN KEY` и `CHECK constraints`. Если транзакция нарушает любое из этих правил, PostgreSQL формирует ошибку и блокирует фиксацию изменений.
- **Изолированность (Isolation):** Предотвращение взаимного влияния одновременно выполняющихся транзакций. PostgreSQL использует стратегию контроля версий (`Versioning`), благодаря которой читающие пользователи видят непротиворечивое представление данных без необходимости блокировки ресурсов на чтение.
- **Долговечность (Durability):** Гарантия того, что зафиксированные данные не будут потеряны при сбоях питания или падении сервера. Это реализуется через журнал предзаписи (`Write-Ahead Logging`, WAL), который позволяет серверу при перезагрузке идентифицировать и завершить откат всех незавершенных операций.

**Команды управления жизненным циклом транзакции:** По умолчанию PostgreSQL может работать в режиме автоматической фиксации (`Autocommit mode`), где каждое выражение фиксируется независимо. Для управления сложной логикой используются команды:

1. **Инициализация:** `BEGIN` или `START TRANSACTION` запускает блок команд. Возможны флаги режима, такие как `READ ONLY` (запрет DML) или `READ WRITE` (по умолчанию).
2. **Фиксация:** `COMMIT` (или `END`) помечает изменения как постоянные и высвобождает занятые ресурсы (блокировки страниц/строк).
3. **Откат:** `ROLLBACK` отменяет все действия с момента начала транзакции.

**Подтранзакции и промежуточные точки сохранения:** Для реализации частичного отката без потери всей проделанной работы используются точки сохранения (`Savepoints`).

- `SAVEPOINT name` создает именованную метку внутри текущей транзакции.
- `ROLLBACK TO SAVEPOINT name` возвращает данные к состоянию на момент создания метки, позволяя продолжить выполнение транзакции.
- `RELEASE SAVEPOINT name` освобождает ресурсы точки сохранения, удаляя ее из стека, но не фиксируя данные (это делает только финальный `COMMIT`).

#### Практическая реализация и синтаксис

**Сценарий атомарного перевода средств между счетами:** В финансовом приложении перевод требует списания с одного счета и зачисления на другой. Если средств недостаточно или возникнет ошибка на втором шаге, вся операция должна быть отменена.

```
-- Инициализация транзакции
START TRANSACTION;

-- Шаг 1: Списание с проверкой баланса (Consistency)
UPDATE account
SET avail_balance = avail_balance - 500
WHERE account_id = 9988 AND avail_balance >= 500;

-- Шаг 2: Проверка, была ли изменена строка (логика приложения)
-- Если строка не изменена (баланс < 500), выполняется ROLLBACK

-- Шаг 3: Зачисление на второй счет
UPDATE account
SET avail_balance = avail_balance + 500
WHERE account_id = 9989;

-- Фиксация (Durability)
COMMIT;
```

.

**Использование SAVEPOINT для пакетной обработки:** Кейс архивации или удаления типов счетов, где одна ошибка не должна прерывать весь процесс.

```
START TRANSACTION;

-- Основное действие
UPDATE product SET date_retired = CURRENT_TIMESTAMP WHERE product_cd = 'XYZ';

-- Создание точки сохранения перед рискованной операцией
SAVEPOINT before_close_accounts;

-- Попытка массового закрытия счетов
UPDATE account SET status = 'CLOSED' WHERE product_cd = 'XYZ';

-- В случае логической ошибки или необходимости частичного отката:
ROLLBACK TO SAVEPOINT before_close_accounts;

-- Финальное закрепление прочих изменений
COMMIT;
```

.

**Режим транзакции BEGIN READ ONLY:** При попытке выполнить `INSERT`, `UPDATE` или `DELETE` в транзакции, запущенной с флагом `READ ONLY`, PostgreSQL выдаст ошибку уровня ядра, предотвращая модификацию данных.

#### Глоссарий терминов

- **ACID Guarantees** — совокупность свойств (атомарность, согласованность, изолированность, долговечность), гарантирующих надежность транзакционных операций.
- **Transaction Lifecycle** — последовательность состояний транзакции от инициализации (`BEGIN`) до окончательной фиксации (`COMMIT`) или отмены (`ROLLBACK`).
- **Savepoint Mechanics** — механизм создания именованных промежуточных состояний внутри транзакции для выполнения частичных откатов.
- **Subtransactions Overhead** — накладные расходы ресурсов сервера на управление вложенными логическими блоками данных внутри одной транзакции.
- **Write-Ahead Logging (WAL) Interplay** — взаимодействие механизма транзакций с журналом предзаписи для обеспечения восстановления данных после аварийного завершения.
- **Transaction Consistency Constraints** — использование ограничений (PK, FK, CHECK) для автоматической проверки бизнес-правил в момент завершения транзакции.

#### Практический кейс: Пакетная обработка заказов с обработкой сбоев через SAVEPOINT

**Сценарий:** В highload-системе необходимо провести платежи по 1000 заказам одним пакетом. **Решение:** Вместо 1000 отдельных транзакций (что создало бы нагрузку на диск из-за частых `COMMIT`), используется одна транзакция. Перед обработкой каждого заказа создается `SAVEPOINT order_N`. Если платеж конкретного заказа отклоняется банком или нарушает условие `CHECK (amount > 0)`, выполняется `ROLLBACK TO SAVEPOINT order_N`. Это позволяет системе продолжить обработку остальных 999 заказов и зафиксировать их одним `COMMIT` в конце, значительно повышая пропускную способность системы.

#### Вопросы и задания для самопроверки

1. **Вопрос:** Какой внутренний механизм PostgreSQL гарантирует, что зафиксированные данные выживут после падения сервера (свойство Durability)?.
2. **Задача:** Напишите транзакцию, которая создает 3 точки сохранения (`sp1`, `sp2`, `sp3`). После каждой точки выполняется `INSERT`. Выполните `ROLLBACK TO sp2`. Какие записи останутся в таблице после финального `COMMIT`?.
3. **Практика:** Создайте таблицу с ограничением `CHECK (balance >= 0)`. В транзакции попытайтесь установить баланс в -100. Опишите поведение PostgreSQL: можно ли будет зафиксировать другие операции этой же транзакции без использования `SAVEPOINT`?.
