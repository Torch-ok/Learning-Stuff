#### Теоретический фундамент и архитектура

В многопользовательской среде СУБД должна управлять одновременным доступом к ресурсам, чтобы предотвратить потерю данных и обеспечить согласованность [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/230). PostgreSQL достигает этого через **блокирование** (`locking`) — механизм, который ограничивает доступ других транзакций к таблицам или строкам, пока удерживающая блокировку транзакция не завершится (`COMMIT` или `ROLLBACK`) [Alan_Beaulieu-Learning_SQL-RU.pdf](230, 232).

**Иерархия и гранулярность блокировок:** PostgreSQL поддерживает блокировки различной степени детализации (`granularities`), что позволяет минимизировать накладные расходы при малом количестве пользователей и обеспечивать высокий параллелизм в нагруженных системах [Alan_Beaulieu-Learning_SQL-RU.pdf](231, 232).

- **Блокировки табличного уровня (`Table-Level Locks`):** Управляют доступом к целым таблицам. Существует иерархия от `Access Share` (устанавливается при `SELECT`, конфликтует только с изменениями схемы) до `Access Exclusive` (устанавливается при `ALTER TABLE`, `DROP TABLE`, `TRUNCATE`), которая полностью блокирует любой доступ к таблице [Alan_Beaulieu-Learning_SQL-RU.pdf](231, 232).
- **Блокировки строчного уровня (`Row-Level Locks`):** Позволяют тысячам пользователей одновременно изменять разные строки в одной и той же таблице, что критично для OLTP-систем [Alan_Beaulieu-Learning_SQL-RU.pdf](231, 232). Основные режимы:
    - `FOR UPDATE` — транзакция планирует обновить строку. Другие транзакции не смогут изменить или заблокировать её до конца текущей.
    - `FOR SHARE` — транзакция планирует только прочитать строку, гарантируя, что она не будет изменена другими до завершения транзакции.
    - `FOR NO KEY UPDATE` — оптимизированная блокировка для обновлений, не затрагивающих поля внешних ключей.

**Управление ожиданиями и неблокирующее чтение:** При возникновении конфликта транзакция по умолчанию переходит в состояние ожидания. Однако современные высоконагруженные паттерны требуют иного поведения:

- **`NOWAIT`**: Если строка занята, запрос немедленно завершается с ошибкой, не дожидаясь освобождения ресурса.
- **`SKIP LOCKED`**: Пропускает заблокированные строки, возвращая только свободные. Это фундаментальный паттерн для реализации очередей задач, исключающий конкуренцию между воркерами.

**Взаимные блокировки (`Deadlocks`):** Тупиковая ситуация возникает, когда две транзакции ожидают ресурсы, удерживаемые друг другом [Alan_Beaulieu-Learning_SQL-RU.pdf](235, 236). PostgreSQL автоматически запускает алгоритм поиска циклов в графе блокировок через интервал `deadlock_timeout` [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/236). При обнаружении тупика одна из транзакций (жертва) принудительно откатывается с ошибкой, позволяя другой завершить работу [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/236).

#### Практическая реализация и синтаксис

Пессимистическая блокировка баланса пользователя (защита от Double Spending):

```
BEGIN;
-- Блокируем конкретную строку счета для записи
SELECT avail_balance
FROM account
WHERE account_id = 9988
FOR UPDATE;

-- Выполнение расчетов и обновление
UPDATE account
SET avail_balance = avail_balance - 500
WHERE account_id = 9988;

COMMIT;
```

[Alan_Beaulieu-Learning_SQL-RU.pdf](232, 233).

Выборка свободных задач из очереди (паттерн Worker):

```
-- Каждый воркер забирает только свободные задачи, не блокируя коллег
WITH next_task AS (
    SELECT id
    FROM task_queue
    WHERE status = 'NEW'
    ORDER BY priority DESC, created_at ASC
    LIMIT 1
    FOR UPDATE SKIP LOCKED
)
UPDATE task_queue
SET status = 'PROCESSING'
FROM next_task
WHERE task_queue.id = next_task.id
RETURNING task_queue.id, task_queue.payload;
```

[Advanced SQL — Chapter 02 — Video #05](https://notebook.google.com/notebook/37) (концепция подзапросов), [Advanced SQL — Chapter 02 — Video #06](https://notebook.google.com/notebook/4) (лимитирование).

**Сценарий возникновения Deadlock:**

|Session A|Session B|
|:--|:--|
|`UPDATE users SET name = 'X' WHERE id = 1;`|`UPDATE users SET name = 'Y' WHERE id = 2;`|
|`UPDATE users SET name = 'Z' WHERE id = 2;` (ожидает B)|`UPDATE users SET name = 'W' WHERE id = 1;` (**DEADLOCK**)|

**Решение:** Всегда обновляйте строки в едином порядке, например, по возрастанию `id` [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/236).

#### Глоссарий терминов

- **Table-Level Locks vs Row-Level Locks** — различие между блокировкой всей сущности (медленно, низкий параллелизм) и отдельных кортежей (быстро, высокий параллелизм) [Alan_Beaulieu-Learning_SQL-RU.pdf](231, 232).
- **Explicit Row Locking (`FOR UPDATE`)** — ручной перевод строки в эксклюзивный режим блокировки для предотвращения конфликтов записи [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/233).
- **Non-blocking Lock Modifiers (`NOWAIT` / `SKIP LOCKED`)** — расширения SQL, позволяющие избежать ожидания освобождения заблокированных ресурсов.
- **Deadlock Detection Algorithm** — внутренний процесс СУБД, выявляющий циклические зависимости между ожидающими транзакциями [Alan_Beaulieu-Learning_SQL-RU.pdf](https://notebook.google.com/notebook/236).
- **Lock Conflict Matrix** — таблица совместимости режимов блокировок, определяющая, может ли новая блокировка быть установлена на ресурс.
- **Queue Processing Pattern (`SKIP LOCKED`)** — архитектурный подход для параллельной обработки данных из общей таблицы без блокировок между потребителями.

#### Практический кейс: Построение отказоустойчивого сервиса обработки задач

**Сценарий:** Финтех-платформе необходимо обрабатывать транзакции через фоновые воркеры. Если два воркера возьмут одну задачу, произойдет дублирование платежа. **Решение:** Реализуется распределенная очередь на таблице `task_queue`. Использование `FOR UPDATE SKIP LOCKED` гарантирует, что каждый воркер получит уникальный набор строк. В случае падения воркера транзакция прервется, блокировка снимется автоматически, и задача снова станет доступна для других процессов [Alan_Beaulieu-Learning_SQL-RU.pdf](230, 235). Это обеспечивает атомарность и надежность без использования внешних брокеров сообщений.

#### Вопросы и задания для самопроверки

1. **Вопрос:** В чем разница между `FOR UPDATE` и `FOR NO KEY UPDATE`?
    - _Ответ: `FOR UPDATE` блокирует возможность создания новых строк, ссылающихся на данную по FK, в то время как `FOR NO KEY UPDATE` позволяет параллельно добавлять дочерние записи, если ключ не меняется._
2. **Задача:** Напишите PL/pgSQL блок, который пытается заблокировать товар для резервирования через `NOWAIT`. Если товар занят другим менеджером, верните сообщение "Ресурс временно недоступен" [SQL. Сборник рецептов, 2-е издание.pdf](https://notebook.google.com/notebook/46).
