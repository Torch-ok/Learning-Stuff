#### Теоретический фундамент и архитектура

В высоконагруженных системах тысячи пользователей одновременно обращаются к одним и тем же данным. Чтобы обеспечить их корректность, PostgreSQL использует механизм контроля версий (`Versioning`), при котором читающие транзакции не блокируют записывающие, и наоборот.

**Классические и специфические аномалии параллельного выполнения:**

- **«Грязное» чтение (`Dirty Read`):** Чтение данных, которые были изменены другой транзакцией, но еще не зафиксированы (`COMMIT`). В архитектуре PostgreSQL эта аномалия невозможна на любом уровне изоляции, так как транзакции всегда видят только подтвержденные данные.
- **Неповторяемое чтение (`Non-Repeatable Read`):** Ситуация, когда при повторном чтении одной и той же строки внутри транзакции данные оказываются изменены другой зафиксированной транзакцией.
- **Чтение «фантомов» (`Phantom Read`):** Появление в результирующем наборе новых строк при повторном выполнении запроса с тем же условием `WHERE` из-за того, что параллельная транзакция успела вставить (`INSERT`) новые записи.
- **Аномалия сериализации (`Serialization Anomaly`) и перекрестная запись (`Write Skew`):** Логические противоречия, возникающие, когда две транзакции одновременно читают один набор данных, а затем обновляют разные части этого набора, нарушая бизнес-логику, которая должна была опираться на неизменность всего набора (информация об этих специфических феноменах выходит за рамки предоставленных источников и требует обращения к официальной документации PostgreSQL).

**Стандартные и фактические уровни изоляции в PostgreSQL:**

- **`READ COMMITTED` (по умолчанию):** Каждый оператор внутри транзакции видит «снимок» (`Snapshot`) данных на момент начала выполнения именно этого оператора. Это защищает от «грязного» чтения, но допускает неповторяемое чтение.
- **`REPEATABLE READ`:** Транзакция видит только те данные, которые были зафиксированы до момента выполнения самого первого оператора в этой транзакции. В PostgreSQL этот уровень также предотвращает чтение фантомов.
- **`SERIALIZABLE`:** Самый строгий уровень изоляции, имитирующий последовательное выполнение транзакций. Если СУБД обнаруживает конфликт зависимостей, который мог бы привести к аномалии, она принудительно прерывает одну из транзакций с ошибкой `serialization_failure`.

**Механика повторных попыток (`Retry Logic`):** При использовании строгих уровней изоляции (особенно `SERIALIZABLE`) база данных может отменить транзакцию из-за конфликта параллельного доступа. В этом случае приложение должно быть спроектировано так, чтобы автоматически перезапустить всю цепочку команд транзакции заново.

#### Практическая реализация и синтаксис

**Пример Non-Repeatable Read на уровне `READ COMMITTED`:**

|Время|Session A (Transaction)|Session B (Parallel)|
|:--|:--|:--|
|T1|`BEGIN;`||
|T2|`SELECT avail_balance FROM account WHERE account_id = 1; -- 1000`||
|T3||`UPDATE account SET avail_balance = 2000 WHERE account_id = 1; COMMIT;`|
|T4|`SELECT avail_balance FROM account WHERE account_id = 1; -- 2000`||
|T5|`COMMIT;`||

Здесь Session A видит два разных значения в рамках одной транзакции, так как на уровне `READ COMMITTED` каждый `SELECT` делает новый снимок данных.

**Сценарий `Write Skew` (Дежурство врачей):** _(Внимание: описание сценария Write Skew является стандартным примером для уровня Repeatable Read, но детали реализации SSI в предоставленных источниках не описаны детально)_. Два врача дежурят, правило: хотя бы один должен остаться. Оба одновременно решают уйти, проверяют `SELECT COUNT(*) WHERE status = 'on_call'` (видят 2), затем оба выполняют `UPDATE SET status = 'off_call'`. В итоге дежурных нет. Уровень `SERIALIZABLE` предотвратил бы это, выдав ошибку одной из транзакций.

**Установка уровня изоляции и обработка ошибок:**

```
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- Выполнение бизнес-логики
UPDATE account SET avail_balance = avail_balance - 500 WHERE account_id = 9988;

-- Если возникнет конфликт параллелизма, сервер вернет:
-- ERROR: could not serialize access due to read/write dependencies among transactions
-- Код ошибки: 40001
COMMIT;
```

.

#### Глоссарий терминов

- **Read Committed Isolation** — уровень изоляции, гарантирующий чтение только зафиксированных изменений на момент начала каждого запроса.
- **Repeatable Read Isolation** — уровень изоляции, обеспечивающий видимость данных на момент начала всей транзакции.
- **Serializable Snapshot Isolation (SSI)** — механизм PostgreSQL для уровня `SERIALIZABLE`, отслеживающий зависимости между транзакциями для предотвращения всех видов аномалий.
- **Dirty Read Anomaly** — чтение «грязных» данных, не зафиксированных другой транзакцией.
- **Non-Repeatable Read Anomaly** — феномен изменения данных в строке между двумя чтениями в одной транзакции.
- **Phantom Read Anomaly** — появление новых строк в выборке из-за параллельных вставок.
- **Write Skew Phenomenon** — аномалия записи, когда транзакции нарушают общие правила целостности, работая с разными, но логически связанными строками (информация требует верификации в документации).
- **Serialization Failure (`40001`)** — стандартный код ошибки PostgreSQL, указывающий на необходимость повторного выполнения транзакции из-за конфликта изоляции.

#### Практический кейс: Устранение гонки условий в системе бронирования авиабилетов

В системе продажи билетов при уровне `READ COMMITTED` возможен «овербукинг»: два пользователя одновременно видят последнее свободное место (`SELECT`), и оба успешно выполняют `INSERT` в таблицу бронирования. **Решение:** Перевод транзакции на уровень `SERIALIZABLE`. В этом случае СУБД отследит, что обе транзакции опирались на результат одного и того же `SELECT`, и при попытке второго пользователя зафиксировать бронь выдаст ошибку `40001`. Приложение поймает эту ошибку и предложит пользователю обновить страницу, где он увидит, что мест больше нет.

#### Вопросы и задания для самопроверки

1. **Вопрос:** Почему в PostgreSQL на уровне `READ COMMITTED` два одинаковых запроса `SELECT` могут вернуть разные суммы остатка?
    - _Ответ: Потому что между первым и вторым запросом могла завершиться параллельная транзакция, и второй запрос сделал новый снимок данных._
2. **Задача:** Транзакция Т1 (`REPEATABLE READ`) читает строку. Транзакция Т2 обновляет эту строку и делает `COMMIT`. Что произойдет, если Т1 попытается обновить ту же строку?
    - _Ответ: Т1 заблокируется до завершения Т2, а после коммита Т2 транзакция Т1 в PostgreSQL выдаст ошибку отката из-за невозможности обновления версии строки._
3. **Практика:** Опишите на псевдокоде алгоритм `While(true)` для клиентского приложения, который обрабатывает транзакцию на уровне `SERIALIZABLE`, включая перехват ошибки `40001`.
