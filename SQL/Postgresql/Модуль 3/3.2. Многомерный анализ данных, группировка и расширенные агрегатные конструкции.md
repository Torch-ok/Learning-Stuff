#### Теоретический фундамент и архитектура

Концепция группировки данных (`GROUP BY`) в реляционных базах данных предназначена для организации похожих строк в группы на основе общих значений в одном или нескольких столбцах. Суть этого процесса заключается в логическом разделении входного набора на непересекающиеся подмножества (партиции), где каждая строка исходной таблицы принадлежит ровно одной уникальной группе,. После формирования групп агрегатные функции применяются к каждой из них отдельно, сворачивая «мешок значений» (`bag of values`) в одно результирующее скалярное значение для каждой группы,.

**Ограничения SELECT и детерминированность:** Согласно стандартам SQL, все столбцы, перечисленные в блоке `SELECT`, которые не являются аргументами агрегатных функций, обязаны быть указаны в блоке `GROUP BY`,. Это требование обусловлено проблемой не детерминированности: если в группе содержится несколько разных значений для колонки, не входящей в критерий группировки, СУБД не сможет однозначно определить, какое именно значение следует вывести в итоговой строке,. Исключение составляют только константы, скалярные подзапросы и оконные функции, которые обрабатываются на более поздних этапах.

**Алгоритмы группировки в PostgreSQL:** Внутренние механизмы выполнения группировки опираются на два основных подхода. При наличии небольших объемов данных или соответствующих индексов используется метод, основанный на сортировке (`GroupAggregate`), где данные упорядочиваются, и группы формируются последовательно,. В высоконагруженных системах чаще применяется метод хэширования (`HashAggregate`), при котором в оперативной памяти строится хэш-таблица для быстрого поиска и накопления агрегатов, что требует значительных ресурсов RAM (Memory Overhead),.

**Фильтрация данных (HAVING):** Блок `HAVING` предназначен для фильтрации результатов уже после выполнения группировки и вычисления агрегатов,. Логический порядок обработки запроса строго определен: сначала `FROM` и `JOIN` определяют источники, затем `WHERE` отсекает сырые строки, `GROUP BY` формирует группы, и только после этого `HAVING` проверяет условия по агрегированным значениям,,,.

> [!warning] Актуализация синтаксиса 
> Ошибочное использование агрегатных функций в блоке `WHERE` приводит к аварийному завершению запроса, так как на этапе `WHERE` группы еще не сформированы и агрегаты не вычислены,.

**Расширенные конструкции многомерного анализа (OLAP):** Для построения сложных отчетов PostgreSQL предоставляет «синтаксический сахар», заменяющий множественные объединения `UNION ALL`:

- **`GROUPING SETS`** — позволяет явно перечислить несколько комбинаций группировки в одном запросе, обеспечивая гибкость анализа,.
- **`ROLLUP`** — создает иерархическую последовательность групп, автоматически вычисляя промежуточные итоги (`Subtotals`) и общий итог (`Grand Total`),,.
- **`CUBE`** — генерирует все возможные комбинации ($2^n$) подмножеств для указанных измерений, формируя основу для OLAP-кубов,,.
- **Функция `GROUPING()`** — используется для идентификации строк, содержащих итоги; она возвращает `1`, если значение столбца является агрегированным результатом (служебный `NULL`), и `0`, если это фактические данные,,.

#### Практическая реализация и синтаксис

Пример группировки с фильтрацией агрегатов для анализа продаж по категориям:

```
-- Группировка товаров по категориям и годам с отсечением низкодоходных групп
SELECT category_id,
       EXTRACT(YEAR FROM sale_date) AS sale_year,
       SUM(price) AS total_revenue
FROM sales
WHERE status = 'PAID' -- Фильтрация сырых данных до группировки
GROUP BY category_id, sale_year
HAVING SUM(price) > 100000 -- Фильтрация групп после агрегации
ORDER BY total_revenue DESC;
```

,,.

Иерархический отчет с использованием `ROLLUP`:

```
-- Получение древовидного отчета: Регион -> Город -> Магазин
SELECT region, city, store_id, SUM(amount) as sales
FROM daily_reports
GROUP BY ROLLUP(region, city, store_id);
-- Результат будет содержать итоги по каждому магазину, городу, региону и итого по всей сети
```

,,.

Использование `GROUPING SETS` для консолидации данных:

```
-- Одновременный расчет продаж по филиалам и по менеджерам за один проход
SELECT branch_id, manager_id, SUM(total_amount)
FROM invoices
GROUP BY GROUPING SETS ((branch_id), (manager_id));
```

,,.

#### Глоссарий терминов

- **Grouping Logic (GROUP BY)** — метод организации строк в уникальные группы на основе совпадения значений в атрибутах,.
- **Post-Aggregation Filter (HAVING)** — условие фильтрации, применяемое к результатам агрегатных функций после этапа группировки,.
- **HashAggregate vs GroupAggregate** — физические алгоритмы СУБД для выполнения группировки через хэш-таблицы в памяти или сортировку данных,.
- **Grouping Sets** — расширение SQL для указания нескольких наборов измерений группировки в рамках одного оператора,.
- **Rollup Subtotals** — иерархический режим агрегации, добавляющий строки промежуточных сумм для каждого уровня измерений,.
- **OLAP Cube (CUBE)** — режим группировки, вычисляющий агрегаты для всех возможных перестановок столбцов,.
- **Grouping Indicator (GROUPING())** — системная функция для определения, является ли значение в строке результатом агрегации уровня выше,.

#### Практический кейс: Иерархический отчет по продажам торговой сети

**Сценарий**: Необходимо сформировать отчет для руководства highload-ритейлера, который показывает продажи в разрезе Регионов, Городов и конкретных Точек продаж. **Решение**: Вместо выполнения трех отдельных запросов и их склейки через `UNION ALL` (что потребовало бы трехкратного сканирования таблицы продаж), используется оператор `GROUP BY ROLLUP(region, city, point_id)`,. Это позволяет PostgreSQL вычислить все уровни иерархии за один проход по данным. Для визуального отделения итоговых строк от обычных в приложении используется функция `GROUPING(point_id)`, которая позволяет подставить текст 'ИТОГО ПО ГОРОДУ' вместо системного `NULL` в ячейку идентификатора точки,.
