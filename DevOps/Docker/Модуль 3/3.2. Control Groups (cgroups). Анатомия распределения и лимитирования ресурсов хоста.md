Безопасность контейнерных сред в 2026 году — это многослойный пирог, где каждый слой компенсирует риски другого. Как мы выяснили ранее, контейнеры используют **Shared Host Kernel** (общее ядро хоста) [Definitions and basic concepts - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-2/definitions-and-basic-concepts). Это означает, что если процесс внутри контейнера получит неограниченный доступ к системным вызовам ядра, он сможет скомпрометировать весь физический сервер [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdfr%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Securing_Docker]. Исторически запуск процесса от имени суперпользователя (**root**) внутри контейнера вызывал оправданную панику у специалистов по информационной безопасности, так как **UID 0** внутри изоляции технически является тем же самым **UID 0** на хосте [Docker_Up_and_Running], [Docker-in-Practice]. Любой «побег» из контейнера (Container Escape) приводил к полному захвату хост-системы [Securing_Docker].

Для минимизации этой угрозы Docker внедрил механизмы сужения вектора атаки, превращая «всемогущего» root в ограниченного исполнителя [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).

#### Механизм Linux Capabilities: Дискретные привилегии
В традиционном Unix-мире привилегии были бинарными: вы либо обычный пользователь, либо root. Технология **Linux Capabilities** разбивает монолитную власть root на десятки мелких, дискретных разрешений [Docker-in-Practice], [Securing_Docker]. Это позволяет следовать принципу наименьших привилегий (**Least Privilege**) [Docker Deep Dive].

Docker по умолчанию отсекает у root-процесса внутри контейнера наиболее опасные права, оставляя только около 14 базовых способностей из более чем 40 доступных в ядре Linux [Docker-in-Practice], [Securing_Docker].

**Как это работает на практике (наш сквозной пример):**
*   **Nginx:** Для того чтобы занять стандартный 80-й порт, процессу требуется привилегия `CAP_NET_BIND_SERVICE`. Docker оставляет её активной по умолчанию, поэтому веб-сервер успешно стартует [Docker-in-Practice].
*   **Безопасность:** При этом у того же Nginx-контейнера изъята привилегия `CAP_SYS_BOOT` (возможность перезагрузить систему) и `CAP_SYS_MODULE` (возможность загружать модули в ядро хоста) [Docker-in-Practice], [Securing_Docker].
*   **Управление:** Если вашему приложению **Flask** не нужно менять владельцев файлов, вы можете превентивно отобрать права на это при запуске:
    `docker container run --cap-drop=CHOWN flask-app` [Docker-in-Practice], [Securing_Docker].

#### Seccomp (Secure Computing Mode): Фильтрация системных вызовов
Если Capabilities ограничивают «права» процесса, то **Seccomp** ограничивает «инструментарий» взаимодействия с ядром. Это своего рода «брандмауэр» для системных вызовов (**syscalls**) [Docker Deep Dive], [Docker для начинающих: что это такое и как пользоваться / Хабр](https://habr.com/ru/companies/netologyru/articles/967546/).

Ядро Linux предоставляет сотни системных вызовов, но среднестатистическому приложению для работы требуется лишь малая их часть. Docker применяет стандартный **Seccomp-профиль** (в формате JSON), который блокирует около 44 системных вызовов из ~300+ доступных, даже если у процесса есть права root [Docker Deep Dive], [Securing_Docker].

**Сценарий блокировки «на подлете»:**
Представьте, что злоумышленник внедрил вредоносный код в ваш бэкенд на **Flask** и пытается выполнить команду `reboot`.
1.  Процесс отправляет системный вызов `reboot()` к ядру хоста [Docker-in-Practice].
2.  **Seccomp-фильтр** Docker перехватывает этот вызов в миллисекунды [Docker Deep Dive].
3.  Поскольку `reboot` отсутствует в «белом списке» разрешенных вызовов стандартного профиля, ядро мгновенно блокирует выполнение [Docker Deep Dive], [Securing_Docker].
4.  Вредоносный процесс получает ошибку **Operation not permitted**, а ваш сервер продолжает работать [Docker_Up_and_Running], [Docker-in-Practice].

Такой подход делает изоляцию Docker в 2026 году достаточно надежной даже для банковского сектора и государственных систем, так как атака на ядро требует обхода сразу нескольких барьеров: Namespaces (изоляция вида), Cgroups (лимиты ресурсов), Capabilities (права) и Seccomp (фильтрация вызовов) [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Docker Deep Dive].

### Тест для самопроверки (Безопасность ядра)

<details>
<summary>1. Почему запуск контейнера с флагом <code>--privileged</code> считается критической ошибкой безопасности в продакшене?</summary>
<blockquote>
<b>Ответ:</b> Флаг <code>--privileged</code> отключает все ограничения: возвращает все Linux Capabilities, отключает Seccomp-фильтрацию и дает контейнеру прямой доступ к устройствам хоста. Это фактически делает изоляцию бессмысленной [Docker_Up_and_Running], [Securing_Docker].
</blockquote>
</details>

<details>
<summary>2. Какая Linux Capability позволяет Nginx слушать порты ниже 1024 (например, 80 или 443)?</summary>
<blockquote>
<b>Ответ:</b> <code>CAP_NET_BIND_SERVICE</code>. Именно это точечное разрешение позволяет запускать веб-серверы от root внутри контейнера, не давая процессу лишних прав на управление всей сетью хоста [Docker-in-Practice].
</blockquote>
</details>

<details>
<summary>3. В чем фундаментальное различие между Capabilities и Seccomp?</summary>
<blockquote>
<b>Ответ:</b> <b>Capabilities</b> работают на уровне логических разрешений процесса (что ему можно делать в ОС), а <b>Seccomp</b> — на уровне интерфейса ядра, разрешая или запрещая конкретные системные вызовы (syscalls) [Docker Deep Dive], [Securing_Docker].
</blockquote>
</details>

<details>
<summary>4. Что произойдет, если приложение внутри контейнера попытается использовать системный вызов <code>mount()</code>, который запрещен в стандартном Seccomp-профиле?</summary>
<blockquote>
<b>Ответ:</b> Ядро Linux вернет ошибку «Permission denied» или «Operation not permitted», и вызов не будет исполнен, предотвращая несанкционированное изменение файловых структур хоста [Docker_Up_and_Running], [Docker-in-Practice].
</blockquote>
</details>

<details>
<summary>5. Какую роль играет USER Namespace в этой цепочке безопасности?</summary>
<blockquote>
<b>Ответ:</b> Он позволяет сопоставить root-пользователя контейнера (UID 0) с обычным непривилегированным пользователем на хосте (например, UID 1001). Даже если злоумышленник «выйдет» из контейнера, для хоста он останется обычным пользователем без прав администратора [Docker Deep Dive], [Securing_Docker].
</blockquote>
</details>
