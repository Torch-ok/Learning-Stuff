Ниже представлены фундаментальные системные абстракции ядра Linux, которые обеспечивают работу контейнеризации в соответствии со стандартами 2026 года.

* **Namespaces (Пространства имен)** — технология ядра Linux, обеспечивающая изоляцию системных ресурсов; она определяет границы видимости для процесса, создавая иллюзию владения собственной операционной системой (виртуализация «вида») [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Docker для начинающих: что это такое и как пользоваться / Хабр](https://habr.com/ru/companies/netologyru/articles/967546/).
* **cgroups v2 (Control Groups version 2)** — механизм ядра для лимитирования, учета и изоляции использования физических ресурсов (CPU, RAM, Disk I/O); версия v2 предоставляет унифицированную иерархию контроллеров, что повышает стабильность управления ресурсами [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Docker Engine - The Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
* **OOM Killer (Out-Of-Memory Killer)** — системная служба ядра, которая принудительно завершает процессы (обычно сигналом `SIGKILL`) при достижении жесткого лимита памяти в контрольной группе или во всей системе для предотвращения краха ядра [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Docker-in-Practice](https://manning.com/books/docker-in-practice).
* **Linux Capabilities** — дискретные привилегии, на которые разбиты абсолютные права суперпользователя `root`; позволяют предоставлять процессу только те разрешения, которые необходимы для работы (например, только право биндить порты), следуя принципу наименьших привилегий [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781785281648/), [Docker-in-Practice](https://manning.com/books/docker-in-practice).
* **Seccomp (Secure Computing Mode)** — средство фильтрации системных вызовов (`syscalls`); ограничивает набор операций, которые процесс может запросить у ядра хоста, значительно сужая вектор атаки в случае взлома приложения [Docker для начинающих: что это такое и как пользоваться / Хабр](https://habr.com/ru/companies/netologyru/articles/967546/), [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781785281648/).
* **OverlayFS** — современный драйвер хранения, реализующий многослойную файловую систему; объединяет несколько директорий в одно виртуальное представление, разделяя неизменяемые слои образа и динамический слой записи [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Docker для начинающих: что это такое и как пользоваться / Хабр](https://habr.com/ru/companies/netologyru/articles/967546/).
* **Copy-on-Write (CoW)** — стратегия оптимизации ресурсов, при которой копия файла создается в записываемом слое контейнера только в момент попытки его изменения, что обеспечивает мгновенный старт и экономию дискового пространства [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Docker-in-Practice](https://manning.com/books/docker-in-practice).

## Практическое упражнение (Развернутый интерактивный кейс Модуля 3)

**Сценарий «Призрачная нехватка памяти»:**
Ваша команда эксплуатирует базу данных **PostgreSQL** в Docker-контейнере на мощном сервере с 64 ГБ RAM. Во время пиковой нагрузки (распродажа в интернет-магазине) контейнер внезапно падает.

**Данные диагностики:**
1. Команда `docker container ls -a` показывает статус `Exited (137)`.
2. Системный лог хоста (`dmesg`) содержит запись: `Memory cgroup out of memory: Killed process 1234 (postgres)`.
3. Мониторинг хоста показывает, что на физическом сервере свободно еще **16 ГБ оперативной памяти**.

**Инженерный анализ и размышления:**
*   **Почему упал контейнер?** Несмотря на обилие памяти на хосте, ядро Linux убило процесс из-за превышения локального лимита в **cgroup** [Docker_Up_and_Running], [Docker-in-Practice]. Код выхода 137 (128 + 9) подтверждает получение сигнала `SIGKILL` от **OOM Killer** [Docker-in-Practice].
*   **Локализация проблемы:** Проверьте параметры запуска контейнера. Если вы использовали флаг `--memory="2g"`, PostgreSQL будет убит сразу после попытки выделить 2.01 ГБ, даже если хост пуст [Securing_Docker].
*   **Правильная настройка:** Для СУБД критически важно соответствие внутренних настроек кэша (`shared_buffers`) и лимитов контейнера. Если `shared_buffers` настроен на 2 ГБ, а лимит контейнера — тоже 2 ГБ, то для фоновых процессов Postgres и системных вызовов памяти не останется, что приведет к падению [Docker_Up_and_Running].

**Задание:** Сформулируйте команду `docker container run` для PostgreSQL, которая предотвратит моментальное уничтожение процесса при кратковременных всплесках, используя лимиты и область подкачки (**swap**) [Docker-in-Practice].

***

**Правильный ответ:**
Необходимо установить жесткий лимит (`--memory`) и дополнительный лимит на swap (`--memory-reservation` или `--memory-swap`), чтобы дать базе данных «пространство для маневра».
```bash
docker container run -d \
  --name postgres-prod \
  --memory="4g" \
  --memory-reservation="2g" \
  --restart unless-stopped \
  postgres:16-alpine
````

_Примечание:_ Использование **Volumes** гарантирует, что данные не исчезнут вместе с эфемерным слоем записи при срабатывании OOM Killer [Volumes in action - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-3/volumes-in-action).
