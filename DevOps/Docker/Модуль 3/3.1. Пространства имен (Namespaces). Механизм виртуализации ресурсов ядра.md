Фундаментальный успех Docker в 2026 году базируется не на магии, а на глубокой эксплуатации возможностей ядра Linux, которые разрабатывались десятилетиями. Если Модуль 1 объяснил нам «зачем», то Модуль 3 отвечает на вопрос «как». И первым, самым важным кирпичом в стене изоляции являются **Namespaces** [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdfr%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).

**Сущность технологии: Ограничение видимости**
Если вкратце, то **Namespaces** — это механизм ядра, который определяет, что процесс **МОЖЕТ ВИДЕТЬ**. В то время как обычный процесс в операционной системе видит всё «железо», все сетевые интерфейсы и все другие процессы, процесс внутри контейнера Docker помещается в своего рода «VR-комнату» [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/). Ядро Linux обманывает этот процесс, подсовывая ему индивидуальные, изолированные экземпляры системных ресурсов. Процесс «думает», что он работает в полноценной ОС, хотя на самом деле он делит ядро с сотнями других соседей [Definitions and basic concepts - MOOC.fi courses](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-2/definitions-and-basic-concepts), [Docker - Полный курс Docker Для Начинающих [3 ЧАСА] / YouTube](https://www.youtube.com/watch?v=n9uCgUzfeRQ).

#### Глубокий разбор ключевых типов Namespaces

Для создания полноценного контейнера Docker комбинирует шесть основных типов пространств имен [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker QnA vijay](https://github.com/vijay/docker-qna). Рассмотрим их работу на примере нашего сквозного стека (**Nginx + Flask + PostgreSQL**).

##### 1. PID Namespace (Process ID) — Изоляция деревьев процессов
В Linux каждый процесс имеет уникальный идентификатор — PID. Процесс, запускаемый первым при старте ОС, получает PID 1 и становится «родителем» для всех остальных [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
*   **Внутри контейнера:** Наше приложение **Flask** запускается внутри своего **PID namespace**. Для него ядро выделяет виртуальный PID 1. Приложение «считает», что оно — единственный хозяин системы [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).
*   **Снаружи (на хосте):** Тот же самый процесс **Flask** виден системному администратору под обычным пятизначным номером (например, PID 45012) [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
*   **Профит:** **PostgreSQL** в соседнем контейнере также имеет свой PID 1. Они не видят процессы друг друга и не могут отправить сигнал `kill` соседу, что критически важно для безопасности [Docker QnA vijay](https://github.com/vijay/docker-qna).

##### 2. NET Namespace — Изоляция сетевого стека
Это пространство имен предоставляет контейнеру собственный сетевой интерфейс (`eth0`), собственный IP-адрес и, что самое важное, собственную таблицу маршрутизации и петлю обратной связи (`localhost`) [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker networking - MOOC.fi courses](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-3/docker-networking).
*   **Пример:** Мы можем запустить **Nginx** на порту 80 внутри одного контейнера и одновременно запустить какой-нибудь старый Apache тоже на порту 80 в другом контейнере на том же физическом сервере [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
*   **Как это работает:** Каждый контейнер имеет свой независимый диапазон портов от 0 до 65535. Конфликта «Address already in use» не происходит, так как порты принадлежат разным сетевым пространствам [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).

##### 3. MNT Namespace (Mount) — Изоляция файловой системы
**MNT namespace** позволяет процессу иметь собственное представление о иерархии папок и точек монтирования. Когда мы заходим в контейнер **PostgreSQL**, мы видим корень системы `/`, который полностью отличается от корня системы хоста [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker QnA vijay](https://github.com/vijay/docker-qna).
*   **Практика:** База данных может использовать специфическую версию библиотеки `libssl` в своем `/usr/lib`, в то время как **Flask** использует совершенно другую версию в своем изолированном `/usr/lib`. Они никогда не «встретятся» и не сломают друг друга [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).

##### 4. Прочие вспомогательные Namespaces
*   **UTS Namespace:** Позволяет контейнеру иметь собственное имя хоста (**hostname**) и доменное имя. Наш бэкенд может называться `flask-prod`, хотя сервер называется `worker-node-01` [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
*   **IPC Namespace:** Изолирует механизмы межпроцессного взаимодействия (разделяемая память, очереди сообщений). Это гарантирует, что процессы **Flask** не смогут случайно прочитать данные из памяти **PostgreSQL** напрямую [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
*   **USER Namespace:** Позволяет сопоставлять идентификаторы пользователей (UID/GID). Вы можете быть `root` (UID 0) внутри контейнера для установки пакетов, но для ядра хоста вы будете обычным непривилегированным пользователем (например, UID 1001), что сводит риск взлома хоста к минимуму [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker QnA vijay](https://github.com/vijay/docker-qna).

> [!tip] Задание для размышления
> **Метафора комнаты с фальшивыми окнами:** Представьте, что вы живете в комнате, где на окнах установлены ЖК-экраны высокого разрешения. На экранах показывают вид на океан (это ваш **NET namespace**), в шкафу висит одежда, которая кажется бесконечной (**MNT namespace**), а в зеркале вы видите себя в короне короля (**PID 1**). Вы уверены, что вы — единственный жилец в огромном поместье. Но на самом деле вы находитесь в маленькой ячейке огромного небоскреба (ядра ОС), где за тонкими стенами живут тысячи таких же «королей» [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).

### Тест для самопроверки (Уровень: Advanced)

<details>
<summary>1. В чем заключается фундаментальная разница между Namespaces и Control Groups (cgroups)?</summary>
<blockquote>
<b>Ответ:</b> <b>Namespaces</b> отвечают за изоляцию («что процесс видит»), создавая иллюзию отдельной ОС. <b>Control Groups (cgroups)</b> отвечают за ограничение ресурсов («сколько процесс потребляет» — CPU, RAM, Disk I/O) [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Securing_Docker.pdf].
</blockquote>
</details>

<details>
<summary>2. Какое пространство имен позволяет запустить два разных веб-сервера на порту 80 на одном физическом сервере?</summary>
<blockquote>
<b>Ответ:</b> <b>NET Namespace</b>. Каждый контейнер получает свой независимый стек протоколов TCP/IP и собственный диапазон портов [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
</blockquote>
</details>

<details>
<summary>3. Почему Flask-приложение внутри контейнера часто имеет PID 1, и чем это опасно при некорректной настройке?</summary>
<blockquote>
<b>Ответ:</b> Благодаря <b>PID Namespace</b>. Процесс с PID 1 является init-процессом и должен уметь обрабатывать системные сигналы (например, SIGTERM) и «усыновлять» осиротевшие процессы. Если Flask не умеет этого делать, контейнер может некорректно завершаться или плодить процессы-зомби [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker_Up_and_Running.pdf].
</blockquote>
</details>

<details>
<summary>4. Что произойдет, если в общем Shared Host Kernel произойдет критическая ошибка (Kernel Panic)?</summary>
<blockquote>
<b>Ответ:</b> Поскольку все контейнеры делят одно ядро, ошибка на уровне ядра приведет к мгновенному падению всех запущенных контейнеров на этом хосте. Это цена за высокую производительность контейнеризации [Securing_Docker.pdf], [Docker-in-Practice.pdf].
</blockquote>
</details>

<details>
<summary>5. Какую роль играет USER Namespace в обеспечении безопасности интернет-магазина?</summary>
<blockquote>
<b>Ответ:</b> Он позволяет процессу Flask работать от имени <code>root</code> внутри контейнера (что удобно для настройки), но при этом ядро хоста будет видеть его как обычного пользователя с ограниченными правами. В случае взлома Flask злоумышленник не получит прав администратора на физическом сервере [Docker Deep Dive Zero to Docker in a single book (Nigel Poulton)](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
</blockquote>
</details>
