Ниже представлены ключевые концепции управления состоянием и данными, определяющие архитектурную надежность контейнеризированных систем в 2026 году.

- **Stateless** — архитектурный подход, при котором приложение не сохраняет внутреннее состояние между запросами; любой экземпляр контейнера является взаимозаменяемым, а данные сессий выносятся во внешние хранилища [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Docker-in-Practice](https://manning.com/books/docker-in-practice).
- **Stateful** — тип приложений (например, СУБД), работа которых напрямую зависит от накопленных данных; такие сервисы требуют строгой привязки к постоянным хранилищам для выживания при перезапусках [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Docker - Полный курс / YouTube](https://www.youtube.com/watch?v=n9uCgUzfeRQ).
- **Docker Volume** — механизм постоянного хранения, полностью управляемый движком Docker; тома изолированы от структуры папок хоста, обладают высокой производительностью и рекомендуются для баз данных в продакшене [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf/Docker Deep Dive Zero to Docker in a single book (Nigel Poulton) (z-lib.org).pdf/Docker Deep Dive Zero to Docker in a single book (Nigel Poulton) (z-lib.org).pdf/Docker Deep Dive Zero to Docker in a single book (Nigel Poulton) (z-lib.org).pdf).
- **Bind Mount** — прямое монтирование конкретной директории или файла с хост-машины в контейнер; используется преимущественно в разработке для синхронизации исходного кода (Hot Reload) [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Chapter 2: Introduction to Containers - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-2/interacting-with-the-container-via-volumes-and-ports).
- **tmpfs mount** — временное хранилище, создаваемое в оперативной памяти (RAM) хоста; данные не пишутся на диск и мгновенно уничтожаются при остановке контейнера, что идеально для чувствительных данных и кэшей [Изучаем Docker, часть 6: работа с данными / Хабр](https://habr.com/ru/companies/ruvds/articles/441574/), [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).
- **Anonymous Volume** — том, которому Docker присваивает случайный хэш вместо понятного имени; создается автоматически, если точка монтирования указана без имени, и его трудно идентифицировать при аудите системы [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker-Cookbook](https://www.oreilly.com/library/view/docker-cookbook/9781491919712/).
- **Storage Driver overhead** — дополнительные вычислительные затраты и задержки ввода-вывода, возникающие при записи в RW-слой контейнера из-за работы механизмов Copy-on-Write [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Docker-in-Practice](https://manning.com/books/docker-in-practice).

## Практическое упражнение (Настройка персистентности данных для PostgreSQL и Hot Reload для Flask)

В рамках нашего сквозного проекта мы развернем связку базы данных и бэкенда, используя современные флаги монтирования `--mount` для обеспечения максимальной предсказуемости и безопасности [Изучаем Docker, часть 6: работа с данными / Хабр](https://habr.com/ru/companies/ruvds/articles/441574/).

### Задача 1: Персистентность PostgreSQL

Нам нужно гарантировать, что при обновлении версии базы данных или случайном удалении контейнера наши таблицы не исчезнут [Volumes in action - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-3/volumes-in-action).

**Команда:**

```bash
# 1. Создаем именованный том
docker volume create postgres_data

# 2. Запускаем БД с подключением тома
docker container run -d \
  --name shop-db \
  -e POSTGRES_PASSWORD=secret \
  --mount type=volume,source=postgres_data,target=/var/lib/postgresql/data \
  postgres:16-alpine
```

**Архитектурный разбор:** Использование `type=volume` позволяет Docker самостоятельно управлять правами доступа внутри `/var/lib/docker/volumes/` [Docker_Up_and_Running]. Даже если мы выполним `docker container rm -f shop-db`, данные в томе `postgres_data` останутся нетронутыми [Изучаем Docker, часть 6: работа с данными / Хабр].

### Задача 2: Разработка Flask с Hot Reload и защитой кода

Нам нужно видеть изменения в коде мгновенно, но при этом мы хотим защитить исходники от случайного изменения процессом внутри контейнера [Docker и Docker Compose - Полный Курс / YouTube](https://www.youtube.com/watch?v=n9uCgUzfeRQ).

**Команда:**

```bash
docker container run -d \
  --name flask-app \
  -p 5000:5000 \
  -e FLASK_ENV=development \
  --mount type=bind,source="$(pwd)"/app,target=/app,readonly \
  --mount type=tmpfs,destination=/app/logs \
  flask-image:latest
```

**Архитектурный разбор:**

1. **Hot Reload:** Через `bind mount` папка `./app` с вашего ноутбука пробрасывается в контейнер. Flask в режиме разработки увидит правки в файлах и перезапустится [Docker Fundamentals: теория и базовая эксплуатация / Хабр].
2. **Immutability в рантайме:** Флаг `readonly` гарантирует, что если в приложении есть уязвимость, злоумышленник не сможет внедрить вредоносный код в ваши файлы на хосте [Securing_Docker].
3. **Изоляция логов:** Поскольку весь `/app` в режиме `ro`, для записи логов мы монтируем отдельный `tmpfs` в `/app/logs`. Логи пишутся в RAM и не нагружают диск, а при взломе — исчезнут после перезагрузки [Изучаем Docker, часть 6: работа с данными / Хабр].
