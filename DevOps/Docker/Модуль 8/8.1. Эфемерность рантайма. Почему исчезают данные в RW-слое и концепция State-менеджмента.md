В современной DevOps-инженерии 2026 года господствует концепция «контейнеры — это скот, а не домашние питомцы» (Cattle, not Pets) [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdfr%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf/Docker Deep Dive Zero to Docker in a single book (Nigel Poulton) (z-lib.org).pdf). Это означает, что любой экземпляр контейнера должен быть взаимозаменяемым, легко удаляемым и возобновляемым без ручной настройки. Однако этот подход наталкивается на фундаментальную проблему: приложениям нужно где-то хранить результаты своей работы.

#### Stateless vs Stateful: Философия состояния

Для Middle DevOps инженера критически важно разделять приложения по типу управления состоянием (State) [Docker QnA vijay](https://github.com/vijay/docker-qna), [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/):

1. **Stateless (Без сохранения состояния):** Наше приложение **Flask** в идеале должно быть именно таким. Оно получает запрос, обрабатывает его и отдает ответ. Если контейнер с Flask упадет, мы просто поднимем новый, и пользователь этого не заметит, так как все важные данные (логины, заказы) Flask уже отправил во внешнюю базу данных [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Docker-in-Practice](https://manning.com/books/docker-in-practice).
2. **Stateful (С сохранением состояния):** Наша СУБД **PostgreSQL** — это классический пример Stateful-сервиса. Её ценность заключается именно в накопленных данных на диске. Если данные PostgreSQL исчезнут при перезагрузке, работа всего интернет-магазина будет парализована [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Docker и Docker Compose - Полный Курс / YouTube](https://www.youtube.com/watch?v=n9uCgUzfeRQ).

#### Жизненный цикл Container Layer (Read-Write слой)

Как мы помним из Модуля 5, при запуске контейнера поверх неизменяемых слоев образа Docker создает тонкий **Read-Write слой** (Container Layer) [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Docker для начинающих: что это такое и как пользоваться / Хабр](https://habr.com/ru/companies/netologyru/articles/967546/).

- **При `docker container restart`:** Данные в RW-слое сохраняются. Процесс PID 1 перезапускается, но файловая система контейнера остается нетронутой [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker QnA vijay](https://github.com/vijay/docker-qna).
- **При `docker container rm`:** Происходит архитектурная «зачистка». Docker полностью удаляет объект контейнера вместе с его индивидуальным RW-слоем [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Изучаем Docker, часть 6: работа с данными / Хабр](https://habr.com/ru/companies/ruvds/articles/441574/). Все данные, которые PostgreSQL успел записать в `/var/lib/postgresql/data` внутри этого слоя, исчезают навсегда [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Volumes in action - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-3/volumes-in-action).

> [!danger]  Архитектурная катастрофа 
> Попытка использовать RW-слой для хранения баз данных, пользовательских аватарок или критических логов — это прямая дорога к потере данных (Data Loss). В 2026 году стандарт эксплуатации требует, чтобы RW-слой оставался «пустым» или содержал только временные неважные файлы [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Docker-in-Practice](https://manning.com/books/docker-in-practice).

#### Накладные расходы и деградация производительности

Помимо риска потери данных, запись в RW-слой контейнера неэффективна с точки зрения системных ресурсов [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Docker-in-Practice](https://manning.com/books/docker-in-practice).

1. **Прослойка Storage Driver:** При записи файла в RW-слой Docker задействует драйвер хранения (например, `overlay2`). Каждая операция записи проходит через механизмы **Copy-on-Write** (CoW): ядро должно найти файл в нижних слоях, скопировать его наверх и только потом изменить [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Docker-in-Practice](https://manning.com/books/docker-in-practice).
2. **I/O Latency:** Эта дополнительная логическая прослойка создает задержки (latency). Если запустить нагруженную базу данных PostgreSQL без внешнего тома, её производительность упадет на 20–40% из-за оверхеда на управление слоями [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Docker-in-Practice](https://manning.com/books/docker-in-practice).
3. **Ограничение пространства:** RW-слой часто имеет жесткие ограничения по объему (зависит от настроек драйвера, например, `dm.basesize`), и база данных может внезапно «упереться в потолок», даже если на хосте еще много свободного места [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/).

**Решение инженера:** Все Stateful-данные должны выноситься за пределы контейнера с помощью **Volumes** или **Bind Mounts**, которые обеспечивают прямую запись на диск хоста, минуя Storage Driver [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Изучаем Docker, часть 6: работа с данными / Хабр](https://habr.com/ru/companies/ruvds/articles/441574/).
