В данном разделе собраны ключевые понятия информационной безопасности контейнерных сред, знание которых необходимо для внедрения практик DevSecOps в 2026 году.

- **Linux Capabilities** — механизм ядра Linux, позволяющий разделить монолитные привилегии пользователя `root` на дискретные единицы доступа (например, право на привязку к портам или управление сетью), предоставляя процессу только необходимые полномочия [Docker-in-Practice](https://manning.com/books/docker-in-practice), [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/).
- **Least Privilege Principle** (Принцип наименьших привилегий) — архитектурная доктрина, согласно которой каждому компоненту системы (контейнеру или пользователю) выдается минимально достаточный набор прав для выполнения его задачи [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/), [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/).
- **Container Breakout** — критический сценарий безопасности, при котором злоумышленник выходит за пределы изоляции контейнера и получает доступ к ресурсам хост-системы через уязвимости ядра или неправильные настройки привилегий [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/), [Using a non-root user - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-4/using-a-non-root-user).
- **Read-only Rootfs** — режим работы рантайма, при котором корневая файловая система контейнера монтируется без прав на запись, что блокирует любые попытки модификации кода или внедрения вредоносных скриптов в `Container Layer` [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/), [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/).
- **Attack Surface** (Поверхность атаки) — совокупность всех потенциально уязвимых точек системы (открытые порты, лишние библиотеки в образе, избыточные привилегии), через которые может быть совершено нападение [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdfr%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).
- **Docker Secrets** — специализированный механизм для безопасного хранения и доставки чувствительных данных (паролей, ключей), монтирующий их в контейнер как временные файлы в оперативной памяти [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/).
- **In-memory mounting** — технология монтирования директорий (`tmpfs`) непосредственно в оперативную память хоста, исключающая запись данных на физический диск и гарантирующая их уничтожение при остановке процесса [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Изучаем Docker, часть 6: работа с данными / Хабр](https://habr.com/ru/companies/ruvds/articles/441574/).

## Практическое упражнение (Харденинг контейнеров Flask и PostgreSQL по стандартам безопасности)

**Инженерная задача:** Вам предоставлен типовой, небезопасный файл `compose.yaml`. Ваша цель — провести полный харденинг (укрепление защиты) системы, внедрив ограничение привилегий, защиту файловой системы и безопасное управление секретами [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/), [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/).

### Итоговый защищенный манифест (compose.yaml)

```yml
name: hardened-stack-2026

services:
  db:
    image: postgres:16-alpine
    # 4. Запуск от имени не-root пользователя (UID 70 в alpine postgres)
    user: "70:70"
    # 1. Полный сброс привилегий и возврат только необходимых для БД
    cap_drop:
      - ALL
    cap_add:
      - CHOWN
      - SETGID
      - SETUID
    # 2. Защита файловой системы + RAM-папки для временных данных
    read_only: true
    tmpfs:
      - /tmp
      - /var/run/postgresql
    volumes:
      - db_data:/var/lib/postgresql/data
    # 3. Использование секретов вместо переменных окружения
    environment:
      - POSTGRES_PASSWORD_FILE=/run/secrets/db_pass
    secrets:
      - db_pass
    networks:
      - backend_net

  web:
    build: ./app
    # 4. Flask работает от непривилегированного пользователя (UID 1001)
    user: "1001:1001"
    # 1. Flask не нужны системные привилегии вообще
    cap_drop:
      - ALL
    # 2. Полная блокировка записи в образ
    read_only: true
    tmpfs:
      - /tmp
      - /app/logs
    # 3. Подключение секрета для связи с базой
    secrets:
      - db_pass
    environment:
      - DB_PASS_PATH=/run/secrets/db_pass
    depends_on:
      db:
        condition: service_healthy
    networks:
      - backend_net
      - frontend_net

secrets:
  db_pass:
    file: ./db_password.txt

volumes:
  db_data:

networks:
  frontend_net:
  backend_net:
```

[Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/), [Изучаем Docker, часть 6: работа с данными / Хабр](https://habr.com/ru/companies/ruvds/articles/441574/).

### Разбор принятых мер:

1. **Capabilities:** Флаг `cap_drop: [ALL]` лишает злоумышленника возможности выполнять любые системные операции даже при захвате процесса [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/). Для PostgreSQL возвращены только права на владение файлами данных [Docker-in-Practice](https://manning.com/books/docker-in-practice).
2. **Read-only & tmpfs:** Блокировка `read_only: true` делает невозможным внедрение вредоносного кода в `/app` [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/). Использование `tmpfs` позволяет приложениям писать временные данные (PID-файлы, логи) в RAM, которые бесследно исчезнут при остановке [Изучаем Docker, часть 6: работа с данными / Хабр](https://habr.com/ru/companies/ruvds/articles/441574/).
3. **Docker Secrets:** Пароли теперь передаются не через открытые переменные, а через зашифрованные файлы в `/run/secrets/`, невидимые в логах и `docker inspect` [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
4. **User:** Директива `user` гарантирует, что если процесс будет скомпрометирован, злоумышленник получит права обычного пользователя, а не `root`, что критически затрудняет атаку на ядро хоста [Using a non-root user - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-4/using-a-non-root-user).

1. **Механика Kernel:** Почему концепция `Shared Host Kernel` делает запуск контейнера от пользователя `root` значительно более опасным, чем запуск полноценной виртуальной машины? [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/).
2. **Иерархия Capabilities:** Опишите, как использование `CAP_NET_BIND_SERVICE` позволяет веб-серверу работать на порту 80, не обладая при этом правами на удаление файлов в системе [Docker-in-Practice](https://manning.com/books/docker-in-practice), [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/).
3. **Безопасность CI/CD:** Каким образом использование многоэтапной сборки (`Multi-stage builds`) и минимальных образов (`Alpine`) способствует уменьшению поверхности атаки приложения? [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).
4. **Риски инспекции:** Выполните команду `docker container inspect`. Какие секции JSON-вывода подтверждают наличие критической уязвимости при использовании `environment` для передачи паролей? [Docker QnA vijay](https://github.com/vijay/docker-qna), [Docker_eBook](https://zzzprojects.com/docker-ebook).
5. **Механика Read-only:** Объясните, почему после активации `read_only: true` процесс Python может упасть с ошибкой `OSError: [Errno 30] Read-only file system` и как системный вызов `write()` блокируется на уровне драйвера файловой системы [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/).
