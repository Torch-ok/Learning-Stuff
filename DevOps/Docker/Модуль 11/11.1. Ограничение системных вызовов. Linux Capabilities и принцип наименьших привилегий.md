В классической модели безопасности Unix существовало бинарное разделение полномочий: либо процесс является непривилегированным, либо он обладает правами суперпользователя `root` (UID 0), что дает ему неограниченную власть над ядром и аппаратными ресурсами [Docker-in-Practice](https://manning.com/books/docker-in-practice), [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/). В контексте контейнеризации 2026 года такой подход неприемлем, так как захват процесса с правами `root` внутри контейнера может привести к полной компрометации хост-системы из-за использования механизма **Shared Host Kernel** [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/), [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdfr%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).

#### Анатомия Linux Capabilities: Расщепление «атома» root

Для Middle DevOps инженера понимание **Linux Capabilities** является ключом к реализации **Принципа наименьших привилегий** (Principle of Least Privilege) [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/). Технически это механизм ядра Linux, который разбивает монолитную власть суперпользователя на десятки дискретных, независимых единиц — «возможностей» (capabilities) [Docker-in-Practice](https://manning.com/books/docker-in-practice), [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).

Вместо того чтобы давать процессу **Nginx** полные права `root`, мы можем выдать ему только одну конкретную привилегию — `CAP_NET_BIND_SERVICE`, которая позволяет биндиться к привилегированным портам (ниже 1024), оставляя все остальные системные вызовы заблокированными [Docker-in-Practice](https://manning.com/books/docker-in-practice), [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/).

#### Проблема избыточности: Настройки Docker по умолчанию

По умолчанию Docker Engine запускает контейнеры с определенным набором включенных возможностей (например, `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `NET_BIND_SERVICE`), который считается «умеренно защищенным» для широкой совместимости приложений [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker-in-Practice](https://manning.com/books/docker-in-practice). Однако даже этот урезанный список содержит потенциальные риски [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/):

- **`CAP_CHOWN`** и **`CAP_FOWNER`**: Позволяют изменять владельца и права доступа к файлам, что опасно при монтировании томов с хоста [Docker-in-Practice](https://manning.com/books/docker-in-practice).
- **Риск повышения привилегий**: При наличии определенных уязвимостей в ядре или рантайме, даже ограниченный набор capabilities может стать рычагом для **Container Breakout** [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/), [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/).

#### Золотой стандарт эксплуатации: Drop ALL

Индустриальным стандартом 2026 года является стратегия «белого списка» [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/):

1. Сначала мы полностью обнуляем все системные привилегии процесса флагом `--cap-drop=ALL` [Docker-in-Practice](https://manning.com/books/docker-in-practice), [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/).
2. Затем точечно возвращаем только те capabilities, без которых приложение падает с ошибкой [Docker-in-Practice](https://manning.com/books/docker-in-practice), [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/).

**Пример запуска Nginx в режиме Hardened:**

```bash
docker container run -d \
  --cap-drop=ALL \
  --cap-add=NET_BIND_SERVICE \
  -p 80:80 \
  nginx:latest
```

[Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/), [Docker-in-Practice](https://manning.com/books/docker-in-practice). В этой конфигурации, если злоумышленник взломает Nginx, он не сможет даже выполнить команду `chown` или изменить сетевой интерфейс, так как соответствующие возможности физически вырезаны из контекста процесса ядром [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/), [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/).

#### Декларативная настройка в compose.yaml

В нашем сквозном проекте (Flask + PostgreSQL) мы настраиваем ограничения в манифесте для максимальной воспроизводимости [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker для новичков — #3 Что нужно знать о Docker compose / Хабр](https://habr.com/ru/articles/804331/).

```yml
services:
  database:
    image: postgres:16-alpine
    cap_drop:
      - ALL
    # PostgreSQL требует некоторые права для управления файлами и памятью
    cap_add:
      - CHOWN
      - SETGID
      - SETUID
    networks:
      - backend_net

  backend:
    image: flask-app:latest
    # Для Flask, работающего на порту 5000, привилегии вообще не нужны
    cap_drop:
      - ALL
    networks:
      - backend_net
      - frontend_net
```

[Docker-in-Practice](https://manning.com/books/docker-in-practice), [Docker для новичков — #3 Что нужно знать о Docker compose / Хабр](https://habr.com/ru/articles/804331/), [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781491917565/).

> [!tip] Практический совет 
> Если ваше приложение падает после `cap_drop: ALL`, используйте утилиту `strace` или смотрите системные логи хоста (audit log), чтобы увидеть, какой именно системный вызов (`syscall`) был заблокирован с ошибкой `EPERM` [Docker-in-Practice](https://manning.com/books/docker-in-practice).
