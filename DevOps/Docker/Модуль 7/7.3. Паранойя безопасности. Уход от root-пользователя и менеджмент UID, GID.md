В индустриальных стандартах 2026 года запуск процессов внутри контейнера с правами суперпользователя считается критической уязвимостью и признаком низкого уровня инженерной культуры [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781785281648/), [Using a non-root user - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-4/using-a-non-root-user). Для Middle DevOps инженера понимание механики разрешений (permissions) и идентификаторов (UID/GID) является фундаментом построения защищенных сред [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781785281648/), [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/).

#### Фундаментальная проблема: UID 0 и Shared Kernel

По умолчанию Docker запускает все процессы от имени пользователя `root` (UID 0) [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/). Это создает опасную иллюзию безопасности: кажется, что «контейнерный root» заперт внутри своей среды [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/).

На самом деле, поскольку контейнеры используют **Shared Host Kernel** (общее ядро хоста), ядро Linux не делает различий между «root внутри» и «root снаружи» на уровне системных вызовов [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781785281648/), [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/).

- **Container Breakout:** Если злоумышленник обнаружит уязвимость в приложении (например, в нашем Flask-бэкенде) или в самом движке Docker, позволяющую выйти за пределы пространств имен (Namespaces), он окажется на хост-машине с полными правами UID 0 [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781785281648/), [Docker-in-Practice](https://manning.com/books/docker-in-practice).
- Это позволяет ему удалять системные бинарные файлы хоста, читать файл `/etc/shadow` или перехватывать сетевой трафик всего сервера [Docker-in-Practice](https://manning.com/books/docker-in-practice), [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/).

#### Namespaces и реальность идентификаторов

Хотя Namespaces изолируют процессы, они не всегда трансформируют числовые значения UID [Docker-in-Practice](https://manning.com/books/docker-in-practice), [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/). Если механизм `user namespaces` (userns-remap) не настроен специально, то процесс с UID 0 внутри контейнера отображается как процесс с UID 0 в таблице процессов хоста [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Using a non-root user - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-4/using-a-non-root-user).

#### Практика: Создание непривилегированного пользователя

Чтобы обезопасить наш сквозной проект, мы должны зафиксировать UID и GID пользователя в `Dockerfile`. Использование стандартных ID (вроде 1000) может привести к коллизиям с реальным пользователем на хосте. В профессиональной среде рекомендуется использовать ID из высокого диапазона, например 10001 [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/).

**Пример реализации для Flask (на Alpine):**

```yml
FROM python:3.11-alpine

# Настройка фиксированных ID
ARG USER_ID=10001
ARG GROUP_ID=10001

# Создаем системную группу и пользователя без пароля и домашней папки
RUN addgroup -g ${GROUP_ID} flaskgroup && \
    adduser -D -u ${USER_ID} -G flaskgroup flaskuser

WORKDIR /app

# Критически важно: меняем владельца файлов ПЕРЕД переключением пользователя
COPY --chown=flaskuser:flaskgroup requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY --chown=flaskuser:flaskgroup . .

# Переключение контекста безопасности
USER flaskuser

CMD ["python", "app.py"]
```

[Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Using a non-root user - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-4/using-a-non-root-user).

#### Нюанс с CHOWN и ловушка Permission Denied

Самая распространенная ошибка Middle-инженеров при уходе от root — забыть передать права на файлы новому пользователю [Using a non-root user - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-4/using-a-non-root-user).

1. Если вы создали папку `/app` и скопировали туда код, будучи `root`, владельцем файлов останется UID 0 [Docker-in-Practice](https://manning.com/books/docker-in-practice).
2. После инструкции `USER flaskuser` приложение запускается от UID 10001 [Using a non-root user - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-4/using-a-non-root-user).
3. Когда Flask пытается записать лог в файл `access.log` или PostgreSQL пытается инициализировать базу в директории, принадлежащей root, система выдаст ошибку **`Permission denied`** [Using a non-root user - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-4/using-a-non-root-user).

По стандартам 2026 года для этого используется флаг `--chown` прямо в инструкции `COPY`, что эффективнее, чем отдельный `RUN chown`, так как не создает лишнего слоя в образе [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Using a non-root user - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-4/using-a-non-root-user).
