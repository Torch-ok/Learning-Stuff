Ниже представлены ключевые концепции сборки образов, понимание которых необходимо для создания эффективных и безопасных Docker-манифестов в соответствии со стандартами 2026 года.

- **Build Context (Контекст сборки)** — набор файлов и директорий, доступных движку Docker в процессе построения образа; обычно это папка, путь к которой указывается в конце команды `docker image build` [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Docker для новичков — #2 Все инструкции Dockerfile / Хабр](https://habr.com/ru/articles/804325/).
- **Build-time Variables (ARG)** — переменные, которые существуют исключительно во время выполнения процесса сборки; они позволяют параметризировать `Dockerfile` (например, указывать версию базового образа), но не попадают в запущенный контейнер [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Docker для новичков — #2 Все инструкции Dockerfile / Хабр](https://habr.com/ru/articles/804325/).
- **Runtime Variables (ENV)** — переменные окружения, которые сохраняются в метаданных образа и доступны приложению как во время сборки, так и в рантайме внутри контейнера [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Docker для новичков — #2 Все инструкции Dockerfile / Хабр](https://habr.com/ru/articles/804325/).
- **Shell Form** — способ записи инструкций (например, `CMD python app.py`), при котором команда запускается как дочерний процесс оболочки `/bin/sh -c`, что препятствует корректной обработке системных сигналов [Docker для новичков — #2 Все инструкции Dockerfile / Хабр](https://habr.com/ru/articles/804325/), [Defining start conditions for the container - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-2/defining-start-conditions-for-the-container).
- **Exec Form** — предпочтительный способ записи (JSON-массив, например `CMD ["python", "app.py"]`), запускающий процесс напрямую, минуя оболочку, что делает приложение основным процессом контейнера [Docker для новичков — #2 Все инструкции Dockerfile / Хабр](https://habr.com/ru/articles/804325/), [Defining start conditions for the container - MOOC.fi](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-2/defining-start-conditions-for-the-container).
- **PID 1** — идентификатор первого процесса в изолированном пространстве имен контейнера; этот процесс отвечает за обработку сигналов (например, `SIGTERM`) и управление жизненным циклом всех дочерних потоков [Docker-in-Practice], [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdfr%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf/Docker Deep Dive Zero to Docker in a single book (Nigel Poulton) (z-lib.org).pdf).
- **Cache Invalidation (Инвалидация кэша)** — процесс, при котором Docker признает кэш слоя недействительным из-за изменения текста инструкции или содержимого копируемых файлов, что вызывает принудительное выполнение этого и всех последующих шагов сборки заново [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Изучаем Docker, часть 4: уменьшение размеров образов и ускорение их сборки / Хабр](https://habr.com/ru/companies/ruvds/articles/440658/).

## Практическое упражнение (Написание первого правильного Dockerfile для Flask)

**Инженерный кейс:** Вам дано Flask-приложение, которое успешно работает на вашем ноутбуке. В корне проекта лежат файлы `app.py` и `requirements.txt`. Ваша задача — упаковать это приложение в Docker-образ, соблюдая три заповеди DevOps-инженера 2026 года: **скорость сборки (кэш)**, **минимальный размер** и **корректный Graceful Shutdown** [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Docker-in-Practice].

Ниже представлен эталонный `Dockerfile` с построчным разбором логики:

```yml
# 1. Используем официальный легковесный образ Python.
# Фиксируем минорную версию для детерминированности сборки.
FROM python:3.11-slim

# 2. Указываем рабочую директорию.
# Все последующие команды будут выполняться в /app. Если папки нет, Docker её создаст.
WORKDIR /app

# 3. Устанавливаем переменные окружения.
# PYTHONUNBUFFERED=1 гарантирует, что логи приложения будут мгновенно
# попадать в STDOUT без буферизации (важно для docker container logs).
ENV PYTHONUNBUFFERED=1

# 4. ШАГ ОПТИМИЗАЦИИ КЭША: Копируем ТОЛЬКО файл с зависимостями.
# requirements.txt меняется редко. Пока он неизменен, Docker будет
# брать результат выполнения следующего шага (установки пакетов) из кэша.
COPY requirements.txt .

# 5. Устанавливаем пакеты.
# Флаг --no-cache-dir критически важен: он не дает pip сохранять кэш внутри образа,
# что экономит сотни мегабайт дискового пространства.
RUN pip install --no-cache-dir -r requirements.txt

# 6. Копируем остальной исходный код проекта.
# Этот слой будет пересобираться при каждом изменении app.py,
# но тяжелый шаг установки зависимостей (шаг 5) будет пропущен благодаря кэшу.
COPY . .

# 7. Информационно документируем порт, на котором работает Flask.
EXPOSE 5000

# 8. Запуск приложения в Exec-форме.
# Это делает процесс python главным процессом (PID 1).
# Теперь при остановке контейнера Flask получит сигнал SIGTERM и успеет
# корректно закрыть соединения.
CMD ["python", "app.py"]
```
