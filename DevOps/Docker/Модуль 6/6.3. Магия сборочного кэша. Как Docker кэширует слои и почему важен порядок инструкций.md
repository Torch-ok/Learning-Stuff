Скорость сборки образа в 2026 году — это не просто вопрос удобства разработчика, а критический фактор эффективности CI/CD-пайплайнов [Deployment pipelines - MOOC.fi courses](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-4/deployment-pipelines). Движок Docker обладает мощным механизмом **Build Cache** (сборочного кэша), который позволяет не пересобирать заново то, что уже было успешно сконфигурировано ранее [Docker QnA vijay](https://github.com/vijay/docker-qna). Для Middle DevOps инженера понимание работы этого кэша на атомарном уровне является обязательным навыком оптимизации [Optimizing the image size - MOOC.fi courses](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-4/optimizing-the-image-size).

#### Как Docker проверяет кэш: Логика движка

Процесс сборки (команда `docker image build`) итерируется по `Dockerfile` построчно, начиная с самой первой инструкции [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf/Docker Deep Dive Zero to Docker in a single book (Nigel Poulton) (z-lib.org).pdf). Для каждой строки Docker ищет в своем локальном хранилище уже существующий слой, который удовлетворяет двум условиям [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Изучаем Docker, часть 4: уменьшение размеров образов и ускорение их сборки / Хабр](https://habr.com/ru/companies/ruvds/articles/440658/):

1. Он был построен на базе того же самого родительского слоя, что и текущий шаг [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
2. Инструкция (текст команды) полностью совпадает с той, что была использована для создания этого слоя [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).

**Особая логика для файлов (COPY и ADD):** Если инструкция подразумевает копирование файлов с хоста в образ, Docker не просто сравнивает текст команды. Он вычисляет контрольные суммы (**checksum**) каждого файла [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Изучаем Docker, часть 4: уменьшение размеров образов и ускорение их сборки / Хабр](https://habr.com/ru/companies/ruvds/articles/440658/). Если в файле изменился хотя бы один байт, Docker сочтет кэш недействительным [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).

#### «Эффект домино»: Каскадная инвалидация кэша

Это фундаментальный закон сборки: как только на каком-то шаге происходит **Cache Miss** (промах кэша), кэш для этой инструкции и **ДЛЯ ВСЕХ ПОСЛЕДУЮЩИХ** инструкций становится невалидным [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).

Представьте это как цепочку звеньев. Если третье звено сломано (изменился файл или команда), Docker вынужден пересобрать всю оставшуюся часть цепи с нуля, даже если текст команд в шагах 4, 5 и 6 не менялся [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf). Именно поэтому инженеры стремятся располагать самые стабильные инструкции (установка системных пакетов) в начале файла, а самые часто меняющиеся (копирование кода приложения) — в самом конце [Optimizing the image size - MOOC.fi courses](https://courses.mooc.fi/org/uh-cs/courses/devops-with-docker-spring-2026/chapter-4/optimizing-the-image-size), [Изучаем Docker, часть 4: уменьшение размеров образов и ускорение их сборки / Хабр](https://habr.com/ru/companies/ruvds/articles/440658/).

#### Классическая ошибка: Код перед зависимостями

Начинающие разработчики часто пишут `Dockerfile` для своего Flask-приложения интуитивно, совершая «медленное самоубийство» по времени сборки [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/):

```yml
# АНТИПАТТЕРН (ТАК ДЕЛАТЬ НЕЛЬЗЯ)
FROM python:3.11-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["python", "app.py"]
```
[Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/)

**Почему это плохо?**
Инструкция `COPY . .` копирует весь проект, включая исходный код. Разработчик меняет код постоянно — несколько раз в час [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/). Каждое изменение в одном файле `.py` сбрасывает кэш на шаге `COPY`. Из-за «эффекта домино» Docker на каждом запуске сборки будет заново выполнять `RUN pip install`, скачивая сотни мегабайт библиотек из интернета [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).

#### Эталонная структура для Python/Flask проекта
Чтобы избежать этой проблемы, мы используем прием разделения слоев: зависимости устанавливаются отдельно от кода [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Docker для новичков — #2 Все инструкции Dockerfile / Хабр](https://habr.com/ru/articles/804325/).

```yml
dockerfile
# ЭТАЛОННАЯ СБОРКА 2026
FROM python:3.11-slim

WORKDIR /app

# Шаг 1: Копируем ТОЛЬКО манифест зависимостей
# requirements.txt меняется редко (раз в неделю/месяц)
COPY requirements.txt .

# Шаг 2: Устанавливаем библиотеки.
# Этот тяжелый слой (200-500 МБ) теперь "намертво" закеширован!
RUN pip install --no-cache-dir -r requirements.txt

# Шаг 3: Копируем постоянно меняющийся исходный код проекта
# Если код изменился, пересоберется только этот (легкий) слой
COPY . .

CMD ["python", "app.py"]
``` 
[Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Docker для новичков — #2 Все инструкции Dockerfile / Хабр](https://habr.com/ru/articles/804325/), [Изучаем Docker, часть 4: уменьшение размеров образов и ускорение их сборки / Хабр](https://habr.com/ru/companies/ruvds/articles/440658/).

При таком подходе, если вы измените строку в `app.py`, Docker увидит, что `requirements.txt` не менялся, пропустит шаг установки библиотек (используя кэш) и выполнит только последний `COPY . .`. Сборка займет 1-2 секунды вместо нескольких минут [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).

### Тест для самопроверки (Сборочный кэш)

<details>
<summary>1. Каким образом Docker проверяет, изменился ли файл в инструкции COPY для принятия решения об использовании кэша?</summary>
<blockquote>
<b>Ответ:</b> Docker вычисляет криптографическую контрольную сумму (checksum) каждого файла. Если содержимое или метаданные файлов не совпадают с теми, что хранятся в кэше, кэш инвалидируется [Docker Deep Dive], [Изучаем Docker, часть 4: уменьшение размеров образов и ускорение их сборки / Хабр].
</blockquote>
</details>

<details>
<summary>2. Что произойдет со всеми инструкциями в Dockerfile после того, как одна из них вызвала промах кэша (Cache Miss)?</summary>
<blockquote>
<b>Ответ:</b> Произойдет каскадная инвалидация ("эффект домино"): все последующие инструкции будут выполняться заново без обращения к кэшу [Docker Deep Dive], [Docker Fundamentals: теория и базовая эксплуатация / Хабр].
</blockquote>
</details>

<details>
<summary>3. Где в Dockerfile (в начале или в конце) эффективнее располагать инструкцию RUN apt-get update?</summary>
<blockquote>
<b>Ответ:</b> В начале. Системные пакеты меняются значительно реже, чем код приложения. Расположение стабильных команд в начале файла позволяет максимально долго сохранять цепочку кэша [Optimizing the image size - MOOC.fi courses], [Изучаем Docker, часть 4: уменьшение размеров образов и ускорение их сборки / Хабр].
</blockquote>
</details>

<details>
<summary>4. Почему порядок COPY requirements.txt . -> RUN pip install -> COPY . . считается "золотым стандартом" для Flask-приложений?</summary>
<blockquote>
<b>Ответ:</b> Потому что это отделяет установку тяжелых зависимостей (которые меняются редко) от копирования кода (который меняется часто). Это позволяет Docker кэшировать установленные библиотеки и не перекачивать их при каждой правке кода [Docker Fundamentals: теория и базовая эксплуатация / Хабр], [Docker для новичков — #2 Все инструкции Dockerfile / Хабр].
</blockquote>
</details>

<details>
<summary>5. С помощью какого флага можно принудительно запустить сборку образа, полностью игнорируя существующий кэш?</summary>
<blockquote>
<b>Ответ:</b> С помощью флага <code>--no-cache=true</code> команды <code>docker image build</code> [Docker Deep Dive], [Docker Fundamentals: теория и базовая эксплуатация / Хабр].
</blockquote>
</details>
