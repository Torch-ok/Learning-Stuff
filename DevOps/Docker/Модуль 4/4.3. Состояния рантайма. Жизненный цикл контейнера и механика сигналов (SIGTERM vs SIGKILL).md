Понимание состояний рантайма и способов управления ими критически важно для обеспечения стабильности нашего интернет-магазина, особенно когда речь идет о корректном завершении транзакций в **PostgreSQL** или обработке активных HTTP-сессий во **Flask** [Docker и Docker Compose - Полный Курс](https://www.youtube.com/watch?v=n9uCgUzfeRQ).

#### Жизненный цикл контейнера: Граф состояний

Согласно архитектурным стандартам 2026 года, контейнер может находиться в одном из следующих состояний [Docker QnA vijay](https://github.com/vijay/docker-qna), [Docker_Up_and_Running]:

1. **Created (Создан):** Контейнер уже существует как объект в файловой системе хоста (`/var/lib/docker/containers`), у него выделены все необходимые `namespaces` и `cgroups`, но основной процесс (PID 1) еще не запущен [Docker-Cookbook].
2. **Running (Запущен):** Основной процесс приложения (например, `gunicorn` для Flask или `postgres` для базы данных) активно выполняется внутри изолированного окружения [Docker QnA vijay](https://github.com/vijay/docker-qna).
3. **Paused (Приостановлен):** Все процессы внутри контейнера «заморожены» на уровне планировщика ядра Linux (используется cgroups freezer). Контейнер не потребляет CPU, но сохраняет всё свое состояние в RAM [Docker_Up_and_Running].
4. **Restarting (Перезапуск):** Промежуточное состояние, когда контейнер завершился аварийно, и движок Docker пытается его поднять согласно политике `--restart` [Docker QnA vijay](https://github.com/vijay/docker-qna).
5. **Exited (Завершен):** Процесс PID 1 завершил свою работу. Если код выхода (Exit Code) равен `0`, завершение считается успешным. Если код отличен от нуля (например, `137` или `1`), это сигнализирует об ошибке или принудительной остановке [Docker-in-Practice], [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).
6. **Dead (Мертв):** Критическое состояние, возникающее редко, обычно при неудачной попытке удаления работающего контейнера или сбоях в драйвере хранения [Docker QnA vijay](https://github.com/vijay/docker-qna).

#### Механика управления: Команды и сигналы

Для переключения между состояниями используются управляющие команды, которые технически транслируются в системные сигналы Linux [Docker-in-Practice].

- **`docker container start`** — запускает ранее остановленный контейнер [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
- **`docker container pause / unpause`** — временно приостанавливает выполнение, не выгружая процесс из памяти [Docker_Up_and_Running].
- **`docker container restart`** — последовательно выполняет `stop` и `start` [Docker QnA vijay](https://github.com/vijay/docker-qna).

##### Битва сигналов: SIGTERM vs SIGKILL

Фундаментальная разница между «вежливой» остановкой и «казнью» процесса кроется в используемых сигналах [Docker-in-Practice].

**1. `docker container stop` (The Polite Request):** Когда вы вводите эту команду, Docker Daemon отправляет процессу PID 1 внутри контейнера сигнал **SIGTERM** (Signal Terminate) [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdfr%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker-in-Practice].

- **Graceful Shutdown:** Это дает нашему приложению **Flask** время (по умолчанию 10 секунд), чтобы закрыть соединения с БД, завершить текущие HTTP-запросы и корректно освободить память [Docker-in-Practice], [Docker_Up_and_Running].
- Если по истечении таймаута процесс всё еще жив, Docker отправляет беспощадный **SIGKILL** [Docker-in-Practice].

**2. `docker container kill` (The Bullet to the Head):** Эта команда не тратит время на переговоры. Она мгновенно отправляет сигнал **SIGKILL** [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker-in-Practice].

- Процесс убивается немедленно на уровне ядра. Файловые дескрипторы могут остаться в некорректном состоянии, временные файлы не будут удалены, а транзакции в **PostgreSQL** могут потребовать восстановления при следующем запуске [Docker_Up_and_Running], [Docker-in-Practice].

> [!warning] Актуализация синтаксиса 
> В старых источниках часто использовалась команда `docker kill` без указания объекта [Docker-Cookbook]. По стандартам 2026 года необходимо использовать строго `docker container kill`, чтобы избежать путаницы с будущими типами объектов рантайма [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).

#### Поиск и фильтрация: Мастерство владения `ls`

В крупном проекте (интернет-магазине) могут быть запущены десятки контейнеров. Для эффективного поиска используются следующие флаги команды `docker container ls` [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Изучаем Docker, часть 5: команды / Хабр](https://habr.com/ru/companies/ruvds/articles/440660/):

- **`-a, --all`:** Показать абсолютно все контейнеры, включая те, что упали или были намеренно остановлены [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
- **`-q, --quiet`:** Вывести только числовые идентификаторы (IDs). Идеально для автоматизации, например: `docker container rm $(docker container ls -aq)` [Docker-in-Practice], [Docker-Cookbook].
- **`--filter`:** Мощный инструмент отбора по критериям [Docker-in-Practice], [Docker_eBook].

**Примеры фильтрации:**

```bash
# Найти только упавшие контейнеры (Exit Code != 0)
docker container ls -a --filter "status=exited"

# Найти контейнер базы данных по имени
docker container ls --filter "name=shop-db"
```
