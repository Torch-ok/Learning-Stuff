Команда `docker container run` является самой часто используемой и, пожалуй, самой сложной командой в арсенале инженера. По стандартам 2026 года важно понимать, что это не просто команда запуска, а «комбо-команда», которая последовательно выполняет действия `docker container create` (создание контейнера из образа) и `docker container start` (запуск основного процесса).

Когда вы нажимаете Enter, Docker Daemon проверяет наличие образа локально, при необходимости скачивает его (pull), выделяет файловую систему, настраивает сетевой интерфейс и запускает процесс приложения внутри изолированных пространств имен.

#### Режимы работы: Detached vs Interactive

Выбор режима запуска определяет, как ваш терминал будет взаимодействовать с процессом внутри контейнера.

##### 1. Демонизированный/фоновый режим (-d / --detach)

Этот режим является стандартом для серверных компонентов нашего проекта, таких как база данных **PostgreSQL**. При использовании флага `-d` Docker запускает контейнер в фоновом режиме и сразу возвращает управление вашей командной строке, выводя лишь полный ID созданного контейнера.

**Пример для PostgreSQL:**

```bash
docker container run -d --name shop-db postgres:16-alpine
```

Процесс базы данных «засыпает» в фоне. Куда девается вывод? Все данные, которые приложение пишет в потоки `STDOUT` и `STDERR`, перехватываются **драйвером логирования** (по умолчанию `json-file`). Чтобы увидеть, что происходит внутри «демонизированного» Postgres, необходимо использовать команду:

```bash
docker container logs -f shop-db
```


##### 2. Интерактивный режим (-it / --interactive --tty)

Этот режим необходим, когда вам нужно «войти» внутрь контейнера для отладки кода **Flask** или запуска Python-скрипта в режиме REPL.

- **-i (--interactive):** Указывает Docker держать стандартный ввод (`STDIN`) открытым, даже если вы не подключены к контейнеру.
- **-t (--tty):** Выделяет виртуальный псевдо-терминал, который эмулирует поведение реального терминала (поддержка цветов, корректная обработка клавиши Enter).

**Пример для Python REPL:**

```bash
docker container run -it python:3.11-slim python
```

Без псевдо-терминала ввод команд в интерактивную оболочку Python был бы невозможен или крайне затруднен из-за отсутствия обратной связи.

#### Именование и политики перезапуска

По умолчанию Docker присваивает контейнерам случайные имена (например, `vigilant_borg`). В профессиональной эксплуатации использование флага `--name` обязательно. Это позволяет обращаться к контейнеру в командах `stop`, `logs` или `exec` по понятному имени, а также использовать его как DNS-имя внутри сети Docker.

##### Настройка самовосстановления (--restart)

Флаг `--restart` определяет, как Docker должен реагировать на завершение процесса внутри контейнера. Рассмотрим доступные значения для нашего стека:

- **always:** Контейнер будет перезагружаться всегда, даже если Docker Daemon был перезапущен или процесс завершился успешно (код 0).
- **unless-stopped:** Идеально для **PostgreSQL**. Контейнер будет перезагружаться автоматически при сбоях и после перезагрузки сервера, но если вы остановили его вручную (`docker container stop`), он не поднимется сам при старте системы.
- **on-failure:** Перезагрузка произойдет только в случае ненулевого кода выхода (ошибки).

> [!danger] Риски для Flask-приложения 
> Если в коде вашего бэкенда на Flask допущена фатальная ошибка (например, неверный синтаксис в конфигурации), и установлена политика `always`, контейнер попадет в бесконечный цикл перезагрузки («crash loop»). Это создает излишнюю нагрузку на CPU хоста и может забить системные логи гигабайтами однотипных сообщений об ошибках за считанные минуты.
