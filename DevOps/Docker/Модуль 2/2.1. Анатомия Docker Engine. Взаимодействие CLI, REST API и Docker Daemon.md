Фундаментальное понимание Docker начинается с осознания того, что перед нами не монолитная программа, а распределенное клиент-серверное приложение [Docker QnA vijay](https://github.com/vijay/docker-qna), [Изучаем Docker, часть 2: термины и концепции / Хабр](https://habr.com/ru/companies/ruvds/articles/439978/). Движок Docker, известный как **Docker Engine**, состоит из трех ключевых уровней абстракции, которые работают в тесной связке, чтобы обеспечить жизненный цикл наших сервисов, таких как **Nginx**, **Flask** и **PostgreSQL** [Docker для начинающих: что это такое и как пользоваться / Хабр](https://habr.com/ru/companies/netologyru/articles/967546/).

#### Компоненты архитектуры Docker Engine
1.  **Docker Client (CLI):** Это интерфейс командной строки (утилита `docker`), с которой взаимодействует пользователь. Его единственная задача — принимать команды, проверять их синтаксис и упаковывать в соответствующие запросы для сервера [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker: Up and Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/).
2.  **REST API:** Промежуточный слой, описывающий набор стандартных HTTP-интерфейсов. Именно через этот мост клиент общается с сервером. Поскольку API открыт и документирован, управлять Docker можно не только через консоль, но и с помощью собственных скриптов на Python или через веб-интерфейсы [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdfr%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker_eBook](https://zzzprojects.com/docker-ebook).
3.  **Docker Daemon (dockerd):** Серверная часть, фоновый процесс (**Daemon**), который выполняет всю «тяжелую» работу. Он слушает запросы к API, управляет образами (**Images**), создает контейнеры (**Containers**), настраивает сети (**Networks**) и монтирует тома (**Volumes**) [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [Docker QnA vijay](https://github.com/vijay/docker-qna).

#### Анатомия команды: Что происходит после нажатия Enter?
Рассмотрим процесс запуска нашего бэкенда командой `docker container run -d flask-app`. В те миллисекунды, что команда обрабатывается системой, происходит следующее:
*   **Упаковка запроса:** Клиент конвертирует вашу команду в HTTP-запрос. Например, вызов превращается в `POST /containers/create` с JSON-телом, содержащим параметры запуска [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker-Cookbook](https://www.oreilly.com/library/view/docker-cookbook/9781491917565/).
*   **Транспортировка:** По умолчанию в Linux запрос отправляется через локальный **UNIX-сокет** по адресу `/var/run/docker.sock`. Это специальный файл, который служит каналом связи между процессами внутри одной ОС [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/).
*   **Прием сервером:** Демон `dockerd` получает запрос, аутентифицирует его и начинает выполнение: проверяет наличие образа `flask-app` в локальном кэше, запрашивает ресурсы у ядра и инициирует создание изолированной среды [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/), [YouTube](https://www.youtube.com/watch?v=n9uCgUzfeRQ).

#### Безопасность сокета и риски "захвата хоста"
Доступ к файлу `/var/run/docker.sock` эквивалентен полному доступу к правам `root` на хостовой машине [Docker-in-Practice](https://manning.com/books/docker-in-practice). Именно поэтому для выполнения команд Docker пользователю необходимо либо использовать `sudo`, либо состоять в системной группе `docker` [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker-in-Practice](https://manning.com/books/docker-in-practice).

> [!danger] Критическая уязвимость
> Если системный администратор решит пробросить сокет внутрь контейнера (например, через `bind mount` с флагом `-v /var/run/docker.sock:/var/run/docker.sock`), то любой процесс внутри этого контейнера (даже если само приложение **Flask** работает от обычного пользователя) сможет отдавать команды демону хоста. Это позволяет злоумышленнику запустить новый привилегированный контейнер с полным доступом к файловой системе сервера, что означает мгновенный и полный захват всей физической машины [Docker-in-Practice](https://manning.com/books/docker-in-practice), [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781785281648).

#### Доказательство: CLI как обертка над API
Чтобы убедиться, что `docker` — это просто "красивая обертка", можно выполнить прямой запрос к демону через утилиту `curl` (используя сокет):
```bash
# Прямой вызов API для получения списка контейнеров
sudo curl --unix-socket /var/run/docker.sock http://localhost/v1.41/containers/json
````

**Ожидаемый результат (фрагмент JSON):**

```json
[
  {
    "Id": "8d12decc75fe...",
    "Names": ["/nginx-frontend"],
    "Image": "nginx:latest",
    "State": "running",
    "Status": "Up 2 hours"
  }
]
```

Этот вывод наглядно демонстрирует, что любая команда CLI — это лишь интерпретация структурированных данных, приходящих от **REST API Engine** [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf), [Docker-Cookbook](https://www.oreilly.com/library/view/docker-cookbook/9781491917565/).

#### Управление удаленным проектом (Flask + Postgres + Nginx)

Благодаря клиент-серверной архитектуре, вы можете управлять всей инфраструктурой интернет-магазина, не находясь на самом сервере. Если демон на удаленном сервере (например, в облаке AWS) настроен на прослушивание **TCP-порта 2376** с использованием **TLS**, разработчик может просто переключить контекст своего локального клиента [Docker_Up_and_Running](https://www.oreilly.com/library/view/docker-up-running/9781491917565/), [Docker-Cookbook](https://www.oreilly.com/library/view/docker-cookbook/9781491917565/).

Использование переменной окружения `DOCKER_HOST` заставляет вашу локальную утилиту `docker` отправлять запросы не в локальный сокет, а по сети:

```bash
export DOCKER_HOST=tcp://1.2.3.4:2376
docker compose up -d
```

После этого команды, введенные на вашем ноутбуке, создадут базу данных **PostgreSQL** и фронтенд **Nginx** непосредственно на удаленной машине, при этом процесс будет выглядеть абсолютно прозрачно для пользователя [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf/Docker Deep Dive Zero to Docker in a single book (Nigel Poulton) (z-lib.org).pdf), [Docker-Cookbook](https://www.oreilly.com/library/view/docker-cookbook/9781491917565/).

> [!warning] Актуализация синтаксиса 
> В старых источниках используется устаревший синтаксис (например, `docker ps`), однако по современным стандартам 2026 года для работы с контейнерами необходимо использовать Management Commands: `docker container ls` [Docker Deep Dive](https://z-lib.org/), [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).
