Ниже представлен перечень фундаментальных архитектурных понятий, определяющих работу современных контейнерных сред по стандартам 2026 года.

* **Docker Daemon (dockerd)** — постоянный фоновый процесс сервера, который управляет всеми объектами Docker: образами, контейнерами, сетями и томами, а также обрабатывает запросы от API [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).
* **UNIX Socket** — специальный файл в системе (обычно `/var/run/docker.sock`), используемый для локального межпроцессного взаимодействия (IPC) между Docker CLI и Docker Daemon; доступ к нему эквивалентен правам `root` на хосте [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
* **OCI (Open Container Initiative)** — открытая структура управления под эгидой Linux Foundation, устанавливающая индустриальные стандарты для форматов образов и рантаймов контейнеров, обеспечивая их совместимость [Docker для начинающих: что это такое и как пользоваться / Хабр](https://habr.com/ru/companies/netologyru/articles/967546/).
* **containerd** — высокоуровневый рантайм, выступающий в роли супервизора; он отвечает за скачивание образов, управление сетевыми интерфейсами и хранилищами, а также координирует жизненный цикл контейнеров [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
* **runC** — низкоуровневый рантайм и эталонная реализация спецификации OCI; его единственная задача — создать изоляционные барьеры (`namespaces`, `cgroups`) и запустить основной процесс приложения, после чего утилита завершает свою работу [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).
* **containerd-shim** — легкий промежуточный процесс, который становится «приемным родителем» для процесса приложения в контейнере; он удерживает открытыми файловые дескрипторы и позволяет Docker Daemon перезагружаться без остановки контейнеров [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
* **Docker Registry** — серверная инфраструктура для хранения и дистрибуции образов Docker; может быть публичной (Docker Hub) или частной (Harbor, AWS ECR) [Docker для новичков — #1 Что такое контейнер, image, DockerHub? / Хабр](https://habr.com/ru/articles/804323/).
* **Semantic Versioning (SemVer)** — методология именования версий в формате `MAJOR.MINOR.PATCH`, позволяющая избежать непредсказуемости, свойственной плавающему тегу `:latest` [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).

## Практическое упражнение (Развернутый интерактивный кейс Модуля 2)

**Сценарий «Выживание в тени демона»:**
Вы работаете DevOps-инженером в компании, поддерживающей крупный интернет-магазин. Инфраструктура включает в себя бэкенд на **Python/Flask** и базу данных **PostgreSQL**, работающие в Docker-контейнерах.

Во время планового обновления ядра Linux администратор случайно повредил права доступа к файлу сокета `/var/run/docker.sock`, установив их в режим `600` (только для `root`), при этом удалив всех пользователей из системной группы `docker`.

**Текущее состояние системы:**
1. Разработчики при попытке выполнить команду `docker container ls` получают критическую ошибку: `permission denied while trying to connect to the Docker daemon socket`.
2. Однако мониторинг показывает, что интернет-магазин продолжает работать: заказы принимаются, а **PostgreSQL** исправно пишет данные на диск.

**Задание:**
1. Объясните архитектурную причину того, почему контейнеры с Flask и Postgres продолжают функционировать, несмотря на недоступность Docker Daemon для CLI-клиента.
2. Опишите шаги по диагностике и восстановлению доступа к управлению движком.

***

**Развернутый правильный ответ и анализ:**

**1. Почему сервисы выжили?**
Это заслуга модульной архитектуры и компонента **containerd-shim**. В современном стеке Docker (по стандартам 2026 года) цепочка запуска выглядит так: `dockerd` → `containerd` → `containerd-shim` → `runC` → процесс приложения [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf).
Как только `runC` запускает процесс **Flask** или **Postgres**, он передает управление процессу `shim` и мгновенно завершается. `containerd-shim` становится родителем для контейнера. Если вышестоящий демон (`dockerd`) становится недоступен, поврежден или даже аварийно завершен, `shim` продолжает удерживать `STDOUT/STDERR` и следить за процессом приложения [Docker Deep Dive](obsidian://open?vault=DevOps&file=Sources%2FDocker%2FPdf%2FDocker%20Deep%20Dive%20Zero%20to%20Docker%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdfr%20in%20a%20single%20book%20(Nigel%20Poulton)%20(z-lib.org).pdf). Это обеспечивает так называемую «независимость рантайма от демона» (daemonless execution).

**2. План спасения:**
*   **Диагностика:** Необходимо выполнить `ls -l /var/run/docker.sock` из-под `sudo`, чтобы увидеть текущего владельца и маску прав доступа [Docker-in-Practice](https://manning.com/books/docker-in-practice).
*   **Восстановление прав:** Для восстановления стандартной работы необходимо вернуть владельца сокета (`root:docker`) и права доступа (`660`). Команда: `sudo chown root:docker /var/run/docker.sock && sudo chmod 660 /var/run/docker.sock` [Securing_Docker](https://www.packtpub.com/product/securing-docker/9781785281648).
*   **Проверка членства:** Убедиться, что текущий пользователь находится в группе `docker`: `groups $USER`. Если нет — добавить его: `sudo usermod -aG docker $USER` и перелогиниться [YouTube](https://www.youtube.com/watch?v=krZ6LXNtGaU).
