После того как мы собрали образ нашего интернет-магазина, возникает логичный вопрос: как доставить этот «замороженный» слепленный артефакт с ноутбука разработчика на боевой сервер? В мире Docker для этого используется централизованная модель распространения, основанная на реестрах (Registries). Если образ — это чертеж здания, то **Docker Registry** — это гигантское мировое хранилище таких чертежей, доступное в любой момент времени [Docker Deep Dive, 151], [Docker для начинающих: что это такое и как пользоваться / Хабр](https://habr.com/ru/companies/netologyru/articles/967546/).

#### Анатомия экосистемы хранения: Публичные vs Приватные реестры
1.  **Docker Hub** — это самый большой в мире публичный реестр образов, используемый по умолчанию [Изучаем Docker, часть 2: термины и концепции / Хабр](https://habr.com/ru/companies/ruvds/articles/439978/). Здесь живут официальные образы (например, `python`, `nginx`, `postgres`), которые курируются компанией Docker, Inc. и сообществом [Docker Deep Dive, 151].
2.  **Private Registries** — корпоративные решения для хранения закрытого кода и проприетарных конфигураций [Docker_Up_and_Running, 703]. К ним относятся такие инструменты, как **Harbor**, **Sonatype Nexus**, **AWS ECR (Elastic Container Registry)** или **Google Container Registry (GCR)**. Они позволяют компаниям настраивать права доступа (ACL), сканировать образы на уязвимости и хранить артефакты внутри своего закрытого сетевого периметра [Docker-Cookbook, 536], [Securing_Docker, 800].

#### Структура именования: Полный путь к образу
В 2026 году стандарт именования образа следует строгому иерархическому формату, который позволяет движку Docker точно определить местоположение ресурса в глобальной сети:

`registry.domain.com/project-name/image-name:tag`

*   **Registry (Host):** Адрес сервера реестра (например, `index.docker.io` для Docker Hub или `my-nexus.local:5000` для локального реестра). Если этот параметр опущен, Docker по умолчанию обращается к Docker Hub [Docker Deep Dive, 150].
*   **Project Name (Namespace):** Имя организации или пользователя. В Docker Hub официальные образы живут в пространстве `library` (например, `library/python`), а пользовательские — под их никами [Chapter 2: Introduction to Containers - MOOC.fi courses, 2].
*   **Image Name (Repository):** Название конкретного приложения (например, наш `flask-backend` или `postgres`) [Docker Deep Dive, 151].
*   **Tag:** Метка версии (например, `3.11-slim`, `16-alpine`). Если не указана, Docker автоматически подставит `:latest` [Chapter 2: Introduction to Containers - MOOC.fi courses, 2], [Изучаем Docker, часть 2: термины и концепции / Хабр](https://habr.com/ru/companies/ruvds/articles/439978/).

#### Развенчание мифа: Почему `:latest` — это мина замедленного действия
Использование тега `:latest` в продакшене считается критическим антипаттерном и «грехом» DevOps-инженера [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/). Многие ошибочно полагают, что `:latest` всегда указывает на самую свежую версию, но технически это просто «плавающий» (floating) тег, который мейнтейнер может присвоить любому образу [Docker_Up_and_Running, 708].

**Сценарий катастрофы в нашем интернет-магазине:**
Представьте, что в файле `compose.yaml` для базы данных вы указали `postgres:latest`.
1.  Сегодня `:latest` указывает на PostgreSQL 15. Вы запустили проект, всё работает.
2.  Через месяц мейнтейнеры выпускают PostgreSQL 16 с изменениями, ломающими обратную совместимость данных, и перевешивают тег `:latest` на новый образ [Docker Deep Dive, 159].
3.  Ваш сервер перезагружается, Docker видит команду «запустить `:latest`», скачивает обновленный образ... и база данных не стартует из-за конфликта версий файлов на диске. Магазин падает, заказы теряются [Docker Deep Dive, 160], [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).

Кроме того, `:latest` убивает возможность отката (Rollback). Если вы обновились до «последнего», вы не знаете, какой именно образ был «последним» вчера [Docker_Up_and_Running, 708].

#### Золотые правила версионирования в 2026 году
Для достижения абсолютной детерминированности и стабильности инженеры используют два подхода:

1.  **SemVer (Семантическое версионирование):** Использование четких меток версий, например `python:3.11.5-slim`. Это гарантирует, что вы получите именно ту версию интерпретатора и дистрибутива, на которых проводилось тестирование [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).
2.  **Pinned Digests (SHA-256):** Самый безопасный метод, при котором вы ссылаетесь на уникальный криптографический хэш содержимого образа. Даже если кто-то подменит тег в реестре, хэш останется неизменным [Docker Deep Dive, 160].

**Пример детерминированного запуска:**
```bash
# Запуск образа через уникальный Digest (SHA-256)
docker container run python@sha256:68c2dea730...f8cf7478
````

Этот метод делает вашу сборку иммунной к любым изменениям в реестре [Docker Deep Dive, 160-161].

> [!warning] Актуализация синтаксиса 
> В старых источниках часто встречается команда `docker images`, однако согласно современному стандарту Management Commands 2026 года для просмотра списка локальных образов следует использовать команду `docker image ls` [Docker Deep Dive, 163], [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).
