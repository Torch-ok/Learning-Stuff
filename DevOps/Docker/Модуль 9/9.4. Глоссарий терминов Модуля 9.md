Ниже приведен перечень фундаментальных сетевых понятий Docker, знание которых необходимо для проектирования отказоустойчивых и безопасных распределенных систем в стандартах 2026 года.

- **Port Forwarding** — механизм перенаправления трафика с определенного порта хост-машины на внутренний порт контейнера (например, `-p 80:5000`), позволяющий внешним клиентам получать доступ к изолированным сервисам,,,.
- **NAT (Network Address Translation)** — технология преобразования сетевых адресов, используемая Docker Daemon для маршрутизации пакетов между физическими интерфейсами сервера и виртуальными интерфейсами контейнеров через цепочки `iptables`,,,.
- **Bridge Network** — виртуальный программный коммутатор (мост), создаваемый Docker в ядре Linux для объединения группы контейнеров в единый широковещательный домен второго уровня,,,,.
- **Service Discovery** — процесс автоматического обнаружения сетевых адресов сервисов; в Docker это позволяет приложению Flask обращаться к базе данных по её имени (например, `db:5432`), не зная текущего динамического IP-адреса,,,,.
- **Embedded DNS** — встроенный в Docker Engine DNS-резолвер, который обслуживает пользовательские сети и обеспечивает сопоставление имен контейнеров или сервисов с их внутренними IP-адресами,,,.
- **Host Network** — сетевой режим, при котором контейнер полностью лишается сетевой изоляции и использует сетевой стек хост-машины напрямую, что обеспечивает максимальную производительность, но повышает риски безопасности,,,.
- **Overlay Network** — тип программно-определяемой сети, позволяющий объединять контейнеры, запущенные на разных физических серверах (узлах кластера), в единую логическую сеть через VXLAN-туннели,,,,.

## Практическое упражнение (Построение изолированного сетевого периметра для Nginx, Flask и PostgreSQL)

**Инженерная задача:** В рамках реализации нашего сквозного проекта необходимо развернуть инфраструктуру веб-приложения с соблюдением принципа «сетевой матрешки». Мы должны гарантировать, что база данных **PostgreSQL** физически недоступна из внешней сети, а веб-сервер **Nginx** может «общаться» только с бэкендом **Flask**, выступающим в роли защищенного шлюза,.

Ниже представлен Bash-скрипт для настройки такого периметра через CLI Docker Engine,.

```bash
#!/bin/bash

# 1. Создаем два сегмента сети: публичный (frontend) и изолированный (backend)
# Пользовательские сети автоматически включают Service Discovery через DNS,.
docker network create --driver bridge frontend_net
docker network create --driver bridge backend_net

# 2. Запускаем PostgreSQL в изолированной сети
# Мы не используем флаг -p, так как базе не нужен доступ во внешний мир,.
docker container run -d \
  --name shop_db \
  --network backend_net \
  -e POSTGRES_PASSWORD=top_secret \
  postgres:16-alpine

# 3. Запускаем Flask-бэкенд в backend_net
# Контейнер Flask будет видеть PostgreSQL по имени "shop_db" благодаря DNS,.
docker container run -d \
  --name flask_app \
  --network backend_net \
  -e DB_HOST=shop_db \
  flask_image:latest

# 4. Динамически подключаем Flask к frontend_net
# Теперь Flask становится "мостом", имея два сетевых интерфейса [9.3. Администрирование сетей].
docker network connect frontend_net flask_app

# 5. Запускаем Nginx в публичной сети с пробросом портов
# Nginx проксирует запросы на "flask_app:5000", но не видит "shop_db",.
docker container run -d \
  --name nginx_proxy \
  --network frontend_net \
  -p 80:80 \
  -v $(pwd)/nginx.conf:/etc/nginx/nginx.conf:ro \
  nginx:latest

echo "Сетевой периметр успешно развернут."
```

**Архитектурные пояснения к решению:**

1. **Сетевая сегментация:** Создание двух сетей `frontend_net` и `backend_net` позволяет реализовать концепцию **DMZ** [9.3. Администрирование сетей]. База данных находится в самом глубоком контуре и не имеет выхода во внешнюю сеть.
2. **Service Discovery:** Приложения сконфигурированы через имена контейнеров (`shop_db`, `flask_app`), что избавляет нас от необходимости хардкодить IP-адреса, которые Docker присваивает динамически,,.
3. **Безопасность:** Злоумышленник, получивший доступ к контейнеру `nginx_proxy`, не сможет просканировать или атаковать `shop_db`, так как между этими сетями отсутствует прямая маршрутизация на уровне ядра Linux,.
