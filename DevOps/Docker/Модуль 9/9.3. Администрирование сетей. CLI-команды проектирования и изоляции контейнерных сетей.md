В профессиональной DevOps-практике 2026 года сеть рассматривается как фундамент всей инфраструктуры: «нет сети — нет приложения». Движок Docker Engine предоставляет развитый набор инструментов управления сетевыми абстракциями через Management Commands группы `docker network`, которые позволяют инженеру динамически изменять топологию связей без перезапуска всей системы, [Docker Fundamentals: теория и базовая эксплуатация / Хабр](https://habr.com/ru/companies/ruvds/articles/1043544/).

#### Жизненный цикл сетевых абстракций в CLI

Для управления ландшафтом сетей используются четыре базовые команды, обеспечивающие полный контроль над виртуальными коммутаторами:

1. **`docker network ls`** — аудит всех существующих сетей на хосте,. В выводе всегда присутствуют три дефолтные сети (`bridge`, `host`, `none`), которые невозможно удалить.
2. **`docker network create`** — создание новой программно-определяемой сети (SDN). По умолчанию в Linux создается сеть типа `bridge`.
    
    ```bash
    # Создание изолированной сети для базы данных
    docker network create --driver bridge backend_net
    ```

3. **`docker network inspect`** — глубокий анализ конфигурации сети в формате JSON,. Команда позволяет увидеть подсеть (`Subnet`), шлюз (`Gateway`) и, что самое важное, список всех подключенных контейнеров с их текущими IP-адресами в секции `Containers`. 
4. **`docker network rm`** и **`docker network prune`** — инструменты очистки. `prune` безвозвратно удаляет все сети, к которым в данный момент не подключено ни одного контейнера.

#### Динамическое управление связями: connect и disconnect

Одной из самых мощных функций Docker является возможность изменять сетевое окружение контейнера «на лету». В отличие от классических виртуальных машин, контейнер может иметь несколько сетевых интерфейсов и принадлежать к нескольким изолированным сетям одновременно,.

- **`docker network connect [сеть] [контейнер]`** — добавляет работающий контейнер в указанную сеть, создавая внутри него новый виртуальный интерфейс и обновляя локальный DNS-резолвер для Service Discovery.
- **`docker network disconnect [сеть] [контейнер]`** — мгновенно обрывает связь контейнера с сетью, удаляя соответствующий интерфейс и записи из `/etc/hosts`.

**Сценарий «Контейнер-мост»:** В нашем сквозном проекте бэкенд **Flask** должен принимать запросы от **Nginx** и отправлять данные в **PostgreSQL**. При этом из соображений безопасности Nginx не должен иметь даже теоретической возможности «увидеть» базу данных. Мы подключаем контейнер Flask к двум сетям: `frontend_net` (где живет Nginx) и `backend_net` (где живет PostgreSQL),. Flask становится единственной точкой входа, обладающей доступом к обоим сегментам,.

#### Реализация концепции DMZ (Демилитаризованной зоны)

Используя CLI-команды, мы можем реализовать эшелонированную защиту нашего стека, предотвращая боковое перемещение (lateral movement) злоумышленника в случае взлома фронтенда.

**Алгоритм настройки безопасной среды:**

1. **Создаем сегменты:**
    
    ```bash
    docker network create public_net   # Внешний контур
    docker network create private_net  # Внутренний контур (БД)
    ```

2. **Запускаем изолированную БД:** 

    ```bash
    bash docker container run -d --name shop_db --network private_net postgres:16-alpine
    ``` 

3. **Запускаем Nginx в публичном контуре:** 

   ```bash
   bash docker container run -d --name nginx_front -p 80:80 --network public_net nginx:latest
   ``` 
   
4. **Связываем миры через Flask:** Сначала запускаем Flask в `private_net`, а затем динамически подключаем его к `public_net`: 
   ```bash docker container run -d --name flask_app --network private_net flask_image docker network connect public_net flask_app```

**Результат:** Контейнеры `nginx_front` и `shop_db` физически не могут обмениваться пакетами, так как у них нет общей сети,. Даже если злоумышленник получит Shell внутри Nginx, команда `ping shop_db` завершится ошибкой `Name or service not known`, так как DNS-сервер публичной сети ничего не знает о существовании базы данных.
