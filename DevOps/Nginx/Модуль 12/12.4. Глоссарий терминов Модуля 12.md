Данный раздел содержит ключевые понятия, необходимые для эксплуатации Nginx в изолированных средах и оперативного решения инцидентов.

- **Docker Unprivileged Nginx** — специализированная сборка образа (например, `nginxinc/nginx-unprivileged`), настроенная для запуска от имени не-root пользователя `nginx` (UID 101), что требует смены стандартного порта на `8080` и путей системных файлов на `/tmp/`.
- **envsubst Templating** — встроенный механизм официальных образов, использующий утилиту `envsubst` для динамической подстановки переменных окружения из шаблонов `.template` в финальные конфигурационные файлы при старте контейнера.
- **502 Bad Gateway** — код ошибки, сигнализирующий о невозможности Nginx установить соединение с бэкендом (FastAPI/Uvicorn) или получении от него некорректного ответа, часто вызванный падением процесса или неверным путем к сокету.
- **504 Gateway Timeout** — состояние, при котором прокси-сервер не дождался ответа от апстрима в течение времени, заданного директивой `proxy_read_timeout`, что обычно указывает на долгие запросы к PostgreSQL.
- **413 Request Entity Too Large** — статусная ошибка, возникающая, когда размер тела HTTP-запроса клиента превышает лимит, установленный директивой `client_max_body_size`.
- **Infinite Redirect Loop** — критическая ошибка конфигурации (цикл перенаправлений), возникающая при совпадении правил `rewrite` самих с собой или конфликтах HTTP/HTTPS, прерываемая Nginx после 10 итераций.
- **nginx -T Dump** — команда для проверки синтаксиса, которая дополнительно выводит в терминал полный текст итоговой конфигурации со всеми раскрытыми директивами `include`, что незаменимо для отладки в Docker.
- **Debug Logging (debug_connection)** — режим сверхподробного логирования всех этапов обработки запроса, который может быть включен выборочно для конкретных IP-адресов разработчиков в блоке `events`.

## Практическое упражнение (Развертывание производственной связки Nginx + FastAPI + PostgreSQL в Docker Compose с отладкой 502/504 ошибок и шаблонизацией)

**Сценарий:** Вам необходимо развернуть отказоустойчивый стек. При старте вы обнаруживаете, что API не отвечает, а загрузка аватарок пользователей обрывается.

### 1. Подготовка инфраструктуры (`docker-compose.yml`)

```yml
services:
  db:
    image: postgres:15-alpine
    environment:
      POSTGRES_PASSWORD: ${DB_PASS}

  app:
    build: ./app
    volumes:
      - shared_run:/run/uvicorn  # Общий том для Unix-сокета
    environment:
      DATABASE_URL: postgresql://user:${DB_PASS}@db/dbname

  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx/templates:/etc/nginx/templates:ro
      - shared_run:/run/uvicorn:ro
    environment:
      - APP_HOST=unix:/run/uvicorn/app.sock
      - CLIENT_MAX_BODY=1M # Исходный малый лимит
    depends_on:
      - app

volumes:
  shared_run:
```

### 2. Шаблон конфигурации (`nginx/templates/default.conf.template`)

```nginx
server {
    listen 80;

    # Использование переменных для envsubst
    client_max_body_size ${CLIENT_MAX_BODY};

    location / {
        proxy_pass http://${APP_HOST};
        include proxy_params;
    }
}
```

### 3. Траблшутинг и решение инцидентов

#### Инцидент А: 502 Bad Gateway
**Локализация:** Команда `docker logs nginx` показывает:

```text
[error] connect() to unix:/run/uvicorn/app.sock failed (2: No such file or directory)
```

**Причина:** FastAPI запущен внутри контейнера `app`, но путь к сокету в коде Uvicorn не совпадает с точкой монтирования в Nginx.
**Решение:** Синхронизировать пути в параметрах запуска `uvicorn --unix-socket /run/uvicorn/app.sock` и перезапустить сервис.

#### Инцидент Б: 504 Gateway Timeout
**Локализация:** При вызове тяжелого отчета в логах:
```text
[error] upstream timed out (110: Connection timed out) while reading response header
```

**Причина:** Обработка в FastAPI занимает 70 секунд, а дефолт Nginx — 60 секунд.
**Решение:** В конфиг добавить `proxy_read_timeout 120s;` и применить `nginx -s reload`.

#### Инцидент В: 413 Request Entity Too Large
**Локализация:** Пользователь видит ошибку в браузере. Лог Nginx:
```text
`client intended to send too large body: 5242880 bytes
```

**Причина:** Лимит `${CLIENT_MAX_BODY}` равен `1M`, а файл весит 5МБ.
**Решение:** Обновить переменную в `.env` файле на `CLIENT_MAX_BODY=10M` и перезапустить контейнеры для работы `envsubst`.

### 4. Финальная диагностика
Выполните дамп конфига, чтобы убедиться в подстановке переменных:
```bash
docker exec nginx nginx -T
```.

### Интерактивный тест для самопроверки

1. **Какой стандартный UID используется для пользователя nginx в unprivileged образах?**
    <details>
    <summary>Ответ</summary>
    UID 101. Это позволяет запускать контейнер с ограниченными правами в системах типа Kubernetes или OpenShift.
    </details>

2. **Куда должны направляться `access_log` и `error_log` в Docker-контейнере для их корректного сбора через `docker logs`?**
    <details>
    <summary>Ответ</summary>
    На символические ссылки `/dev/stdout` и `/dev/stderr` соответственно.
    </details>

3. **Какая ошибка возникнет, если бэкенд Uvicorn упал и перестал слушать порт, на который Nginx проксирует запросы?**
    <details>
    <summary>Ответ</summary>
    502 Bad Gateway (в логах будет сообщение `Connection refused`).
    </details>

4. **Как проверить итоговый скомпилированный конфиг Nginx внутри пода Kubernetes без доступа к исходным файлам?**
    <details>
    <summary>Ответ</summary>
    Выполнить команду `kubectl exec <pod_name> -- nginx -T`. Это покажет все вложенные include в одном выводе.
    </details>

5. **Что произойдет, если количество внутренних редиректов в Nginx превысит 10?**
    <details>
    <summary>Ответ</summary>
    Nginx вернет ошибку 500 Internal Server Error с записью в логах "rewrite or internal redirection cycle".
    </details>
