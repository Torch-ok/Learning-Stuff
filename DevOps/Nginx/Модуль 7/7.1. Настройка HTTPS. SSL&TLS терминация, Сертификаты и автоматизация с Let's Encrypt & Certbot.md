В современной архитектуре высоконагруженных систем Nginx выступает не просто как веб-сервер, а как стратегический узел безопасности, обеспечивающий шифрование данных в транзите. Для Middle DevOps инженера настройка HTTPS — это не только установка сертификата, но и правильное проектирование архитектуры терминации трафика для обеспечения максимальной производительности бэкенда.

#### 7.1.1. Концепция TLS-терминации (TLS Termination)

**TLS-терминация** — это процесс завершения зашифрованного соединения на стороне прокси-сервера (Nginx), после чего трафик передается на бэкенд (Uvicorn / FastAPI) в открытом виде (HTTP) или перешифровывается с использованием облегченных протоколов.

**Зачем выносить шифрование на Nginx:**

1. **Снятие нагрузки с бэкенда:** Операции SSL Handshake и симметричного шифрования крайне ресурсоемки. Асинхронные Worker-процессы Nginx, написанные на C, значительно эффективнее справляются с криптографией, чем интерпретируемый Python-код бэкенда, ограниченный Global Interpreter Lock (GIL).
2. **Централизованное управление:** Все SSL-сертификаты хранятся в одном месте, что упрощает их обновление и аудит.
3. **Оптимизация соединений:** Nginx может поддерживать долгоживущие Keepalive-соединения с клиентами по HTTPS, в то время как взаимодействие с бэкендом внутри закрытого контура происходит по быстрым Unix-сокетам или TCP.

#### 7.1.2. Ключевые директивы конфигурации SSL/TLS

Базовая настройка защищенного сервера требует определения параметров внутри блока `server`.

- **`ssl_certificate`** — задает путь к файлу сертификата в формате PEM. В Production-среде необходимо использовать так называемый **Fullchain** — файл, содержащий сертификат вашего домена, а затем все промежуточные сертификаты удостоверяющего центра (CA).

- **`ssl_certificate_key`** — задает путь к закрытому ключу (Private Key).
    
- **`ssl_protocols`** — определяет разрешенные версии протокола TLS. По стандартам безопасности 2026 года необходимо использовать:
    
    ```
    ssl_protocols TLSv1.2 TLSv1.3;
    ```
    
    Использование SSLv3, TLS 1.0 и TLS 1.1 **категорически запрещено**, так как эти протоколы содержат критические уязвимости и признаны небезопасными всеми современными браузерами. TLS 1.3 является предпочтительным, так как он обеспечивает более быстрый Handshake (1-RTT) и повышенную стойкость к атакам.

> [!important] Безопасность ключей 
Файл закрытого ключа должен быть доступен для чтения только мастер-процессу Nginx (который обычно запускается от `root`). Рекомендуется устанавливать права доступа `chmod 600` на файл ключа.
#### 7.1.3. Автоматизация с Let's Encrypt и Certbot

Let's Encrypt предоставляет бесплатные SSL-сертификаты с коротким сроком жизни (90 дней), что делает автоматизацию их выпуска обязательной.

##### Механика валидации HTTP-01 challenge

Для подтверждения владения доменом утилита `certbot` использует метод **HTTP-01 challenge**. Let's Encrypt отправляет запрос на ваш сервер по адресу `http://<domain>/.well-known/acme-challenge/`. Nginx должен отдать временный токен, созданный `certbot`, чтобы подтвердить валидность запроса.

Для этого в конфигурации Nginx создается специальный блок:

```nginx
location /.well-known/acme-challenge/ {
    root /var/www/certbot;
}
```

##### Использование Certbot

Существует два основных подхода к работе с утилитой:

1. **`certbot --nginx`**: Полностью автоматический режим. Certbot сам находит блоки `server`, правит конфиги и добавляет пути к сертификатам. Удобно для быстрых стартов, но может внести хаос в сложные конфигурации.
2. **`certbot certonly --webroot`**: Более "чистый" режим для Senior DevOps. Certbot только получает сертификаты и складывает их в `/etc/letsencrypt/live/`, не трогая конфиги Nginx. Пути к файлам прописываются вручную.

##### Автоматизация продления

Поскольку сертификаты живут 90 дней, в системе настраивается автоматическая задача через `systemd timer` или `cron`. Критически важным элементом является **post-hook** — команда, которая заставляет Nginx перечитать сертификаты после их обновления:

```bash
certbot renew --post-hook "nginx -s reload"
```

Команда `nginx -s reload` предпочтительнее `restart`, так как она обновляет конфигурацию без разрыва текущих соединений пользователей.
