В данном разделе собраны ключевые понятия и протоколы, обеспечивающие криптографическую защиту и контроль доступа в веб-инфраструктуре на базе Nginx.

- **TLS Termination (TLS-терминация)** — процесс расшифровки входящего HTTPS-трафика на стороне Nginx перед его передачей на бэкенд в открытом виде (HTTP), что освобождает ресурсы процессора на серверах приложений [Основы NGINX глазами разработчика / YouTube](https://www.youtube.com/watch?v=...).
- **Certbot / ACME Protocol** — клиентское ПО и протокол взаимодействия, позволяющие автоматизировать получение, проверку и продление SSL-сертификатов от удостоверяющего центра Let's Encrypt [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).
- **OCSP Stapling** — технология оптимизации, при которой веб-сервер самостоятельно кэширует статус валидности своего сертификата и передает его клиенту в процессе хэндшейка, избавляя браузер от лишних запросов к CA [Модуль ngx_http_ssl_module](https://nginx.org/ru/docs/http/ngx_http_ssl_module.html#ssl_stapling).
- **TLS 1.3 Handshake** — современный стандарт установления защищенного соединения за один цикл обмена данными (1-RTT), обеспечивающий максимальную производительность и исключающий устаревшие алгоритмы шифрования [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).
- **HSTS (Strict-Transport-Security)** — защитный HTTP-заголовок, инструктирующий браузер взаимодействовать с сайтом исключительно по протоколу HTTPS в течение длительного времени [Complete-NGINX-Cookbook-2019](https://www.nginx.com/resources/library/complete-nginx-cookbook/).
- **Content Security Policy (CSP)** — механизм безопасности, позволяющий задать белый список разрешенных источников ресурсов (скриптов, стилей), что эффективно предотвращает XSS-атаки и инъекции [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).
- **HTTP 308 Redirect** — статус постоянного перенаправления, который, в отличие от 301, строго требует от клиента сохранения исходного HTTP-метода (POST, PUT) при обращении к новому адресу [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).
- **Basic Auth (.htpasswd)** — метод проверки подлинности пользователя на уровне протокола HTTP, использующий файл с парами логин:хэш-пароля для ограничения доступа к ресурсам [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).

## Практическое упражнение (Комплексный SSL/TLS харденинг Nginx для защищенного доступа к FastAPI с Let's Encrypt и Security Headers)

**Сценарий:** Нам необходимо подготовить Production-конфигурацию Nginx для FastAPI-приложения, обеспечив наивысший рейтинг безопасности (A+ по версии SSL Labs) и защитив служебные эндпоинты от несанкционированного доступа.

### Шаг 1: Генерация параметров безопасности

Перед настройкой Nginx необходимо создать файл параметров Диффи-Хеллмана повышенной стойкости и файл паролей.

```bash
# Генерация 4096-битных параметров DH
sudo openssl dhparam -out /etc/nginx/ssl/dhparam.pem 4096

# Создание файла паролей для администратора (требует apache2-utils)
sudo htpasswd -c /etc/nginx/.htpasswd admin_devops
``` 
[Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536), [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).

### Шаг 2: Итоговая конфигурация Nginx (`/etc/nginx/sites-available/fastapi_secure.conf`)
```nginx
# 1. Принудительный редирект на HTTPS с сохранением методов API
server {
    listen 80 default_server;
    listen [::]:80 default_server;
    server_name api.example.com;

    return 308 https://$host$request_uri;
}

server {
    listen 443 ssl http2; # HTTP/2 для производительности
    server_name api.example.com;

    # 2. SSL сертификаты (пути certbot)
    ssl_certificate /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;

    # 3. SSL Харденинг
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:DHE-RSA-AES128-GCM-SHA256:DHE-RSA-AES256-GCM-SHA384;
    ssl_prefer_server_ciphers off; # TLS 1.3 сам выбирает лучший шифр

    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1d;
    ssl_session_tickets off; # Защита PFS

    ssl_dhparam /etc/nginx/ssl/dhparam.pem;

    # 4. OCSP Stapling
    ssl_stapling on;
    ssl_stapling_verify on;
    ssl_trusted_certificate /etc/letsencrypt/live/api.example.com/chain.pem;
    resolver 8.8.8.8 8.8.4.4 valid=300s;
    resolver_timeout 5s;

    # 5. HTTP Security Headers
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self';" always;

    # 6. Защита служебного URI /docs
    location /docs {
        satisfy any; # Либо IP, либо пароль

        allow 192.168.1.0/24; # Офисная сеть
        deny all;

        auth_basic "Restricted Access to Documentation";
        auth_basic_user_file /etc/nginx/.htpasswd;

        proxy_pass http://uvicorn_backend;
    }

    location / {
        proxy_pass http://uvicorn_backend;
        include proxy_params;
    }
}
``` 
[Модуль ngx_http_ssl_module](https://nginx.org/ru/docs/http/ngx_http_ssl_module.html), [Complete-NGINX-Cookbook-2019](https://www.nginx.com/resources/library/complete-nginx-cookbook/), [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).

### Шаг 3: Проверка конфигурации
1.  **Синтаксис:** `sudo nginx -t`.
2.  **Заголовки:** `curl -I https://api.example.com` (проверка наличия `Strict-Transport-Security` и `X-Content-Type-Options`).
3.  **Аутентификация:** Попытка зайти на `/docs` должна вернуть `401 Unauthorized` без правильных учетных данных.

### Интерактивный тест для самопроверки

1. **Какую команду Certbot следует использовать, чтобы получить сертификат, не изменяя конфигурационные файлы Nginx вручную?**
    <details>
    <summary>Ответ</summary>
    `certbot --nginx`. Эта команда автоматически находит блоки server и прописывает необходимые пути к сертификатам [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).
    </details>

2. **Зачем нужна директива `ssl_dhparam`?**
    <details>
    <summary>Ответ</summary>
    Она указывает путь к файлу с параметрами Диффи-Хеллмана, которые используются для обеспечения безопасного обмена ключами в DHE-шифрах, гарантируя стойкость к расшифровке прошлых сессий [Модуль ngx_http_ssl_module](https://nginx.org/ru/docs/http/ngx_http_ssl_module.html).
    </details>

3. **От какой атаки защищает заголовок `X-Content-Type-Options: nosniff`?**
    <details>
    <summary>Ответ</summary>
    От MIME-sniffing атак, при которых браузер пытается угадать тип контента (например, исполнить картинку как JS-скрипт), игнорируя заголовок Content-Type [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).
    </details>

4. **Что делает параметр `always` в директиве `add_header`?**
    <details>
    <summary>Ответ</summary>
    Гарантирует, что заголовок будет добавлен в ответ сервера даже при кодах ошибок (например, 404 или 500), а не только при успешных ответах 2xx [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).
    </details>

5. **Какое значение `$upstream_cache_status` вы увидите в логах, если Nginx отдал зашифрованный ответ, сохраненный ранее?**
    <details>
    <summary>Ответ</summary>
    Статус `HIT`. Кэширование работает прозрачно для SSL/TLS после терминации трафика [Основы NGINX глазами разработчика / YouTube](https://www.youtube.com/watch?v=...).
    </details>
