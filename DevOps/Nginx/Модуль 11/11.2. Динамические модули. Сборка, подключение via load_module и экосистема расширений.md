Архитектура Nginx построена на модульном принципе, где ядро (Core) предоставляет лишь базовые механизмы управления соединениями и чтением конфигурации, а вся прикладная логика — от обработки HTTP до фильтрации изображений — реализуется через специализированные модули,. В высоконагруженных окружениях 2026 года инженер должен уметь гибко управлять функционалом сервера, выбирая между монолитной стабильностью и гибкостью динамической загрузки в runtime,.

#### 11.2.1. Монолитная сборка vs. Динамическая загрузка

До версии 1.9.11 Nginx поддерживал исключительно **статическую компиляцию** модулей. Это означало, что любое изменение набора функций (например, добавление поддержки Brotli) требовало полной пересборки бинарного файла `nginx`,.

- **Static Modules (Статические модули)** — встраиваются непосредственно в основной бинарный файл на этапе компиляции с помощью флага `./configure --add-module=...`. Они обеспечивают максимальную производительность, так как загружаются вместе с процессом и не требуют дополнительных операций в памяти,.
- **Dynamic Modules (Динамические модули)** — поставляются в виде отдельных файлов с расширением `.so` (shared objects). Они компилируются отдельно и подключаются к уже установленному серверу без его замены, что упрощает обновление и поддержку в рамках пакетных менеджеров (APT, YUM),.

#### 11.2.2. Механика работы директивы load_module

Для активации внешнего расширения используется директива `load_module`, которая должна быть расположена строго на верхнем уровне конфигурации — в **Main Context**,.

**Синтаксис:**

```
load_module modules/ngx_http_geoip2_module.so;
```

> [!warning] Актуализация синтаксиса 
> Динамические модули КАТЕГОРИЧЕСКИ требуют бинарной совместимости с основным процессом Nginx. Это означает, что модуль `.so` должен быть собран не просто той же версией Nginx (например, 1.31.0), но и с абсолютно идентичными флагами компиляции (флаги оптимизации, поддержка потоков, библиотеки SSL),. Несоблюдение этого правила приведет к ошибке запуска процесса или аварийному завершению (Segmentation Fault).

#### 11.2.3. Пошаговый процесс сборки динамического модуля

Если необходимый функционал (например, `headers-more`) отсутствует в официальном репозитории или в пакетах Angie, инженер выполняет сборку из исходного кода,.

1. **Загрузка исходных кодов:** Скачиваются исходники текущей версии Nginx и исходный код модуля (например, с GitHub),.
2. **Конфигурация:** Выполняется команда `./configure` с параметром `--add-dynamic-module`.
    
    ```
    ./configure --with-compat --add-dynamic-module=/path/to/module_source
    ```
    
    _Параметр `--with-compat` критически важен, так как он обеспечивает бинарную совместимость с другими сборками той же версии._
3. **Компиляция модулей:** Вместо полной сборки выполняется команда `make modules`, которая создает только файлы `.so` в директории `objs/`,.
4. **Установка:** Полученный файл `.so` копируется в системную директорию модулей (обычно `/usr/lib/nginx/modules/`),.

#### 11.2.4. Экосистема сторонних модулей в Production

Современная инфраструктура опирается на проверенные временем расширения, которые расширяют возможности Nginx до уровня полноценной платформы доставки приложений (Application Delivery Platform),.

- **GeoIP2 (`ngx_http_geoip2_module`)** — позволяет определять местоположение пользователя по IP и выполнять маршрутизацию запросов (например, направлять трафик из Азии на ближайший кластер),,.
- **Brotli (`ngx_http_brotli_module`)** — стандарт сжатия 2026 года от Google, превосходящий Gzip по степени компрессии текстовых данных,,.
- **Headers-More (`ngx_http_headers_more_filter_module`)** — предоставляет расширенный контроль над заголовками HTTP, позволяя удалять или изменять заголовки `Server` и `X-Powered-By` для скрытия деталей стека от сканеров.
- **Lua (`ngx_http_lua_module`)** — превращает Nginx в мощный скриптовый сервер, позволяя выполнять сложную логику проверки токенов или взаимодействия с Redis прямо на этапе обработки запроса,,.

### Интерактивный тест для самопроверки

1. **В каком контексте `nginx.conf` разрешено использовать директиву `load_module`?**
    <details>
    <summary>Ответ</summary>
    Только в `main` контексте (на верхнем уровне, вне блоков `http`, `events` или `stream`) [9], [10].
    </details>

2. **Что произойдет, если попытаться подключить динамический модуль, собранный для версии Nginx 1.25, к серверу версии 1.29?**
    <details>
    <summary>Ответ</summary>
    Сервер выдаст ошибку бинарной несовместимости при тестировании конфигурации (`nginx -t`) или откажется запускаться из-за несовпадения сигнатур версии [11], [3].
    </details>

3. **Какой флаг компиляции позволяет собрать модуль так, чтобы он был бинарно совместим с другими сборками Nginx той же версии?**
    <details>
    <summary>Ответ</summary>
    Флаг `--with-compat` [14].
    </details>

4. **В чем преимущество динамических модулей перед статическими для системного администратора?**
    <details>
    <summary>Ответ</summary>
    Они позволяют добавлять или удалять функционал сервера без полной пересборки основного бинарного файла, что значительно упрощает эксплуатацию и автоматизацию [7], [1], [3].
    </details>

5. **Какая утилита Nginx (модуль) позволяет превратить прокси в полноценный шлюз с логикой на языке программирования (например, для проверки JWT)?**
    <details>
    <summary>Ответ</summary>
    Модули `njs` (JavaScript), `ngx_http_lua_module` (Lua) или `ngx_http_perl_module` (Perl) [26], [25], [27].
    </details>
