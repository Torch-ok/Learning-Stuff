В высоконагруженных сетевых архитектурах 2026 года встроенные переменные Nginx являются фундаментальным инструментом для создания гибких, адаптивных и «умных» конфигураций. Переменные представляют собой именованные значения, которые вычисляются во время выполнения (runtime) и отражают текущее состояние запроса, клиента или бэкенда. Для Senior DevOps инженера они служат базой для динамической маршрутизации трафика к микросервисам (FastAPI / Uvicorn), прецизионного логирования и реализации сложной логики без внесения изменений в код приложения.

#### Роль встроенных переменных в контексте запроса

Переменные позволяют Nginx обрабатывать каждый HTTP-запрос индивидуально, основываясь на его метаданных. Большинство переменных вычисляются в контексте конкретного запроса и кэшируются на время его обработки для минимизации нагрузки на CPU. Они используются как параметры директив (например, в `proxy_pass` или `rewrite`), а также для формирования детализированных журналов доступа (`access_log`).

#### Ключевые группы встроенных переменных

Для эффективного управления трафиком Middle/Senior специалисты оперируют четырьмя основными категориями переменных.

##### 1. Сетевые и клиентские переменные

Эти переменные описывают физические параметры соединения между клиентом и Nginx.

- **`$remote_addr`** — IP-адрес клиента в текстовом виде.
- **`$binary_remote_addr`** — IP-адрес клиента в бинарном представлении (всегда 4 байта для IPv4 или 16 для IPv6), что критично для эффективной работы модулей ограничения лимитов (`limit_conn`, `limit_req`), так как экономит память в разделяемых зонах.
- **`$remote_port`** — порт, с которого клиент инициировал соединение.
- **`$server_addr`** — IP-адрес сервера Nginx, который принял запрос (для получения значения может потребоваться системный вызов, если не использована директива `bind`).
- **`$server_port`** — порт сервера, на котором был принят запрос (обычно 80 или 443).

##### 2. Структура URI и аргументы

Эти переменные позволяют разделять и анализировать компоненты запрашиваемого URL для маршрутизации.

- **`$request_uri`** — первоначальный полный URI запроса в том виде, в котором его прислал клиент, включая все аргументы. Используется, когда нужно передать исходный путь на бэкенд без изменений.
- **`$uri`** (и его алиас **`$document_uri`**) — текущий нормализованный URI без аргументов. Значение может меняться в процессе обработки запроса (например, при внутренних перенаправлениях или использовании `index`).
- **`$args`** (и алиас **`$query_string`**) — строка всех аргументов запроса после символа «?».
- **`$is_args`** — возвращает символ «?», если в запросе есть аргументы, и пустую строку в противном случае.
- **`$arg_NAME`** — динамическая переменная, позволяющая извлечь значение конкретного Query-параметра по его имени (например, `$arg_id` для получения значения `id=123`).

##### 3. Заголовки и хост

Инструменты для работы с метаданными протокола HTTP.

- **`$host`** — имя хоста из строки запроса или из поля заголовка «Host», либо имя сервера, соответствующего запросу. Обладает наивысшим приоритетом при выборе виртуального сервера.
- **`$http_NAME`** — префикс для доступа к любому заголовку запроса клиента. Имя заголовка приводится к нижнему регистру, а тире заменяются на подчеркивания (например, `$http_user_agent`, `$http_authorization`).
- **`$sent_http_NAME`** — позволяет получить значение любого заголовка ответа, отправляемого Nginx (например, `$sent_http_content_type`).

##### 4. Статусы и бэкенд (Upstream)

Переменные для мониторинга производительности кластера микросервисов FastAPI / Uvicorn.

- **`$status`** — итоговый HTTP-код ответа сервера клиенту.
- **`$body_bytes_sent`** — количество байт, отправленных клиенту (исключая HTTP-заголовки).
- **`$upstream_addr`** — IP-адрес и порт (или путь к Unix-сокету) выбранного сервера бэкенда.
- **`$upstream_status`** — HTTP-статус ответа, полученный от бэкенда.
- **`$upstream_response_time`** — время (в секундах с точностью до миллисекунд), затраченное бэкендом на формирование ответа.

> [!warning] Актуализация синтаксиса 
> В старых конфигурациях часто использовались регулярные выражения в `rewrite` для выделения частей URI, которые уже доступны во встроенных переменных. Например, вместо `rewrite ^/(.*)$ $1 break;` для получения пути эффективнее использовать переменную `$uri`, что экономит циклы CPU на работе движка PCRE.

#### Динамический роутинг к микросервисам: Практические примеры

Использование переменных позволяет создавать конфигурации API Gateway, где путь к бэкенду определяется «на лету».

**Пример 1: Маршрутизация по Query-параметру версии API**

```nginx
location /api {
    # Динамически выбираем апстрим на основе параметра v (например, /api/users?v=2)
    set $backend_version "v1_backend";
    if ($arg_v = "2") {
        set $backend_version "v2_backend";
    }
    proxy_pass http://$backend_version;
}
```

**Пример 2: Использование переменных в логировании для отладки Uvicorn**

```nginx
log_format upstream_debug '[$time_local] client=$remote_addr '
                           'request="$request" status=$status '
                           'upstream=$upstream_addr upstream_status=$upstream_status '
                           'rt=$request_time urt=$upstream_response_time';

access_log /var/log/nginx/upstream.log upstream_debug;
```

### Интерактивный тест для самопроверки

1. **В чем заключается принципиальное отличие переменной `$request_uri` от переменной `$uri`?**
    <details>
    <summary>Ответ</summary>
    `$request_uri` содержит полный оригинальный путь с аргументами в том виде, как его прислал клиент [14, 15]. `$uri` содержит нормализованный путь (без аргументов, с раскрытыми символами типа `%XX` и удаленными лишними слэшами), который может меняться во время обработки запроса [1, 18].
    </details>

2. **Как в конфигурации Nginx обратиться к значению клиентского HTTP-заголовка `X-Custom-Auth`?**
    <details>
    <summary>Ответ</summary>
    Необходимо использовать переменную `$http_x_custom_auth`. Nginx автоматически переводит имена заголовков в нижний регистр и заменяет тире на подчеркивания при использовании префикса `$http_` [21, 23].
    </details>

3. **Почему для зоны `limit_req_zone` рекомендуется использовать `$binary_remote_addr`, а не `$remote_addr`?**
    <details>
    <summary>Ответ</summary>
    `$binary_remote_addr` хранит IP-адрес в компактном бинарном виде (4 байта для IPv4), тогда как `$remote_addr` хранит его как строку (до 15 байт) [7, 8]. Использование бинарного формата позволяет хранить в 4-5 раз больше состояний клиентов в том же объеме разделяемой памяти [9].
    </details>

4. **Какая переменная позволяет узнать, сколько времени конкретно сервер FastAPI (Uvicorn) обрабатывал «тяжелый» запрос до того, как Nginx начал получать ответ?**
    <details>
    <summary>Ответ</summary>
    Переменная `$upstream_response_time` [26, 31]. Она фиксирует время от момента отправки запроса на бэкенд до получения последнего байта ответа [26].
    </details>

5. **Что вернет переменная `$is_args`, если к Nginx пришел запрос `GET /search` без параметров?**
    <details>
    <summary>Ответ</summary>
    Она вернет пустую строку. Если бы запрос содержал параметры (например, `/search?q=test`), переменная вернула бы символ «?» [20, 21].
    </details>
