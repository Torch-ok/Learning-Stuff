При проектировании логики обработки запросов в Nginx начинающие администраторы часто пытаются использовать директиву `if` по аналогии с императивными языками программирования (Python, C). Однако Nginx — это декларативная система, управляемая состояниями и фазами обработки запроса [Development guide](https://nginx.org/en/docs/dev/development_guide.html#http_phases). Непонимание внутренней архитектуры этого механизма породило известную в индустрии концепцию **«If is Evil»**, описывающую непредсказуемое поведение сервера при использовании условной логики в контексте `location` [Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).

#### 8.3.1. Анатомия проблемы: Что происходит под капотом

Главная причина «злобности» `if` заключается в том, что при его использовании внутри `location` Nginx создает **скрытый внутренний контекст** (implicit location) [NGINX as a Reverse Proxy / Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).

**Архитектурные последствия:**

1. **Захват обработчика контента (Content Handler):** Когда условие `if` истинно, запрос попадает во внутренний контекст, который назначает собственный обработчик контента [NGINX as a Reverse Proxy / Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536). Если внутри `if` нет директив проксирования, но они есть во внешнем `location`, Nginx может просто «забыть» отправить запрос на бэкенд FastAPI / Uvicorn [NGINX as a Reverse Proxy / Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).
2. **Игнорирование try_files:** Директива `try_files` принципиально не работает, если в том же `location` присутствует `if`. Внутренний контекст `if` имеет приоритет, и внешний обработчик `try_files` никогда не вызывается, что приводит к ошибкам 404 там, где файл физически существует [NGINX as a Reverse Proxy / Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).
3. **Сброс наследования:** Директивы, определенные на уровне `server` или в начале `location`, могут не наследоваться внутренним контекстом `if`, что ломает конфигурацию заголовков или лимитов [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).
4. **Риск сегфолтов (Segmentation Fault):** В редких и сложных конфигурациях использование `if` в связке с некоторыми модулями может привести к аварийному завершению рабочих процессов (crash) из-за некорректного управления памятью во вложенных контекстах [Troubleshooting Techniques / Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).

#### 8.3.2. Границы безопасного использования if

Несмотря на вышесказанное, `if` не является запрещенной директивой, если использовать ее в строго определенных рамках [Модуль ngx_http_rewrite_module](https://nginx.org/ru/docs/http/ngx_http_rewrite_module.html).

**Безопасные сценарии:**

- **Контекст `server`:** Использование `if` на уровне сервера (вне `location`) считается безопасным, так как здесь еще не определен финальный обработчик контента [NGINX as a Reverse Proxy / Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).
- **Только `return` или `rewrite ... last/break`:** Внутри `location` директива `if` безопасна только в том случае, если она немедленно прерывает текущую обработку и делает редирект или внутренний переход [NGINX as a Reverse Proxy / Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).

> [!warning] Актуализация синтаксиса 
> Использование `if` для проверки существования файлов (например, `if (!-f $request_filename)`) является устаревшей и небезопасной практикой. Современный стандарт Nginx предписывает использовать для этих целей директиву `try_files`, которая работает быстрее и предсказуемее [Troubleshooting Techniques / Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).

#### 8.3.3. Безопасные альтернативы

Для реализации сложной логики без ущерба для стабильности Senior DevOps инженеры используют специализированные инструменты Nginx.

##### Директива map: Таблицы соответствия

Директива `map` позволяет создавать динамические переменные на основе значений других переменных [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/). Она объявляется в контексте `http` и вычисляется только в момент обращения к переменной, что делает ее крайне производительной [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).

_Пример: Динамический выбор бэкенда на основе заголовка:_

```nginx
http {
    map $http_x_use_staging $fastapi_backend {
        default "production_cluster";
        "yes"   "staging_cluster";
    }

    server {
        location / {
            proxy_pass http://$fastapi_backend;
        }
    }
}
``` 
[Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/), [10 Tips for Deploying NGINX as an API Gateway / YouTube](https://www.youtube.com/watch?v=...)

##### Директива try_files: Проверка ресурсов
Эта директива специально создана для замены `if` при работе с файловой системой. Она последовательно проверяет наличие файлов и каталогов, передавая управление последнему параметру (обычно именованному `location` с бэкендом) только если ничего не найдено на диске [Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).

*Пример: SPA-роутинг и fallback на FastAPI:*
```nginx
location / {
    # Пытаемся отдать статику, если нет — идем на бэкенд
    try_files $uri $uri/ @uvicorn;
}

location @uvicorn {
    proxy_pass http://unix:/run/uvicorn.sock;
}
``` 
[Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536), [Rewrite Rule Guide / Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).

### Интерактивный тест для самопроверки

1. **Почему использование `try_files` вместе с `if` в одном блоке `location` не дает ожидаемого результата?**
    <details>
    <summary>Ответ</summary>
    Потому что `if` создает скрытый внутренний контекст со своим обработчиком контента, который перехватывает управление и не дает выполниться обработчику `try_files` [NGINX as a Reverse Proxy / Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).
    </details>

2. **В каких контекстах использование директивы `if` считается архитектурно безопасным?**
    <details>
    <summary>Ответ</summary>
    В контексте `server` и в контексте `location`, но только если внутри `if` используются исключительно директивы `return` или `rewrite` с флагами `last` или `break` [NGINX as a Reverse Proxy / Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).
    </details>

3. **Какую ошибку (HTTP статус) вернет Nginx при возникновении бесконечного цикла внутренних перенаправлений из-за некорректных правил `if/rewrite`?**
    <details>
    <summary>Ответ</summary>
    Ошибка 500 Internal Server Error с пометкой в логах "rewrite or internal redirection cycle" [Модуль ngx_http_core_module](https://nginx.org/ru/docs/http/ngx_http_core_module.html#internal).
    </details>

4. **Чем `map` лучше, чем последовательность блоков `if` для установки значений переменных?**
    <details>
    <summary>Ответ</summary>
    `map` работает на этапе конфигурации, не вмешивается в фазы обработки запроса, не создает скрытых контекстов и обеспечивает более быстрый поиск по скомпилированной хеш-таблице [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).
    </details>

5. **Что произойдет, если запрос попадет в блок `if`, внутри которого нет директивы `proxy_pass`, хотя она определена во внешнем `location`?**
    <details>
    <summary>Ответ</summary>
    Запрос будет обработан внутренним контекстом `if`, который «не знает» о необходимости проксирования, и клиент, скорее всего, получит 404 или некорректный статический ответ [NGINX as a Reverse Proxy / Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).
    </details>
