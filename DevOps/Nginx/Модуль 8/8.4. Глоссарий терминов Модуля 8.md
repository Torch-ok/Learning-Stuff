В данном разделе представлены ключевые абстракции и инструменты Nginx, предназначенные для динамического управления контекстом запроса и трансформации URI.

- **Nginx Built-in Variables** — предопределенные именованные значения (например, `$uri`, `$host`, `$arg_id`), которые вычисляются в рантайме и позволяют Nginx принимать решения на основе метаданных текущего HTTP-запроса [Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).
- **return vs rewrite** — сравнение двух методов изменения логики запроса: `return` мгновенно завершает обработку и возвращает статус, тогда как `rewrite` изменяет строку URI с помощью регулярных выражений для продолжения обработки [Модуль ngx_http_rewrite_module](https://nginx.org/ru/docs/http/ngx_http_rewrite_module.html).
- **Rewrite Flags (last/break)** — параметры, управляющие поведением Nginx после перезаписи URI: `last` инициирует новый поиск `location`, а `break` останавливает обработку директив модуля `rewrite` в текущем блоке [Configuring NGINX and NGINX Plus as a Web Server](https://docs.nginx.com/nginx/admin-guide/web-server/web-server/).
- **301 vs 308 Redirect** — типы постоянных перенаправлений; код 308 является предпочтительным для API на базе FastAPI, так как он гарантирует сохранение исходного HTTP-метода при повторном запросе клиента [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).
- **If is Evil** — широко известная концепция, предостерегающая от использования `if` внутри `location` из-за создания скрытых контекстов и непредсказуемого игнорирования других директив, таких как `try_files` или `proxy_pass` [Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).
- **Map Directive** — высокопроизводительная директива в контексте `http`, позволяющая создавать новые переменные на основе значений существующих по принципу таблицы соответствий, заменяя громоздкие блоки `if` [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).
- **Query String Manipulation** — процесс извлечения конкретных аргументов (через `$arg_NAME`) или очистки всей строки параметров (с помощью символа `?` в конце `rewrite`) для нормализации запросов к бэкенду [Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).

## Практическое упражнение (Безопасный рефакторинг legacy-конфигурации: Избавление от "If is Evil", настройка map-блоков и оптимизация редиректов для FastAPI)

**Сценарий:** Вы получили в наследство конфигурацию API-шлюза, которая работает нестабильно: статика часто отдает 404, а клиенты мобильных приложений жалуются, что POST-запросы превращаются в GET после редиректов. Ваша задача — провести глубокий рефакторинг.

### 1. Исходный проблемный конфиг (`legacy_api.conf`)

```nginx
# ОПАСНО: Использование if для проверки хоста и файлов
server {
    listen 80;
    server_name example.com www.example.com;

    if ($host = 'www.example.com') {
        rewrite ^/(.*)$ http://example.com/$1 permanent;
    }

    location / {
        # ОПАСНО: if внутри location ломает try_files
        if (!-f $request_filename) {
            proxy_pass http://uvicorn_v1;
        }

        # Этот блок может быть проигнорирован из-за if выше
        try_files $uri $uri/ =404;
    }

    location /api/v1/ {
        # Плохая практика: использование if для выбора версии API
        if ($http_x_use_beta = "true") {
            proxy_pass http://uvicorn_beta;
        }
        proxy_pass http://uvicorn_stable;
    }
}
``` 
[Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536), [ngx_http_rewrite_module](https://nginx.org/ru/docs/http/ngx_http_rewrite_module.html).

### 2. Рефакторенный конфиг (`modern_api.conf`)
```nginx
# 1. Выбор бэкенда через map (в контексте http)
map $http_x_use_beta $fastapi_upstream {
    default "uvicorn_stable";
    "true"  "uvicorn_beta";
}

# 2. Канонический редирект через отдельный server block
server {
    listen 80;
    server_name www.example.com;
    return 301 $scheme://example.com$request_uri;
}

server {
    listen 80;
    server_name example.com;

    # 3. Безопасная проверка файлов через try_files
    location / {
        try_files $uri $uri/ @fastapi_proxy;
    }

    # Именованный location для проксирования
    location @fastapi_proxy {
        proxy_pass http://$fastapi_upstream;
        include proxy_params;
    }

    # 4. Бесшовная перезапись API путей
    # Задача: /v1/old_user?id=123 -> /api/v2/users/123
    location /v1/old_user {
        # Используем ? в конце для отсечения старого id из Query String
        rewrite ^/v1/old_user$ /api/v2/users/$arg_id? last;
    }

    location /api/v2/ {
        proxy_pass http://$fastapi_upstream;
    }
}
``` 
[Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536), [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/), [10 Tips for Deploying NGINX as an API Gateway](https://www.youtube.com/watch?v=...).

### 3. Проверка через CLI
Выполним запрос к старому API и проверим редирект:
```bash
curl -IL "http://example.com/v1/old_user?id=123"
````

**Ожидаемые логи обработки:**

1. Nginx находит `location /v1/old_user`.
2. Извлекает значение `123` из переменной `$arg_id`.
3. Выполняет `rewrite`, отсекая оригинальные аргументы (`?` в конце).
4. Флаг `last` инициирует новый поиск.
5. Запрос попадает в `location /api/v2/` с URI `/api/v2/users/123`.
6. Переменная `$fastapi_upstream` вычисляется один раз через `map`.
