Для обеспечения стабильности высоконагруженных систем на базе FastAPI и Nginx инженеру необходимо иметь инструмент для моментального аудита состояния веб-сервера. Встроенный модуль `ngx_http_stub_status_module` предоставляет базовые метрики производительности, позволяя оценить текущую нагрузку на `worker_processes`, эффективность использования соединений и наличие сетевых аномалий. Эти данные являются критически важными для систем мониторинга (Prometheus, Zabbix, Nagios), которые используют данный эндпоинт для построения графиков и настройки алертов.

#### 10.2.1. Настройка изолированного эндпоинта `stub_status`

Поскольку модуль предоставляет данные о состоянии всех соединений сервера, его эндпоинт должен быть строго изолирован от публичного доступа.

**Рекомендованная конфигурация:**

```nginx
server {
    listen 80;
    server_name localhost;

    location /stub_status {
        # Активация модуля мониторинга
        stub_status;

        # Правила контроля доступа (ACL)
        allow 127.0.0.1;       # Разрешить доступ локально
        allow 192.168.1.0/24;  # Разрешить доступ из сети мониторинга или VPN
        deny all;              # Запретить всем остальным

        # Оптимизация: отключаем логирование запросов мониторинга
        access_log off;
    }
}
```

**Технические пояснения:**
1.  **`stub_status;`** — директива включает сбор статистики. Она может быть объявлена только внутри блока `location`.
2.  **`access_log off;`** — мониторинговые системы могут опрашивать сервер раз в секунду. Отключение логирования этих запросов снижает нагрузку на дисковую подсистему и предотвращает «замусоривание» аналитических логов.
3.  **Глобальность данных:** Информация, выдаваемая модулем, является глобальной для всего экземпляра Nginx и не ограничивается виртуальным сервером, в котором описан `location`.

#### 10.2.2. Анатомия метрик и анализ счетчиков

При обращении к эндпоинту (например, через `curl http://localhost/stub_status`) Nginx возвращает текстовый ответ следующего вида:

```text
Active connections: 2532
server accepts handled requests
 1476737983 1476737983 3553635810
Reading: 93 Writing: 13 Waiting: 2426
```

**Детальный разбор показателей:**

*   **`Active connections`** — текущее суммарное количество активных клиентских соединений, включая те, что находятся в режиме ожидания (`Waiting`).
*   **`accepts`** — общее количество принятых TCP-соединений с момента старта мастер-процесса.
*   **`handled`** — количество успешно обработанных соединений.
*   **`requests`** — совокупное количество HTTP-запросов от клиентов. Разделив это число на `handled`, можно вычислить средний показатель запросов на одно соединение (Req/Conn), что помогает оценить эффективность настройки Keep-Alive.
*   **`Reading`** — количество соединений, в которых Nginx в данный момент читает заголовки запроса от клиента. Высокое значение может указывать на медленных клиентов или атаку типа Slowloris.
*   **`Writing`** — количество активных соединений, где Nginx читает тело запроса, выполняет обработку (включая ожидание ответа от FastAPI/Uvicorn) или пишет ответ клиенту.
*   **`Waiting`** — количество простаивающих соединений (Keep-Alive), которые ожидают следующего запроса от клиента. Большое число «ждущих» соединений при малом `Active connections` говорит о том, что ресурсы сокетов расходуются на удержание 

> [!warning] Сигнал об аварии
> В штатном режиме значения `accepts` и `handled` должны быть идентичны. Если `handled` меньше, чем `accepts`, это означает, что Nginx сбрасывает соединения из-за исчерпания ресурсов (например, лимита `worker_connections`) или находится под атакой, переполняющей очереди ядра.
#### 10.2.3. Ограничения Open-Source версии (OSS)

Модуль `stub_status` в стандартной версии Nginx предоставляет лишь «узкую щель» в обзор системы. Он имеет ряд ограничений по сравнению с коммерческим решением Nginx Plus.

| Возможность | Nginx Open-Source (`stub_status`) | Nginx Plus / Nginx Controller |
| :--- | :--- | :--- |
| **Формат данных** | Только простой текст | Нативный JSON через REST API |
| **Статистика апстримов** | Отсутствует | Детальные метрики по каждому серверу в `upstream` |
| **Коды ответов** | Не отслеживаются | Разбивка ответов по статусам (1xx, 2xx, 3xx, 4xx, 5xx) |
| **Кэширование** | Нет данных | Информация о зонах кэша, hit/miss ratio и свободном месте |
| **Визуализация** | Требует сторонних экспортеров (Prometheus Exporter) | Встроенный интерактивный Dashboard в реальном времени |

Для получения расширенной телеметрии в OSS-версии часто используются сторонние модули или инструменты агрегации логов (ELK Stack, ClickHouse), которые позволяют восстановить недостающую информацию на основе `access_log`.

### Интерактивный тест для самопроверки

1. **Какая директива необходима для активации страницы мониторинга внутри `location`?**
    <details>
    <summary>Ответ</summary>
    Директива `stub_status;`. Она включает сбор и отображение метрик для данного контекста.
    </details>

2. **О чем свидетельствует ситуация, когда значение `accepts` значительно больше значения `handled`?**
    <details>
    <summary>Ответ</summary>
    Это критический индикатор того, что сервер не может обработать все входящие соединения и сбрасывает их. Обычно это связано с достижением лимита `worker_connections` или нехваткой файловых дескрипторов в ОС.
    </details>

3. **Включает ли счетчик `Active connections` те соединения, которые находятся в состоянии `Waiting`?**
    <details>
    <summary>Ответ</summary>
    Да, `Active connections` — это суммарный показатель всех открытых в данный момент соединений, включая простаивающие Keep-Alive сессии.
    </details>

4. **В каком состоянии находится соединение, если оно учитывается в метрике `Reading`?**
    <details>
    <summary>Ответ</summary>
    Nginx в этот момент считывает HTTP-заголовки запроса, присланные клиентом.
    </details>

5. **Можно ли с помощью стандартного `stub_status` узнать количество ошибок 502 Bad Gateway, возникших при обращении к FastAPI?**
    <details>
    <summary>Ответ</summary>
    Нет, стандартный модуль `stub_status` в Open-Source версии не умеет классифицировать запросы по HTTP-кодам ответов. Для этого требуется Nginx Plus или анализ `access_log`.
    </details>
