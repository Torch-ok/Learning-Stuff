Директива `location` является ключевым инструментом маршрутизации трафика внутри виртуального сервера Nginx. Она позволяет гибко распределять запросы между обработкой статических файлов, проксированием на бэкенды (FastAPI/Uvicorn) и выполнением специфических правил трансформации URI. Для Middle DevOps специалиста критически важно понимать не только синтаксис, но и математическую логику выбора финального блока `location` ядром сервера.

#### Анатомия и синтаксис директивы

Базовый синтаксис директивы: `location [modifier] uri { ... }`. Nginx работает с «нормализованным» URI: перед началом поиска он декодирует текст в формате `%XX`, преобразует относительные пути `.` и `..` в реальные и заменяет два и более подряд идущих слэшей на один. Сопоставление всегда происходит посимвольно, а не по логике каталогов файловой системы.

#### Модификаторы сопоставления URI

Существует четыре основных типа сопоставления, определяющих приоритет обработки:

1. **Точное совпадение (` = `):** Имеет наивысший приоритет. Если URI запроса байт-в-байт совпадает с указанной строкой, поиск немедленно прекращается.
    - _Пример:_ `location = / { ... }` ускоряет обработку запросов к корню сайта.
2. **Приоритетное префиксное совпадение (`^~`):** Если это правило оказывается самым длинным подходящим префиксом, Nginx прекращает поиск и **не проверяет** регулярные выражения. Этот модификатор часто путают с регулярным выражением, но это обычная строка.
3. **Регулярные выражения (`~` и `~*`):**
    - `~` — поиск с учетом регистра.
    - `~*` — поиск без учета регистра. Регулярные выражения могут содержать «выделения» (captures), которые в дальнейшем используются в конфигах бэкенда через позиционные переменные `$1`, `$2` и т.д..
4. **Обычное префиксное совпадение (без модификатора):** Проверяется в первую очередь, но не прекращает поиск, если не найдено точное совпадение или префикс с `^~`. Побеждает всегда самый длинный и специфичный префикс.

> [!warning]  Актуализация синтаксиса
> В старых версиях (0.7.1–0.8.41) любое точное совпадение с обычным префиксом могло прерывать поиск, однако в современном Nginx 1.29+ для гарантированной остановки поиска следует использовать модификаторы ` = ` или `^~`.

#### Пошаговый алгоритм поиска URI

Ядро Nginx выполняет поиск в строго определенной последовательности:

1. **Поиск по префиксам:** Nginx сканирует все `location`, заданные строками (префиксные правила).
2. **Проверка точного совпадения:** Если найдено совпадение с модификатором ` = `, поиск завершается.
3. **Сохранение лучшего префикса:** Nginx запоминает самый длинный подходящий префикс для текущего URI.
4. **Проверка приоритета префикса:** Если у самого длинного найденного префикса есть модификатор `^~`, поиск по регулярным выражениям пропускается, и выбирается этот `location`.
5. **Поиск по регулярным выражениям:** Nginx проверяет все блоки с `~` и `~*` **в том порядке, в котором они написаны в конфиге**. Как только найдено первое совпадение — поиск прекращается.
6. **Фоллбэк:** Если ни одно регулярное выражение не подошло, используется сохраненный ранее самый длинный префиксный `location`.

#### Классические ошибки: Порядок имеет значение

Главная ловушка для новичков заключается в том, что порядок объявления префиксных `location` в файле не важен (Nginx всегда найдет самый длинный), но порядок регулярных выражений — критичен.

- Если в конфиге блок `location ~* \.jpg$ { ... }` стоит выше, чем `location ~* \.jpe?g$ { ... }`, то запрос к `.jpeg` файлу может быть обработан неверно, если первое выражение перехватит его по ошибке или специфике логики.
- Всегда помещайте более специфичные регулярные выражения выше общих.

#### Практические примеры для FastAPI стека

Для нашего сквозного примера высоконагруженного API рекомендуется следующее разделение путей:

```nginx
server {
    listen 443 ssl;
    server_name api.example.com;

    # 1. Точный матч для главной страницы API
    location = / {
        return 200 '{"status": "API active"}';
    }

    # 2. Проксирование API на FastAPI/Uvicorn
    # Используем префиксный матч, чтобы все версии API уходили на бэкенд
    location /api/v1/ {
        proxy_pass http://uvicorn_backend;
        include proxy_params;
    }

    # 3. Приоритетная отдача статики (CSS/JS)
    # Использование ^~ гарантирует, что Regex для картинок не перехватит этот путь
    location ^~ /static/ {
        root /var/www/app;
        expires 30d;
        add_header Cache-Control "public, no-transform";
    }

    # 4. Обработка медиа-файлов через регулярные выражения
    location ~* \.(?:jpg|jpeg|gif|png|ico|cur|gz|svg|svgz|mp4|ogg|ogv|webm|htc)$ {
        root /var/www/app/media;
        access_log off;
        expires max;
    }
}
```

### Интерактивный тест для самопроверки

1. **Какой модификатор заставляет Nginx полностью игнорировать поиск по регулярным выражениям, если префикс совпал?**
    <details>
    <summary>Ответ</summary>
    Модификатор `^~`. Если это самый длинный найденный префикс, Nginx не переходит к этапу проверки регулярных выражений [10, 13, 14].
    </details>

2. **Влияет ли порядок написания префиксных location (без модификаторов) в конфиге на итоговый выбор?**
    <details>
    <summary>Ответ</summary>
    Нет. Nginx всегда ищет и выбирает максимально совпадающий (самый длинный) префикс независимо от его положения в файле [5, 17, 18].
    </details>

3. **Что произойдет, если URI запроса совпадает одновременно с `location /api/` и `location ~* ^/api/v1/`?**
    <details>
    <summary>Ответ</summary>
    Победит регулярное выражение `~*`, так как оно проверяется после префиксного поиска и имеет приоритет над обычным префиксом (если у префикса нет модификатора `^~`) [9, 10, 19].
    </details>

4. **Зачем использовать модификатор ` = ` для часто запрашиваемых путей?**
    <details>
    <summary>Ответ</summary>
    Для оптимизации производительности: при точном совпадении поиск прекращается мгновенно, экономя циклы CPU на перебор других префиксов и регулярных выражений [11, 12].
    </details>

5. **Какой код ответа вернет Nginx для внешнего запроса в блок, помеченный директивой `internal`?**
    <details>
    <summary>Ответ</summary>
    Код `404 Not Found`. Такие блоки доступны только для внутренних перенаправлений самого сервера [27, 28].
    </details>
