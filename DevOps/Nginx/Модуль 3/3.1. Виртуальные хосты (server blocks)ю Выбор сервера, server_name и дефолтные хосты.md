Концепция виртуального хостинга (Virtual Hosting) является фундаментом работы Nginx, позволяя на одном физическом сервере и одном IP-адресе обслуживать тысячи независимых доменных имен,. Механика работы контекста `server` заключается в логическом разделении ресурсов, которые будут отдаваться в зависимости от параметров входящего запроса,.

#### Директива listen: IP-адреса, порты и системные флаги

Директива `listen` определяет адрес, порт или путь к UNIX-сокету, на которых сервер будет принимать запросы,.

- **Порты и IP-адреса:** Если порт не указан, используется стандартный порт 80,. Если адрес не указан, сервер слушает на всех доступных интерфейсах,.
- **IPv6:** Для работы с протоколом IPv6 адрес указывается в квадратных скобках: `listen [::]:80;`,.
- **Флаг `default_server`:** Этот параметр помечает блок `server` как основной для данной пары IP:порт,. Если запрос не соответствует ни одному `server_name`, он будет обработан именно этим хостом,.
- **Параметры сокетов:** Современный Nginx поддерживает такие параметры, как `reuseport` (создание отдельного сокета для каждого воркера) и `ssl` (включение режима SSL непосредственно в директиве `listen`),,.

> [!warning]  Актуализация синтаксиса
> В старых версиях Nginx использовался параметр `default`. По современным стандартам необходимо использовать `default_server`,. Также вместо устаревшей директивы `ssl on;` следует указывать параметр `ssl` прямо в `listen`,.

#### Директива server_name и сопоставление Host-заголовка

После сопоставления IP-адреса и порта Nginx проверяет заголовок `Host` входящего HTTP-запроса на соответствие значениям в директиве `server_name`.

1. **Точное совпадение (Exact match):** Полное соответствие строки домену (например, `server_name example.com;`),.
2. **Маски (Wildcards):** Символ `*` может заменять первую или последнюю часть имени: `*.example.com` или `www.example.*`,.
3. **Регулярные выражения (Regex):** Задаются с префиксом `~`. Например, `server_name ~^www\d+\.example\.com$;`,,. Именованные выделения (captures) создают переменные, которые можно использовать в конфигурации бэкенда FastAPI.
4. **Специальные значения:**
    - `""` (пустая строка) — совпадает с запросами, в которых отсутствует заголовок `Host`,.
    - `_` (нижнее подчеркивание) — используется как условное "любое" имя для дефолтных серверов-заглушек,.

#### Алгоритм выбора виртуального сервера

Ядро Nginx следует строгому пошаговому алгоритму при поступлении нового запроса:

1. **Поиск по IP и порту:** Сначала выбираются все блоки `server`, соответствующие IP-адресу и порту запроса,.
2. **Точное имя:** Выбирается сервер с точным совпадением домена в `server_name`,.
3. **Wildcard в начале:** Поиск самого длинного совпадения с маской в начале (например, `*.example.org`),.
4. **Wildcard в конце:** Поиск самого длинного совпадения с маской в конце (например, `mail.*`),.
5. **Регулярные выражения:** Проверка regex-имен в порядке их появления в конфигурационном файле,.
6. **Fallback:** Если совпадений не найдено, запрос уходит в `default_server` для данного порта,. Если `default_server` не задан явно, используется первый описанный в конфиге сервер,.

#### Паттерн безопасности: Catch-all сервер

В высоконагруженных архитектурах (Nginx + FastAPI/Uvicorn) критически важно не допускать обработку случайных запросов или сканеров основным приложением. Для этого создается сервер-заглушка:

```nginx
server {
    listen 80 default_server;
    listen [::]:80 default_server;
    server_name _;

    # Сбрасываем соединение без ответа (код 444 специфичен для Nginx)
    return 444;
}
```

Такой подход гарантирует, что запросы по прямому IP-адресу или на несуществующие поддомены будут мгновенно оборваны, не нагружая Event Loop вашего бэкенда,,.
