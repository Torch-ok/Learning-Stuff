При использовании Nginx в качестве `Reverse Proxy` возникает фундаментальная проблема «сетевой слепоты» бэкенд-приложения. Поскольку клиент устанавливает TCP-соединение непосредственно с Nginx, а Nginx, в свою очередь, открывает новое соединение с `Uvicorn`, для бэкенда единственным видимым источником запроса становится IP-адрес самого прокси-сервера (обычно `127.0.0.1` или адрес в локальной сети Docker). Это делает невозможным корректную работу систем авторизации по IP, ведение аналитики и генерацию абсолютных путей внутри `FastAPI`.

#### Проброс сетевого контекста через proxy_set_header

Для передачи метаданных об исходном запросе используется директива `proxy_set_header`, которая позволяет переопределять или добавлять поля HTTP-заголовка, передаваемые вышестоящему серверу.

**Основные заголовки контекста:**

- **`Host $host`** — передает имя хоста из строки запроса или заголовка `Host` от клиента. Это критично для бэкендов, обслуживающих несколько доменов, так как без этой настройки Nginx по умолчанию передаст значение `$proxy_host` (имя, указанное в `proxy_pass`).
- **`X-Real-IP $remote_addr`** — передает реальный IP-адрес клиента бэкенду. Переменная `$remote_addr` содержит адрес того узла, который непосредственно установил соединение с Nginx.
- **`X-Forwarded-For $proxy_add_x_forwarded_for`** — используется для передачи цепочки IP-адресов, через которые прошел запрос. Переменная `$proxy_add_x_forwarded_for` автоматически добавляет `$remote_addr` к существующему списку адресов в заголовке `X-Forwarded-For`, если он был передан клиентом.
- **`X-Forwarded-Proto $scheme`** — сообщает бэкенду протокол (HTTP или HTTPS), по которому обратился клиент. Это необходимо `FastAPI` для корректного построения ссылок `External URL` и работы механизмов `HSTS`.

> [!warning]  Актуализация синтаксиса
> Директивы `proxy_set_header` наследуются с родительского уровня только в том случае, если на текущем уровне не определено ни одной собственной директивы `proxy_set_header`. Чтобы избежать потери заголовков, рекомендуется выносить их в отдельный файл и подключать через `include`.

#### Стандартизация: заголовок Forwarded (RFC 7239)

Хотя заголовки семейства `X-Forwarded-*` являются стандартом де-факто, существует официальный стандарт RFC 7239, вводящий единый заголовок `Forwarded`. Он объединяет информацию об IP-адресе, протоколе и интерфейсе в одну строку: `Forwarded: for=192.0.2.60;proto=https;by=203.0.113.43`. Несмотря на наличие стандарта, большинство современных прокси-серверов и балансировщиков (AWS ELB, Google Cloud Load Balancer) по-прежнему используют и ожидают `X-Forwarded-For`.

#### Санитария заголовков и работа с символами

Nginx по умолчанию придерживается строгих правил безопасности при обработке HTTP-заголовков.

1. **Символы подчеркивания:** По умолчанию Nginx помечает заголовки, содержащие символы подчеркивания (например, `X_Custom_Header`), как невалидные и сбрасывает их. Это сделано для предотвращения конфликтов с переменными окружения в CGI-сценариях. Если ваше приложение требует таких заголовков, необходимо явно включить директиву `underscores_in_headers on;` в контексте `http` или `server`.
2. **Очистка заголовков:** Для защиты инфраструктуры от утечки информации (например, версии Nginx или времени сервера) можно «обнулить» заголовки, передав пустую строку: `proxy_set_header Server "";`.
3. **Игнорирование:** Директива `ignore_invalid_headers on;` (включена по умолчанию) заставляет Nginx игнорировать любые заголовки с недопустимыми именами, не соответствующими спецификациям.

### Интерактивный тест для самопроверки

1. **Почему бэкенд за Nginx видит IP-адрес `127.0.0.1`, если не настроен проброс заголовков?**
    
2. **В чем разница между `$host` и `$http_host` при передаче заголовка бэкенду?**
    
3. **Что произойдет, если установить `proxy_set_header X-Custom-Auth "";`?**
    
4. **Какая директива позволяет Nginx принимать заголовки клиента с именами вида `Session_ID`?**
    
5. **Какое значение примет заголовок `X-Forwarded-For` на бэкенде, если клиент отправил `1.1.1.1`, а его запрос прошел через Nginx с IP `2.2.2.2`?**
