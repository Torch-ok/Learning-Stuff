В современной архитектуре распределенных систем Nginx чаще всего выступает в роли **Reverse Proxy** (Обратного прокси). В отличие от классического прокси-сервера, который защищает клиента, обратный прокси служит щитом и координатором для группы бэкенд-серверов, таких как наш стек на базе FastAPI и Uvicorn.

#### Архитектурная разница: Forward Proxy vs. Reverse Proxy

Понимание различий между этими двумя типами проксирования критично для проектирования безопасных сетей.

1. **Forward Proxy (Прямой прокси):** Устанавливается на стороне клиента или в его локальной сети. Его основная задача — принимать запросы от группы клиентов и пересылать их в интернет, скрывая реальные IP-адреса пользователей или обеспечивая фильтрацию контента.
2. **Reverse Proxy (Обратный прокси):** Устанавливается на стороне сервера и является «входной дверью» для всех внешних запросов. Он терминирует соединения клиентов и инициирует новые запросы к внутренним бэкендам (Upstreams).

**Преимущества Reverse Proxy для Middle DevOps:**

- **Маскирование инфраструктуры:** Клиент не знает о существовании Uvicorn или PostgreSQL; он взаимодействует только с Nginx.
- **Балансировка нагрузки:** Nginx распределяет трафик между несколькими инстансами FastAPI.
- **Безопасность:** Единая точка для терминации TLS и фильтрации атак на уровне L7.
- **Оптимизация:** Nginx эффективно раздает статику, освобождая Event Loop Python для бизнес-логики.

#### Механика директивы proxy_pass

Директива `proxy_pass` является основным инструментом передачи запроса от Nginx к вышестоящему (upstream) серверу. Она задает протокол (HTTP/HTTPS) и адрес сервера (IP, домен или Unix-сокет).

##### Влияние завершающего слэша на трансформацию URI

Одной из самых частых причин ошибок в конфигурации является непонимание того, как наличие URI в параметре `proxy_pass` меняет путь запроса, приходящий на бэкенд.

**Сценарий 1: proxy_pass БЕЗ URI (без слэша после порта)** Если адрес указан без пути (например, `proxy_pass http://127.0.0.1:8000`), Nginx передает исходный клиентский URI на бэкенд в неизменном виде.

```nginx
    proxy_pass http://127.0.0.1:8000; # URI отсутствует
}
# Запрос клиента: /api/v1/users
# Запрос к бэкенду: /api/v1/users
```

**Сценарий 2: proxy_pass С URI (со слэшем или путем)** Если в `proxy_pass` указан путь (даже одиночный слэш `/`), Nginx выполняет замену: часть URI, совпавшая с `location`, отбрасывается, а остаток приклеивается к URI из директивы.

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8000/; # Указан URI "/"
}
# Запрос клиента: /api/v1/users
# Совпавшая часть "/api/" отбрасывается
# Запрос к бэкенду: /v1/users
```

##### Использование с регулярными выражениями

Существуют важные ограничения: если `location` задан регулярным выражением, использование URI в `proxy_pass` **запрещено**. В этом случае Nginx не может однозначно определить, какую часть пути следует заменять, и передает URI «как есть».

> [!warning]  Актуализация синтаксиса
> В старых конфигурациях часто использовались конструкции `if` для трансформации путей перед проксированием. В современной практике 2026 года для этого следует использовать именованные `location` в связке с `try_files` или явные правила `rewrite ... break` внутри блока `location`, чтобы избежать непредсказуемого поведения.

#### Сетевое взаимодействие с бэкендом (Uvicorn)

Когда запрос попадает в `location` с `proxy_pass`, Nginx выполняет следующие действия под капотом:

1. **Установка соединения:** Рабочий процесс (`Worker`) открывает TCP-соединение или Unix-сокет к адресу, указанному в `proxy_pass`. Если используется пул соединений, Nginx может переиспользовать уже открытый сокет (Keepalive).
2. **Трансляция заголовков:** Nginx копирует заголовки клиентского запроса, преобразуя их по необходимости (например, добавляя `Host` или `X-Forwarded-For`).
3. **Передача тела (Buffering):** По умолчанию Nginx сначала полностью вычитывает тело запроса от клиента в буфер и только потом начинает передачу бэкенду. Это защищает асинхронный Uvicorn от медленных клиентов (Slowloris-защита).
4. **Событийный цикл:** Пока бэкенд обрабатывает запрос, `Worker` Nginx не блокируется; он возвращается в `Event Loop` для обслуживания других соединений. Уведомление о готовности ответа от бэкенда придет через системный вызов `epoll`.
