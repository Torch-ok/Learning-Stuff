В современной высоконагруженной архитектуре Nginx редко выступает в роли одиночного веб-сервера; чаще всего он служит точкой входа (Frontend/Proxy) для специализированных серверов приложений, таких как Uvicorn (ASGI) или Gunicorn (WSGI). Для Middle DevOps инженера критически важно понимать физику взаимодействия прокси-сервера с бэкендом на уровне системных вызовов ядра и сетевых протоколов.

#### Выбор способа взаимодействия: TCP vs Unix Domain Sockets

При организации связи между Nginx и Uvicorn доступны два основных механизма: сетевые сокеты и локальные файлы сокетов.

1. **TCP-сокеты (`http://127.0.0.1:8000`):**
    
    - **Механика:** Соединение проходит через полный сетевой стек ядра Linux.
    - **Преимущества:** Позволяет разносить Nginx и Uvicorn на разные физические серверы или контейнеры.
    - **Недостатки:** Возникает «сетевой оверхед» (Network Overhead) — ядро вынуждено инкапсулировать данные в TCP-пакеты, вычислять контрольные суммы и проверять порты даже при работе внутри одной ОС.
2. **Unix Domain Sockets (`http://unix:/tmp/uvicorn.sock`):**
    
    - **Механика:** Обмен данными происходит напрямую через буферы в памяти ядра, используя файл сокета как дескриптор.
    - **Преимущества:** Избавление от сетевого оверхеда дает прирост производительности и снижение задержек (Latency).
    - **Особенности:** Требует настройки прав доступа к `.sock`-файлу; рабочий процесс Nginx (`worker`) должен иметь права на чтение и запись в этот файл, иначе возникнет ошибка `502 Bad Gateway`.

#### Проксирование WebSocket в FastAPI

Протокол WebSocket обеспечивает полнодуплексный обмен данными в реальном времени, что необходимо для чатов, систем уведомлений и дашбордов в FastAPI. Поскольку WebSocket начинает жизнь как обычный HTTP/1.1 запрос, Nginx требует специфической настройки для «апгрейда» соединения.

**Механика Upgrade:** Клиент отправляет заголовок `Upgrade: websocket`. Nginx, как Reverse Proxy, по умолчанию не пробрасывает заголовки `Upgrade` и `Connection` бэкенду, что приводит к обрыву рукопожатия. Чтобы этого избежать, используется блок `map` для динамической установки значений.

```nginx
# В контексте http для динамического переключения
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

server {
    listen 443 ssl;
    server_name api.example.com;

    location /ws {
        proxy_pass http://unix:/run/uvicorn.sock;

        # Явный проброс заголовков для WebSocket
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;

        # Удержание долгоживущих соединений
        proxy_read_timeout 3600s; # 1 час простоя
        proxy_send_timeout 3600s;
    }
}
```

**Борьба с таймаутами:** Стандартные таймауты `proxy_read_timeout` и `proxy_send_timeout` в Nginx обычно составляют 60 секунд. Для WebSocket это критично: если в канале нет активности 1 минуту, Nginx закроет TCP-сессию. Установка больших значений (например, `3600s`) позволяет удерживать соединение активным даже при длительном отсутствии данных от клиента или FastAPI.

#### Интеграция с другими протоколами

Помимо ASGI-серверов, Nginx поддерживает нативные модули для взаимодействия с иными стеками технологий через специализированные директивы `*_pass`.

- **PHP-FPM (`fastcgi_pass`):** Использует протокол FastCGI для исполнения PHP-скриптов. Настройка включает передачу параметров через `fastcgi_param` для определения пути к файлу.
- **uWSGI (`uwsgi_pass`):** Использует бинарный протокол uwsgi для работы с Python WSGI-приложениями (Django/Flask). Считается более производительным, чем HTTP-проксирование для классических WSGI-стеков.

> [!warning]  Актуализация синтаксиса
> В старых источниках рекомендуется использовать `proxy_http_version 1.0` для проксирования, однако для работы WebSocket и `keepalive`-соединений с бэкендом необходимо явно указывать `proxy_http_version 1.1;`.

### Интерактивный тест для самопроверки

1. **Почему использование Unix Domain Sockets быстрее, чем TCP-соединение с бэкендом на том же сервере?**
    <details>
    <summary>Ответ</summary>
    UDS обходит сетевой стек ядра, исключая этапы инкапсуляции данных в TCP-пакеты, проверку контрольных сумм и маршрутизацию трафика через локальный сетевой интерфейс. [5, 9]
    </details>

2. **Зачем в контексте WebSocket-проксирования используется директива `map`?**
    <details>
    <summary>Ответ</summary>
    Для динамического управления заголовком `Connection`. Если клиент запрашивает апгрейд (`Upgrade`), Nginx передает `upgrade`, в противном случае — устанавливает `close`, что гарантирует корректную работу и WebSocket, и обычного HTTP. [19, 23]
    </details>

3. **Какая ошибка в логах Nginx чаще всего указывает на отсутствие прав доступа к Unix-сокету Uvicorn?**
    <details>
    <summary>Ответ</summary>
    Ошибка `502 Bad Gateway`. В `error_log` при этом будет запись `(13: Permission denied) while connecting to upstream`. [16, 44]
    </details>

4. **Что произойдет с WebSocket-соединением, если оставить `proxy_read_timeout` равным 60 секундам?**
    <details>
    <summary>Ответ</summary>
    Если в течение 60 секунд ни клиент, ни сервер не отправят данные (или ping/pong пакеты), Nginx разорвет соединение по таймауту. [24, 26, 45]
    </details>

5. **В чем принципиальное отличие директивы `fastcgi_pass` от `proxy_pass`?**
    <details>
    <summary>Ответ</summary>
    `proxy_pass` использует протокол HTTP/HTTPS для связи, тогда как `fastcgi_pass` использует бинарный протокол FastCGI, специфичный для серверов приложений вроде PHP-FPM. [29, 31, 32, 36]
    </details>
