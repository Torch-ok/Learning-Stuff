Серверное кэширование в Nginx — это стратегический инструмент Middle DevOps инженера, позволяющий радикально снизить нагрузку на инфраструктуру. В современных высоконагруженных системах на базе асинхронного стека FastAPI / Uvicorn и PostgreSQL, каждый запрос, дошедший до бэкенда, потребляет ресурсы Event Loop Python и циклы CPU базы данных. Кэширование позволяет Nginx сохранять результаты ответов в быстрой памяти или на диске и отдавать их повторно, не инициируя новый цикл обработки на стороне приложения. Это не только ускоряет время ответа для пользователя, но и создает «запас прочности» системы во время всплесков трафика (bursts).

#### Анатомия директив управления кэшем

Настройка кэширования начинается с определения зоны хранения в глобальном контексте и её последующей активации в конкретных блоках маршрутизации.

##### Директива proxy_cache_path

Эта директива настраивает физическое хранилище и метаданные кэша. Она допустима **только в контексте `http`**.

- **`keys_zone=name:size`** — создает зону разделяемой памяти, где хранятся активные ключи кэша и метаданные ответов. Зона в 10 МБ позволяет хранить около 80 000 ключей.
- **Путь хранения** — первый параметр указывает директорию на диске (например, `/var/nginx/cache`).
- **`levels=1:2`** — определяет иерархию подкаталогов. Значение `1:2` означает, что файлы будут разложены по папкам на основе последнего символа MD5-хэша ключа и двух предшествующих ему символов. Это предотвращает замедление дисковых операций из-за тысяч файлов в одном каталоге.
- **`max_size`** — устанавливает предел дискового пространства для кэша.
- **`inactive`** — время, в течение которого данные остаются в кэше, если к ним не было обращений. По умолчанию составляет 10 минут.
- **Служебные процессы:**
    - **Cache Manager** — периодически проверяет размер кэша и удаляет наименее востребованные (LRU) элементы при достижении лимита `max_size`.
    - **Cache Loader** — запускается при старте Nginx и загружает метаданные ранее закэшированных файлов с диска в зону разделяемой памяти.

##### Подключение и правила хранения

- **`proxy_cache`** — активирует использование конкретной зоны в контекстах `http`, `server` или `location`.
- **`proxy_cache_key`** — формирует строку, хэш которой станет именем файла в кэше. По умолчанию используется `$scheme$proxy_host$request_uri`. В сложных API ключи могут дополняться куками или заголовками: `"$host$request_uri $cookie_user"`.
- **`proxy_cache_valid`** — задает время актуальности кэша для разных HTTP-кодов. Например, `proxy_cache_valid 200 302 10m;` закэширует успешные ответы на 10 минут, а `proxy_cache_valid 404 1m;` защитит бэкенд от сканирования несуществующих ресурсов.

> [!warning] Актуализация синтаксиса 
> По умолчанию Nginx не кэширует ответы, содержащие заголовок `Set-Cookie`. Чтобы включить кэширование таких ответов (если кука не влияет на контент), необходимо использовать директиву `proxy_ignore_headers Set-Cookie;` и обязательно включить значение куки в `proxy_cache_key` для разделения сессий пользователей.

#### Защита от сбоев и "кэш-шторма"

Высоконагруженные API требуют механизмов, предотвращающих каскадные отказы при промахах кэша или падении бэкендов.

1. **`proxy_cache_use_stale`** — позволяет Nginx отдавать "протухший" (stale) контент из кэша, если FastAPI вернул ошибку, таймаут или в данный момент обновляет этот элемент (`error`, `timeout`, `updating`, `http_500` и др.). Это обеспечивает работоспособность сайта даже при временном отказе бэкенда.
2. **`proxy_cache_lock`** — предотвращает "кэш-шторм" (Cache Stampede). Если несколько запросов одновременно обращаются к отсутствующему в кэше ресурсу, только один запрос будет пропущен к Uvicorn, остальные будут ожидать появления ответа в кэше.
3. **Переменная `$upstream_cache_status`** — крайне полезна для отладки и мониторинга. Её значение обычно выводят в кастомный HTTP-заголовок `add_header X-Cache-Status $upstream_cache_status;`. Статусы включают:
    - **HIT** — ответ отдан из кэша.
    - **MISS** — ответ отсутствовал и был запрошен у бэкенда.
    - **BYPASS** — кэш проигнорирован из-за директивы `proxy_cache_bypass`.
    - **EXPIRED** — запись в кэше устарела.
    - **STALE** — отдан устаревший контент из-за проблем на бэкенде.

#### Управление кэшированием на стороне FastAPI

Разработчик может гибко управлять поведением Nginx, передавая специфические заголовки в ответах Python-приложения.

- **`X-Accel-Expires`** — приоритетный заголовок для Nginx. Он задает время кэширования в секундах специально для прокси-сервера, при этом сам заголовок не передается конечному клиенту. Значение `0` полностью отключает кэширование конкретного ответа.
- **`Cache-Control` и `Expires`** — стандартные заголовки. Если `X-Accel-Expires` отсутствует, Nginx анализирует их для определения срока жизни кэша. Параметры `no-cache`, `no-store` или `private` запрещают сохранение ответа.
- **Валидация (`ETag` и `Last-Modified`)** — Nginx поддерживает ревалидацию просроченных элементов через директиву `proxy_cache_revalidate on;`. Если бэкенд возвращает `304 Not Modified`, Nginx обновляет метаданные текущего файла в кэше, не скачивая тело заново.
