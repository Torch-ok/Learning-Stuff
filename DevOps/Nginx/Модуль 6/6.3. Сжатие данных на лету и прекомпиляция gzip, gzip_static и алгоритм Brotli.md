Сжатие текстового контента — это фундаментальный механизм оптимизации в высоконагруженных системах, позволяющий радикально сократить объем передаваемого трафика и время ответа сервера для конечного пользователя. Снижение объема данных напрямую влияет на показатель RTT (Round Trip Time), так как меньшее количество TCP-пакетов требует меньше подтверждений (ACK) и быстрее утилизирует пропускную способность канала.

#### Модуль ngx_http_gzip_module: Сжатие на лету

Модуль `ngx_http_gzip_module` является фильтром, который сжимает ответы «на лету» перед их отправкой клиенту, что может уменьшить размер передаваемых данных в 2 и более раз.

**Ключевые директивы настройки:**

- **`gzip on;`** — активирует механизм сжатия.
- **`gzip_types`** — определяет перечень MIME-типов, подлежащих сжатию. По умолчанию сжимается только `text/html`. Для современного стека (FastAPI) необходимо явно добавлять `application/json`, а также `text/css`, `application/javascript` и `text/xml`.
    - **Внимание:** КАТЕГОРИЧЕСКИ НЕ РЕКОМЕНДУЕТСЯ включать сжатие для типов `image/jpeg` или `application/zip`, так как эти форматы уже сжаты. Повторное сжатие только увеличит нагрузку на CPU и может привести к увеличению итогового размера файла за счет метаданных архиватора.
- **`gzip_comp_level`** — степень сжатия от 1 до 9. Уровень 1 — самый быстрый с минимальной нагрузкой на процессор; уровень 9 обеспечивает максимальное сжатие, но потребляет значительные ресурсы CPU. «Золотым стандартом» для Production-сред считается диапазон 4–6, обеспечивающий оптимальный баланс.
- **`gzip_min_length`** — минимальный размер ответа (в байтах), начиная с которого будет применяться сжатие. Рекомендуется устанавливать значение не менее 1024 байт (1KB). Сжатие мелких файлов бессмысленно, так как оверхед от HTTP-заголовков сжатия может сделать итоговый пакет больше оригинала.
- **`gzip_proxied`** — разрешает сжатие для проксированных запросов (определяется по наличию заголовка `Via`).
- **`gzip_vary on;`** — вставляет заголовок `Vary: Accept-Encoding` в ответ сервера. Это сообщает промежуточным кэширующим прокси-серверам, что ответ существует в двух вариантах (сжатом и несжатом), предотвращая отдачу Gzip-контента клиентам, которые его не поддерживают.

#### Модуль gzip_static: Экономия ресурсов CPU

Для статических файлов фронтенда (JS/CSS-бандлы) использование динамического сжатия при каждом запросе является неэффективным расходованием ресурсов. Модуль `ngx_http_gzip_static_module` позволяет Nginx отдавать заранее подготовленные файлы с расширением `.gz` вместо обычных.

- **Механика:** Если клиент поддерживает Gzip и на диске рядом с файлом `style.css` лежит `style.css.gz`, Nginx отдаст сжатую версию напрямую через `sendfile`, не нагружая процессор операциями архивации.
- **Сборка:** Модуль не собирается по умолчанию; требуется флаг конфигурации `--with-http_gzip_static_module`.

#### Brotli: Современная альтернатива Gzip

Алгоритм **Brotli** (разработка Google) обеспечивает на 15–30% лучшую степень сжатия текстовых данных по сравнению с Gzip при сопоставимой скорости декомпрессии в браузере.

- **Особенности:** Brotli требует наличия HTTPS-соединения для работы в большинстве браузеров.
- **Настройка:** По аналогии с Gzip, Brotli поддерживает динамическое сжатие (`brotli on;`) и отдачу прекомпилированных файлов (`brotli_static on;` для `.br` файлов).
- **Производительность:** Хотя Brotli на максимальных степенях (11) крайне медлителен при сжатии, на средних уровнях (4–6) он эффективнее Gzip и отлично подходит для динамических JSON-ответов FastAPI.

> [!warning] Актуализация синтаксиса 
> В старых конфигурациях часто устанавливают `gzip_http_version 1.0;`. По современным стандартам (2026) следует использовать `gzip_http_version 1.1;` (значение по умолчанию), так как поддержка сжатия в HTTP/1.0 была нестабильной и сегодня не актуальна.
