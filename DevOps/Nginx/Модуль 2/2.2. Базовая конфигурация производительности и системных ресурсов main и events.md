Для достижения максимальной пропускной способности в 2026 году при работе с асинхронными бэкендами на базе FastAPI и Uvicorn, настройка Nginx должна начинаться на уровне взаимодействия с ядром ОС Linux. Контексты `main` (глобальный) и `events` определяют системные лимиты и стратегию обработки соединений, которые являются фундаментом для стабильной работы под нагрузкой [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).

#### Системные директивы контекста main

Глобальный контекст управляет жизненным циклом процессов и их правами в системе.

- **`user`** — определяет непривилегированного пользователя и группу, под которыми будут функционировать `Worker`-процессы [Основная функциональность](https://nginx.org/ru/docs/ngx_core_module.html#user). В современных дистрибутивах это обычно `nginx` или `www-data`. Запуск воркеров не от `root` — критическое требование безопасности: в случае взлома злоумышленник получит доступ только к ресурсам, разрешенным этому пользователю [Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).
- **`worker_processes auto`** — задает количество рабочих процессов. Значение `auto` автоматически выставляет их число равным количеству ядер CPU [Основная функциональность](https://nginx.org/ru/docs/ngx_core_module.html#worker_processes). Поскольку каждый воркер Nginx является однопоточным, это позволяет максимально эффективно утилизировать вычислительные мощности без лишней конкуренции за процессорное время [Основы NGINX глазами разработчика / YouTube](https://www.youtube.com/watch?v=...).
- **`worker_cpu_affinity`** — выполняет «привязку» (pinning) конкретных воркеров к ядрам процессора [Основная функциональность](https://nginx.org/ru/docs/ngx_core_module.html#worker_cpu_affinity). В высоконагруженных системах (C10K и выше) это радикально снижает количество кэш-промахов (L1/L2 cache misses) и минимизирует накладные расходы на переключение контекста в планировщике задач ядра [Оптимизация производительности Nginx/Angie / YouTube](https://www.youtube.com/watch?v=...).

#### Математика дескрипторов: `worker_rlimit_nofile`

Каждое сетевое соединение в Linux представлено как файловый дескриптор. Если Nginx работает как Reverse Proxy для FastAPI/Uvicorn, формула расчета лимитов усложняется:

1. Одно соединение от клиента = 1 дескриптор.
2. Одно проксирующее соединение от Nginx к бэкенду (Uvicorn) = еще 1 дескриптор.
3. Итого: для обслуживания одного активного пользователя в режиме проксирования Nginx требуется минимум **2 сокета** [NGINX Cookbook](https://docs.nginx.com/nginx/admin-guide/).

Директива **`worker_rlimit_nofile`** позволяет увеличить лимит открытых файлов (`ulimit -n`) для воркеров без перезагрузки всей ОС [Основная функциональность](https://nginx.org/ru/docs/ngx_core_module.html#worker_rlimit_nofile). Рекомендуется устанавливать значение с запасом, минимум в 2 раза превышающее общее число соединений [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).

#### Контекст `events`: Сетевой рантайм

Блок `events` отвечает за физику обработки входящего трафика.

- **`worker_connections`** — лимит одновременных соединений на один рабочий процесс [Основная функциональность](https://nginx.org/ru/docs/ngx_core_module.html#worker_connections). Общая емкость сервера рассчитывается как `worker_processes` * `worker_connections`. При установке больших значений (например, 4096 и выше) необходимо убедиться, что `worker_rlimit_nofile` в контексте `main` позволяет открыть такое количество сокетов [Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).
- **`use epoll`** — явно указывает использовать метод обработки событий `epoll` [Основная функциональность](https://nginx.org/ru/docs/ngx_core_module.html#use). Это наиболее производительный масштабируемый механизм в Linux (сложность $O(1)$), позволяющий обрабатывать тысячи соединений без деградации CPU [Основы NGINX глазами разработчика / YouTube](https://www.youtube.com/watch?v=...).
- **`multi_accept on`** — указывает воркеру принимать все новые соединения сразу за один цикл уведомления, а не по одному. Это ускоряет обработку резких всплесков трафика (bursts) [Основная функциональность](https://nginx.org/ru/docs/ngx_core_module.html#multi_accept).

> [!warning] Актуализация синтаксиса
>  Современные версии Nginx (1.29.x+) автоматически выбирают наиболее эффективный метод (`epoll` или `kqueue`), поэтому явное указание `use epoll;` часто является избыточным, но допустимым для явного контроля конфигурации [Оптимизация Nginx и Angie под высокие нагрузки / YouTube](https://www.youtube.com/watch?v=...).

#### Эталонный листинг верхней части nginx.conf (High-Load stack)

```nginx
# Контекст main (Global)
user  nginx;
worker_processes  auto; # Оптимально для многоядерных систем
worker_cpu_affinity auto; # Снижение Context Switching

# Лимит дескрипторов: (worker_connections * 2) + запас для логов
worker_rlimit_nofile 65535;

error_log  /var/log/nginx/error.log warn;
pid        /var/run/nginx.pid;

events {
    # Метод обработки событий (epoll выбран автоматически на Linux)
    worker_connections  16384;

    # Принимать все новые соединения сразу
    multi_accept on;
}
```
