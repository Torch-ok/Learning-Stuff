В эпоху Infrastructure as Code (IaC) и методологии DevSecOps ручное редактирование единого монолитного файла `nginx.conf` считается антипаттерном. Для обеспечения масштабируемости, безопасности и удобства автоматизации через такие инструменты, как Ansible или Terraform, конфигурация Nginx должна быть декомпозирована на логические модули [Complete-NGINX-Cookbook-2019](https://www.nginx.com/resources/library/complete-nginx-cookbook/).

#### Директива include и механика Wildcards

Основой модульности является директива `include`, которая позволяет вставлять содержимое одного конфигурационного файла в другой непосредственно в момент парсинга [Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).

- **Синтаксис:** `include file | mask;` [Модуль ngx_http_core_module](https://nginx.org/ru/docs/http/ngx_http_core_module.html#include).
- **Контекст:** Директива валидна в любом контексте, что позволяет выносить как глобальные настройки `http`, так и специфичные правила `location` [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).
- **Использование масок (Wildcards):** Современный стандарт — `include /etc/nginx/conf.d/*.conf;`. Это позволяет Master-процессу автоматически подхватывать все манифесты с расширением `.conf` при запуске или `reload` [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).

> [!warning] Актуализация синтаксиса
>  
> В старых системах можно встретить включение файлов без расширения или с произвольными именами. По современным стандартам (особенно в официальных репозиториях RHEL/CentOS) следует использовать только расширение `.conf`, чтобы избежать случайного включения временных файлов редакторов или резервных копий [Complete-NGINX-Cookbook-2019](https://www.nginx.com/resources/library/complete-nginx-cookbook/).

#### Архитектурные школы: Debian vs RedHat (Modern)

Существует два основных подхода к управлению активными конфигурациями виртуальных хостов (серверов).

##### 1. Дебиановский подход (Legacy-стандарт)

В дистрибутивах Ubuntu и Debian традиционно используется структура с двумя каталогами [Complete-NGINX-Cookbook-2019](https://www.nginx.com/resources/library/complete-nginx-cookbook/):

- **/etc/nginx/sites-available/** — «склад» всех созданных конфигураций.
- **/etc/nginx/sites-enabled/** — каталог с символическими ссылками (symlinks) на файлы из первой папки. Только те сайты, чьи ссылки присутствуют здесь, будут загружены Nginx.

Для управления используются скрипты `a2ensite` / `a2dissite` (или их аналоги) либо ручное создание ссылок:

```bash
ln -s /etc/nginx/sites-available/my_fastapi.conf /etc/nginx/sites-enabled/
```

**Плюс:** Возможность быстро отключить сайт, не удаляя его конфигурацию. **Минус:** Избыточность и сложность для систем автоматизации IaC [Complete-NGINX-Cookbook-2019](https://www.nginx.com/resources/library/complete-nginx-cookbook/).

##### 2. Редхатовский и Контейнерный подход (Modern Standard)

В RHEL, Rocky Linux и официальных Docker-образах Nginx используется упрощенная структура [Complete-NGINX-Cookbook-2019](https://www.nginx.com/resources/library/complete-nginx-cookbook/):

- **/etc/nginx/conf.d/** — основной каталог для всех активных манифестов.

Все `.conf` файлы из этого каталога подключаются напрямую в блоке `http` основного файла `nginx.conf`. Этот подход считается более предпочтительным в DevSecOps, так как конфигурация определяется состоянием файловой системы (что лежит в папке, то и работает), что идеально для CI/CD пайплайнов [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).

#### Практическая декомпозиция: Вынос общих параметров

Для нашего сквозного примера (Nginx + FastAPI/Uvicorn) монолитный конфиг следует разделить на переиспользуемые блоки. Это предотвращает дублирование (DRY) и снижает вероятность ошибок в настройках безопасности [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).

**Шаг 1: Создание общих параметров проксирования (`/etc/nginx/proxy_params.conf`)**

```nginx
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_connect_timeout 60s;
proxy_read_timeout 60s;
```

**Шаг 2: Создание настроек безопасности SSL (`/etc/nginx/ssl_params.conf`)**

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
ssl_prefer_server_ciphers off; # Современный стандарт для TLS 1.3
ssl_session_cache shared:SSL:10m;
ssl_session_timeout 1d;
add_header Strict-Transport-Security "max-age=63072000" always;
```

**Шаг 3: Основной конфиг сервера в `conf.d/my_app.conf`**

```nginx
server {
    listen 443 ssl;
    server_name api.example.com;

    ssl_certificate /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    include ssl_params.conf; # Подключение модулей безопасности

    location / {
        include proxy_params.conf; # Подключение настроек для Uvicorn
        proxy_pass http://uvicorn_backend;
    }
}
```

Такая структура позволяет обновить настройки TLS или таймауты сразу для всех сайтов на сервере, отредактировав один файл [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).
