Конфигурация Nginx строится по древовидному принципу, где настройки группируются в логические блоки, называемые контекстами. Понимание этой иерархии является критическим навыком для Middle DevOps инженера, так как некорректное размещение директив или непонимание физики их наследования приводит к трудноотлавливаемым багам в работе высоконагруженных систем.

#### Основные контексты конфигурации

Все директивы Nginx делятся на простые (одна строка, заканчивающаяся `;`) и блочные (обернутые в `{ }`). Если блочная директива может содержать внутри себя другие директивы, она формирует контекст.

1. **Main (Global) Context:** Это корень конфигурационного файла (`/etc/nginx/nginx.conf`). Директивы, находящиеся здесь, определяют глобальные параметры работы всего процесса Nginx, такие как идентификатор пользователя (`user`), количество рабочих процессов (`worker_processes`) и пути к основным логам ошибок.
2. **`events` Context:** Вложен в `main`. Здесь настраиваются параметры сетевого рантайма: метод обработки соединений (например, `epoll`) и лимит одновременных подключений на один воркер (`worker_connections`).
3. **`http` Context:** Глобальный контейнер для всей конфигурации веб-трафика. Здесь задаются общие параметры для всех виртуальных хостов: MIME-типы, настройки логирования доступа и параметры сжатия `gzip`.
4. **`server` Context:** Описывает конкретный виртуальный хост. Определяет, на каких портах слушать входящий трафик (`listen`) и на какие доменные имена откликаться (`server_name`).
5. **`location` Context:** Находится внутри `server`. Определяет правила обработки конкретных URI-путей или групп файлов (например, через регулярные выражения). Контексты `location` могут быть вложенными.
6. **`upstream` Context:** Определяет группу бэкенд-серверов (например, кластер FastAPI/Uvicorn), на которые Nginx будет балансировать трафик.

#### Физика наследования директив

Наследование в Nginx всегда работает по направлению сверху вниз (от родительского контекста к дочернему). Однако поведение директив при переопределении зависит от их типа.

##### Директивы типа Value (Переопределение)

Директивы, принимающие одно значение (например, `root`, `client_max_body_size`, `index`), наследуются дочерним контекстом, если в нем не указано иное. Если же дочерний контекст (например, `location`) содержит свою директиву `root`, значение родителя (контекста `server`) для этого блока полностью игнорируется и заменяется новым.

##### Директивы типа Array (Замещение)

К этому типу относятся директивы, которые могут быть указаны несколько раз для накопления значений (например, `add_header`, `proxy_set_header`, `error_page`).

> [!warning] Критическая особенность наследования
>  Если в дочернем контексте (например, в `location`) указана хотя бы одна директива `add_header`, то **все** директивы `add_header` родительского контекста (например, `server`) для этого блока аннулируются. Это часто приводит к потере важных заголовков безопасности (HSTS, CSP) при попытке добавить специфичный заголовок в конкретный `location`.

#### Борьба с дублированием кода (DRY в Nginx)

Антипаттерном является копирование одинаковых настроек (например, `root` или `index`) в каждый блок `location`. Это затрудняет поддержку: при смене корневой директории придется вносить правки в десятки мест.

Правильный подход — выносить общие настройки на максимально высокий доступный уровень (`http` или `server`), позволяя дочерним контекстам наследовать их автоматически. Для модульных конфигураций необходимо использовать директиву `include`, разделяя настройки TLS, заголовки и параметры проксирования по отдельным файлам.

### Интерактивный тест для самопроверки

1. **Где должна располагаться директива `worker_connections`?**
    
2. **Что произойдет с заголовком `add_header X-Frame-Options "DENY";`, заданным в контексте `http`, если в блоке `location` добавить `add_header X-Debug "true";`?**
    
3. **В какой контекст следует вынести директиву `root /var/www/data;`, если она одинакова для всех URI виртуального хоста?**
    
4. **Может ли контекст `upstream` находиться внутри контекста `server`?**
    
5. **Какая команда CLI поможет увидеть итоговую конфигурацию со всеми вложенными `include` для проверки правильности наследования?**
