В данном разделе систематизированы ключевые понятия, определяющие структуру конфигурации и взаимодействие Nginx с системными ресурсами операционной системы.

- **Main Context** — глобальный контекст конфигурации (корень файла `nginx.conf`), содержащий директивы, которые управляют работой всего сервера и не входят в специфические блоки,.
- **Events Context** — специализированный контекст, в котором настраиваются параметры обработки сетевых соединений и выбирается событийная модель (например, `epoll`),.
- **HTTP Context** — основной контейнер для всех настроек, связанных с протоколом HTTP, включая описание виртуальных серверов и параметров проксирования,.
- **Inheritance Overhead** — логика наследования директив, при которой переопределение «массивных» директив (таких как `add_header`) в дочернем контексте приводит к полной потере значений родительского контекста.
- **Worker Connections** — директива, задающая максимальное количество одновременных соединений, которые может поддерживать один рабочий процесс,.
- **File Descriptors Limit (nofile)** — системное ограничение на количество открытых файлов (файловых дескрипторов), которое Nginx увеличивает через директиву `worker_rlimit_nofile` для поддержки тысяч соединений,.
- **Symlinks Architecture** — традиционная для Debian/Ubuntu структура организации конфигов с разделением на `sites-available` и активные ссылки в `sites-enabled`, считающаяся устаревшей в современных контейнерных средах,.

## Практическое упражнение (Декомпозиция монолитного конфига и настройка базового Nginx под FastAPI)

**Сюжет:** Вы заступили на смену и получили «грязный» `nginx.conf`. Все настройки процессов, логирования и три разных виртуальных сервера (включая API на FastAPI) свалены в один файл длиной 300 строк. Это затрудняет поддержку и нарушает принципы IaC,.

### Задача:

1. Рассчитать лимиты: сервер имеет 4 ядра CPU. Необходимо обеспечить поддержку 4096 одновременных соединений в режиме Reverse Proxy к `Uvicorn`,.
2. Выполнить декомпозицию: выделить виртуальные хосты в `conf.d/`, а повторяющиеся заголовки — в отдельный фрагмент,.
3. Применить изменения через Graceful Reload,.

### Исходный «грязный» конфиг (фрагмент):

```nginx
user www-data;
worker_processes 1; # ОШИБКА: не использует все ядра
events { worker_connections 1024; }
http {
    # Здесь смешаны заголовки, логи и три блока server { ... }
    add_header X-Frame-Options "SAMEORIGIN";
    server { listen 80; server_name api.example.com; location / { proxy_pass http://127.0.0.1:8000; } }
    server { listen 80; server_name static.example.com; location / { root /var/www/static; } }
    # ... еще 200 строк ...
}
```

### Шаг 1: Расчет параметров системы

Для 4 ядер устанавливаем `worker_processes 4`. Каждое прокси-соединение требует 2 дескриптора, следовательно, для `worker_connections 4096` нам нужно минимум `worker_rlimit_nofile 10000` (с запасом на логи и файлы),.

### Шаг 2: Новая файловая структура

```
/etc/nginx/
├── nginx.conf
├── snippets/
│   └── common_headers.conf
└── conf.d/
    └── fastapi_api.conf
```

### Шаг 3: Финальные файлы

**Файл `/etc/nginx/snippets/common_headers.conf`:**

```nginx
add_header X-Frame-Options "SAMEORIGIN" always;
add_header X-Content-Type-Options "nosniff" always;
```

**Файл `/etc/nginx/conf.d/fastapi_api.conf`:**

```nginx
server {
    listen 80;
    server_name api.example.com;

    location / {
        include snippets/common_headers.conf;
        proxy_pass http://127.0.0.1:8000; # Наш Uvicorn
    }
}
```

**Файл `/etc/nginx/nginx.conf`:**

```nginx
user nginx;
worker_processes auto;
worker_rlimit_nofile 10000;

events {
    worker_connections 4096;
}

http {
    include /etc/nginx/conf.d/*.conf;
}
```

### Шаг 4: Валидация и применение

```bash
sudo nginx -t     # Проверка синтаксиса
sudo nginx -s reload # Применение без разрыва соединений
```

### Интерактивный тест для самопроверки

1. **Где (в каком контексте) должна быть объявлена директива `worker_rlimit_nofile`?**
    <details>
    <summary>Ответ</summary>
    В контексте `main` (глобальном), так как она влияет на системные лимиты процессов всего сервера.,
    </details>

2. **Какая команда позволяет увидеть финальный скомпилированный конфиг со всеми вставками `include`?**
    <details>
    <summary>Ответ</summary>
    Команда `nginx -T`. Она выводит полный текст конфигурации в STDOUT, что полезно для отладки наследования.,
    </details>

3. **Что произойдет, если сумма `worker_connections` всех воркеров превысит системный лимит `ulimit -n`?**
    <details>
    <summary>Ответ</summary>
    Nginx начнет выдавать ошибки "Too many open files" в `error_log` и перестанет принимать новые соединения, несмотря на запас в конфиге.,
    </details>

4. **Почему подход `sites-enabled` с симлинками считается устаревшим (deprecated) в официальной документации NGINX Cookbook?**
    <details>
    <summary>Ответ</summary>
    Он признан избыточным и неудобным для автоматизации. Современным стандартом является использование единой директории `conf.d/`.
    </details>

5. **Какая директива используется для ограничения максимального размера тела запроса (например, для защиты FastAPI от загрузки гигантских файлов)?**
    <details>
    <summary>Ответ</summary>
    Директива `client_max_body_size`, которая может быть задана в контекстах `http`, `server` или `location`.,
    </details>
