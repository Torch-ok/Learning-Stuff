В данном разделе систематизированы ключевые понятия, определяющие политики безопасности и механизмы защиты ресурсов сервера Nginx от злонамеренного или избыточного потребления.

- **Rate Limiting** — механизм ограничения интенсивности входящих запросов к серверу для предотвращения перегрузки бэкенда и защиты от автоматизированных атак.
- **Leaky Bucket Algorithm** — фундаментальный алгоритм «дырявого ведра», используемый Nginx для сглаживания пульсирующей нагрузки и обеспечения стабильной скорости обработки запросов.
- **limit_req_zone** — директива, определяющая параметры зоны разделяемой памяти для хранения счетчиков состояния запросов на основе выбранного ключа (например, IP-адреса).
- **burst & nodelay** — параметры контроля всплесков трафика: `burst` задает размер очереди для запросов сверх лимита, а `nodelay` предписывает обрабатывать их немедленно без внесения сетевых задержек.
- **limit_conn** — механизм ограничения количества одновременно установленных TCP-соединений с одного ключа (обычно IP), критически важный для защиты от исчерпания файловых дескрипторов.
- **Slowloris Attack** — тип DoS-атаки, основанный на удержании максимального количества соединений открытыми путем крайне медленной передачи данных, что приводит к блокировке воркеров приложения.
- **429 Too Many Requests** — семантически корректный HTTP-статус ответа, возвращаемый клиенту при превышении установленных лимитов частоты или соединений.
- **client_max_body_size** — директива, устанавливающая жесткий лимит на размер тела запроса (например, загружаемого файла), предотвращающая атаки на переполнение RAM и дискового пространства.

## Практическое упражнение (Комплексная защита FastAPI от DDoS, Brute-force и Slowloris атак с помощью Rate Limiting и контроля ресурсов)

**Сценарий:** Публичный API шлюз на базе Nginx проксирует запросы к асинхронному бэкенду FastAPI (Uvicorn). В ходе аудита безопасности выявлены попытки перебора паролей на эндпоинте авторизации и аномально большие запросы, забивающие очередь обработки бэкенда.

### Техническое задание:

1. **Brute-force protection:** Ограничить частоту запросов к `/api/v1/login` до 5 запросов в минуту с разрешенным всплеском в 2 запроса без задержек.
2. **General API protection:** Для всех остальных эндпоинтов в `/api/` установить лимит 20 запросов в секунду с буфером 10.
3. **Connection limit:** Ограничить количество параллельных TCP-сессий с одного IP до 10 для защиты от Slowloris.
4. **Payload control:** Установить глобальный лимит тела запроса 1 МБ, увеличив его до 20 МБ исключительно для локации загрузки файлов.
5. **Status codes:** Настроить возврат кода 429 при превышении всех лимитов частоты и соединений.

### Итоговая конфигурация Nginx (`/etc/nginx/conf.d/security_policy.conf`):

```nginx
# 1. Объявление зон разделяемой памяти в контексте http
# Зона для авторизации: 10МБ хватит на ~160k состояний IP
limit_req_zone $binary_remote_addr zone=login_limit:10m rate=5r/m;
# Зона для общего API: 20 запросов в секунду
limit_req_zone $binary_remote_addr zone=api_general:10m rate=20r/s;
# Зона для контроля соединений
limit_conn_zone $binary_remote_addr zone=addr_conn:10m;

server {
    listen 443 ssl;
    server_name api.secure-app.com;

    # Глобальный лимит размера тела запроса
    client_max_body_size 1M;

    # Кастомизация ошибок
    limit_req_status 429;
    limit_conn_status 429;
    limit_req_log_level warn;

    # Лимит параллельных соединений на весь сервер
    limit_conn addr_conn 10;

    location /api/v1/login {
        # Жесткий лимит на попытки входа
        limit_req zone=login_limit burst=2 nodelay;
        proxy_pass http://uvicorn_backend;
    }

    location /api/v1/upload {
        # Расширенный лимит только для загрузки файлов
        client_max_body_size 20M;
        limit_req zone=api_general burst=10;
        proxy_pass http://uvicorn_backend;
    }

    location /api/ {
        # Общий лимит для всех API эндпоинтов
        limit_req zone=api_general burst=10;
        proxy_pass http://uvicorn_backend;
    }
}
```

### Симуляция атаки и верификация:

1.  **Тест Brute-force авторизации:**
    ```bash
    # Попытка сделать 10 запросов на логин за секунду
    ab -n 10 -c 1 https://api.secure-app.com/api/v1/login
    ```
    **Результат:** Первые 3 запроса (1 по лимиту + 2 burst) пройдут со статусом `200 OK`, остальные 7 будут немедленно отклонены со статусом `429 Too Many Requests`.

2.  **Тест загрузки гигантского файла:**
    ```bash
    # Попытка отправить файл 5МБ на стандартный эндпоинт
    curl -X POST -F "data=@large_file.json" https://api.secure-app.com/api/v1/user/profile
    ```
    **Результат:** Сервер вернет ответ `HTTP/1.1 413 Request Entity Too Large`.

3.  **Анализ логов (`/var/log/nginx/error.log`):
```text
2026/07/26 02:40:00 [warn] ... limiting requests, client: 192.168.1.50, server: api.secure-app.com, request: "POST /api/v1/login HTTP/1.1"
```

## Вопросы для самопроверки к Модулю 9

1.  **В чем заключается математическое преимущество использования `$binary_remote_addr` перед `$remote_addr` при выделении зоны разделяемой памяти?**.
2.  **Как изменится поведение Nginx при обработке всплеска запросов (burst), если из конфигурации `limit_req` убрать параметр `nodelay`?**.
3.  **Почему для современных API-интерфейсов рекомендуется заменять стандартный код ошибки 503 на 429 с помощью `limit_req_status`?**.
4.  **Каким образом директива `client_body_timeout` защищает асинхронный Event Loop Uvicorn от атак типа Slowloris?**.
5.  **Можно ли одновременно применять несколько директив `limit_conn` в одном контексте `location`, и какова будет логика их срабатывания?**.

---

### Интерактивный тест для самопроверки

1. **Сколько уникальных IP-адресов может отслеживать зона `limit_req_zone` размером 10 МБ на 64-битной архитектуре?**
    <details>
    <summary>Ответ</summary>
    Примерно 160 000 состояний. Бинарный адрес IPv4 занимает 64 байта в памяти зоны на данной архитектуре.
    </details>

2. **Запрос пришел со скоростью 10 r/s при лимите `rate=1r/s` и `burst=5 nodelay`. Сколько запросов будет обработано успешно в первую секунду?**
    <details>
    <summary>Ответ</summary>
    6 запросов: 1 запрос по основному лимиту + 5 запросов из буфера burst. Все последующие запросы будут отклонены.
    </details>

3. **Что произойдет, если размер загружаемого JSON-файла составит 512 КБ, а `client_body_buffer_size` равен 16 КБ?**
    <details>
    <summary>Ответ</summary>
    Nginx примет запрос (так как он меньше `client_max_body_size`), но запишет тело во временный файл на диске, так как оно превышает размер буфера в RAM.
    </details>

4. **Какая директива позволяет ограничить общее количество соединений ко всему виртуальному серверу, а не к конкретному IP?**
    <details>
    <summary>Ответ</summary>
    `limit_conn_zone $server_name zone=total:10m;` с последующим вызовом `limit_conn total 1000;`.
    </details>

5. **Какой параметр `limit_req` позволяет реализовать «двухстадийное» ограничение (часть всплеска без задержек, часть — с задержками)?**
    <details>
    <summary>Ответ</summary>
    Параметр `delay`. Например, `burst=12 delay=9` пропустит 9 запросов мгновенно, а следующие 3 — с задержкой.
    </details>
