В высоконагруженных архитектурах, где Nginx терминирует тысячи TLS-сессий и проксирует их на асинхронный стек FastAPI / Uvicorn, критической точкой отказа часто становится не частота запросов (RPS), а количество одновременно удерживаемых соединений. Если лимиты не настроены, злоумышленник или некорректно работающий клиент могут занять все доступные слоты `worker_connections`, заставив сервер отклонять легитимный трафик. Ограничение параллельных соединений (Connection Limiting) — это механизм контроля «состояния» (state), позволяющий гарантировать, что ресурсы сетевого стека распределяются между пользователями справедливо.

#### 9.2.1. Отличие Rate Limiting от Connection Limiting

Для системного инженера важно различать две фазы контроля:

- **Ограничение частоты (`limit_req`)**: Регулирует интенсивность поступления новых запросов (например, 5 запросов в секунду). Один клиент может открыть **одно** Keep-alive соединение и отправить через него 100 запросов — `limit_req` будет проверять каждый из них.
- **Ограничение соединений (`limit_conn`)**: Регулирует количество открытых TCP-сессий в данный конкретный момент времени. Если клиент открыл 10 вкладок в браузере, каждая из которых удерживает соединение с FastAPI, `limit_conn` зафиксирует 10 состояний.

В условиях асинхронного бэкенда Uvicorn это критично: каждый открытый сокет потребляет файловый дескриптор и память, а при передаче «тяжелых» ответов из PostgreSQL соединение может оставаться активным долгое время, блокируя ресурсы.

#### 9.2.2. Работа модуля ngx_http_limit_conn_module

Управление лимитами осуществляется через создание зон разделяемой памяти, доступных всем Worker-процессам Nginx.

##### Директива limit_conn_zone

Объявляется строго в контексте `http`. Она задает ключ, по которому будут группироваться соединения, и объем памяти для хранения счетчиков.

**Синтаксис:** `limit_conn_zone $binary_remote_addr zone=addr:10m;`.

- **Ключ `$binary_remote_addr`**: В отличие от строкового `$remote_addr`, бинарное представление IPv4 занимает всего 4 байта, что в 4-5 раз эффективнее для RAM. Зона в 10 МБ позволяет отслеживать до 160 000 уникальных IP-адресов одновременно.
- **Ключ `$server_name`**: Позволяет ограничить суммарное количество соединений ко всему виртуальному серверу. Это защищает весь узел Nginx от исчерпания глобальных лимитов ОС (`somaxconn`), если один из проектов попал под атаку.

##### Директива limit_conn

Применяется в контекстах `http`, `server` или `location`. Она активирует проверку на основе ранее созданной зоны.

```nginx
http {
    # Зона для лимитов по IP (10 МБ памяти)
    limit_conn_zone $binary_remote_addr zone=perip:10m;
    # Зона для лимитов на весь сервер
    limit_conn_zone $server_name zone=perserver:10m;

    server {
        # Лимит для API: не более 10 соединений с одного адреса
        limit_conn perip 10;
        # Глобальный лимит сервера: не более 2000 соединений суммарно
        limit_conn perserver 2000;

        # Кастомизация кода ответа на 429 (Too Many Requests)
        limit_conn_status 429;
        limit_conn_log_level warn;

        location /api/v1/stream {
            proxy_pass http://uvicorn_backend;
            # Для тяжелых стриминговых эндпоинтов лимит еще жестче
            limit_conn perip 2;
        }
    }
}
```

#### 9.2.3. Защита от Slowloris и исчерпания сокетов

**Slowloris** — это тип атаки, при которой клиент открывает множество соединений и отправляет/читает данные крайне медленно, по одному байту в несколько секунд. Цель — удерживать сокет открытым как можно дольше, пока лимит `worker_connections` на стороне Nginx или пул воркеров в Uvicorn не будет исчерпан.

`limit_conn` эффективно противодействует этому, не позволяя одному IP-адресу «завесить» более установленного числа сокетов. В дополнение к этому рекомендуется включать `reset_timedout_connection on;`, что заставляет Nginx мгновенно сбрасывать сокет по таймауту через `TCP RST`, освобождая память немедленно.

#### 9.2.4. Кастомизация статуса и отладка

По умолчанию при превышении лимита Nginx возвращает `503 Service Unavailable`. Однако в современных API стандарта 2026 года для ошибок на стороне клиента (превышение квоты) необходимо использовать код `429 Too Many Requests`.

Для анализа эффективности лимитов в Nginx Plus / Angie можно использовать параметр `limit_conn_dry_run on;`. В этом режиме соединения не разрываются, но в переменную `$limit_conn_status` записывается статус `REJECTED_DRY_RUN`, что позволяет проанализировать логи и настроить «боевые» лимиты без риска для пользователей.

### Интерактивный тест для самопроверки

1. **В чем заключается основное преимущество использования `$binary_remote_addr` вместо `$remote_addr` в качестве ключа зоны?**
    <details>
    <summary>Ответ</summary>
    Бинарный формат IP-адреса имеет фиксированный размер (4 байта для IPv4), что позволяет экономить до 80% памяти в разделяемой зоне и хранить в несколько раз больше состояний клиентов.
    </details>

2. **Может ли клиент с одним IP-адресом обойти ограничение `limit_conn`, если он использует HTTPS?**
    <details>
    <summary>Ответ</summary>
    Нет. Ограничение `limit_conn` работает после установления TCP-соединения и TLS-хендшейка. Nginx уже знает IP-адрес клиента и применяет лимит до обработки HTTP-запроса.
    </details>

3. **Что произойдет, если в блоке `server` настроено два лимита: `limit_conn perip 10;` и `limit_conn perserver 1000;`?**
    <details>
    <summary>Ответ</summary>
    Будут срабатывать оба ограничения одновременно. Запрос будет отклонен, если клиент превысит свой лимит в 10 соединений ИЛИ если суммарное количество соединений к серверу превысит 1000.
    </details>

4. **Какая директива позволяет немедленно освободить память сокета при таймауте, не дожидаясь состояния `FIN_WAIT`?**
    <details>
    <summary>Ответ</summary>
    `reset_timedout_connection on;`. Она отправляет `TCP RST`, что критично при отражении Slowloris-атак.
    </details>

5. **Почему статус-код 429 предпочтительнее стандартного 503 при срабатывании `limit_conn`?**
    <details>
    <summary>Ответ</summary>
    Код 503 означает ошибку на стороне сервера (сервис временно недоступен), тогда как 429 четко указывает клиенту, что проблема на его стороне — он отправляет слишком много запросов.
    </details>
