В архитектуре высоконагруженных систем 2026 года, где Nginx терминирует трафик для асинхронного стека FastAPI / Uvicorn, контроль потребления ресурсов на уровне каждого запроса является критическим элементом стабильности. Без жестких ограничений злоумышленник или некорректно работающий клиент могут инициировать атаку на исчерпание ресурсов (DoS), заполнив оперативную память воркеров или дисковое пространство сервера гигантскими объемами данных.

#### 9.3.1. Директива `client_max_body_size`: Ограничение объема данных

Директива `client_max_body_size` задает максимально допустимый размер тела запроса клиента, который Nginx готов принять. Это основной инструмент борьбы с загрузкой сверхбольших файлов, которые могут парализовать работу бэкенда и базы данных PostgreSQL.

- **Механика:** Если размер тела запроса (указанный в заголовке `Content-Length`) превышает установленный лимит, Nginx немедленно прекращает чтение и возвращает клиенту ошибку `413 Request Entity Too Large`.
- **Гибкость настройки:** Директива может быть объявлена в контекстах `http`, `server` или `location`, что позволяет применять разные политики безопасности для разных частей приложения.
- **Отключение лимита:** Установка значения в `0` полностью отключает проверку размера, что крайне опасно в Production-средах и допускается только для доверенных внутренних сервисов.

> [!warning] Актуализация синтаксиса 
> При настройке лимитов для эндпоинтов загрузки файлов (например, в FastAPI через `UploadFile`) учитывайте накладные расходы на кодирование. Если вы хотите разрешить загрузку файла размером 12 МБ, лимит в Nginx следует установить на уровне `16M`, так как из-за особенностей передачи данных итоговый объем тела запроса может быть на ~30% больше исходного файла.

**Пример разделения лимитов:**

```nginx
server {
    listen 443 ssl;
    client_max_body_size 2M; # Общий лимит для REST API

    location /api/v1/user/avatar {
        # Специальный эндпоинт для загрузки медиа
        client_max_body_size 10M;
        proxy_pass http://uvicorn_backend;
    }
}
```

#### 9.3.2. Управление буферами тела и заголовков

Для эффективной передачи данных асинхронному бэкенду Nginx использует систему буферов, предотвращающую лишние дисковые операции.

1. **`client_body_buffer_size`**: Определяет размер буфера в RAM для чтения тела запроса. Если тело запроса больше этого буфера, Nginx сохраняет остаток (или всё тело) во временный файл на диске. В высоконагруженных системах рекомендуется подбирать размер так, чтобы типичные JSON-ответы API полностью помещались в RAM (стандарт — 8K или 16K в зависимости от платформы).
2. **`client_header_buffer_size`**: Задает размер буфера для чтения заголовков. Стандартного `1k` обычно достаточно, но если ваше приложение использует тяжелые Cookies или JWT-токены в заголовке `Authorization`, этот лимит может потребоваться увеличить. При его превышении Nginx задействует `large_client_header_buffers`.

#### 9.3.3. Сетевые таймауты как защита от Slowloris

Таймауты в Nginx 2026 года служат «предохранителями», принудительно закрывающими соединения, которые не проявляют активности, освобождая ресурсы для живых клиентов.

- **`client_body_timeout`**: Задает время ожидания между двумя последовательными операциями чтения тела запроса. Если клиент перестал передавать данные (например, при медленной атаке Slowloris), соединение будет разорвано с ошибкой `408 Request Time-out`.
- **`client_header_timeout`**: Лимит времени на чтение всего заголовка запроса. Также завершается ошибкой `408`, если клиент удерживает соединение, не передавая заголовки.
- **`send_timeout`**: Время ожидания между двумя операциями записи ответа клиенту. Если клиент перестал принимать данные от Nginx (например, из-за сетевого сбоя на стороне мобильного устройства), сокет будет закрыт.

#### 9.3.4. Оптимизация Keep-Alive соединений

Механизм HTTP Keep-Alive позволяет переиспользовать TCP-соединения, что критично для снижения нагрузки на CPU при TLS-рукопожатиях. Однако неправильная настройка может привести к исчерпанию лимита открытых файлов (`worker_rlimit_nofile`).

- **`keepalive_timeout`**: Задает время, в течение которого простаивающее соединение остается открытым. Значение `0` полностью запрещает Keep-Alive. В 2026 году рекомендуется балансировать между `65s` и `120s` для обеспечения комфортного UX.
- **`keepalive_requests`**: Ограничивает количество запросов, которые можно отправить через одно соединение. Современный дефолт в Nginx — `1000` запросов (в старых версиях было 100), что предотвращает утечки памяти и позволяет плавно обновлять рабочие процессы.

### Интерактивный тест для самопроверки

1. **Какой HTTP-код вернет Nginx клиенту, если размер загружаемого файла превысит значение `client_max_body_size`?**
    <details>
    <summary>Ответ</summary>
    HTTP статус `413 Request Entity Too Large` [6, 8].
    </details>

2. **Что произойдет с телом запроса, если его размер больше `client_body_buffer_size`, но меньше `client_max_body_size`?**
    <details>
    <summary>Ответ</summary>
    Nginx запишет часть тела запроса (или всё тело) во временный файл на диске, что снизит производительность из-за операций ввода-вывода (I/O) [17, 19].
    </details>

3. **В чем заключается разница между `client_body_timeout` и общим временем выполнения запроса?**
    <details>
    <summary>Ответ</summary>
    `client_body_timeout` измеряет время не на всю передачу, а только между двумя последовательными операциями чтения данных от клиента [24, 25].
    </details>

4. **Зачем в высоконагруженных системах рекомендуется устанавливать большое значение для `keepalive_requests` (например, 1000 и выше)?**
    <details>
    <summary>Ответ</summary>
    Чтобы максимально эффективно переиспользовать установленные TCP и TLS соединения, экономя ресурсы процессора на операциях Handshake, особенно при высоком RPS [29, 30].
    </details>

5. **Какая директива позволяет немедленно разорвать TCP-соединение по таймауту, отправляя пакет RST, чтобы не занимать сокет в состоянии `FIN_WAIT1`?**
    <details>
    <summary>Ответ</summary>
    Директива `reset_timedout_connection on;` [43, 44].
    </details>
