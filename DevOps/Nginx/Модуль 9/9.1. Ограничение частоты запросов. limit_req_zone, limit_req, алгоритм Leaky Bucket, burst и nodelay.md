В современных высоконагруженных архитектурах 2026 года Nginx выступает не просто как прокси-сервер, а как стратегическая «первая линия обороны» для асинхронных стеков на базе FastAPI / Uvicorn и PostgreSQL. Ограничение частоты запросов (Rate Limiting) является критически важным инструментом для предотвращения исчерпания ресурсов бэкенда, вызванного DDoS-атаками прикладного уровня (L7), агрессивным парсингом данных (Scraping) или попытками Brute-force авторизации. Без этих лимитов «тяжелый» поисковый бот или злоумышленник могут заблокировать Event Loop Python-приложения или утилизировать все доступные CPU-циклы базы данных, сделав сервис недоступным для легитимных пользователей.

#### 9.1.1. Алгоритм Leaky Bucket: Математика «Дырявого ведра»

Nginx реализует Rate Limiting на основе алгоритма **Leaky Bucket** («дырявое ведро»).

- **Физика процесса:** Представьте ведро, на дне которого есть отверстие строго определенного диаметра (параметр `rate`). Входящие запросы — это вода, наполняющая ведро. Если вода поступает медленнее или с той же скоростью, с которой она вытекает, ведро остается пустым или наполняется частично. Если запросы приходят слишком часто, ведро начинает наполняться.
- **Сглаживание пиков:** Если в конфигурации не указаны дополнительные параметры, Nginx будет вносить искусственные задержки (RTT), чтобы «выровнять» поток запросов до заданной скорости.
- **Переполнение:** Как только объем входящей «воды» превышает размер ведра (зоны памяти и лимита `burst`), новые запросы немедленно отбрасываются с ошибкой.

#### 9.1.2. Директива limit_req_zone: Настройка зоны памяти

Ограничение начинается с объявления зоны в контексте `http`, где будет храниться состояние счетчиков запросов.

**Синтаксис:**

```nginx
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=5r/s;
```

- **Ключ ограничения (`key`):** Чаще всего используется переменная `$binary_remote_addr`.
    - **Почему это важно:** В отличие от строковой переменной `$remote_addr`, бинарное представление IPv4-адреса занимает фиксированные 4 байта (32 бита) или 16 байт для IPv6. Это позволяет экономить память в 4-5 раз: зона размером 10 МБ способна хранить состояние для ~160 000 уникальных IP-адресов на 64-битных системах.
- **Параметр `rate`:** Частота запросов задается в запросах в секунду (`r/s`) или минуту (`r/m`).
    
> [!warning] Актуализация синтаксиса 
Даже если вы укажете `1r/s`, Nginx внутри себя оперирует миллисекундами. Это означает, что при лимите `1r/s` второй запрос, пришедший через 100 мс после первого, будет либо задержан, либо отброшен, если не настроен `burst`.
    

#### 9.1.3. Применение лимитов: burst, nodelay и delay

Директива `limit_req` активирует ограничения внутри блоков `server` или `location`.

- **`burst` (всплеск):** Задает максимальное количество запросов, которые клиент может сделать сверх установленного лимита `rate`. Эти запросы помещаются в очередь и обрабатываются с задержкой, чтобы соответствовать общему лимиту.
- **`nodelay`:** Самый востребованный параметр для современных API на FastAPI. Он заставляет Nginx обрабатывать все запросы в рамках лимита `burst` немедленно, не внося искусственных сетевых задержек (RTT). Однако счетчик все равно учитывает эти запросы, и последующие обращения будут отклонены до тех пор, пока «ведро не опустеет».
- **`delay`:** Появился в более свежих версиях для реализации двухстадийного ограничения. Позволяет пропустить первые `N` запросов без задержки, а остальные запросы из `burst`-буфера — с задержкой.

**Пример эталонной защиты эндпоинта авторизации:**

```nginx
limit_req_zone $binary_remote_addr zone=auth_limit:10m rate=1r/m; # Очень жесткий лимит

server {
    location /api/v1/login {
        # Разрешаем всплеск до 5 запросов мгновенно, далее — блок на минуту
        limit_req zone=auth_limit burst=5 nodelay;

        # Меняем стандартную ошибку 503 на более корректную 429
        limit_req_status 429;

        proxy_pass http://uvicorn_backend;
    }
}
```

#### 9.1.4. Кастомизация ответов и логирование

По умолчанию при превышении лимита Nginx возвращает ошибку `503 Service Unavailable`, что семантически неверно, так как проблема на стороне клиента, а не сервера.

*   **`limit_req_status 429;`** — возвращает стандартный код `429 Too Many Requests`, который правильно интерпретируется современными фронтенд-библиотеками.
*   **`limit_req_log_level warn;`** — позволяет снизить уровень серьезности записей в `error_log`. По умолчанию используется `error`, что может зашумлять логи при частых атаках.

### Интерактивный тест для самопроверки

1. **В каком контексте конфигурации Nginx разрешено объявлять зону `limit_req_zone`?**
    <details>
    <summary>Ответ</summary>
    Только в контексте `http`. Использование этой директивы внутри `server` или `location` приведет к ошибке синтаксиса.
    </details>

2. **Почему использование `$binary_remote_addr` предпочтительнее для Rate Limiting, чем `$remote_addr`?**
    <details>
    <summary>Ответ</summary>
    Бинарный формат IP-адреса потребляет фиксированные 32/64 байта в памяти вместо динамической строки, что позволяет хранить в разы больше состояний клиентов в той же зоне разделяемой памяти.
    </details>

3. **Что произойдет с запросом, попавшим в лимит `burst`, если параметр `nodelay` НЕ указан?**
    <details>
    <summary>Ответ</summary>
    Nginx примет запрос, но будет удерживать его обработку, внося искусственную задержку, чтобы скорость ответов соответствовала заданному `rate`.
    </details>

4. **Какой HTTP-статус возвращает Nginx по умолчанию при срабатывании ограничения, и какой статус рекомендуется устанавливать в Production?**
    <details>
    <summary>Ответ</summary>
    По умолчанию возвращается `503`, но рекомендуется устанавливать `429`, так как код 500-го уровня указывает на ошибку сервера, а 400-го — на ошибку клиента (превышение квот).
    </details>

5. **Как работает параметр `delay=5` в директиве `limit_req zone=name burst=12 delay=5`?**
    <details>
    <summary>Ответ</summary>
    Первые 5 запросов из всплеска будут обработаны мгновенно, последующие запросы до достижения лимита в 12 (всего 7 штук) будут обрабатываться с задержкой.
    </details>
