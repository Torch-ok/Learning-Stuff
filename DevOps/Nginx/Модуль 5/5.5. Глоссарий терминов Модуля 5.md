В данном разделе представлены ключевые сетевые абстракции и параметры, позволяющие Nginx эффективно управлять распределением трафика и обеспечивать непрерывность сервиса.

- **Upstream Context** — специализированный блок внутри контекста `http`, описывающий именованную группу бэкенд-серверов для последующего проксирования [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html).
- **Round Robin** — алгоритм балансировки по умолчанию, распределяющий запросы по списку серверов циклически в порядке их следования [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).
- **Least Connections** — интеллектуальный метод распределения трафика, при котором новый запрос направляется серверу с наименьшим количеством активных соединений [Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).
- **IP Hash** — метод балансировки, использующий IP-адрес клиента (первые три октета IPv4) в качестве ключа для хэширования, что гарантирует привязку пользователя к конкретной ноде бэкенда [NGINX Content Caching](https://docs.nginx.com/nginx/admin-guide/content-cache/content-caching/).
- **Server Weight** — численный коэффициент, определяющий долю запросов, направляемых серверу; чем выше вес, тем больше нагрузки получает узел [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html).
- **Max Fails / Fail Timeout** — параметры детекции сбоев; `max_fails` задает лимит ошибок, после которого сервер помечается как недоступный на срок, указанный в `fail_timeout` [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).
- **Backup Server** — резервный инстанс в апстриме, который начинает принимать трафик только в случае выхода из строя всех основных узлов кластера [Complete-NGINX-Cookbook-2019](https://www.nginx.com/resources/library/complete-nginx-cookbook/).
- **Passive Health Checks** — механизм мониторинга здоровья бэкендов на основе анализа реальных ответов пользователям без отправки специальных синтетических запросов [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).

## Практическое упражнение (Настройка отказоустойчивого апстрима для кластера Uvicorn с резервным сервером и least_conn)

**Сценарий:** Архитектура проекта требует балансировки нагрузки между тремя инстансами FastAPI, запущенными через Uvicorn. Некоторые эндпоинты выполняют "тяжелую" обработку данных, поэтому стандартный циклическое распределение неэффективно. Необходимо внедрить механизм автоматического исключения упавших нод и предусмотреть "тревожный" резервный сервер.

### Техническая конфигурация (`/etc/nginx/conf.d/uvicorn_cluster.conf`)

```nginx
# Определение пула бэкендов
upstream uvicorn_pool {
    # 1. Алгоритм для учета занятости воркеров Python
    least_conn;

    # 2. Основные ноды кластера
    # fail_timeout=30s отвечает за срок исключения (согласно ТЗ)
    server 127.0.0.1:8001 max_fails=3 fail_timeout=30s;
    server 127.0.0.1:8002 max_fails=3 fail_timeout=30s;
    server 127.0.0.1:8003 max_fails=3 fail_timeout=30s;

    # 3. Резервный сервер
    server 127.0.0.1:8004 backup;
}

server {
    listen 80;
    server_name api.local;

    location / {
        proxy_pass http://uvicorn_pool;

        # 4. Настройка Failover (перехват ошибок бэкенда)
        # Если нода вернула 502/504, Nginx сразу перебросит запрос живой ноде
        proxy_next_upstream error timeout http_502 http_503 http_504;

        include proxy_params;
    }
}
```

### Симуляция падения и анализ логов

1.  **Действие:** Принудительно остановите процесс Uvicorn на порту 8002: `kill -9 <PID_UVICORN_8002>`.
2.  **Эффект:** При первых трех запросах, которые алгоритм попытается отправить на порт 8002, Nginx получит ошибку `connection refused`. Благодаря `proxy_next_upstream`, клиент не увидит ошибку — запрос будет бесшовно передан на порты 8001 или 8003,.
3.  **Исключение:** После третьей ошибки в течение 30 секунд сервер `8002` будет помечен как `unhealthy` и полностью исключен из балансировки на 30 секунд.
4.  **Анализ логов (`error.log`):**
    ```text
    2026/07/25 10:00:01 [error] 1234#0: *56 connect() failed (111: Connection refused) while connecting to upstream, client: 192.168.1.10, server: api.local, upstream: "http://127.0.0.1:8002/..."
    2026/07/25 10:00:05 [warn] 1234#0: *59 upstream server temporarily disabled while connecting to upstream, client: 192.168.1.11, server: api.local, upstream: "http://127.0.0.1:8002/..."
    ```
    *   Первая строка фиксирует конкретный сетевой сбой.
    *   Вторая строка (`warn`) сообщает, что сервер набрал критическую массу ошибок (`max_fails`) и временно выведен из строя.

### Интерактивный тест для самопроверки

1. **Какой алгоритм балансировки в Nginx гарантирует, что запросы одного клиента попадут на один и тот же бэкенд?**
    <details>
    <summary>Ответ</summary>
    `ip_hash`. Метод вычисляет хэш на основе IP-адреса клиента для обеспечения Session Affinity,.
    </details>

2. **За что отвечает параметр `fail_timeout` в контексте Passive Health Checks?**
    <details>
    <summary>Ответ</summary>
    Он выполняет две функции: 1) Задает временное окно для накопления ошибок `max_fails`. 2) Устанавливает длительность периода, на который сервер будет исключен из балансировки после сбоя,.
    </details>

3. **Можно ли использовать параметр `backup` совместно с методом `ip_hash`?**
    <details>
    <summary>Ответ</summary>
    Нет, использование `backup` запрещено совместно с методами балансировки `hash`, `ip_hash` и `random`,.
    </details>

4. **Что произойдет, если все серверы в `upstream` группе (включая основные и backup) одновременно вернут ошибку?**
    <details>
    <summary>Ответ</summary>
    Nginx вернет клиенту результат работы с последним опробованным сервером (обычно это ошибка 502 или 504).
    </details>

5. **Какая команда позволяет временно вывести сервер из балансировки для обслуживания, не удаляя его из конфигурации и сохраняя структуру хэширования?**
    <details>
    <summary>Ответ</summary>
    Параметр `down` внутри директивы `server`,.
    </details>
