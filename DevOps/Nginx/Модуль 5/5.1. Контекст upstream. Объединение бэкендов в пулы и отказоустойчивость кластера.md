В современной системной инженерии концепция **горизонтального масштабирования (Horizontal Scaling)** является единственным жизнеспособным путем развития инфраструктуры под растущую нагрузку [Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536). В отличие от вертикального масштабирования, которое упирается в физический потолок ресурсов одного сервера и становится экономически нецелесообразным, горизонтальный подход позволяет наращивать мощность за счет добавления новых узлов в кластер [Основы NGINX глазами разработчика / YouTube](https://www.youtube.com/watch?v=...). Роль Nginx в этой архитектуре — выступать в качестве интеллектуального диспетчера, объединяющего разрозненные инстансы бэкенда в единый отказоустойчивый пул с помощью контекста `upstream` [Nginx Cookbook / Derek DeJonghe](https://docs.nginx.com/nginx/admin-guide/).

#### Концепция контекста upstream

Директива `upstream` создает именованную группу серверов, к которой можно обращаться из директив проксирования (таких как `proxy_pass`, `fastcgi_pass` или `uwsgi_pass`) [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html).

**Архитектурные требования:**

- **Размещение:** Блок `upstream` должен располагаться строго внутри контекста `http`, но вне любых блоков `server` [Complete-NGINX-Cookbook-2019](https://www.nginx.com/resources/library/complete-nginx-cookbook/).
- **Инкапсуляция:** Клиент взаимодействует только с точкой входа Nginx (Frontend), не зная о структуре и количестве бэкендов (Backends) за ним [Основы NGINX глазами разработчика / YouTube](https://www.youtube.com/watch?v=...).
- **Гибкость:** Внутри одного пула можно комбинировать различные типы соединений: TCP-порты и Unix Domain Sockets [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html).

#### Управление пулом серверов Uvicorn / FastAPI

Для высоконагруженного стека на базе FastAPI рекомендуется запускать несколько независимых инстансов Uvicorn. Это позволяет обойти ограничения GIL (Global Interpreter Lock) в Python и эффективно утилизировать все ядра процессора [Оптимизация производительности Nginx/Angie / YouTube](https://www.youtube.com/watch?v=...).

**Пример эталонной конфигурации пула:**

```nginx
upstream fastapi_cluster {
    # Использование разделяемой памяти для хранения состояния (только в коммерческих версиях или Angie)
    zone cluster_backend 64k;

    # Инстансы на разных портах (TCP)
    server 127.0.0.1:8001 weight=3;
    server 127.0.0.1:8002 weight=1;

    # Инстанс через Unix Socket (минимальные задержки)
    server unix:/run/uvicorn/uvicorn.sock;

    # Резервный сервер (HA)
    server spare.example.com:8080 backup;
}

server {
    listen 443 ssl;
    server_name api.example.com;

    location / {
        proxy_pass http://fastapi_cluster;
        include proxy_params;
    }
}
```
[NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/), [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html)

#### Внутренняя механика и DNS-резолвинг

Nginx хранит состояние бэкендов в оперативной памяти. Для Middle/Senior DevOps инженера важно понимать, как Nginx обрабатывает доменные имена внутри блока `upstream`.

1.  **Статический резолвинг (по умолчанию):** Nginx разрешает доменные имена из директивы `server` один раз при старте или перезагрузке конфигурации [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html). Если IP-адрес бэкенда изменится (например, в динамическом облаке AWS), Nginx продолжит слать трафик на старый IP до выполнения `reload` [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).
2.  **Динамический резолвинг:** Для работы с динамическими IP-адресами используется директива `resolver` и параметр `resolve` у сервера [Модуль ngx_http_core_module](https://nginx.org/ru/docs/http/ngx_http_core_module.html), [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).
    *   **`resolver`** — задает адрес DNS-сервера и время кэширования ответов (`valid`) [Модуль ngx_http_core_module](https://nginx.org/ru/docs/http/ngx_http_core_module.html).
    *   **`resolve`** — заставляет рабочий процесс периодически перепроверять IP-адрес домена в рантайме без перезапуска Nginx [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html).

#### Концепция отказоустойчивости (High Availability)

Отказоустойчивость кластера в Nginx базируется на механизме **пассивных проверок работоспособности (Passive Health Checks)** [Complete-NGINX-Cookbook-2019](https://www.nginx.com/resources/library/complete-nginx-cookbook/). В отличие от активных проверок (доступных в коммерческих сборках), пассивные мониторят реальные ответы бэкендов на запросы пользователей [Настройка балансировки в Nginx / YouTube](https://www.youtube.com/watch?v=...).

**Алгоритм действий Nginx при аварии:**
1.  **Детектирование:** Если инстанс Uvicorn возвращает ошибку или соединение с ним обрывается, Nginx засчитывает «неудачную попытку» [Модуль ngx_http_proxy_module](https://nginx.org/ru/docs/http/ngx_http_proxy_module.html).
2.  **Порог срабатывания:** Параметр **`max_fails`** определяет количество таких попыток в течение времени **`fail_timeout`** [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html).
3.  **Изоляция:** По достижении лимита сервер помечается как недоступный на срок `fail_timeout` и исключается из балансировки [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).
4.  **Failover (Перехват):** Директива **`proxy_next_upstream`** позволяет Nginx мгновенно передать «упавший» запрос другому живому бэкенду из пула, так что клиент даже не заметит сбоя (за исключением задержки) [Модуль ngx_http_proxy_module](https://nginx.org/ru/docs/http/ngx_http_proxy_module.html).

> [!warning] Актуализация синтаксиса
> В современных конфигурациях для HA-кластеров крайне рекомендуется использовать `proxy_next_upstream error timeout http_502 http_503 http_504;`, чтобы обеспечить бесшовную работу приложения при временных отказах отдельных нод Uvicorn [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).

### Интерактивный тест для самопроверки

1. **В каком контексте конфигурации Nginx ОБЯЗАТЕЛЬНО должен быть объявлен блок `upstream`?**
    <details>
    <summary>Ответ</summary>
    Блок `upstream` объявляется только в контексте `http`. Его нельзя размещать внутри блоков `server` или `location`. [Complete-NGINX-Cookbook-2019](https://www.nginx.com/resources/library/complete-nginx-cookbook/)
    </details>

2. **Что произойдет, если IP-адрес бэкенда изменится, а в Nginx настроен статический резолвинг без параметра `resolve`?**
    <details>
    <summary>Ответ</summary>
    Nginx будет продолжать отправлять запросы на старый IP-адрес, кэшированный в момент старта процесса, что приведет к ошибкам проксирования (например, 502 Bad Gateway) до ручной перезагрузки или `reload` конфигурации. [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/)
    </details>

3. **За какой функционал отвечают параметры `max_fails` и `fail_timeout` в директиве `server` внутри апстрима?**
    <details>
    <summary>Ответ</summary>
    Они реализуют пассивные проверки здоровья (Passive Health Checks): `max_fails` задает лимит неудачных попыток, а `fail_timeout` — время, в течение которого эти попытки считаются, и срок, на который сервер будет исключен из пула при сбое. [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html)
    </details>

4. **Какую роль играет параметр `backup` в описании сервера в `upstream`?**
    <details>
    <summary>Ответ</summary>
    Сервер, помеченный как `backup`, не получает трафик в обычном режиме. Он активируется только тогда, когда все остальные основные серверы пула вышли из строя или стали недоступны. [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/)
    </details>

5. **Какая директива позволяет передать запрос другому серверу в группе, если первый выбранный сервер вернул ошибку 504?**
    <details>
    <summary>Ответ</summary>
    Директива `proxy_next_upstream http_504;` (обычно используется в связке с `error` и `timeout`). [Модуль ngx_http_proxy_module](https://nginx.org/ru/docs/http/ngx_http_proxy_module.html)
    </details>
