При проектировании высоконагруженных систем Middle DevOps инженеру часто приходится сталкиваться с **гетерогенными кластерами** — пулами серверов, где узлы обладают разной вычислительной мощностью (например, часть инстансов FastAPI работает на старом железе, а часть — на современных многоядерных процессорах) [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/). Директива `server` внутри контекста `upstream` предоставляет набор параметров для прецизионного управления распределением трафика и обеспечения высокой доступности (HA) [Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).

#### Пропорциональное распределение: Параметр weight

Параметр `weight` (вес) задает приоритетность выбора сервера в алгоритме балансировки [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html).

- **Механика:** По умолчанию вес всех серверов равен 1 [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/). Если одному из серверов назначить `weight=5`, он будет получать в пять раз больше запросов, чем узлы с весом по умолчанию [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).
- **Применение:** Это критически важно, если ваш кластер FastAPI развернут на узлах с разным количеством ядер CPU [Оптимизация производительности Nginx/Angie / YouTube](https://www.youtube.com/watch?v=...). Статистически нагрузка будет распределяться как средневзвешенное значение [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).

```nginx
upstream heterogeneous_cluster {
    server node_powerful:8000 weight=5; # Современный сервер
    server node_old:8000      weight=1; # Узел для подстраховки
}
```

#### Механизм детекции сбоев: max_fails и fail_timeout

В Open Source версии Nginx реализованы **пассивные проверки здоровья (Passive Health Checks)** [Complete-NGINX-Cookbook-2019](https://www.nginx.com/resources/library/complete-nginx-cookbook/). В отличие от активных проверок, Nginx не шлет специальные «пинг-запросы», а анализирует реальные ответы бэкенда на запросы пользователей [Основы NGINX глазами разработчика / YouTube](https://www.youtube.com/watch?v=...).

1. **`max_fails`** — количество неудачных попыток связи с сервером (таймаутов или ошибок 5xx), после которых узел считается недоступным [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html). Значение по умолчанию — 1 [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).
2. **`fail_timeout`** — выполняет двойную роль:
    - Задает временное окно, в течение которого должны произойти ошибки `max_fails` [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html).
    - Определяет длительность периода, на который сервер будет исключен из пула балансировки после фиксации сбоя [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html).
    - Значение по умолчанию — 10 секунд [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).

> [!warning] Актуализация синтаксиса 
> Если в `upstream` группе указан только один сервер, параметры `max_fails` и `fail_timeout` игнорируются, и такой сервер никогда не помечается как упавший, даже если он недоступен [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html).

#### Резервирование и обслуживание: backup и down

Эти параметры позволяют гибко управлять жизненным циклом нод в кластере без потери запросов [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).

- **`backup`** — помечает сервер как запасной [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html). Nginx не будет отправлять на него трафик до тех пор, пока работают основные ноды. Это идеальное место для «страховочного» сервера в другом дата-центре или облаке [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).
- **`down`** — принудительно выводит сервер из балансировки [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html). В отличие от удаления строки из конфига, сохранение сервера с флагом `down` позволяет сохранить текущую статистику хэширования в методе `ip_hash`, предотвращая перераспределение всех сессий клиентов [Модуль ngx_http_upstream_module](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html).

#### Защита FastAPI от каскадных отказов

В связке с асинхронным Python-бэкендом грамотная комбинация параметров предотвращает ситуацию, когда «подвисший» запрос на одной ноде FastAPI парализует весь кластер [Основы NGINX глазами разработчика / YouTube](https://www.youtube.com/watch?v=...).

**Пример эталонной конфигурации отказоустойчивого пула:**

```nginx
upstream uvicorn_pool {
    # Основные рабочие лошадки
    server 127.0.0.1:8001 weight=3 max_fails=2 fail_timeout=30s;
    server 127.0.0.1:8002 weight=3 max_fails=2 fail_timeout=30s;

    # Нода на обслуживании (деплой новой версии)
    server 127.0.0.1:8003 down;

    # Резервный инстанс на случай катастрофы
    server spare_node.local:8000 backup;
}
```

В данном примере, если нода на порту 8001 дважды вернет ошибку в течение 30 секунд, Nginx исключит ее на полминуты, давая Uvicorn-воркеру возможность перезапуститься или очистить очереди запросов, не перегружая его новыми входящими соединениями [NGINX_Cookbook-final](https://www.nginx.com/resources/library/complete-nginx-cookbook/).
