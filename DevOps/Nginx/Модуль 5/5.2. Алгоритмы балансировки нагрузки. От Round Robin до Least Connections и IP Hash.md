Выбор алгоритма балансировки — это определение стратегии «интеллектуального диспетчера» Nginx по распределению входящих запросов между узлами кластера. В высоконагруженных системах 2026 года правильный выбор метода позволяет избежать перегрузки отдельных инстансов FastAPI и минимизировать задержки (Latency) для конечных пользователей [Основы NGINX глазами разработчика / YouTube](https://www.youtube.com/watch?v=...).

#### Round Robin (Метод по умолчанию)

Самый простой и предсказуемый алгоритм, при котором запросы распределяются по списку серверов циклически. Nginx поочередно передает управление каждому бэкенду, обеспечивая равномерную «справедливую» очередь.

- **Синтаксис:** Не требует специальной директивы.
- **Сценарий применения:** Идеален для гомогенных пулов (одинаковое железо), где все эндпоинты FastAPI выполняют задачи примерно одинаковой сложности.

```nginx
upstream fastapi_app {
    server backend1.example.com;
    server backend2.example.com;
}
```

#### Least Connections (`least_conn`)

Алгоритм направляет очередной запрос тому серверу, у которого на текущий момент зафиксировано наименьшее количество активных соединений. Nginx анализирует собственные данные о количестве открытых сокетов к каждому `upstream`.

- **Синтаксис:** Директива `least_conn;` внутри блока `upstream`.
- **Сценарий применения:** Критически важен для асинхронных стеков (Uvicorn), где задачи имеют разный «вес». Если один запрос к FastAPI запускает тяжелую аналитику на 10 секунд, а другой — простую проверку здоровья за 10 мс, `least_conn` не даст «завалить» первый сервер новыми входящими задачами, пока он занят.

```nginx
upstream fastapi_smart {
    least_conn;
    server 127.0.0.1:8001;
    server 127.0.0.1:8002;
}
```

#### IP Hash (`ip_hash`)

Обеспечивает привязку клиента к конкретному бэкенду (Session Affinity). Nginx берет IP-адрес клиента (первые три октета IPv4 или полный адрес IPv6) и вычисляет хэш, который однозначно указывает на один из серверов пула.

- **Синтаксис:** Директива `ip_hash;`.
- **Сценарий применения:** Используется, когда архитектура бэкенда хранит состояние сессии локально, а не в общем хранилище типа PostgreSQL или Redis. Это «бедный» способ обеспечить постоянство сессий без переписывания кода приложения.

```nginx
upstream stateful_app {
    ip_hash;
    server backend1.example.com;
    server backend2.example.com;
}
```

#### Generic Hash (`hash`)

Позволяет администратору самому определить ключ для хэширования. В качестве ключа можно использовать любую комбинацию переменных Nginx (URI, аргументы запроса, специфические заголовки).

- **Синтаксис:** `hash $key [consistent];`.
- **Консистентное хэширование:** При добавлении параметра `consistent` используется метод `ketama`, который минимизирует перераспределение ключей при падении или добавлении новых нод в кластер.
- **Сценарий применения:** Оптимизация работы кэша бэкенда. Если хэшировать запросы по `$request_uri`, то запросы к одному и тому же ресурсу всегда будут попадать на один и тот же инстанс FastAPI, что повышает эффективность локального кэширования.

```nginx
upstream partitioned_api {
    hash $request_uri consistent;
    server backend1:8000;
    server backend2:8000;
}
```

#### Random

Nginx выбирает бэкенд случайным образом. При использовании параметра `two` активируется алгоритм «Power of Two Choices».

- **Механика Power of Two:** Nginx случайным образом выбирает два сервера и из них выбирает лучший на основе заданного метода (по умолчанию `least_conn`).
- **Сценарий применения:** Высокомасштабируемые среды с несколькими балансировщиками Nginx перед одним пулом бэкендов. В такой схеме балансировщики не знают о состоянии друг друга, и чистый `least_conn` может привести к эффекту «стадного поведения» (herd effect), когда все балансировщики одновременно кидают трафик на одну «свободную» ноду. `random two` элегантно решает эту проблему.

```nginx
upstream large_cluster {
    random two least_conn;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080;
}
```

> [!warning] Актуализация синтаксиса 
> В старых источниках можно встретить использование `sticky` без контекста. Важно помнить, что продвинутые методы `sticky cookie` и `sticky route` доступны только в коммерческой версии Nginx Plus или в альтернативных сборках (например, Angie), в то время как `ip_hash` является базовым инструментом Open Source.
