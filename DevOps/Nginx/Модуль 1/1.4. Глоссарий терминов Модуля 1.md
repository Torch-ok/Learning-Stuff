В данном разделе собраны ключевые архитектурные понятия, знание которых необходимо для понимания принципов работы Nginx как высокопроизводительного сетевого узла.

- **C10K Problem** — концептуальная задача обслуживания 10 000 одновременных соединений на одном сервере, ставшая драйвером перехода от многопоточных архитектур к событийно-ориентированным [Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).
- **Master Process** — управляющий процесс Nginx, отвечающий за чтение конфигурации, привязку к портам и управление жизненным циклом рабочих процессов [Development guide](https://nginx.org/en/docs/dev/development_guide.html).
- **Worker Process** — рабочий процесс, выполняющий фактическую обработку клиентских запросов, включая терминацию TLS, парсинг HTTP и взаимодействие с бэкендами [Руководство для начинающих](https://nginx.org/ru/docs/beginners_guide.html).
- **Event Loop** — цикл обработки событий внутри `Worker`-процесса, позволяющий эффективно переключаться между тысячами неблокирующих соединений [Development guide](https://nginx.org/en/docs/dev/development_guide.html).
- **Non-blocking I/O** — механизм ввода-вывода, при котором процесс не останавливает выполнение в ожидании данных от сокета, а продолжает работу, реагируя на уведомления от ядра ОС [Nginx для начинающих / Хабр](https://habr.com/ru/companies/gnivc/articles/977196/).
- **epoll / kqueue** — высокоэффективные механизмы мультиплексирования системных вызовов в ядрах Linux и BSD соответственно, обеспечивающие масштабируемость Nginx при огромном количестве дескрипторов [Mastering Nginx](https://www.packtpub.com/product/mastering-nginx/9781785283536).
- **Graceful Reload** — механизм горячей перезагрузки конфигурации без обрыва существующих соединений, реализуемый путем запуска новых воркеров и плавного завершения старых [Nginx Cookbook / Derek DeJonghe](https://docs.nginx.com/nginx/admin-guide/).

## Практическое упражнение (Развертывание базового веб-сервера Nginx и первичная диагностика)

**Цель:** Развернуть Nginx на ОС семейства Linux, провести глубокую валидацию конфигурации и на практике изучить механизм `Graceful Reload` через наблюдение за идентификаторами процессов (PID).

### Шаг 1: Установка и запуск

Установите пакет Nginx и запустите службу. Проверьте её статус в системе инициализации `systemd`.

```bash
# Для Ubuntu/Debian
sudo apt update && sudo apt install nginx -y
sudo systemctl start nginx
sudo systemctl status nginx
```

**Ожидаемый результат:** В выводе терминала должна появиться строка `Active: active (running)`. Обратите внимание на дерево процессов в нижней части вывода `systemctl status` — там будут видны один `master` и один или несколько `worker`-процессов.

### Шаг 2: Первичная диагностика через CLI

Перед любыми изменениями необходимо убедиться в целостности текущей конфигурации. Используйте флаги `-t` и `-T`.

```bash
# Простая проверка синтаксиса
sudo nginx -t
# Полный дамп конфигурации для анализа всех include
sudo nginx -T
```

**Инженерный комментарий:** Команда `nginx -T` незаменима в продакшене, так как она позволяет увидеть итоговую конфигурацию, которую Nginx «держит в голове», включая все подключенные файлы из `/etc/nginx/conf.d/`.

### Шаг 3: Модификация контента

Внесите изменения в стандартную страницу приветствия, чтобы убедиться, что сервер корректно отдает статику. Путь к файлу обычно определяется директивой `root` в блоке `server` (по умолчанию `/var/www/html/index.nginx-debian.html` или `/usr/share/nginx/html/index.html`).

```bash
echo "<h1>Nginx Module 1: Architecture Success</h1>" | sudo tee /var/www/html/index.html
```

### Шаг 4: Наблюдение за Graceful Reload

Зафиксируйте текущие PID процессов, выполните `reload` и проанализируйте изменения в системных логах.

```bash
# Фиксация текущих PID
ps -ef | grep nginx

# Выполнение горячей перезагрузки
sudo nginx -s reload

# Проверка новых PID
ps -ef | grep nginx
```

**Анализ логов (`journalctl -u nginx` или `/var/log/nginx/error.log`):** В логах вы увидите записи о том, что `Master`-процесс перечитал конфигурацию и отправил сигнал `SIGQUIT` (плавное завершение) старым воркерам.

- PID процесса `master` останется **прежним**.
- PID процессов `worker` **изменятся**, так как старые процессы дообслужили клиентов и завершились, а `master` породил новые процессы с обновленной конфигурацией.
